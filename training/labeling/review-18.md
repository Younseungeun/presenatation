# 18차 검토 요청 — 2차 검수가 API가 아니라 **사람이 나르는 대화**가 되었습니다

## 0. 무엇이 바뀌었습니까

설계상 검수는 2단이었습니다: **①결정적 규칙 → ②AI 검수기**.

**②는 운영에서 한 번도 돈 적이 없고, 앞으로도 돌지 않습니다.** 외부 AI API를 운영 경로에서
쓰지 않기로 확정됐습니다(비용이 아니라 방침입니다). `createClaudeScreenerFromEnv`가 null을
돌려주고 파이프라인은 1차에서 끝납니다 — 그동안 문서에 "2차"라고 적혀 있던 칸은 **비어
있었습니다.**

그 자리를 **사람이 나르는 대화**가 채웁니다:

```
리서처 게시 요청
   ↓
①결정적 규칙 (6층)        ← 이것만 자동입니다
   ↓ WARN/BLOCK
관리자 보류 큐
   ↓ [질문지 복사] 버튼
운영자가 대화창(교사)에 붙여 넣음
   ↓ 교사가 판정
운영자가 그 판정으로 승인/반려 + 유형 선택
   ↓
학습 라벨  →  학생 모델 재학습
```

**이것은 "②를 수동으로 대체했다"가 아닙니다.** 성질이 다른 장치이고, 자동 2차에는 없던
고장 방식이 생겼습니다:

| | 자동 2차 (설계상) | 수동 2차 (지금 실제) |
|---|---|---|
| 언제 도는가 | 모든 WARN 건에 **항상** | 운영자가 **누를 때만** |
| 대화 맥락 | 매 건 독립 요청 | **한 창에서 연속 — 앞 건이 뒤 건에 남는다** |
| 교정 사례 | 과거 운영자 오탐/미탐 8건 자동 주입 | **없다** |
| 원문 경계 | 요청마다 무작위 `BOUNDARY-<hex>` | **없다** (2절 ②) |
| 위험종목 표시 | 있음 | **없다** (2절 ②) |
| 수익성 구간 눈금 | 있음 | **없다** (2절 ②) |
| 출력 | 구조화 출력 스키마가 강제 | 사람이 읽고 옮겨 적음 |
| 교사 신원 | `rule+claude:claude-opus-5` 로 기록 | **아무 데도 안 남는다** (2절 ④) |
| 처리량 | 초당 여러 건 | 건당 1~2분, 사람 손 |
| 비용 | 종량 과금 | **운영자 시간** — 밀리면 안 물어보게 된다 |

**고정 제약**: 즉시 거절은 결정적 규칙만 · λ=4(오탐 1건 = 미탐 4건) · **운영 경로 외부 API 0회
(방침, 협상 대상 아님)** · 학생 모델 KoELECTRA-small 14M · 운영자 1~2인

## 1. 이번 회차에 실측한 것

### 17차 검토의 반증 조건 3이 실제로 터졌습니다

검토는 이렇게 적었습니다 — *"라틴 조각을 아는 용어로 면제하면, 사전에 없는 정상 표기가
오탐이 된다."* 붙여 쓴 합성어 25건을 실측했습니다:

| | 오탐 |
|---|---|
| 띄어 쓴 형태 (`nm 공정`) 102건 | 0건 |
| **붙여 쓴 형태 (`nm공정`) 25건** | **12건 (48%)** |

터진 것: `nm공정` `bps금리` `pp상승` `macOS용` `iPhone판매` `iPad출하` `mmWave대역`
`microLED개발` `webOS기반` `eSports산업` `iGaming시장` `kWh단가`

전부 한국어 리포트에 정상적으로 나오는 표기입니다. **16차에 띄어 쓴 형태로만 재서 못
봤습니다** — 측정의 구멍이지 규칙의 구멍이 아니었고, 검토가 그걸 짚었습니다.

가른 것: **라틴 조각이 아는 용어인가.** `nm`·`bps`·`iphone`은 단위·제품명이고, 회피의
조각(`le`·`KaKao`·`won`)은 아닙니다. 토큰 안의 **모든** 라틴 조각이 사전에 있을 때만
합성어로 봅니다.

결과: 신조어 127건 오탐 **0** · 회피 8/8 유지 · 적대 코퍼스 36/36 · 정상 54건 오탐 **0**.

사전을 만들면서 시험에 못을 박았습니다 — **`won`·`ka`·`tele`를 넣으면 시험이 빨개집니다.**
그 순간 `won금보장`·`KaKao톡`이 통과하기 때문입니다. 사전은 부채라, 부채가 늘 때
비명을 지르는 장치를 같이 넣었습니다.

## 2. 수동 경로에서 찾은 결함 다섯과, **고치려는 방법**

**결함은 확인된 사실입니다. 고치는 방법이 검토받고 싶은 것입니다.**
각 항목에 `고치려는 것` / `이 수정이 기대는 가정` / `아직 모르는 것`을 붙였습니다.

---

### ① 질문지 조립기가 **둘** 있고, 서로 다른 것을 물어봅니다

같은 날 두 갈래로 만들어졌습니다:

| | `server/teacherPack.ts` | `domain/manualReviewPrompt.ts` |
|---|---|---|
| 배선 | **`/api/admin/compliance/ask` → `AskTeacher.tsx` (동작 중)** | **아무 데도 안 붙음** |
| 규정문 | `SYSTEM_PROMPT` **그대로 인용** | 문서 안에 **다시 씀 (복제)** |
| 원문 조립 | `buildStudentText` (학생 입력 형식) | 직접 조립 |
| 출력 형식 | JSONL `{"id","labels":[...]}` | `판정/유형/사유/지적 타당성` |
| 원문 경계 | 없음 | 요청마다 무작위 `BOUNDARY-<hex>` |
| 오탐 신고 | **받을 자리 없음** | `지적 타당성: 타당/과함` |
| 답 파싱 | 없음 (운영자가 손으로) | `parseManualReviewAnswer` (미배선) |
| 라벨 공간 | `STUDENT_LABELS` (학생용, 8종) | `RISK_CATEGORY_LABEL` (전체) |

#### 고치려는 것

**`teacherPack.ts` 를 정본으로 삼고, 제 쪽에서 셋만 옮겨 붙입니다.** 제 것은 **지웁니다.**

근거는 `teacherPack` 의 원칙이 제 것보다 낫기 때문입니다 — *"규정을 복제하지 않는다.
여기 규정을 따로 적으면 프롬프트가 바뀔 때 조용히 어긋난다."* 저는 규정을 문서에 다시
적었고, 그건 정확히 그 함정입니다.

옮겨 붙일 셋: **무작위 경계**(②) · **오탐 신고 칸**(③) · **답 파싱**(못 읽으면 null).

남기지 않는 이유: 두 벌을 두면 다음 사람이 어느 것이 진짜인지 모르고, 한쪽만 고치는
사고가 납니다. 지금은 운영 데이터 0건이라 지우는 값이 가장 쌉니다.

#### 이 수정이 기대는 가정

**출력 형식은 `labels` 배열을 유지하는 것이 낫다** — 학생 라벨 공간에 그대로 들어가
재학습 경로가 짧아집니다.

그 대가로 `MISSING_DISCLOSURE`·`RISKY_INSTRUMENT` 는 라벨 공간 밖이라 **교사가 그
유형을 지적할 방법이 없습니다.** 저는 그래도 된다고 봅니다 — 그 둘은 종목 데이터로
**결정론적으로** 판정되므로 규칙이 이미 확실히 알고, 교사에게 물을 이유가 없습니다.

#### 아직 모르는 것

그 가정이 맞다면 교사에게는 그 두 유형을 **아예 안 보여주는 것**이 맞습니다(지금은
1차 소견 목록에 섞여 나갑니다). 그런데 안 보여주면 교사가 문맥을 잃습니다.

---

### ② 규정문이 약속한 것 **셋이 질문지에 하나도 없습니다**

`teacherPack.ts` 는 `SYSTEM_PROMPT` 를 그대로 싣습니다. 그 규정문은 **사용자 메시지에
무엇이 들어 있는지를 세 군데서 전제**합니다:

| 규정문이 하는 말 | 질문지의 실제 |
|---|---|
| *"사용자 메시지에는 무작위 경계 표시(BOUNDARY)로 감싼 리포트 원문이 들어옵니다"* | **경계 없음.** `## 항목 [review:xxx]` 라는 평범한 마크다운 제목 아래 원문이 그냥 붙는다 |
| MISSING_DISCLOSURE — *"거래소가 위험을 경고한 종목인데**(사용자 메시지에 표시됨)**"* | **위험종목 표시 없음** |
| CARD_MISMATCH — *"'뚜렷하게 다름' 같은 감각이 아니라 **아래 사용자 메시지에 표시된 구간 경계**로 판정하세요"* | **구간 경계 눈금 없음** |

결과가 각각 다릅니다:

- 교사는 **있지도 않은 봉투**를 찾으라는 지시를 받습니다. 리서처가 본문에 `## 항목` 이나
  `---` 를 적으면 그게 문서 구조의 일부처럼 보입니다. 자동 경로에서는 API가 시스템
  메시지와 사용자 메시지를 **물리적으로** 갈랐지만, 수동 경로는 **한 덩어리 텍스트**라
  경계가 그 텍스트 안에만 존재합니다
- 교사는 위험종목 여부를 모르므로 **MISSING_DISCLOSURE 를 영원히 판정할 수 없습니다**
- 교사는 눈금이 없으므로 크기를 **규정문이 명시적으로 금지한 "감각"으로** 판정합니다

#### 고치려는 것

**`buildStudentText` 대신 `buildUserMessage` 를 부릅니다.** 자동 경로가 쓰는 바로 그
함수이고, **이미 export 되어 있고**, 셋을 전부 만듭니다 — 무작위 경계·위험종목 줄·
수익성 구간 눈금. 새로 쓸 코드가 사실상 없습니다.

이것은 `teacherPack` **자기 원칙의 확장**입니다. 그 파일은 "규정을 복제하지 않는다"를
**시스템 프롬프트에만** 적용하고 사용자 메시지에는 적용하지 않았습니다. 규정문과 사용자
메시지는 **한 쌍으로 설계된 것**이라 한쪽만 인용하면 어긋납니다.

같이 고칠 것: **1차 소견의 인용문(`quote`)도 리서처 원문**이라 지금 경계 **밖에** 뿌려지고
있습니다. 경계 안으로 넣습니다 — 자동 경로가 교정 사례를 경계 안에 넣은 것과 같은 이유입니다.

#### 이 수정이 기대는 가정

**교사가 보는 것과 학생이 배울 것이 달라도 된다.** `teacherPack` 이 `buildStudentText` 를
고른 근거가 *"교사가 보는 것과 학생이 배울 것이 같은 모양이어야 한다"* 였는데, 저는
이것이 **두 가지를 섞은 것**이라고 봅니다:

- **학생 입력**은 학생이 실제로 추론 때 받는 것이라 `buildStudentText` 여야 합니다
- **교사 입력**은 판정 근거라 규칙이 아는 모든 맥락을 받아야 합니다

둘 다 같은 `ScreeningInput` 하나에서 나오므로 어긋나지 않습니다. 학습 라벨로 옮길 때
학생 텍스트를 그때 다시 만들면 됩니다.

#### 아직 모르는 것

**운영자가 붙여 넣을 때 뒤가 잘리면 닫는 경계가 사라집니다.** 문서가 3KB에서 6KB로
늘어나면 더 그렇습니다. 지금 생각한 대응은 **여는 경계 바로 앞에 "닫는 경계 값과 총
길이"를 미리 적어 두어** 교사가 *"닫는 경계를 못 봤다"* 고 말할 수 있게 하는 것인데,
이게 실효가 있는지 모르겠습니다.

### ③ 빈 배열이 **두 가지 뜻**이라 오탐 신고가 사라집니다

답 형식이 `{"id":"review:xxx","labels":[]}` 인데, 빈 배열 안에 서로 다른 둘이 접혀 있습니다:

- **"애초에 잘못 잡았다"** (오탐 — **규칙**을 고쳐야 한다)
- **"지적은 타당한데 게시를 막을 정도는 아니다"** (경미 — **심각도**를 고쳐야 한다)

11차 K-1이 이 둘을 가르는 것을 명시적으로 못 박았고, 그 구별이 학생 모델 자동 격하를
좌우합니다 — *"값이 둘뿐이면 무심코 누른 승인이 명시적 오탐 신고와 같아지고, 25건 중
6건이면 학생 모델이 영구히 꺼진다."* 17차 U-6은 같은 이유로 경미를 학습에서 뺐습니다.

#### 고치려는 것

**JSONL 아래 한 줄만 더 받습니다** — 형식을 갈아엎지 않습니다.

```
{"id":"review:xxx","labels":[]}
지적: 과함          ← labels 가 빈 배열일 때만
```

`타당` = 경미(학습에서 제외) · `과함` = 오탐(하드 네거티브로 학습).

그리고 **교사 값과 운영자 값을 따로 저장합니다.** 화면은 교사 답으로 기본 선택만 해 두고,
`findingsValid` 에는 **운영자가 최종적으로 고른 값**이 들어갑니다.

#### 이 수정이 기대는 가정

**둘을 따로 저장하면 독립성 상실을 되찾을 수 있다.** 자동 경로에서는 교사와 운영자가
독립이었는데, 수동에서는 운영자가 교사 답을 **보고** 고르므로 독립이 아닙니다. 두 값이
같은 출처에서 나오면 정확도 지표가 자기 자신을 재게 됩니다.

따로 저장하면 **불일치율 자체가 교사 품질의 지표**가 됩니다 — 운영자가 교사와 다르게
고른 비율이 곧 "교사를 얼마나 믿을 수 있나"입니다.

#### 아직 모르는 것

운영자가 실무에서 **교사 답을 그대로 누를** 가능성이 높습니다. 그러면 불일치율이 0으로
붙고 지표가 죽습니다. 그때 그 0이 "교사가 정확하다"인지 "운영자가 안 봤다"인지 못 가릅니다.

### ④ 교사에게 물어본 건과 안 물어본 건이 **영구히 구별되지 않습니다**

`reviewer` 문자열은 검수 시점에 한 번 쓰이고 갱신되지 않습니다
(`complianceService.ts:238`). 수동으로 물어봐도 `rule` 그대로입니다. 그 결과:

- 화면의 **"2차 AI 검수가 돌지 않았습니다"** 경고가 **답을 받은 뒤에도 계속 뜹니다**
- 학습 라벨에 `labeler: operator:<userId>` 만 남아, **운영자가 스스로 판단한 것**과
  **교사 답을 옮긴 것**이 같은 얼굴입니다
- 대화창의 교사는 **버전이 올라갑니다.** API 교사는 `claude-opus-5` 로 박혀 나갔지만,
  수동 교사가 어느 시점의 무엇이었는지 아무 기록이 없습니다

17차 U-6에서 라벨 출처를 남긴 이유가 *"특정 판정만 빼고 재학습할 수 있게"* 였는데,
가장 갈라야 할 축이 안 남고 있습니다.

#### 고치려는 것

- 답을 기록할 때 `reviewer` 를 갱신: `rule` → `rule+manual:<교사표식>`.
  `hadSecondTier` 가 true가 되어 화면 경고가 사라집니다
- 학습 라벨의 `labeler` 에 **접미로** 붙입니다: `operator:<id>|teacher:<표식>`.
  **접두를 건드리지 않는 이유**는 `train.py --exclude-labeler` 가 접두 매칭이라
  기존 제외 규칙이 그대로 살아야 하기 때문입니다
- **교사 표식은 운영자가 매 건 적지 않습니다.** 앱 설정에 "현재 쓰는 교사" 한 칸을 두고,
  바뀔 때만 고칩니다. 매 건 손으로 적게 하면 틀립니다

#### 이 수정이 기대는 가정

**교사가 바뀌는 빈도가 낮다.** 낮으니까 설정 한 칸으로 충분하다는 판단입니다.

#### 아직 모르는 것

**운영자가 설정을 안 고치면 라벨이 조용히 틀립니다.** 이건 ⑤의 "안 물어보고 승인"과
같은 종류의 조용한 고장이라, 잡을 장치가 따로 필요할 것 같은데 무엇인지 모르겠습니다.

---

### ⑤ 교정 사례가 수동 경로에 안 실립니다 — 되먹임이 **한 방향으로만** 돕니다

자동 경로는 매 요청에 과거 운영자 판정 8건(확인된 오탐·미탐)을 교정 사례로 실어
보냅니다 (`complianceService.ts:286`, `screeningAccuracy.ts:309`). **교사가 지난 실수를 보고
판정합니다.**

수동 경로에는 그 블록이 없습니다. 운영 데이터가 100건 쌓여도 교사는 매번 처음부터
판정합니다. 만들려는 되먹임 고리가 **학생 쪽으로만 돌고 교사 쪽으로는 안 돕니다.**

#### 고치려는 것

②의 수정이 이것도 같이 고칩니다 — `buildUserMessage` 가 교정 사례 블록을 **경계 안에**
만들어 넣습니다. 따로 쓸 코드가 없습니다.

다만 **8건이 아니라 4건으로 시작**하려 합니다. 사람이 복사하는 문서라 길이가 곧 부담입니다.

#### 이 수정이 기대는 가정

**교사→교사 순환이 생기지 않는다.** 교정 사례에 들어가는 것은 교사 답이 아니라
**운영자가 명시적으로 오탐·미탐이라고 신고한 건**입니다. 사람의 결정이 원천이라
교사가 자기 답을 다시 먹지 않습니다.

#### 아직 모르는 것

**그 독립이 수동에서는 흐려집니다.** 운영자가 교사 답을 보고 신고 여부를 정하므로,
교사 답 → 운영자 신고 → 교정 사례 → 교사 답의 **간접 순환**이 생깁니다. 자동 경로에도
같은 구조가 있었는데(운영자는 늘 교사 소견을 보고 판정했습니다) 아직 드러나지 않은 것인지,
수동에서만 문제가 되는지 모르겠습니다.

## 3. 검토 질문

### V-1. 정본을 `teacherPack` 으로 삼고 제 것을 지우는 것이 옳습니까 (2절 ①)

- **`labels` 배열을 유지**하는 판단이 맞습니까? 유지하면 `MISSING_DISCLOSURE`·
  `RISKY_INSTRUMENT` 를 교사가 지적할 수 없는데, "그 둘은 결정론적이라 물을 이유가 없다"는
  제 근거가 성립합니까?
- 성립한다면 그 두 유형의 1차 소견을 **교사에게 보여줘야 합니까, 감춰야 합니까?**
  보여주면 답할 수 없는 것을 보여주는 것이고, 감추면 문맥을 잃습니다
- 배선 안 된 쪽을 **지우는 것**이 맞습니까, 아니면 형식이 둘 다 필요한 국면이 옵니까?

### V-2. `buildUserMessage` 재사용이 옳습니까 — "교사 입력 ≠ 학생 입력" (2절 ②)

- 이 전환이 맞습니까? **교사에게 위험종목·눈금을 주면 교사가 규칙과 같은 답을 내게 되어
  교사의 독립적 가치가 줄어드는 것 아닙니까?** (규칙이 이미 그 정보로 판정했습니다)
- 반대로 안 주면 교사는 규정문이 지시한 판정을 **수행할 수 없습니다.** 어느 쪽 손해가 큽니까?
- **붙여넣기 잘림**에 대한 제 대응(닫는 경계 값을 앞에 미리 적기)이 실효가 있습니까?
  아니면 문서 길이에 상한을 두고 넘으면 본문을 잘라 보내야 합니까? 자르면 뒤쪽 위반이
  통째로 안 보입니다
- 사람도 이 문서를 읽습니다. **사람에 대한 인젝션**(운영자가 본문의 지시문에 넘어가는 것)은
  경계로 막히지 않습니다. 별도 장치가 필요합니까?

### V-3. 오탐 신고를 교사에게 한 줄 더 받는 것이 옳습니까 (2절 ③)

- 받아야 합니까, 아니면 **운영자가 최종 결정권자이므로 교사는 유형만 말하면** 됩니까?
- **교사 값과 운영자 값을 따로 저장**하고 불일치율을 교사 품질 지표로 쓰는 설계가
  성립합니까? 운영자가 교사 답을 그대로 눌러 **불일치율이 0으로 붙으면** 그 0을
  "교사가 정확하다"와 "운영자가 안 봤다" 중 무엇으로 읽어야 합니까? 가릴 방법이 있습니까?
- 애초에 **운영자에게 교사 답을 보여주기 전에 먼저 고르게** 해야 합니까(독립 확보)?
  그러면 운영자 작업이 두 배가 되는데 λ=4 아래에서 값어치가 있습니까?

### V-4. 교사 신원을 설정 한 칸으로 두는 것이 옳습니까 (2절 ④)

- `reviewer` 갱신으로 화면 경고가 사라지는 동작이 맞습니까? (경고가 사라지면 "물어봤다"가
  화면에서 확인되지만, 반대로 **답이 나빴는데도 경고가 사라집니다**)
- **운영자가 설정을 안 고쳐서 라벨이 조용히 틀리는 것**을 무엇으로 잡습니까?
- 교사 모델이 바뀌면 **그 전 라벨과 그 후 라벨을 섞어도 됩니까?** 섞으면 안 된다면
  경계를 날짜로 긋습니까, 운영자 신고로 긋습니까?
- `labeler` 접미 확장(`operator:<id>|teacher:<표식>`)이 맞습니까, 아니면 **필드를 따로**
  두는 것이 맞습니까? 지금이 가장 싼 시점이라 한 번에 정하고 싶습니다

### V-5. 교정 사례 4건이 맞습니까 — 간접 순환은 문제입니까 (2절 ⑤)

- **4건이 맞습니까?** 운영자 부담(문서 길이)과 교정 효과의 손익분기가 몇 건입니까?
- **교사 답 → 운영자 신고 → 교정 사례 → 교사 답**의 간접 순환이 실제 위험입니까?
  자동 경로에도 같은 구조가 있었는데 왜 문제가 안 됐습니까 — 아니면 됐는데 안 드러났습니까?
- 순환을 끊어야 한다면: **교사에게 물어본 건에서 나온 신고는 교정 사례에서 뺍니까?**
  그러면 남는 것이 거의 없습니다(대부분이 물어본 건이 될 테니)

### V-6. 대화 맥락 이월 — 아직 고칠 방법을 못 정했습니다

운영자는 한 대화창에서 보류 건을 **연속으로** 물어봅니다. 앞 건의 판정이 뒤 건에 남습니다.
자동 2차는 매 건이 독립 요청이라 이 문제가 원리적으로 없었습니다. **이건 제가 고칠 방법을
못 정한 유일한 항목입니다** — 코드로 강제할 수 있는 자리가 안 보입니다.

- 이 이월이 **실제로 판정을 바꿉니까?** 바꾼다면 어느 방향입니까 — 앞에서 반려가 나오면
  뒤도 엄해집니까(라벨이 위반 쪽으로 쏠림), 아니면 그 반대입니까?
- **지금 가진 것으로 잴 수 있습니까?** 같은 90건을 ⓐ 매번 새 대화 ⓑ 한 대화에서 연속으로
  물어 판정 일치율을 보는 것이 유효한 실험입니까? 표본 90건으로 몇 %p 차이를 잡습니까?
- 후보 셋 중 무엇입니까:
  **ⓐ 건마다 새 대화를 강제** (운영자가 지킬 방법이 화면 쪽에 있습니까?) /
  **ⓑ 질문지에 "앞 건과 무관하게 판정하라"를 넣는다** (그게 실제로 듣습니까?) /
  **ⓒ 여러 건을 한 번에 묶어 보낸다** — 묶으면 이월이 **의도적**이 되어 오히려 낫습니까
  (같은 기준이 한 번에 적용됨), 아니면 더 나쁩니까(한 건의 오판이 묶음 전체로 번짐)?

### V-7. 처리량 병목과 재학습 시점 — 근거가 약한 두 숫자

건당 1~2분(복사 → 붙여넣기 → 읽기 → 유형 선택). 운영자 1~2인.

**가장 나쁜 결말이 명확합니다**: 큐가 밀리면 운영자가 **안 물어보고 그냥 승인**합니다.
라벨은 남는데 근거가 없고, 그 라벨이 학습셋에 섞입니다. **조용히 일어납니다.**

- 고치려는 것: **"질문지를 복사하지 않고 내려진 결정의 비율"을 센다.** 이것으로 충분합니까?
- **모든 보류를 물어봐야 합니까?** 갈라야 한다면 기준은 — 심각도(BLOCK만)? 층(⑤음성변형·
  ⑥훼손처럼 규칙이 약한 층만)? 소견 개수? 리서처 등급?
- λ=4 아래에서 **안 물어보고 승인**과 **안 물어보고 반려** 중 어느 쪽이 기본값입니까?
- 재학습 시점으로 **오탐 50건 또는 미탐 20건 중 먼저 도달할 때**를 생각했는데 근거가
  없습니다. 어떻게 유도합니까?
- 수동 라벨은 **보류된 건에서만** 나옵니다 — 규칙이 통과시킨 정상 문장은 큐에 안 올라옵니다.
  즉 학습셋이 **위반 쪽으로 구조적으로 쏠립니다.** 정상 표본을 따로 뽑아 넣어야 합니까?
- 재학습한 학생이 **나아졌다는 것을 무엇으로 압니까?** 적대 코퍼스 90건은 17차 2절대로
  이미 학습셋이라 못 씁니다. 손코퍼스 86문장이 유일한 채점지인데 충분합니까?

## 5. 18차 답변을 받아 구현한 것 (2026-08-21)

검토는 **여섯 항목 모두 `고쳐서`**를 냈고, 관통하는 결론은 하나였습니다 —
*"독립성은 코드 구조가 아니라 작업자의 클릭 순서에서 나온다."*

| 항목 | 검토가 고친 것 | 구현 |
|---|---|---|
| **V-1** | 답할 수 없는 유형도 **읽기 전용 문맥으로 보여줄 것** — 감추면 교사가 없는 위반을 지어낸다 | 1차 소견을 둘로 갈라 싣고 "답에 쓰지 마세요" 명시 |
| **V-2** | 닫는 경계만으로 부족 — **총 길이 + 마지막 낱말**을 맨 위에 | `buildUserMessage` 재사용 + 무결성 머리글. 교사가 첫 문장으로 거절할 수 있다 |
| **V-3** | **UI 순서 강제** — 운영자가 먼저 결정한 뒤에야 답 입력 | 서버가 거절(`recordTeacherAnswer`) + 결정 난 건만 답 상자가 뜨는 별도 줄 |
| **V-4** | 하루 첫 건에 **교사 모델을 강제로 확인** | `AppSetting.updatedAt` 이 오늘이 아니면 확인 요구. 새 칸 없이 |
| **V-5** | 아무 오탐이 아니라 **교사와 사람이 갈린 건만** | `getTeacherCorrections` — 불일치 건에서만 뽑는다 |
| **V-6** | 묶음(ⓒ) **버려라**. 강제 문구(ⓑ) + 체크박스(ⓐ) | 질문지 맨 위 맥락 폐기 문구 + 새 대화 체크박스 + **답의 id 대조** |
| **V-7** | BLOCK·신규 리서처 강제 · 안 물어보면 **승인** · 정상 10% 섞기 | `teacherAskPolicy` + `cleanSampleRatio` |

### 새 표를 만들었습니다 — `TeacherAnswer`

교사 답을 `ComplianceReview` 행에 붙이지 않았습니다. **`ShadowComplianceReview` 와 같은
이유**입니다: 같은 행에 두면 언젠가 집계 쿼리의 WHERE 하나가 빠져 교사 답이 운영자
판정과 합쳐지고, 그 순간 정확도 지표가 자기 자신을 재게 됩니다.

`disagreed` 한 칸이 두 가지의 원천입니다 — **교사 품질 지표**(불일치율)와
**다음 질문지의 교정 사례**.

### 구현하면서 검토안을 두 군데 바꿨습니다

**① 맥락 이월 실험의 문항 (`npm run probe:bleed`)**

검토는 "손코퍼스 86 + 신조어 127 = 213건"을 제안했는데 **신조어 127건은 쓸 수 없습니다.**
그것은 문장이 아니라 `nm공정`·`bps금리` 같은 **토막**이고, 규칙의 토큰 판별을 재려고
만든 것입니다. 리포트로 내밀면 교사는 두 조건 모두에서 "이건 리포트가 아닙니다"라고
답합니다 — 두 조건의 답이 같으니 이월을 **재지 못하면서 표본만 희석합니다.**

대신 문장인 것으로 채웠습니다: **손코퍼스 86 + 대조군 54 = 140건** (위반 52 / 정상 88).

그리고 스크립트가 **표본의 한계를 스스로 말합니다**: 140건에서 잡을 수 있는 최소 차이가
약 **7%p** 입니다. 그보다 작은 차이가 나오면 *"이월이 없다"가 아니라 "이 표본으로는
못 잰다"* 라고 출력합니다. 15차에 대조군 8건으로 "오탐 0%"라고 말했다가 두 번 뚫린
것과 같은 실수를 막는 장치입니다.

**② 정상 표본 10%의 한계**

V-7의 "통과분 10%를 섞는다"를 구현하면서 **모집단이 생각과 다르다**는 것을 확인했습니다.
`TRUE_NEGATIVE` 는 운영자가 판매 중 리포트를 보고 **유지(KEPT)를 명시적으로 누른 건**만
입니다 — 소견 없이 조용히 통과해 아무도 다시 안 본 리포트는 판정이 없어 애초에
조회되지 않습니다. 즉 표본이 "운영자가 한 번 더 본 정상"이지 "정상 전체"가 아닙니다.

**쏠림이 부분적으로만 풀립니다.** 진짜 정상 표본은 DART 대조군 쪽이 답이고, 코드에
그 사실을 적어 두었습니다.

### 구현 중에 잡은 결함 하나 (시험이 잡았다)

`지적:` 줄을 **포함 검사**로 읽고 있었습니다. `지적: 타당하지 않음` 이 `타당`을 품고
있어서 **정반대로 읽힙니다** — 그리고 그 라벨이 그대로 학습에 들어갑니다.
`타당`·`과함` 정확 일치로 바꿨고, 그 외의 서술은 거절합니다(사람이 고릅니다).

### 반증 조건 셋 — 둘은 아직 못 잽니다

| 조건 | 상태 |
|---|---|
| **① 무결성 해시가 잘림을 막는가** | **교사가 필요합니다.** 잘린 질문지를 실제로 넣어 봐야 압니다 |
| **② UI 순서 강제 후 불일치율이 지표가 되는가** | **운영 1주가 필요합니다.** 재는 장치는 만들었습니다(`getTeacherAskCoverage`) |
| **③ 교정 사례 4건이 성능을 안정시키는가** | **교사 + 운영 데이터가 필요합니다** |

②의 계기판은 지금 돌아갑니다 — 관리자 화면 위에 세 숫자가 뜹니다:
**안 물어보고 결정 / 답 안 적음 / 교사와 갈림.** 한 숫자로 접지 않은 이유는 셋이
서로 다른 고장을 가리키기 때문입니다.

### 사장님이 하실 것

```
npm run probe:bleed
```

문항 140건이 두 벌 나옵니다.
- `training/bleed/condition-a-fresh.json` — **매번 새 대화창**에 하나씩
- `training/bleed/condition-b-sequential.md` — **한 대화창**에 위에서부터 차례로

답을 `answers-a.jsonl` · `answers-b.jsonl` 로 모은 뒤:

```
npm run probe:bleed -- score
```

**140건 × 2조건이라 품이 많이 듭니다.** 다 하실 필요는 없고, 앞에서부터 40건씩만 해도
차이의 방향은 보입니다(다만 그때 잡을 수 있는 최소 차이는 약 13%p로 커집니다 —
스크립트가 실제 표본 수로 다시 계산해 알려 줍니다).
