# 14차 검토 요청 — 표기 회피 방어를 붙인 뒤, 다음 설계를 어디로 끌고 갈 것인가

## 0. 시스템 현재 상태

INTOVILL은 리서처의 투자 리포트를 게시 전에 자동 검수합니다. 13차 검토(P-1~P-6) 답변을 전부 구현했고, 그 과정에서 **설계 자체를 바꿔야 할 것 세 가지**가 드러났습니다. 이 문서는 그 결과를 놓고 다음 설계를 묻습니다.

**고정 제약** (바뀌지 않았습니다)

| | |
|---|---|
| 즉시 거절(REJECT) 권한 | **결정적 규칙만.** 모델은 아무리 확신해도 보류(HOLD)까지 |
| 비용 모델 | 오탐 > 미탐. **λ = 4** (오탐 1건 = 미탐 4건) |
| 외부 API | 운영 경로에서 **0회.** 전량 자체 서버 CPU |
| 학생 모델 | KoELECTRA-small 14M, ONNX, 8개 다중 라벨 |

## 1. 13차에서 바꾼 것

규칙 층이 1단에서 **4단**이 되었습니다. 각 층은 앞 층이 못 보는 것만 봅니다.

| 층 | 무엇을 보나 | 심각도 |
|---|---|---|
| ① 원문 | 정규식 그대로 | BLOCK 가능 |
| ② 기호 제거 사본 | `원 금 보 장` — 글자를 벌린 것 | WARN 상한 |
| ③ **깊은 정규화 사본** (신설) | NFKC + 자모 합성 — `ⓘⓓ`, `ㅇ ㅝ ㄴ ㄱ ㅡ ㅁ` | WARN 상한 |
| ④ **훼손 사실 자체** (신설) | 무엇을 감췄는지와 무관하게 **감췄다는 것** | WARN 고정 |

|---|---|---|

### 1-2. 채택한 설계 원칙 셋

**(가) 해독하지 않는다.** 13차 답변은 동형자 표(`0↔O`, `5↔S`)와 한/영 음차 표를 권했지만, 실제 자료에서 그 표는 성립하지 않았습니다 — `카ka5톡`의 `5`는 `S`가 아니라 `O`(카카오)입니다. 같은 글자가 문맥마다 다른 것을 대신하므로 표는 항상 한 수 뒤가 됩니다.

대신 **바꿨다는 사실만** 지적합니다(`SCREENING_EVASION`). `텔le그ram`이 무슨 뜻인지 몰라도 "한 낱말에 한글·라틴이 섞였고 상장 종목이 아니다"는 판정할 수 있어 **새 변형에 표 없이 반응**합니다.

대가는 **유형을 못 짚는 것**입니다. 리서처는 "외부 채널 유도"가 아니라 "글자를 정상 표기로 고치라"는 안내를 받습니다. 이것을 해독기 실패가 아니라 **정규화를 강제하는 깔때기**로 설계했습니다 — 고친 글은 전체 규칙을 다시 만나고, 거기서 진짜 유형이 나옵니다. **이 가정이 R-2의 쟁점입니다.**

**(나) 마침표 가드를 간격 판별식으로 교체.** 예전 코드에는 이렇게 적혀 있었습니다:

```ts
// 회피는 한 표현 안에서 글자를 벌리지, 중간에 마침표를 찍지 않는다.
if (/[.!?\n]/.test(text.slice(start, endIndex + 1))) continue;
```

**이 가정이 틀렸습니다.** 적대적 코퍼스의 표준 형태가 정확히 마침표입니다(`텔.레.그.램`, `원.금.보.장`, `손.실.없.는`). 오탐(`복원. 금보장 구역`)을 막으려 넣은 가드가 그대로 회피 통로였습니다.

지금은 **간격의 규칙성**으로 가릅니다 — 회피는 읽히게 하려 글자마다 고르게 벌리고(간격 `[2,2]`), 우연은 한 곳에만 끼어듭니다(간격 `[1]`). 줄바꿈은 예외 없이 버립니다(제목·요약·본문 이음매를 넘은 매칭은 서로 다른 필드의 글자가 이웃한 것).

**(다) 화이트리스트 없이는 신호를 켜지 않는다.** 종목 마스터(16,553건) 없이 문자 혼용 신호를 켜면 대조군 8건 중 **5건이 오탐**입니다 — `삼성SDI`, `POSCO홀딩스`, `KT&G`가 전부 문자를 섞어 씁니다. λ=4 아래에서 오탐 5건은 미탐 20건어치라, 근거 없이 켜는 쪽이 더 비쌉니다. 그래서 아는 이름 집합을 못 받으면 이 층은 **아무 소견도 내지 않습니다.**

교착어 처리가 필수였습니다: 마스터엔 `삼성SDI`인데 문장엔 `삼성SDI의`로 나옵니다(오탐 5건의 실제 원인). **접두어 매칭은 쓰면 안 됩니다** — `카카오`는 상장사이고 `카톡`은 금지어라, 접두어를 허용하면 `카카오톡`이 통째로 화이트리스트에 들어갑니다.

### 1-3. 13차 답변 중 측정으로 **반증된** 것

**P-6의 "정규화 거리를 보편 방어로"는 성립하지 않습니다.**

| 기법 | 치환 거리 중앙값 |
|---|---|
| 대조군 8건 | **0.000** (전부) |
| ① 한/영 혼용 | **0.000** |
| ② 구분기호 | **0.000** |
| ③ 음성 변형 | **0.000** |
| ④ 은유 | **0.000** |
| ⑤ 유니코드 | 0.250 |
| ⑤ 자모 분리 | 0.400 |

NFKC·자모 합성이 **실제로 글자를 바꾼 경우**에만 신호입니다. 다만 그 범위에서는 대조군이 정확히 0이라 **임계값 0**을 쓸 수 있습니다("한 글자라도 바뀌었으면 사람이 일부러 넣은 것").

⚠ 첫 측정에서는 대조군(0.190)이 한/영 혼용(0.125)**보다 높게** 나왔습니다. 원문과 정규화본을 그대로 견주면 사실상 **띄어쓰기 개수**를 재게 되기 때문입니다(정상 한국어는 띄어쓰기가 많고 회피 문구는 짧다). 양쪽에서 기호를 먼저 걷어낸 뒤 견주니 신호가 바로 섰습니다.

## 2. 구현 중 드러난 것 — 이것이 이번 검토의 진짜 재료입니다

### 2-1. **측정한 92%가 운영에서는 0%였습니다**

44건 코퍼스로 28% → 92%를 측정하고 보고까지 마친 뒤에 발견했습니다. 운영 경로(`screenReport`, 작성 중 사전 검사)가 `applyRules(input)`를 **문맥 없이** 부르고 있었고, 문맥이 없으면 그 층은 **설계대로 침묵**합니다. 92%는 탐침 스크립트에서만 참인 숫자였습니다.

이 실패가 위험한 이유는 **고장 나지 않는다**는 것입니다. 예외도 경고도 없고, 820건 시험이 전부 초록이고, `ctx.knownNames ?? new Set()`은 완벽하게 정상인 코드로 보입니다.

같은 모양을 이 저장소는 반복해서 만났습니다:

| 회차 | 조용한 무동작 |
|---|---|
| 8차 | 학습셋 = 채점지 (성적이 자기 답안을 채점) |
| 9차 | 사이드카 유실 — 게시는 계속되는데 패러프레이즈 탐지만 0% |
| 12차 | 평가 하네스가 **빈 예측 카드**로 측정 (운영 입력엔 항상 카드가 있다) |
| 13차 | 라운드 전체를 **학습에 넣어** 일반화 측정 불가 |
| **이번** | **신호를 켜는 배선 누락** |

지금 한 조치: 배선 수정 + **구조 시험**(`screeningWiring.test.ts`) — 1차 검수를 부르는 모든 파일이 종목 마스터를 함께 넘기는지 소스를 훑어 강제합니다. 값이 아니라 **자리**를 시험합니다.

**그런데 이 조치는 이 한 자리만 지킵니다.** 다음 신호를 붙일 때 같은 일이 또 생깁니다.

### 2-2. 보이지 않는 문자는 아직 전부 뚫립니다 (실측)

원금보장·텔레그램을 각 글자 사이에 보이지 않는 문자를 끼워 넣고 통과시켰습니다:

| 문자 | 코드포인트 | 결과 |
|---|---|---|
| 제로폭 공백 ZWSP | U+200B | **뚫림** |
| 제로폭 비접합 ZWNJ | U+200C | **뚫림** |
| 워드 조이너 WJ | U+2060 | **뚫림** |
| 소프트 하이픈 | U+00AD | **뚫림** |
| 결합 문자 (´) | U+0301 | **뚫림** |
| BOM | U+FEFF | 잡힘 |
| 전각 공백 | U+3000 | 잡힘 |
| NBSP | U+00A0 | 잡힘 |

**8종 중 5종이 통과합니다.** 잡힌 셋은 우연입니다 — JS 정규식 `\s`가 U+00A0·U+3000을 포함하기 때문이지, 설계된 방어가 아닙니다.

### 2-3. 화이트리스트가 새 공격면이 되었습니다

종목 마스터 16,553건 중 **한글·라틴 혼용 표기가 2,727건**입니다(`LG에너지솔루션`, `SK하이닉스`, `알파벳 A`, `하이트진로2우B`, `소닉SVM`…). 이 2,727건은 이제 **문자 혼용 신호를 끄는 열쇠**입니다.

지금 측정: 금지 어휘(`카톡`·`텔레그램`·`원금`·`보장`·`리딩`·`단톡`·`상담`)를 품은 상장 종목명 **0건**. 종목명 끼워넣기 공격 5종도 전부 다른 층에서 잡힙니다.

**문제는 이것이 오늘의 사실이라는 것입니다.** 종목 마스터는 매일 06:00에 동기화되고, 그때 새 종목이 들어옵니다. 금지어와 충돌하는 이름이 상장되는 날 **규칙 하나가 조용히 꺼집니다** — 그리고 그것을 보는 장치가 없습니다.

### 2-4. 설계된 깔때기가 기존 규칙과 충돌합니다

`SCREENING_EVASION`은 유형을 짚지 못하고 "정상 표기로 고치라"만 말합니다. 설계 의도는 **고친 글이 전체 규칙을 다시 만나는 것**입니다.

그런데 이 저장소에는 이런 규칙이 이미 있습니다:

```ts
export const REPUBLISH_REVIEW_THRESHOLD = 3;
// 반려가 3회 쌓이면 검수를 통과해도 자동 게시하지 않고 운영자 검토를 거친다.
// 근거: 반려 사유·인용문을 공개하므로 문구를 조금씩 바꿔 재제출하면 규칙을 이진 탐색할 수 있다.
```

**두 설계가 정면으로 부딪힙니다.** 회피 지적 → 고침 → 다른 규칙에 걸림 → 고침 → … 세 번이면 자동 통과 경로가 닫히고 운영자 큐로 갑니다. **성실하게 고치는 리서처와 규칙을 이진 탐색하는 공격자가 같은 카운터를 공유합니다.**

## 3. 검토 질문

### R-1. 조용한 무동작을 일반적으로 어떻게 관측하는가

2-1의 다섯 사례는 전부 같은 모양입니다: **없어야 할 것이 없는 게 아니라, 있어야 할 것이 없는데 아무 일도 안 일어난다.** 예외 처리로는 안 잡힙니다 — 실패가 아니라 침묵이기 때문입니다.

지금 쓰는 것 둘:
- **카나리아** (학생 모델): 알려진 입력에 알려진 출력이 나오는지 매 기동마다 확인. 어긋나면 학생을 통째로 뺀다
- **구조 시험** (이번에 추가): 소스를 훑어 배선을 강제

제 판단은 **카나리아를 규칙 층에도 넣는 것**입니다. 44건 코퍼스 중 몇 건을 "반드시 걸려야 하는 문장"으로 지정하고, 검수 프로세스가 뜰 때 실제 파이프라인에 통과시켜 안 걸리면 운영자 알림을 냅니다.

- 이 방향이 맞습니까? 아니면 구조 시험(정적)만으로 충분하고 런타임 카나리아는 과합니까?
- 카나리아가 **스스로 조용히 죽는 것**은 무엇이 막습니까? (카나리아의 카나리아 문제)
- 더 일반적으로: 이 저장소가 다섯 번 같은 실패를 했다면 **개별 처방이 아니라 구조적 원인**이 있을 것입니다. 무엇입니까? "선택적 인자(optional parameter)로 능력을 주입하는 패턴" 자체가 원인입니까 — 그렇다면 대안은 무엇입니까?
- 이 판단을 위해 무엇을 재야 합니까?

### R-2. 유형을 못 짚는 지적은 유지할 만한가 — 그리고 반복 반려 상한과의 충돌

2-4의 충돌입니다. 선택지 셋을 봤습니다:

- **(가) 회피 반려는 카운터에서 뺀다** — "표기를 고치라"는 규칙 탐색이 아니라 형식 교정이므로. 위험: 공격자가 회피 표기로 반려를 유발해 카운터를 우회하며 무한 재제출
- **(나) 회피 지적은 반려가 아니라 즉시 되돌림으로 처리** — 게시 요청 자체를 받지 않고 작성 화면에 되돌려 보낸다(제출 이력이 안 남는다). 위험: 반복 시도 기록이 사라져 어뷰징 탐지 근거를 잃는다
- **(다) 그대로 둔다** — 3회 안에 못 고치는 사람은 사람이 한 번 보는 게 맞다

- 어느 쪽입니까? 다른 답이 있습니까?
- 근본 질문: **"글자를 고치라"는 지적을 반려로 세는 것이 옳습니까?** 이 저장소는 자동 만료를 반려로 세지 않습니다("시간이 만든 결과지 사람의 판단이 아니므로"). 같은 논리가 여기 적용됩니까?
- 그리고 1-2(가)의 전제 자체를 봐 주십시오 — **"고치면 진짜 규칙에 걸린다"는 깔때기 가정이 성립합니까?** 성립하지 않는 경우는 무엇입니까? (예: 회피가 유일한 위반이었고 정상 표기로 고치면 아무 규칙에도 안 걸리는 문장. 그러면 우리는 결백한 사람을 한 바퀴 돌린 것입니다)
- 이걸 재려면 무엇이 필요합니까?

### R-3. 보이지 않는 문자를 어디까지 걷어낼 것인가

2-2의 실측입니다. 제 판단은 **서식 전용 문자는 전부 제거**입니다 — ZWSP·ZWNJ·ZWJ·WJ·소프트 하이픈·BOM·불가시 연산자(U+2061~2064)·유니코드 태그(U+E0000~E007F). 이들은 한국어 투자 리포트에 정당한 용도가 없습니다.

**결합 문자(U+0300~036F)는 다릅니다.** 라틴 문자에서는 뜻을 바꾸고(`e` vs `é`), 한글 위에 쌓이면 순수한 훼손입니다. 여기서 막힙니다.

- 서식 전용 문자 제거에 동의하십니까? 빠뜨린 블록이 있습니까?
- **결합 문자는 어떻게 다룹니까?** "한글 자소 뒤에 오는 결합 문자만 제거"가 타당합니까, 아니면 결합 문자 존재 자체를 ④층의 훼손 신호로 넘깁니까?
- 이모지·변형 선택자(U+FE0F)는? 리서처가 정상적으로 씁니다
- **이 목록도 결국 표입니다.** 1-2(가)에서 "표는 항상 한 수 뒤"라고 했는데, 여기서는 표를 씁니다. 두 판단이 모순입니까, 아니면 갈리는 기준이 있습니까? 제 생각엔 **유니코드 서식 문자는 유한하고 표준이 정의한 닫힌 집합**이라 회피 표기와 성질이 다르지만, 이 구분이 옳은지 봐 주십시오
- 오탐 대조군을 어떻게 설계해야 이 판단이 근거를 갖습니까? 지금 대조군 8건은 너무 작습니다

### R-4. 화이트리스트를 어떻게 감시할 것인가

2-3입니다. 매일 동기화되는 16,553건이 규칙을 끄는 열쇠인데, 새 열쇠가 들어오는 것을 아무도 안 봅니다.

제 판단은 **동기화 배치에 충돌 검사를 붙이는 것**입니다 — 새로 들어온 종목명을 전체 금지 정규식에 통과시켜, 걸리면 그 종목을 화이트리스트에서 제외하고 운영자에게 알립니다.

- 이 방향이 맞습니까? 제외하면 그 종목을 정상적으로 분석하려는 리서처가 회피로 지적당합니다 — 어느 쪽 오류가 더 쌉니까?
- **부분 충돌**은 어떻게 합니까? 종목명이 금지어를 포함하지는 않지만 금지어의 일부와 겹치는 경우
- 화이트리스트를 **토큰 완전일치**로 쓰는 것 자체가 옳습니까? 대안(예: 종목명이 문장에서 종목으로 쓰였는지 문맥으로 판단)은 규칙이 할 수 있는 일이 아닌 것 같은데, 그렇다면 이 한계를 어디에 적어 두어야 합니까?
- 2,727건이라는 숫자가 위험한 크기입니까? 무엇을 재면 알 수 있습니까?

### R-5. ③음성 변형·④은유를 학생 모델에 맡긴 것을 어떻게 검증하는가

규칙이 원리적으로 못 하는 자리라고 판단해 학생 모델에 남겼습니다. 측정은 ③ 100% / ④ 75%인데, **그 데이터의 상당수가 학습에 들어가 있어 일반화를 뜻하지 않습니다.** 13차 P-5에서 지적받고도 이번 44건은 채점지로 분리했지만, 이전 96건은 이미 학습셋에 있습니다.

- **기법군 단위 분할(leave-one-technique-out)**을 어떻게 운영 절차로 만듭니까? 자료를 받을 때마다 사람이 판단하면 언젠가 빠뜨립니다
- 이미 오염된 학습셋(96건)은 어떻게 합니까? `--exclude-labeler`로 빼고 재학습하면 회피 탐지 능력이 함께 사라집니다
- ④ 은유는 규칙이 0%이고 학생이 75%입니다. 그런데 학생은 REJECT를 못 합니다 — **은유형 회피는 아무리 잘 잡아도 전량 사람 검수 부담**으로 남습니다. 이 부담을 어떻게 셉니까? 출시 인력 계획에 직결됩니다
- 14M 모델의 천장이 어디인지 재는 방법이 있습니까? 지금은 "못 잡으면 데이터를 더 넣는다"만 하고 있어, 데이터 부족과 용량 한계를 구별하지 못합니다

### R-6. λ = 4를 층마다 같게 둘 것인가

λ=4는 "성실한 리서처를 막는 것이 위반을 놓치는 것보다 4배 비싸다"는 정책값입니다. 그런데 층마다 **오탐의 실제 대가가 다릅니다**:

| 층 | 오탐이 리서처에게 뜻하는 것 |
|---|---|
| ① 원문 규칙 BLOCK | **즉시 거절.** 사람 확인 없이 게시가 죽는다 |
| ②③ 정규화 WARN | 보류 — 운영자가 승인하면 살아난다 (수 시간 지연) |
| ④ 훼손 신호 WARN | "표기를 고치라" — 고치면 바로 재제출 가능 |

④의 오탐은 거절도 지연도 아니고 **한 번의 재작성**입니다. 그렇다면 ④에서는 λ가 4보다 작아야 하고, 더 공격적으로 잡아도 됩니다.

- 이 추론이 맞습니까? 층별 λ를 두는 것이 타당합니까, 아니면 단일 λ의 단순함이 더 값집니까?
- 맞다면 ④의 λ는 얼마여야 하고, 그 값을 무엇으로 정당화합니까?
- 반대 논거도 봐 주십시오: **오탐은 지연이 아니라 신뢰의 문제**일 수 있습니다. 성실한 리서처가 "글자를 고치라"는 말을 반복해서 들으면 시스템을 신뢰하지 않게 되고, 그것은 λ로 셀 수 없습니다. 이 비용을 어떻게 다룹니까?
- 그리고 R-2와 엮입니다 — ④의 오탐이 반복 반려 카운터를 올린다면 "한 번의 재작성"이 아니라 **운영자 큐행**입니다. λ를 논하기 전에 그 결합부터 끊어야 합니까?

## 4. 답변 형식

각 질문에 대해:

1. **결론** — 무엇을 하라는 것인지 한 문장
2. **근거** — 왜 그 선택인지. 특히 **λ=4**와 **"규칙만 REJECT 가능"** 제약 아래에서 어떻게 정당화되는지
3. **먼저 재야 할 것** — 이 결정 전에 측정해야 하는 수치와, 그 측정에 필요한 표본. **지금 있는 것으로 잴 수 있는지**를 밝혀 주십시오(대조군이 8건뿐입니다)
4. **반증 조건** — 무엇이 관측되면 이 결론이 틀린 것인지

**지난 회차에서 얻은 교훈을 반영해 주십시오:**

- **P-6은 측정으로 반증됐습니다.** 그럴듯한 구조적 신호가 실제로는 띄어쓰기를 재고 있었습니다. 이번 답변도 같은 운명일 수 있다고 보고, **어떻게 재면 그것이 드러나는지**를 함께 적어 주십시오
- **추상적 권고는 쓸모가 없습니다.** "관측 가능성을 높이십시오" 대신, 44건 코퍼스와 대조군 8건에 대해 **어떤 숫자가 나와야 채택인지**를 적어 주십시오
- **가정을 코드 주석에 적어 두는 것으로는 안 막힙니다.** `회피는 마침표를 찍지 않는다`가 정확히 그렇게 틀렸습니다. 답변에 가정이 들어간다면 **그 가정을 붙잡을 시험**을 함께 적어 주십시오
