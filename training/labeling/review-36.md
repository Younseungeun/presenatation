# 36차 검토 요청 (사건 구동 — 창업자 지시 "검수 정확도를 더 높여라") — 정확도 로드맵 사전 등록 3건

## 0. 사건과 제약

창업자 질문: "SOLICIT zero-shot 73.7% 는 낮다. 현 방식(인코더 분류기 학습)이 최선인가?"
정직한 답을 먼저 적습니다: **현 방식은 절대 최선이 아니라 제약 안의 국소 최적**입니다.
천장은 셋 — ① 데이터 기근(합성 ~1,000문장, 합성의 한계는 r6 결함·r8 포화·r9 제로섬로
3회 실측) ② 인코더 구조(문장을 벡터 하나로 접는 2020년식 — 부정·간접화법·은유의 문맥
추론이 구조적으로 약함) ③ 외부 AI 호출 0 제약.

**창업자가 이번에 재확정한 제약 (이 프롬포트의 전제)**:
- **외부 AI API 호출 0** — 게시 검수 경로에서 영구 유지 (③은 풀지 않는다)
- **추가 현금 비용 0** — 정확도 개선은 이미 계획된 호스팅 사양(110M 서빙용 8코어급 +
  충분한 RAM) 안에서 해결한다. 유료 API·추가 서버·유료 데이터 전부 배제

이 제약 아래에서 정확도를 올리는 길은 둘뿐이고(운영 데이터 + 로컬 추론의 격 상향),
그것을 안건 셋으로 올립니다.

## MM-1. 로컬 소형 LLM 2단 검수 (핵심 안건 — 실측 승인 요청)

### 왜 이것이 남은 가장 큰 지렛대인가

인코더(IRIS)는 "이 문장이 학습한 위반 패턴과 닮았나"를 재고, LLM 은 "이 문장이 무슨
**뜻**인가"를 읽습니다. r6 가 반복 실측한 약점 — 부정형("연락 주셔도 알려드릴 수
없습니다"), 간접 유도("아시는 분은 아시죠"), 은유 — 는 정확히 LLM 이 인코더와 격이
다른 자리입니다. 지금까지 이 길이 닫혀 있던 이유는 **지연**(LLM CPU 추론 수 초~수십 초
> 동기 검수 예산 1.5초)이었는데, 교체 시점에 구현하기로 합의된 **비동기 검수 큐**가
그 제약을 풀었습니다 — 게시 확정이 몇십 초 늦어도 되는 구조에서는 느린 대신 정확한
2차 검수가 성립합니다. **외부 호출 0**: 가중치를 반입해 서버 안에서 돌립니다(110M 과
같은 반입 경로 — 운영자가 브라우저로 받아 넣음).

### 구조 (절대 조건 불변)

```
규칙 엔진 (즉시·BLOCK 권한 유지) ─┐
IRIS 110M (1차·WARN)             ├─ 소견 병합 → 보류/게시
로컬 LLM (2차·영구 WARN) ────────┘         ↓
                                    운영자 최종 판정 (불변)
```

- LLM 은 **영구 WARN** — 즉시 거절 권한 없음("사람 확인 없이 정상 리포트를 죽이지
  않는다" 절대 조건 그대로). 프롬프트 인젝션 방어도 기존 2중 구조 재사용(무작위 경계 +
  규칙 소견은 병합에서 생존)
- 적용 대역: **비동기 큐의 전건 2차** 제안 — 출시 규모(하루 수백 건 이하)에서는
  건당 10~30초 CPU 추론도 큐가 소화. 트래픽 성장 시 "IRIS 애매 대역(0.3~0.7)만"으로
  좁히는 스위치를 미리 설계

### 실측 계획 (이번 안건의 범위 — 편입이 아니라 실측 승인까지)

1. 모델 후보 반입: 한국어 가능 소형 LLM 1~4B 양자화(gguf/onnx) 2~3종 — 운영자 반입,
   구체 후보는 반입 가능성(라이선스·크기) 확인 후 확정
2. **오프라인 하네스로 IRIS 와 나란히 실측**: 같은 잣대(채점지 86 + 문서 34 + r6 264 +
   홀드아웃 101) — LLM 은 이 자료를 학습하지 않으므로 전부 zero-shot 이라 오염 없음.
   프롬프트는 유형 정의 + 소수 예시(채점지 밖 문장으로), JSON 소견 강제
3. 처리량 실측: 운영 대리 분포 100건 기준 건당 추론 시간·시간당 처리량 vs 예상 게시량

### 채택선 (사전 등록)

- r6 264 λ=4 순이익 > P1-A(+75) — 특히 부정형 하드네그 오탐 ≤ 3(P1-A 동급 이상)
- 채점지 부정문·risk_heavy 오탐 증가 0, 즉시 거절 오탐 0(WARN 전용이라 구조적 충족)
- 처리량 ≥ 예상 피크 게시량 × 2 (큐가 밀리지 않는 조건)

### gap 17 함정 / 반증 조건

- gap 17: "LLM 이니 만능"이라는 기대. 소형 LLM 의 실제 위험은 **환각 소견**(없는 위반을
  그럴듯한 인용과 함께 만들어냄)과 형식 불복종(JSON 이탈)이다 — 벤치 점수가 아니라
  우리 잣대 실측으로만 판단한다
- 반증 조건: ① 후보 전종이 r6 에서 P1-A 이하 ② 오탐(환각)이 IRIS 초과 ③ 처리량이
  게시량을 못 따라감 — 하나라도 나오면 트랙 폐기, 현 3겹 구조 유지

## MM-2. 운영 데이터 경로에 LLM 라벨 축적을 얹는다 (LL-3 확장)

LL-3(첫 50건 동결 / 이후 학습 후보)은 그대로 두고 한 가지를 얹습니다: LLM 2차가
채택되면 그 소견도 운영자 판정과 함께 기록되어, **운영자가 확정한 건만** 미래 재학습
라벨이 됩니다(기존 operatorTraining 규칙 그대로 — LLM 소견 단독은 라벨이 아니다.
그러면 LLM 의 환각이 학습 자료로 세탁된다). 판정 요청: 이 축적 규칙이 맞습니까.

## MM-3. "정확도"의 공식 잣대 명문화

창업자의 "더 높은 정확도"를 재려면 잣대부터 하나여야 합니다. 지금은 모델 단독
벤치(r6 73.7% 같은)와 시스템 성적(규칙+IRIS 95.5% + 운영자)이 섞여 읽힙니다. 제안:
**출시 후 공식 잣대 = 시스템 3종** — ① 즉시 거절 오탐 0(절대 조건) ② 보류 오탐률
(운영자 승인 비율) ③ 게시 후 미탐 발견율(강제 철회 건수). 모델 단독 벤치는 후보 비교
전용으로 강등. 판정 요청: 이 정의가 맞습니까 — 아니면 다른 축이 필요합니까.
