# 콘텐츠 자동 검수 시스템

게시 전에 글을 검사해 **거절 / 보류 / 통과**를 정하는 시스템을 다룬다. 규제 콘텐츠,
커뮤니티 모더레이션, 광고 심사처럼 "기계가 1차로 거르고 사람이 최종 판단하는" 구조 전반에 적용된다.

이 스킬의 내용은 투자 리서치 마켓플레이스에서 실제로 운영 설계를 하며 얻은 것이다.
추상적인 모범 사례가 아니라 **실제로 터진 결함과 그 대응**에서 나왔다.

---

## 1. 먼저 정해야 할 단 하나의 질문

**오탐(정상 글을 막는 것)과 미탐(위반 글을 통과시키는 것) 중 무엇이 더 비싼가?**

이 답이 나머지 설계 전부를 결정한다. 대충 "둘 다 나쁘다"로 넘어가면 심각도·임계값·모델
채택 기준을 매번 감으로 정하게 된다.

판단 기준은 **되돌릴 수 있는가**다:

- 미탐이 났을 때 사후에 내리고 환불·정정할 수 있다면 → 미탐은 복구 가능하다
- 오탐이 났을 때 사용자는 대개 다시 오지 않는다 → 오탐은 복구 불가능한 경우가 많다

예시 판단: 리서치 마켓플레이스는 대금이 에스크로에 있고 강제 철회가 가능해서 미탐은
전액 환불로 되돌아간다. 반면 정상 리포트가 막히면 리서처(공급)를 잃는다.
→ **오탐이 더 비싸다** → 자동 거절 권한을 극단적으로 아낀다.

반대 성격의 서비스(아동 안전, 금융 사기)라면 결론이 뒤집히고, 그러면 아래 권고도 뒤집힌다.
**결론을 코드 주석과 설계 문서에 명시**해 두면 이후 모든 판단의 기준점이 된다.

## 2. 결정(decision)과 처리(action)를 분리하라

가장 많이 하는 실수: 탐지 결과의 심각도를 그대로 처리 방침으로 쓰는 것.

같은 "위반이다"라도 **누가 그렇게 말했는지**에 따라 처리가 달라야 한다.

| 판단 주체 | 오탐 가능성 | 적정 처리 |
|---|---|---|
| 결정적 규칙 (오탐이 사실상 0인 표현만) | 거의 없음 | 즉시 거절 |
| AI 판단 | 있음 | 보류 → 사람 결정 |
| 사람이 입력한 문자열 사전 | 오타 하나면 발생 | 보류 |
| 임베딩 유사도 | 부정문에 취약 | 보류 |
| 검사 실패(장애) | 판단 자체가 없음 | 보류 |

구현은 두 타입을 나누는 것으로 충분하다:

```ts
type Decision = 'PASS' | 'WARN' | 'BLOCK' | 'UNAVAILABLE';  // 무엇을 찾았나
type Action   = 'PUBLISH' | 'HOLD' | 'REJECT';              // 그래서 어떻게 하나

function resolveAction(ruleDecision, finalDecision): Action {
  if (ruleDecision === 'BLOCK') return 'REJECT';   // 규칙이 잡은 것만 즉시 거절
  return finalDecision === 'PASS' ? 'PUBLISH' : 'HOLD';
}
```

**자동 거절 권한은 오탐률이 검증된 탐지기에만 준다.** 나머지는 전부 보류다.
보류는 사람이 승인으로 되살릴 수 있지만, 거절은 되살릴 사람이 없다.

---

## 3. 보류(HOLD)는 반드시 세 가지를 갖춰야 한다

보류를 도입하는 순간 **운영자가 시스템의 단일 실패 지점**이 된다. 이걸 방치하면
"자동 검수를 만들었는데 아무것도 게시되지 않는" 상태가 된다.

1. **즉시 알림** — 큐 페이지를 열어야만 알 수 있으면 위반 콘텐츠의 판매 시간이 길어진다
2. **지연 재알림** — 보류 시점 1회 알림만으로는 운영자가 자리를 비운 사이 방치된다.
   건별로 쏘지 말고 **요약 1건**으로 묶고, 같은 건은 하루 1회로 제한한다 (알림 폭탄은 무시된다)
3. **자동 만료** — 승인해도 더 이상 게시될 수 없는 건(시한 경과 등)은 자동으로 정리한다.
   큐에 처리 불가능한 건이 쌓이면 정말 봐야 할 건을 가린다

**자동 만료는 사람의 판정으로 기록하지 않는다.** 시간이 만든 결과를 사람의 판단으로
남기면 §5의 정확도 지표가 오염된다. 큐에서만 내린다.

## 4. 사용자에게 정직하게 말하라

검수 결과를 화면에 보여줄 때 세 가지를 지킨다.

**"통과 보장"이라고 하지 않는다.** 1차 검사만 돌려놓고 "게시 가능합니다"라고 하면,
2차에서 보류될 때 화면이 거짓말을 한 셈이 된다. 할 수 있는 말은
*"명백한 금지 표현은 없습니다. 최종 판단은 제출 후에 이뤄집니다"*까지다.

**경고 강도를 사실로 조절한다.** 오탐이 잦은 유형까지 똑같이 "차단됩니다"라고 겁을 주면
사용자는 곧 경고 전체를 무시한다. 그렇다고 표시를 죽이면 서버는 여전히 막으므로 화면이
거짓말을 한다. 둘 다 피하는 유일한 방법은 **실제 결과를 덧붙이는 것**이다:

> 참고: 이 유형으로 보류된 최근 12건 중 9건은 검토 후 게시가 승인됐습니다.

**막힌 이유를 숨기지 않는다.** 사유·인용문을 알려주지 않으면 사용자는 무엇을 고쳐야 할지
모른 채 같은 실수를 반복한다. 다만 이 공개는 §7의 이진 탐색 문제를 부르므로 짝이 되는
방어가 필요하다.

---

## 5. 사람의 최종 결정이 곧 정답 라벨이다

검수가 맞았는지는 **운영자가 승인/반려를 누르는 순간에만** 알 수 있다. 그 순간에 라벨을
같이 저장하지 않으면 오탐률을 영원히 모른다 — 그러면 규칙을 고치는 것도, 모델을 바꾸는 것도
전부 감으로 하게 된다.

| 운영자 결정 | 라벨 | 뜻 |
|---|---|---|
| 보류 → 승인 (기본값) | 오탐 | 막지 말았어야 했다 |
| 보류 → 승인 + "지적은 타당" 체크 | 경미 | 심각도를 낮춰야 한다 (규칙 삭제가 아님) |
| 보류 → 반려 | 정탐 | 맞게 잡았다 |
| 통과 → 사후 철회 | **미탐** | 놓쳤다 |

설계 요령 세 가지:

- **기본값이 가장 흔한 경우여야 한다.** 승인의 대다수는 과잉 지적이므로 승인 = 오탐을
  기본으로 두고 예외만 체크하게 한다. 라벨 입력을 필수로 만들면 아무렇게나 눌린다.
- **미탐은 별도 경로가 필요하다.** 통과한 건은 대기 큐에 없어서, 큐 기준으로 라벨을 쓰면
  아무것도 잡히지 않는다. 대기 건이 없으면 **가장 최근 검사 기록**에 라벨을 붙인다.
  이 경로가 없으면 미탐률은 데이터가 아무리 쌓여도 0으로 보인다.
- **소견마다 출처를 남긴다** (`source: 'rule' | 'ai' | 'learned' | 'semantic'`).
  오탐이 정규식 탓인지 프롬프트 탓인지 구분해야 처방이 나온다.

반려 시 **실제 위반 유형**을 따로 받으면 "반려는 맞았지만 엉뚱한 유형을 짚은" 소견도
오탐으로 잡힌다.

## 6. 모델보다 평가셋을 먼저 만들어라

모델(임베딩·분류기·LLM)을 도입하기 전에 **라벨된 평가셋과 기준선 수치**가 있어야 한다.
없으면 모델을 붙여놓고도 좋아졌는지 알 수 없다.

핵심은 **문장 종류를 나누는 것**이다. 전체 탐지율 하나로는 실상이 숨는다:

| 종류 | 뜻 | 정규식의 실제 성적(예) |
|---|---|---|
| 직설 | 금지 표현을 그대로 씀 | 91.7% |
| 회피 | 글자를 벌리거나 기호 삽입 | 100% |
| **패러프레이즈** | 같은 뜻, 다른 말 | **0%** |
| 정상 문장 | 평범한 글 | 오탐 0% |
| **부정문** | 금지 표현을 **부정**함 | 오탐 60% |
| 면책 문구 | 리스크 고지 | 오탐 0% |

패러프레이즈 0%가 **모델이 메워야 할 정확한 몫**이고, 이 수치가 곧 모델 채택 여부의
판정 기준이 된다. 채택 기준을 미리 문장으로 못 박아 두면 나중에 눈대중을 피할 수 있다:

> 오탐률이 기준선을 넘지 않는 선에서 패러프레이즈 탐지율이 가장 높은 설정을 고른다.

평가 하네스는 탐지기를 **"문장 → 소견 목록" 함수**로만 보게 만든다. 그러면 규칙이든
임베딩이든 LLM이든 같은 잣대로 잴 수 있고, 구현이 바뀌어도 하네스는 그대로다.

손으로 만든 코퍼스는 **절대 수치가 아니라 변경 전후 비교**에만 쓴다. 운영자 판정이
쌓이면 그쪽이 진짜 검증셋이 되고 초기 코퍼스는 회귀 테스트용으로 남는다.

자세한 코퍼스 설계와 지표 정의는 `references/evaluation.md`.

## 7. 알려진 함정

전부 실제로 겪은 것이다. 상세한 재현 조건과 대응은 `references/pitfalls.md`.

- **부정문 오탐** — "수익을 보장하지 않습니다"(표준 면책 문구)가 금지어 규칙에 걸려
  즉시 거절됐다. 한국어 부정 범위는 정규식으로 못 잡는다 → 확신 정도로 나눠 처리
- **글자 벌리기 회피** — "원 금 보 장". 공백·기호를 걷어낸 사본에 같은 규칙을 한 번 더
  돌리되, 우연히 생기는 매칭 때문에 **심각도를 낮춘다**
- **프롬프트 인젝션** — 본문이 그대로 AI에 들어간다. 고정 태그는 본문에 같은 태그를 적어
  빠져나갈 수 있으므로 **요청마다 바뀌는 무작위 경계**로 감싸고, 규칙 레벨에도 같은
  탐지를 둬서 AI가 완전히 장악돼도 사람 검토를 우회할 수 없게 한다
- **규칙 이진 탐색** — 사유를 공개하면 문구를 조금씩 바꿔 재제출하며 규칙을 알아낼 수 있다
  → 반복 반려 시 **자동 통과 경로만** 닫는다(게시 자체를 막지 않는다)
- **모델 교체 시 조용한 오답** — 임베딩 벡터에 모델 식별자를 함께 저장하지 않으면,
  차원이 우연히 같을 때 예외도 없이 틀린 유사도가 나온다
- **사전이 썩는다** — 사람이 등록한 표현도 정확도를 측정해야 한다. 걸린 횟수 대비 실제
  확정 비율이 낮으면 재검토 대상으로 표시

## 8. 흔한 작업 절차

### 검수 규칙을 추가할 때

1. 오탐이 사실상 0인가? 아니면 심각도를 WARN으로 (§2)
2. 부정 문맥에서 어떻게 되는지 확인 — "~하지 않습니다"를 붙여 테스트
3. 평가셋에 위반 예시와 **비슷하지만 정상인 문장**을 함께 추가
4. 기준선 대비 오탐률이 오르지 않는지 확인

### 유형(카테고리)을 추가할 때

유형은 지표의 축이기도 하다. 추가하면 유형별 정확도·오탐 분해가 자동으로 따라와야 하고,
운영자가 반려 시 고를 수 있는 목록에도 들어가야 한다.

### 모델을 도입할 때

1. 평가셋·기준선이 이미 있는지 확인 (§6) — 없으면 그것부터
2. 포트(인터페이스)를 먼저 두고 어댑터를 갈아끼운다. 공급자가 없으면 **완전히 비활성**이어야
   한다 — 기능이 조용히 반쯤 켜지는 것이 가장 나쁘다
3. 임계값은 스윕해서 정하고, 고른 근거를 주석에 남긴다
4. 브라우저에서 돌리는 판단은 **게이트가 될 수 없다** (클라이언트는 조작 가능).
   예방(UX)은 브라우저, 집행은 서버 — 같은 모델을 양쪽에서 돌린다

### 심각도를 바꿀 때

거절 → 보류는 안전한 방향, 보류 → 거절은 위험한 방향이다. 후자는 그 탐지기의 오탐률이
평가셋에서 0인지 먼저 확인한다.

## 9. 이 리포지토리에서 작업할 때

파일 지도, 데이터 모델, 실행 명령, 확장 지점은 `references/architecture.md`를 읽는다.
검수 코드를 고치기 전에 반드시 확인할 것 — 어떤 함수가 어떤 불변식을 지키고 있는지가
거기 적혀 있다.

바꾸고 나면 항상:

```bash
npm run eval:screening   # 기준선 대비 탐지율·오탐률·즉시거절 오탐
npx vitest run           # 회귀 테스트 (즉시거절 오탐 0건이 못 박혀 있다)
```
