# 검수 모델 실행 계획 (2026-08-19 결정)

`docs/review-request-model-1.md`가 남긴 미결 질문(F-1~F-6)에 답을 정하고, 그 답대로
파이프라인을 코드로 깔았다. 이 문서가 결정의 기록이고, 실행 절차는 `training/README.md`다.

## 만드는 것

앱 안에서 도는 자체 검수 모델(학생) 하나. 잡는 것은 둘:

1. **문장 단위 위반** — 규칙이 원리적으로 못 잡는 패러프레이즈 (현재 규칙 탐지율 0%)
2. **문서 단위 정합성** — 본문 결론 ↔ 예측 카드(종목·방향·크기·시한) 모순 (현재 규칙 0%)

학습 방식은 **증류**: 교사(Claude 검수기 + 나중엔 운영자 판정)의 라벨로 소형 한국어
인코더를 파인튜닝하고, ONNX로 **서버에만** 싣는다 (3차 확정 — 아래 "서버 전용").

## 미결 질문에 대한 결정

| | 결정 | 근거 |
|---|---|---|
| F-1 임베딩 단계 | **검수 게이트로는 건너뛴다.** 의미 인덱스는 서버 전용으로만 유지 | 콜드스타트가 어차피 라벨을 만들 수 있어 "학습 불필요" 장점이 소멸. 부정 취약 + 문서 단위 불가. 운영자 사전의 "재학습 없이 즉시 반영" 성질만 서버에 남긴다 |
| F-2 모델 수 | **하나** — 인코더 1 + 출력 8차원 다중 라벨 (7유형 + CARD_MISMATCH) | 헤드를 나눠도 구조 이득이 없고 앱 탑재 비용만 두 배. 라벨 불균형(문서 42건)은 pos_weight + `--doc-weight`로 다루고, 그래도 문서 쪽이 채택선 미달이면 그때 분리 |
| ~~F-3 실행 예산~~ | **폐기 (3차 확정)** — 서버 전용이라 크기 예산 자체가 없다 | 아래 "서버 전용 확정" 참고. 100MB·200ms는 브라우저 탑재를 전제한 값이었다 |
| ~~F-4 버전 어긋남~~ | **폐기 (3차 확정)** — 판단 주체가 하나라 어긋날 것이 없다 | 브라우저와 서버 두 벌이 있을 때만 성립하던 문제 |
| F-5 시점 | **API는 유지하고 학생은 지금 준비한다** — 단 그림자 모드로만 | 비용(월 만 원대)은 근거가 아니다. 근거는 ① 작성 중 실시간 검사는 API로 불가 ② API 장애 시 그날 게시 전체가 큐로 감. 그림자 모드는 무해하므로 준비를 미룰 이유가 없다 |
| F-6 1인 라벨 | 합성 라벨링의 **의도↔교사 불일치 목록**을 사람 재검토 경로로 쓴다 | 이중 라벨을 전수로 할 여력이 없으니 어긋난 곳만 본다. risk_heavy 채택선은 손코퍼스 의존을 인정하고, 운영자 판정이 쌓이는 대로 검증셋 교체 |

## 파이프라인 (깔린 코드)

```
[자료 원천]  ※ 8차에서 ①의 용도가 바뀌었다 — 학습셋이 아니라 **채점지**다
 ① 손코퍼스 128건 ──── npm run train:export ──→ training/data/train.v1.jsonl
      **학습 금지.** SCREENING_CORPUS + COHERENCE_CORPUS 를 그대로 내보낸 것이고,
      그 둘이 곧 eval:student 의 채점지다. 7차까지 이 파일을 학습에 넣고 있었으므로
      그 회차들의 하네스 수치는 홀드아웃 성적이 아니다 (본 문제 다시 푼 점수).
 ② 합성 확장     ──── npm run train:synth-corpus → training/data/synth.v2.jsonl (491건)
      대화 교사가 직접 쓴다 — API 키 불필요. 유형별 위반 30 + 하드 네거티브 25,
      중립 정상 60, 문서 단위(CARD_MISMATCH) 23 + 정상 문서 23.
      **생성 시점에 누설을 막는다**: 채점지와 문자 3-gram 자카드 0.6 이상이면 중단.
 ③ 운영자 판정   ──── 출시 후 ComplianceReview.operatorVerdict → 진짜 학습셋

[형식 계약] src/domain/studentText.ts — 한 곳에만 정의
  buildStudentText(): 카드+제목+요약+본문 → 모델 입력 문자열 (학습·추론 공유)
  STUDENT_LABELS:     출력 8차원의 순서 (labels.json으로 내보내 train.py가 읽음)

[학습] training/train.py  → [변환] training/export_onnx.py → model.int8.onnx

[채택 판정] 평가 하네스 (val F1 아님)
  npm run eval:screening  규칙 기준선     npm run eval:teacher  교사 문장 (신설)
  npm run eval:coherence  교사 문서
```

**채택선 (3차 개정)** — 제약 안에서 최대화. 개정 이유는 옛 채택선이 **학생 단독**을
쟀는데 운영에서는 규칙과 합집합으로 병합된다는 것(mergeFindings). 학생·규칙이 서로 다른
정상 문장을 잘못 잡으면 둘 다 통과하고도 합산이 두 배가 된다.
- 게이트(하네스): **학생 단독 오탐률 ≤ 교사**. 그 안에서 패러프레이즈(문장)·
  risk_heavy 통과(문서) 기준 탐지율 최대. 임계값은 **단일**로 스윕한다.
- 함께 **반드시 보고**: 규칙+학생 **합산** 오탐률. 이 값에 고정 문턱을 두지 않는다 —
  17.6%는 지금 규칙이 우연히 만든 실측치일 뿐 감당 한계가 아니고, 그렇다고 25%처럼
  재지 않은 숫자를 박으면 이 저장소의 상수 근거 규칙을 스스로 어긴다.
  **감당 가능한 큐 크기는 그림자 모드의 실측으로 정하고, 배포 직전에 확정한다.**
- 교사 성적이 곧 천장 — 교사가 절대 상한을 넘으면 증류 전에 프롬프트 보강이 먼저다.

## 교사 라벨을 만드는 두 경로

| | API 교사 | 대화 교사 |
|---|---|---|
| 명령 | `eval:teacher` / `train:synth` | `label:pack` → `label:ingest` → `eval:teacher -- --from` |
| 비용 | 종량 과금 (건당 약 $0.035) | 구독에 포함 |
| 조건 | temperature 0 + 구조화 출력 강제 | 대화 — 재현성이 그만큼 보장되지 않는다 |
| 규정문 | `SYSTEM_PROMPT` | **같은 상수를 팩에 그대로 싣는다** (복제 금지) |
| 라벨 표식 | `claude:모델명` | `conversation:모델명` |
| **용도 (H-2 확정)** | 기준선 측정 + 학습 라벨 | **학습 라벨 생산 전용** — 평가 인용 불가, `eval:teacher --from`이 경고를 강제 출력 |

두 경로의 산출물은 같은 `TrainingExample` 형식이고 같은 하네스로 채점되므로 섞어 쓸 수
있다. 다만 조건이 다르므로 `labeler`로 항상 구분해 둔다.

**1차 측정 (2026-08-19, 대화 교사, 문장 86/86)**: 탐지율 100% · 오탐률 0%
(규칙 기준선 53.8% · 17.6%). **전체가 참고치다 — 채택선·천장으로 인용 불가** (2차 검토
H-2 확정): 라벨링 세션이 코퍼스 원본을 먼저 읽어 판정이 회상일 수 있고, "정상 구간은
깨끗하니 오탐률 0%는 유효"라던 처음 주장도 철회했다 — 그 구간 구분 자체가 사람의 기억에
기댄 검증이다. 유효한 교사 기준선은 API(temperature 0) 또는 운영자 판정에서만 나온다.
상세는 `training/labeling/README.md`.

## 순서와 차단 요인

1. ~~`ANTHROPIC_API_KEY`~~ — **대화 교사 경로로 우회했다.** 키는 재현성 있는 재측정과
   대량 라벨링이 필요해질 때 다시 검토한다 (막힌 단계가 아니라 선택지)
2. **유효한 교사 기준선은 아직 0건이다** — 대화 측정(문장 86/86)은 H-2로 참고치 강등.
   문장은 `eval:teacher`, 문서(risk_heavy 채택선의 근거)는 `eval:coherence` — 둘 다
   API 키가 생기는 날 처음 잰다. 대화 라벨링은 학습셋 생산에만 계속 쓴다
3. 학습셋 확장 — `label:pack -- --task generate` 로 유형별 위반 ≥ 50건까지
4. huggingface 접근 가능한 네트워크에서 학습 (**재배포 라이선스는 서버 전용 확정으로 소멸**)
5. ONNX 추론 어댑터(`Detector` 구현, 서버) + **단일** 임계값 스윕 → 하네스로 채택 판정
6. 그림자 모드(서버에서 학생·교사 병행, 처리 권한 없음) → 일치율 검증 → 실권 부여

## 2차 검토 반영 (2026-08-19 — docs/review-request-model-2.md의 H-1~H-4 답변 처리)

| 항목 | 처리 | 내용 |
|---|---|---|
| H-1 학습셋 혼입 | **채택 — 근거 하나는 기각** | 대화 교사 라벨을 학습셋에 섞는다. 검토자가 제안한 롤백 레버를 그대로 구현 — `train.py --exclude-labeler conversation:` (접두사 일치, 반복 지정 가능). 단 "temperature 편차가 데이터 증강 효과"라는 근거는 받지 않는다: **입력의 다양성은 증강이지만 라벨의 비일관성은 라벨 노이즈다.** 같은 문장에 다른 라벨이 붙는 것은 모델을 일반화시키는 게 아니라 결정 경계를 흐리고, 수백 건 규모에서는 해가 이득보다 크다. 섞는 진짜 근거는 추적 가능성과 롤백이다 |
| H-2 평가·생산 분리 | **채택 — 제안보다 더 밀고 감** | Ground Truth를 동결한다: 손코퍼스 128건(채점 124 + 관측 4)의 **사람 라벨** + 이후 운영자 판정. (검토자는 86건이라 했으나 문서 코퍼스 42건 포함 128이 맞다.) 교사 기준선은 API(temperature 0) 또는 운영자 판정 위에서만 인정. 검토자는 "태우지 마라"는 규율을 제안했지만 **규율은 G-α에서 이미 한 번 실패한 방어**라, 도구가 막게 했다 — `eval:teacher --from`이 `conversation:` 라벨을 감지하면 "채택선 인용 불가" 경고를 무조건 출력한다. 1차 측정의 "오탐 0%는 깨끗한 구간이라 유효" 주장도 철회 — 그 구분 자체가 사람의 기억에 기댄 검증이다 |
| H-3 분포 편향 | 채택 | 그림자 모드에서 무너지는 것은 사고가 아니라 **검증 프로세스의 성공**이다 — 에스크로 환불·리서처 이탈 같은 실비용 없이 실패 데이터를 얻는 자리. "작업이 되돌아간다"는 비용 인식을 버리고, 그림자 모드 → 재학습 루프를 정규 절차로 본다 |
| H-4 단일 출력 | 채택 | 8차원 단일 출력으로 먼저 간다. 14M [CLS]가 "결론 추출 → 카드 대조" 2단 추론을 못 할 가능성은 검토자와 같은 판단 — 그 실패 판정을 하네스(risk_heavy 오탐 이중 조건)에 위임하고, 미달이면 NLI 교차 인코더로 분리한다. 갈림길은 이미 선언돼 있어 결정 비용이 없다 |

## 비용 설계 (2026-08-19 사용자 지시 — "비용은 최소화 하는 방향으로")

### 원칙 — 비용을 줄이는 순서가 있다

1. **호출을 없앤다** (가장 큼) — 규칙이 BLOCK하면 AI를 부르지 않는다(이미 구현).
   증류 모델의 존재 이유 자체가 이것이다: 학생이 게이트를 맡으면 건당 API 비용이 0이 된다.
2. **재는 것을 공짜로 만든다** — 교사 라벨링·평가는 대화 교사 경로로 과금 없이 돈다.
3. **남는 호출을 싸게 한다** — 캐싱·effort·Batch API.
4. **싼 모델로 내린다** (마지막) — 판정 품질이 곧 학생의 천장이라 교사는 내리지 않는다.
   생성(다양성이 목적)은 이미 sonnet이다.

**절대 하지 않는 것**: 오탐률을 대가로 비용을 줄이는 것. 오탐 1건의 비용(리서처 이탈)이
API 호출 수천 건보다 비싸다 — 이 스레드의 첫 번째 확정 사항이다.

### 건당 비용 구조 (Opus 5, 입력 $5 / 출력 $25 per 1M)

| | 토큰 | 비용 | 비중 |
|---|---|---|---|
| 입력 (시스템 2,401자 + 리포트 상한 1,400자) | ≈ 4,000 | $0.020 | 57% |
| 출력 (사고 + findings JSON) | ≈ 600 | $0.015 | 43% |
| **합계** | | **≈ $0.035** | |

입력이 상한으로 묶여 있어(`REPORT_TEXT_LIMITS`) 건당 비용에 천장이 있다.
**출력이 43%인데 그 크기를 정하는 `effort`가 근거 없이 medium으로 박혀 있었다** —
상수로 빼고 측정 경로를 주석에 적었다(`claudeScreener.EFFORT`).

### 적용한 것

| 조치 | 근거 | 상태 |
|---|---|---|
| 시스템 프롬프트 캐싱 | 요청마다 안 바뀌는 유일한 덩어리, 입력의 절반가량 | 적용 — **단 베팅이다**, 아래 참고 |
| 캐시 TTL은 기본값(5분) | 쓰기 1.25배 → 손익분기 히트율 21.7%. 1시간은 쓰기 2배라 52.6%가 필요하다. 확실히 이기는 자리(평가·라벨링 연속 루프)는 5분으로도 전부 적중하므로 낮은 문턱을 고른다 | 적용 |
| 캐시 토큰 기록 (`ScreeningUsage`) | 캐싱이 이득인지 손해인지 **사후 판정**하기 위해. 안 재면 영원히 모른다 | 적용 |
| 비용 계산 단일화 (`screeningCostUsd`) | 스크립트마다 단가를 적으면 단가 변경 시 어느 수치가 낡았는지 알 수 없다 | 적용 |
| `effort` 상수화 + 측정 경로 | 비용의 43%를 정하는 값인데 근거가 없었다 | 적용 (측정은 API 키 대기) |

**캐싱은 확정이 아니라 베팅이다.** 캐시 쓰기는 정가의 1.25배, 읽기는 0.1배라
히트율 21.7%를 넘어야 이긴다. 평가·라벨링 루프(수십~수백 건 연속 호출)에서는 확실히
이기지만, **운영 검수는 리서처가 게시할 때만 도는 산발적 호출이라 미달일 수 있다.**
`eval:teacher`가 히트율과 절감액을 함께 출력하고, 운영 기록에서도 미달이면 되돌린다 —
판단은 감이 아니라 그 수치로 한다.

### 하지 않은 것과 이유

- **Batch API (50% 할인)** — 라벨링·평가는 지연에 둔감해 적격이지만, 대화 교사 경로가
  이미 **그 작업을 0원으로** 만들었다. API 경로로 대량 라벨링을 하게 되는 날 도입한다.
- **교사를 싼 모델로 교체** — 교사 판정이 곧 학생의 천장이다. 여기서 아낀 돈은
  학생의 상한을 깎는 값으로 치른다.
- **재제출 시 검수 결과 재사용(내용 해시)** — temperature 0이라 같은 내용이면 같은 답이
  나오므로 이론상 가능하지만, 반려 후 재제출은 대개 내용을 고쳐서 오므로 적중률이 낮다.
  스키마 변경 비용 대비 이득이 불확실해 보류.

## 3차 검토 반영 (2026-08-19 — review-request-model-3.md의 F-1~F-4)

검토 의견이 **두 벌** 왔고 F-3에서 정반대였다. 결론이 갈린 항목은 문서로 정하지 않고
스위치로 만들어 하네스에 판정을 넘겼다.

| 항목 | 처리 | 내용 |
|---|---|---|
| **F-4 서버 전용** | **채택 — 이번 회차에서 가장 큰 결정** | 브라우저 온디바이스 계획 **폐기**. 두 검토자가 같은 결론이었고, 두 번째가 내가 답하지 못한 "왜 처음에 브라우저를 넣었는가"에 답을 줬다: **검사 주체가 종량제 API였을 때 타이핑마다 과금되는 것을 피하려던 해법**이었고, 주체가 자체 모델로 바뀌면서 전제가 소멸했는데 해법만 남아 기존 확정(규칙 은닉)과 충돌하고 있었다 — 잔재(vestigial design). 폐기로 사라진 것: 크기 예산(1차 F-3)·버전 동기화(1차 F-4)·**가중치 재배포 라이선스 블로커**·첫 로드 UX. 남는 것: 가중치 수급(학습용) |
| F-1 임계값 | 채택 + **플랜 B를 두 번째 안으로** | **단일 임계값**으로 스윕한다(128건에 8차원 스윕은 검증셋 과적합). 미달 시 8차원으로 쪼개지 않고 **이미 있는 위험 성격 4단계**(규제/소비자/무결성/품질)로 4개만 둔다 — 새 축을 만들지 않고 도메인 분류를 재사용하므로 표본이 확보되고 "규제는 보수적으로, 품질은 엄격하게"라는 사업 논리가 그대로 붙는다 |
| F-2 합산 채택선 | 채택 — **(ㄱ) 규칙 축소는 기각** | 규칙은 즉시 거절 권한을 가진 **유일하게 검증된 층**이라 학생으로 교체하지 않는다. 합산 예산은 올리되 **숫자를 지금 박지 않는다** — 첫 검토는 "25%"를 제시했으나 재지 않은 값이고, 이 저장소는 근거 없는 상수를 테스트로 막는다(이번 회차에도 그 테스트가 내 실수를 잡았다). 게이트는 학생 단독 오탐률 ≤ 교사로 두고, **합산은 반드시 함께 보고**하되 감당 한계는 그림자 모드 실측으로 배포 직전에 정한다 |
| F-3 라벨 마스킹 | **판정 보류 — 스위치로 전환** | 두 검토가 정반대였고 논거가 둘 다 성립한다. 마스킹 반대: 위반 73건 × 미명시 7차원 = **511개 음성 신호가 사라지고** 남는 음성은 정상 51건 × 8 = 408개뿐이라, 유형 간 경계를 배울 자리가 없어져 라벨 남발(=오탐)로 기운다. 마스킹 찬성: 겹치는 문장에 거짓 음성을 가르치는 것은 명백한 노이즈다. → `train.py --mask-unlabeled` 플래그로 두고 **둘 다 돌려 오탐률이 낮은 쪽을 채택**한다. 기본값은 OFF(음성 신호가 더 귀하다는 판단). 마스킹 시 분모에서도 가린 차원을 빼도록 구현했다 — 안 그러면 라벨이 하나뿐인 예시일수록 손실이 작아져 덜 배운다 |

**서버 전용이 새로 만든 비용이 있다.** 브라우저를 포기하면 API 종량제는 사라지지만
그 부하가 **우리 서버 추론**으로 옮겨온다 — 사전 검사는 디바운스 600ms로 타이핑 중에
계속 돈다. 0이 아니라 형태가 바뀐 것이고, 아직 아무도 재지 않았다(4차 검토 G-1).

## 4차 검토 반영 (2026-08-19 — review-request-model-4.md의 G-1~G-4)

| 항목 | 처리 | 내용 |
|---|---|---|
| **G-1 사전 검사 부하** | **채택 — 내 잠정 답을 버림** | 나는 "학생을 사전 검사에서 빼고 제출 시에만"을 제안했는데, 그러면 예방 기능의 목적(제출→보류→수정 왕복 제거)이 되돌아간다. 검토안은 **빼는 대신 트리거를 나눈다**: 1층 규칙은 600ms 디바운스 유지(CPU ≈ 0), **2층 학생은 단락 이동·임시 저장·유휴 시에만** 백그라운드 호출. 커버리지를 지키면서 호출 수를 타이핑 횟수에서 떼어낸다 |
| G-2 그림자 졸업 | **채택 — 단 한 항목은 정정** | 핵심은 **통과 건 무작위 감사**다. 운영자 라벨이 보류 건에만 생기는 편향을 그것으로 깬다 — 교사·학생이 모두 통과시킨 리포트의 5~10%를 운영자가 블라인드 검수. 다만 검토안의 "무작위 통과 표본의 **오탐** 0건"은 성립하지 않는다: **통과된 건에서는 오탐이 발생할 수 없다**(오탐 = 정상을 막는 것). 그 표본이 재는 것은 **미탐**이고, 오탐은 이미 라벨이 있는 보류 큐에서 잰다. 둘을 섞으면 감사의 목적 자체가 흐려지므로 갈라 적는다 |
| G-3 캐싱 | **채택 — 근거는 정정** | 운영 ON / 로컬 개발 OFF(`COMPLIANCE_PROMPT_CACHE=off`) + **프롬프트 크기 CI 상한**. 상한은 내가 "기우인지 모르겠다"고 적었던 프롬프트 팽창을 실제로 막는 장치라 그대로 채택했다. 다만 "첫 호출 후 5분이 지나면 히트율 99%로 수렴"은 **틀렸다** — 5분 TTL은 마지막 사용으로부터 5분이라 게시가 산발적이면 매번 미스다. 그 주장은 트래픽이 연속일 때만 성립하고, 출시 전 규모(리서처 30~50명)에서는 보장되지 않는다. 켜 두는 근거는 여전히 **비대칭**(최악 +6.4% / 최선 −23%)이고 판정은 실측이다 |
| G-4 effort | **채택 — 한 가지 제약을 덧붙임** | 교사 기준선의 effort는 내리지 않는다(천장을 스스로 낮추는 자해). 내려도 되는 자리는 대량 라벨 생산뿐. **덧붙인 제약**: 집행(운영 검수)과 기준선 측정은 **반드시 같은 effort**여야 한다 — 교사 기준선의 쓰임이 ① 증류 천장 ② 지금 운영이 내는 성적 둘이라, 갈라지면 그 숫자가 어느 쪽도 설명하지 못한다. 그래서 `COMPLIANCE_EFFORT`는 라벨 생산 전용 레버이고, 내려서 만든 라벨은 `reviewerId`에 `@low`가 박혀 나중에 그것만 걷어낼 수 있다 |

### 측정해야 할 것 (전부 운영 데이터 대기)

| 무엇 | 어디서 | 무엇에 쓰나 |
|---|---|---|
| 리포트 1편당 (단락 이동 + 유휴) 횟수 vs 디바운스 횟수 | 작성 화면 계측 | 2층 트리거가 실제로 호출을 얼마나 줄이는지 |
| 동시 작성자 50명 기준 Peak RPS | 부하 계산 | 서버 CPU 예산 (지금은 예산 자체가 없다) |
| 통과 건 무작위 감사의 **미탐**률 | 그림자 모드 | 졸업 조건 ① |
| 보류 큐 운영자 판정 일치율의 신뢰구간 수렴 | 그림자 모드 | 졸업 조건 ② — 임의의 표본 수가 아니라 **수렴 지점**이 근거다 |
| Latency p99 · 메모리 이상점 | 그림자 모드 | 졸업 조건 ③ |
| 캐시 히트율 | `eval:teacher` + 운영 기록 | 캐싱 유지·철회 (손익분기 21.7%) |
| medium vs low 라벨 일치 (표본 10~20) | `train:synth --label` | 라벨 생산에 low를 써도 되는지 |

### 미해결 — 2층 트리거가 만드는 새 문제

트리거를 나누면 **리서처가 언제 검사가 돌았는지 모른다.** 지금 사전 검사는 타이핑을
멈추면 곧 결과가 갱신되므로 화면이 항상 최신이지만, 2층이 단락 이동·유휴에서만 돌면
"지금 보이는 소견이 방금 쓴 문단까지 본 것인가"에 답할 수 없다. 이 저장소는 검수 화면이
거짓말하지 않는 것을 원칙으로 못 박아 뒀으므로(`"통과 보장"이라고 말하지 않는다`),
**2층이 마지막으로 돈 시점을 화면에 표시**해야 한다. 문구·형태는 미정.

## 5차 검토 반영 (2026-08-19 — review-request-model-5.md의 F-1~F-4)

| 항목 | 처리 | 내용 |
|---|---|---|
| **F-1 서빙 토폴로지** | **채택 — Python 사이드카** | pm2 프로세스 하나 추가(`screener-sidecar`, FastAPI/Uvicorn), 웹이 localhost HTTP로 호출. 이유는 성능이 아니라 **토크나이저 동일성**이다 — 학습(Python HF)과 서빙이 같은 코드·같은 토크나이저를 쓰면 E-3'가 질문 자체로 사라진다. "운영 프로세스 하나 더"의 비용을 과대평가하고 있었다: 이미 `ecosystem.config.cjs`를 쓰고 있어 항목 하나 추가다 |
| F-2 그림자 저장 | **채택 — 별도 테이블** | `ShadowComplianceReview`(FK → ComplianceReview, cascade). 같은 행에 칸을 더하면 **언젠가 집계 쿼리의 WHERE 하나가 빠져 그림자 소견이 실집행에 합쳐진다** — 조심하는 대신 구조적으로 불가능하게 만든다. 기존 집계는 이 표를 모른다. 내가 "칸이 다르니 안전한가"를 헷갈려 한 지점의 답이다 |
| F-3 Postgres 전환 | **채택 — 걱정 자체가 해소됨** | 사이드카로 가면 학생 추론이 웹 프로세스에서 아예 돌지 않고, HTTP 호출은 Node 비동기 I/O라 **SQLite 쓰기 자물쇠를 잡지 않는다.** F-1의 답이 F-3을 함께 풀었다. 전환은 앞당기지 않는다 |
| F-4 졸업 조건 | **채택 — 단 비용 주장은 기각** | 라벨별 단계적 실권 부여 + 감사 배치화는 채택. 그러나 *"희귀 라벨만 API로 남기면 건당 $0.035 → $0.005"*는 **성립하지 않는다** — 아래 참고 |

### F-4 정정 — 라벨별 졸업은 안전 장치이지 비용 장치가 아니다

**호출 단위와 라벨 단위가 다르다.** Claude 검수는 리포트 1건에 API 1회이고, 그 한 번의
응답이 전 유형의 소견을 함께 돌려준다. **라벨 하나를 학생에게 넘겨도 그 호출은 그대로
나간다** — 남은 유형 중 하나라도 API가 맡고 있으면 건당 비용은 $0.035 그대로다.

프롬프트에서 졸업한 유형의 지침을 빼서 입력 토큰을 줄이는 길도 닫혀 있다: ① 시스템
프롬프트가 바뀌면 캐시가 깨지고 ② **동결된 교사 기준선과 비교 불가능해진다**(같은 규정문이
아니게 되므로). 기준선의 재사용이 이 스레드의 뼈대라 그 대가가 절감보다 크다.

비용이 실제로 줄어드는 유일한 길은 **호출 자체를 건너뛰는 것**이고, 그 설계는 이미
로드맵 3단계에 있다 — *"API는 저신뢰·무작위 감사·신규 리서처만"*. 즉 라우팅은 **라벨이
아니라 건(件) 단위**로 걸어야 한다. 두 장치는 목적이 다르므로 함께 간다:

| 장치 | 단위 | 목적 |
|---|---|---|
| 라벨별 단계적 실권 부여 | 라벨 | **안전** — 검증된 유형부터 학생에게 권한을 준다 |
| 건 단위 라우팅 (로드맵 3단계) | 리포트 | **비용** — 학생이 자신 있고 위험이 낮은 건은 API를 아예 안 부른다 |

### F-1 보완 — 사이드카 장애는 게시 장애가 된다

학생에게 실권을 준 뒤 사이드카가 죽으면, 그 유형의 판정이 `UNAVAILABLE`이 되어 **그날
게시가 통째로 보류 큐로 간다**(운영자 1명). 지금 Claude API 장애와 같은 성질이지만
구성요소가 하나 늘어난 만큼 확률도 는다. 그래서 두 가지를 지킨다:

- **공급자가 없으면 완전히 꺼진다** — `createEmbeddingProviderFromEnv()`가 null을 돌려주는
  것과 같은 패턴. 반쯤 켜진 상태가 가장 나쁘다.
- **그림자 모드에서는 사이드카 장애가 게시를 절대 막지 않는다** — 판정에 관여하지 않으므로
  실패는 삼키고 기록만 비운다.

   **검증 표본 공급 속도를 인위적으로 올리는 유일한 수단**이다 (주 15분 목표)
4. 단일 임계값 스윕 → 하네스 채택 판정

## 6차 검토 반영 (2026-08-19 — review-request-model-6.md의 F-1~F-4)

여섯 회차의 결정 대부분이 **한 번도 실행된 적 없는 코드 위에 서 있다**는 것을 6차에서
확인했고, 이번 반영은 그 부채를 갚을 수 있는 형태로 바꾸는 작업이다.

| 항목 | 처리 | 내용 |
|---|---|---|
| **F-1 스텁 사이드카** | **채택 — 내 우려를 정확히 뚫음** | 나는 "스텁은 배관만 재고 진짜 위험(토크나이저)은 못 잰다"고 막혀 있었다. 답은 **무작위 로짓이 아니라 토크나이저 스텁**이다 — 가중치 없이 토크나이저만 올리면 배관 + **토크나이저 동일성**을 함께 실측할 수 있다. `sidecar/app.py`가 `/screen`에서 `token_count`·`token_ids_head`를 돌려주고, `/health`가 지문을 낸다 |
| F-2 부채 추적 | 채택 | `design-debt.txt` 신설. 등급은 `[Type]`(타입·시험만) / `[Mock]`(외부 없이 E2E 실행) / `[Live]`(실측값 확보). 갚는 순서는 위험도도 실행 가능성도 아니라 **다음 단계의 블로커를 무엇이 푸는가** — 스키마가 없으면 그림자 기록을 못 남기고, 기록이 없으면 졸업 조건을 못 잰다 |
| F-3 학습 환경 | 채택 — Colab 기각 | 재현성 붕괴와 데이터 반출이라는 내 두 우려가 Colab을 기각하기에 충분하다는 판정. **파일 반입 + 로컬 오프라인 로드**로 간다. `train.py`의 기본 경로를 허브 이름에서 `../local_models/student-base`로 바꿨다 — 기본값이 로컬이어야 "코드를 고쳐 우회"하는 일이 안 생긴다 |
| F-4 마이크로 배치 | 채택 — 기본값으로 강제 | 86건을 한 번에 돌리면 미검증 조건에서 천장이 동결된다. `eval:teacher`의 **기본값을 10건**으로 두고 전량은 `--limit 0`을 명시해야 돌게 했다. 표본은 앞에서 자르지 않고 균등 간격으로 뽑는다 — 코퍼스가 유형별로 묶여 있어 앞 10건은 전부 같은 유형이다 |

### 덧붙인 것 — 토크나이저 지문 (F-1 확장)

사이드카를 Python으로 두면 학습·서빙이 같은 토크나이저를 쓰지만, **같은 파일인지는
여전히 보장되지 않는다.** 그래서 지문을 대조한다:

- `train.py`가 학습 시 토크나이저 파일들의 내용 해시를 `config.json:tokenizer_sha`에 기록
- 사이드카 `/health`가 자기 지문과 학습 지문을 함께 반환
- 다르면 웹 어댑터는 소견을 쓰지 않는다

이름이 아니라 **내용**을 해싱하고 정렬해 이어 붙인다(디렉터리 순회 순서는 OS마다 다르다).
임베딩 벡터에 모델 식별자를 함께 저장하는 것과 같은 계열의 방어다 — 어긋나면 예외가
아니라 조용히 틀린 답이 나오기 때문이다.

### 이번 회차에 만든 것

| 파일 | 등급 | 무엇 |
|---|---|---|
| `design-debt.txt` | — | 미검증 결정 명세 (줄 수가 곧 빚) |
| `sidecar/app.py` · `requirements.txt` | `[Type]` | 토크나이저 스텁 사이드카 (가중치 없이 뜬다) |
| `local_models/README.md` | — | 반입할 파일 목록과 이유 |
| `training/train.py` | `[Type]` | 로컬 기본 경로 + `tokenizer_fingerprint()` |
| `scripts/evalTeacher.ts` | `[Type]` | 마이크로 배치 (기본 10건, 전량은 명시해야 함) |

## 확정 — 운영에 Anthropic API를 쓰지 않는다 (2026-08-19 사용자 결정)

**목표: 출시 전까지 학생 모델을 완성해 자동 검수를 규칙과 함께 그것이 맡는다.** 되는 데까지 학습시키고,
출시 후 운영자 판정으로 계속 가르친다.

### 그동안의 오류 — API 키가 조용히 임계 경로로 돌아와 있었다

사용자는 처음부터 "API 키 말고 구독으로"라고 지시했고 대화 교사 경로는 그래서 만들었다.
그런데 **2차 검토 H-2에서 내가 "대화 라벨은 기준선이 될 수 없다"를 도구로 강제**하면서,
교사 기준선을 재려면 API가 반드시 필요해졌다. 모든 채택선이 그 기준선에 걸려 있었으므로
API 키가 임계 경로로 복귀했고, **그 뒤 4개 회차 동안 "API 키 미설정"을 블로커로 적으면서
이미 안 쓰기로 한 것을 블로커라 부르는 모순을 한 번도 짚지 않았다.**

### 고친 것 셋

| 무엇 | 전 | 후 |
|---|---|---|
| H-2 규칙 | 대화 라벨은 기준선 불가 | **저장소를 본 적 없는 세션**의 라벨은 기준선 인정. `label:ingest -- --clean-session` → `conversation-clean:` 표식. 기본값은 여전히 오염 가정(실수의 방향이 "덜 인정"이어야 한다) |
| 채택선 | ① 학생 오탐률 ≤ **교사** ② ≤ 규칙 보류율 | ① 학생 오탐률 ≤ **17.6%**(규칙 보류율) ② **패러프레이즈 탐지율 > 0%**. 교사 성적은 문턱이 아니라 참고선 |
| 비용 최적화(캐싱·effort·비용계산) | `[Live] 대기` = 갚아야 할 빚 | `[보류] 미사용 경로` — 지우지 않되 빚에서 뺀다 |

### 왜 채택선이 뒤집히나 — 학생은 API를 이길 필요가 없다

운영에 API가 없으면 **비교할 상대가 없다.** 학생이 이겨야 할 상대는 지금 실제로 도는 것,
즉 규칙뿐이고 규칙의 성적은 이렇다:

| | 규칙 |
|---|---|
| 직설 / 회피 | 100% |
| **패러프레이즈** | **0%** |
| 오탐(보류율) | 17.6% |

그러므로 **정상 리포트를 지금보다 더 막지 않으면서 패러프레이즈를 조금이라도 잡으면
그 자체로 순이익**이다. "교사만큼 해야 한다"는 훨씬 높은 문턱이었고, 그 문턱은 운영에
존재하지도 않는 상대가 세운 것이었다.

### 정직하게 남는 위험

학생이 완성되기 전에 출시하면 **돌려 말한 위반이 그대로 게시된다** — 규칙이 못 잡으면
`PASS → PUBLISH`이기 때문이다(공급자가 없을 때의 현재 동작). 이 구멍을 메우는 것이
학생 모델의 존재 이유이고, 사용자의 목표(출시 전 완성)가 정확히 그것을 겨눈다.

## 그림자 기록 경로 구현 (2026-08-19) — 첫 [Mock] 부채 상환

`design-debt.txt`의 첫 블로커였던 스키마가 풀려 그림자 경로를 붙였다.

| 파일 | 무엇 |
|---|---|
| `src/infra/compliance/studentClient.ts` | 사이드카 포트. `STUDENT_SIDECAR_URL`이 없으면 **null → 한 줄도 안 돈다**(임베딩 어댑터와 같은 패턴). 2초 타임아웃, 모든 실패를 삼킴 |
| `src/server/shadowScreeningService.ts` | 그림자 기록 + 일치율 집계 |
| `src/server/complianceService.ts` | `screenAndRecord` 커밋 **뒤에** 그림자 호출 |
| `__tests__/shadowScreeningService.test.ts` | 불변식 8건 |

**설계에서 가장 중요한 두 줄**:

1. **트랜잭션 밖에서 돈다.** 안에 넣으면 사이드카 지연이 게시 트랜잭션을 늘리고, 긴
   트랜잭션은 SQLite 쓰기 락으로 결제까지 밀어낸다(`measure:contention` 실측: 4벌 1,281ms).
   그래서 검수 기록 id를 `randomUUID()`로 **미리 만들어** 커밋 후에 연결한다 —
   트랜잭션을 키우지 않고도 행을 가리킬 수 있다.
2. **어떤 실패도 게시를 막지 않는다.** 사이드카 장애·타임아웃·예외·**DB 쓰기 실패**까지
   전부 삼킨다. 학생은 아직 아무것도 처리하지 않으므로, 그 실패가 게시를 죽이면
   "권한 없는 판정이 게시를 죽인" 것이라 정의상 모순이다. 시험이 네 갈래를 각각 고정한다.

**토크나이저 지문 대조도 여기서 집행된다** — 학습 지문과 서빙 지문이 다르면 소견을 버리고
기록하지 않는다. 틀린 답을 기록하면 일치율이 오염되고, 일치율은 졸업 조건이다.
스텁 모드(가중치 없이 토크나이저만)는 **기록한다** — 배관이 돌았다는 증거이고 지연은
그 자체로 측정값이다.

## 8차 검토 반영 (2026-08-20 — review-request-model-8.md의 E-1~E-6)

이번 회차의 머리는 성능이 아니라 **측정 장치**였다. 두 회차 동안 보고한 "채택 불가"가
죽은 ONNX 그래프의 그림자였다는 것이 드러났고, 검토는 그 사고가 다시 나지 않게 하는
쪽으로 답했다.

| 항목 | 답변 | 반영 |
|---|---|---|
| E-1 검토 답변의 우선순위 | 유효성·동등성 검사가 성능 개선보다 **무조건 앞** | 채택 — 아래 판단 기준을 규칙으로 적었다 |
| E-2 채택선 | ⓑ 순이익으로 재정의 | 채택 — `scripts/evalStudent.ts`, 최소최대 선택은 **더 밀고 감** |
| E-3 손잡이 두 개 | 저울은 원칙에서 못 박고 임계값만 스윕. 지표는 PR-AUC | 채택 — `--cost-ratio`, 체크포인트 선택을 macro-AP로 |
| E-4 스타일 섭동 | 이미 물리적으로 격리돼 불필요 | 채택 — 백로그에서 **닫는다** |
| E-5 문서 라벨 결합 | 잘못된 결합. 영구 제외 | 채택 — 주석을 "미졸업"에서 "구조적 불가"로 |
| E-6 켜도 되는가 | ⓑ 바로 켠다 (WARN 전용) | 채택 — `STUDENT_MODE` 기본 `live`. **관문을 하나 더 달았다** |

### E-1 — 무엇을 미루면 안 되는가 (이 스레드의 상시 규칙)

검토 답변이 회차마다 4~6개 오는데 전부 실행하면 그 회차가 답변 실행으로 끝난다.
줄 세우는 기준은 **"이 검사가 실패하면 무슨 일이 일어나는가"**다:

| 실패했을 때 | 성격 | 순서 |
|---|---|---|
| 지표가 안 오른다 | **성능** (데이터 추가, 하이퍼파라미터) | 나중 |
| 지금까지의 숫자가 **전부 무효가 된다** | **유효성·동등성** (학습/평가 분리, PyTorch↔ONNX 대조) | **먼저** |

7차 E-2(로짓 대조)를 미룬 대가가 한 회차였다. 그 검사는 5분이었고, 실패했을 때
무효가 되는 것이 "그 회차의 모든 측정"이었다. **자가 똑바른지 확인한 뒤에 물건을
올려놓는다** — 성능 개선은 그다음이다.

### E-2 — 채택선을 순이익으로 (구 기준 폐기)

구: `합산 오탐률 ≤ 규칙 보류율(17.6%)`.
병합이 합집합이라 합산 오탐은 언제나 규칙 이상이고, 따라서 이 조건은 **학생에게
오탐 예산 0건**을 강제했다. 3차가 세운 원칙은 "오탐이 미탐보다 나쁘다"였지
"오탐은 절대 불가"가 아니었다.

신: **순이익 = (새로 잡은 미탐 건수) − λ × (새로 만든 오탐 건수) > 0**, λ = 4.
비율이 아니라 건수로 세고, 규칙 기준선은 **같은 부분집합**에서 다시 잰다(사이드카
호출이 실패한 건이 한쪽 분모에만 들어가면 뺄셈이 성립하지 않는다).

**검토안보다 한 걸음 더 갔다 — 설정 선택을 최소최대로.** λ=4는 아직 측정이 아니라
선언이다(운영 데이터 0건). 그래서 λ ∈ {2, 4, 10}의 순이익을 함께 찍고, 채택 설정은
**가장 불리한 λ에서 순이익이 최대**인 것으로 고른다. 실측에서 이 규칙은 t=0.4(λ=4에서
동점이지만 새 오탐 1건)가 아니라 **t=0.5(새 오탐 0건)**를 고른다 — λ가 나중에 어디로
정해지든 후회가 가장 작은 자리다.

### E-3 — 저울은 유도하고, 지표는 임계값에서 떼어낸다

`pos_weight = (음성/양성) ÷ λ`. 불균형을 상쇄한 뒤 비용비만큼 되돌린다.
이 코퍼스에서 (음성/양성) ≈ 15, λ = 4 → **약 3.75**. 8차 중반에 손으로 고른 3과
거의 같은 자리인데, **값이 아니라 근거가 바뀐 것**이다.
λ는 하네스의 `COST_RATIO`와 같은 수여야 한다 — 학습이 한 비용비로 배우고 채택 판정이
다른 비용비로 재면 둘 다 옳아도 합쳐서 틀린다.

체크포인트 선택을 `macro-F1@0.5` → **`macro-AP`(평균 정밀도)**로 바꿨다. F1@0.5는
한 점에서 잰 값이라 저울을 바꾸면 출력 분포가 통째로 밀려 성적이 오르내린다 —
분류력이 변한 것인지 눈금이 옮겨간 것인지 구별할 수 없다. AP는 순위만 보므로
단조 변환에 흔들리지 않고, 임계값을 나중에 스윕하는 이 파이프라인에 맞다.
sklearn을 들이지 않고 직접 구현했다(오프라인 반입 환경에서 의존성 하나가 반입 목록이다).

#### ⚠ 아래 실측은 9차에 **일부 철회**됐다 (docs/review-request-model-9.md C·D절)

"하네스 결과가 전 구간 동일"은 사실이 아니었다 — 사이드카의 옛 프로세스가 포트를 쥐고
있어 **같은 모델을 두 번 잰 것**이었다. 깨끗한 프로세스로 다시 재면 λ=4가 더 좋다
(t=0.5 패러프레이즈 66.7% → **70.8%**, 순이익 16 → **17**).
A-3 기각은 그대로 유지된다 — 근거가 "하네스 동일"에서 "절벽의 원인이 죽은 그래프였다"로
좁아졌을 뿐이다. 남은 이상: **AP는 λ=1이 높은데 하네스는 λ=4가 낫다**(9차 F-3에서 질문).

#### 실측 — 그리고 8차의 A-3 가설은 **기각**된다

같은 데이터·같은 시드로 저울만 바꿔 두 벌을 학습했다. λ=1은 옛 동작과 정확히 같다
(pos_weight = 음성/양성 ≈ 15).

| | pos_weight | val macro-AP | 하네스 (t=0.3~0.8) |
|---|---|---|---|
| λ=1 (옛 동작) | ≈ 15 | **0.755** | — |
| λ=4 (유도값, 배포) | ≈ 3.8 | 0.716 | 순이익 14 / 16 / **16** / 9 / 3 / 0 |

읽는 법 둘.

**① AP는 λ=1이 오히려 높다.** 차이 0.039는 검증 분할 49건에서 잡음 범위지만, 적어도
"저울을 낮춰서 분류력이 좋아졌다"는 주장은 성립하지 않는다.

**② 하네스 결과는 임계값 0.3~0.8 전 구간에서 두 팔이 같았다.** 저울이 바꾸는 것은
출력의 **눈금**이고, 그 눈금은 뒤따르는 임계값 스윕이 그대로 되돌린다. λ=4 학습의
`macro-F1@0.5`가 6에포크까지 **정확히 0.000**이었던 것이 같은 사실의 다른 얼굴이다 —
0.5를 넘는 출력이 하나도 없었을 뿐 순위는 이미 학습되고 있었다(같은 시점 AP 0.553).

→ **8차 A-3("pos_weight가 임계값 절벽의 원인")을 기각한다.** 절벽의 원인은 죽은
ONNX 그래프였고(8차 A-1), 저울은 그 위에서 관측된 그림자를 설명하려던 사후 가설이었다.
저울을 비용비에서 유도하는 것은 여전히 옳지만 **성능 때문이 아니라 근거 때문이다** —
128건짜리 채점지에서 손잡이 두 개를 함께 흔들지 않기 위해서다.

**스윕 범위도 함께 넓혔다** (0.05~0.8). 저울을 낮추면 분포가 아래로 밀리는데 옛 범위는
0.3에서 시작해, 눈금이 더 내려간 모델이 오면 "채택 불가"가 나온다 — 모델이 아니라
자의 문제다. 넓혀 보니 t≤0.1 구간에서 **risk_heavy 오탐이 100%**로 드러났고
(문장 라벨이 문서 본문에도 붙는다), 채택선 ②가 그 자리를 정확히 막았다.

### E-4 — 스타일 섭동은 닫는다

7차가 요구한 이유는 학습셋과 평가셋 양쪽에 같은 문체가 섞여 있어 자기 문체 과적합을
구별할 길이 없었기 때문이다. 8차의 B-1이 그 조건을 없앴다 —
**학습 = 100% 합성(내 문체), 평가 = 100% 손코퍼스(다른 문체)**로 물리적 격리.
따라서 하네스의 패러프레이즈 66.7%는 이미 "내 문체로 배워 남의 문체를 얼마나 잡는가"다.
섭동을 더 만들어도 같은 질문에 더 나쁜 방법으로 답할 뿐이다.

### E-6 — 켠다, 다만 관문을 하나 더 달고

`STUDENT_MODE`: `off` | `shadow` | `live`. 사이드카 URL이 있으면 기본 `live`.
소견은 규칙·학습 표현·의미 검색과 **같은 1차 단계**에 실리고, 심각도는 항상 WARN이라
거절 권한이 없다(최악이 운영자 큐가 길어지는 것).

**검토안에 없던 것을 하나 더 넣었다: 라이브 진입 관문(`usable()`).**
지문 대조가 지금까지 그림자 서비스 **안에만** 있었다. 그림자에서는 어긋난 기록을
버리면 그만이었지만(결측), 라이브에서 어긋난 소견은 **리서처의 게시를 실제로 멈춘다.**
그대로 켰다면 토크나이저가 갈라진 날 조용히 틀린 답이 남의 게시를 막았을 것이다.
결과는 캐시한다(성공은 영구, 실패는 60초) — 리포트마다 `/health`를 부르면 호출이 두 배다.

**라이브일 때 그림자 기록은 돌지 않는다.** 소견이 이미 본 기록에 `source: 'student'`로
들어가고 운영자 판정이 그 행에 붙으므로, 그림자 표가 답하던 질문에 본 기록이 더 잘
답한다. 여기서 또 부르면 호출이 두 배가 되고, 두 답이 다르면 어느 쪽이 판정에 쓰인
것인지 알 수 없게 된다.

**`FindingSource`에 `'student'`를 더했다** — `'ai'`와 반드시 나눈다. 둘 다 모델이지만
**오탐을 고치는 방법이 다르다**: 2차 AI의 오탐은 프롬프트에 과거 사례를 붙여 고치고,
학생의 오탐은 코퍼스에 하드 네거티브를 넣고 재학습해야 고쳐진다. 그래서 프롬프트
되먹임(`calibrationExamples`)에서 학생 오탐을 제외했다 — 안 그러면 2차 AI에게 남의
잘못을 가르치고 예시 자리만 잡아먹는다.

### 후속 질문에 대한 답 — `exit(1)`이 아니라 `/health`의 준비 플래그

검토자가 물은 것: 카나리아 실패를 사이드카의 `exit(1)`로 처리할 것인가,
`/health`에 플래그로 노출해 웹이 판단하게 할 것인가.

**플래그다.** 근거 넷:

1. **`exit(1)`은 증거를 지운다.** 웹이 보는 것이 "연결 거부"뿐이면 *안 떴다*·*죽었다*·
   *라벨이 어긋났다*가 구별되지 않는다. 9차에 나를 구한 것이 정확히 그 반대였다 —
   프로세스가 **살아서 틀린 값을 말해 준 덕분**에 옛 프로세스를 찾았다.
2. **감시자를 붙이면 재기동 루프가 된다.** 사이드카를 서비스로 올리는 것이 다음 과제인데
   (F-2), 그 위에서 `exit(1)`은 진단 가능한 실패를 로그 폭우로 바꾼다.
3. **판단이 두 곳으로 갈라진다.** `usable()`이 이미 스텁·낡음·지문을 한자리에서 막고
   시험이 그 성질을 고정한다. 사이드카에 두 번째 거부권을 두면 이 스레드가 반복해서
   데인 모양(같은 판단이 두 곳에 있는 것)이 된다.
4. **카나리아는 포트 선점을 못 막는다.** 옛 프로세스는 자기 카나리아를 통과한다 —
   자기 모델로 구운 정답이기 때문이다. 그 자리는 `model_stale`이 맡는다. 두 장치가
   서로 다른 실패를 잡으므로 `exit`으로 겹칠 이유가 없다.

다만 **`/screen`도 스스로 거부한다** — 생산자가 쓰레기를 안 내보내는 것이지 판단을
나누는 것이 아니다. `usable()`을 거치지 않는 호출자가 생기는 날 그 줄이 유일한 방어가 된다.

### G-1 — 정답을 손으로 적지 않는다

검토안은 "특정 라벨의 로짓이 x 이상, 토큰 수 y개"였다. 그대로 하면 **재학습할 때마다
카나리아가 깨지고**, 그렇다고 매번 손으로 다시 적으면 아무것도 주장하지 않는 기록이 된다.

대신 **내보내기가 굽는다**: `export_onnx.py`가 배포되는 그 파일로 `CANARY_TEXTS`를
통과시켜 로짓을 `canary.json`에 적고, 사이드카가 기동 시 같은 입력을 지금 이 스택으로
돌려 대조한다. 그러면 카나리아가 주장하는 것이 분명해진다 —
**"서빙 스택이 내보내기가 본 것을 그대로 재현하는가."**

- 정답을 PyTorch가 아니라 **배포본**으로 굽는다 — int8을 배포하면 int8로. PyTorch로
  구우면 int8 배포에서 영원히 어긋난다(정밀도를 일부러 버린 것이므로)
- **라벨 목록을 함께 박는다** — 순서가 바뀌면 로짓은 그대로인데 뜻이 달라진다.
  값 대조로는 안 잡히는 유일한 어긋남이라 이름을 따로 적는다
- `canary.json`이 없으면 **통과가 아니라 미검증**이다. 검사할 수 없는 상태를 통과로
  적으면 카나리아를 둔 이유가 사라진다

실측: 카나리아 3건 통과, 최대 오차 **4.87e-07**.

### G-3 — 지시대로 해보고 **되돌렸다**

검토의 진단(ⓒ: AP는 라벨 간 영점 정렬을 보지 않는데 배포는 단일 임계값을 쓴다)은
지금도 맞다고 본다. 처방(체크포인트를 검증셋 순이익으로 고르라)도 그대로 구현했다.
**다만 임계값은 고정하지 않았다** — `t=0.5` 고정은 8차 E-3의 교훈(저울을 바꾸면 눈금이
옮겨간다)에 정면으로 걸린다. 대신 0.05~0.8을 훑어 **스윕한 뒤의 최선**을 쟀다.

그렇게 학습하고 하네스로 재니 **나빠졌다**:

| | AP 선택 | **순이익 선택 (지시대로)** |
|---|---|---|
| 고른 임계값 | t=0.5 | t=0.6 |
| 최악 λ 순이익 | **17** | 15 |
| 패러프레이즈 | **70.8%** | 62.5% |

**원인은 지표가 아니라 표본이다.** 검증 49건에 λ=4면 오탐 1건이 정탐 4건을 지운다 —
실제로 순이익이 아홉 에포크 동안 0에 붙어 있다가 최대 +2였고, 전 구간에서 t=0.8을 골랐다.
사실상 **"아무것도 예측하지 마라"가 그 지표의 최적해**다. 반면 AP는 순위쌍 전부를 쓰므로
같은 49건에서 훨씬 많은 정보를 뽑는다.

→ **역할을 나눈다. 원칙이 아니라 표본 크기 때문이다:**

| | 표본 | 지표 | 이유 |
|---|---|---|---|
| 체크포인트 선택 (매 에포크) | 검증 49건 | **macro-AP** | 부드럽고 정보 밀도가 높다 |
| 채택 판정 (배포 결정) | 하네스 128건 | **순이익** | 배포가 실제로 답해야 하는 질문 |

AP가 사실상 같은(소수 둘째 자리까지 동일한) 두 체크포인트 사이에서는 순이익이 고르게 뒀다 —
그 자리에서는 검토의 논거(영점 정렬)가 그대로 유효하다.

**미해결로 남는 것**: 검증셋이 커지면(수백 건) 순이익 선택이 다시 옳아질 수 있다.
지금의 결론은 "그 처방이 틀렸다"가 아니라 **"49건에서는 못 쓴다"**이다.

### G-6 — 결론부 한정 규칙의 실측

| 문서 단위 | 이전 | **이후** |
|---|---|---|
| 전체 탐지율 | 0% | **19.0%** |
| 방향 반대 | 0/8 | **3/8 (37.5%)** |
| 리스크로 위장한 방향 반대 | 0/4 | **1/4 (25%)** |
| 크기 어긋남 · 기간 어긋남 | 0 | **0** (어휘로는 원리적으로 불가) |
| 정합적인 리포트 오탐 | 0/7 | **0/7** |
| **리스크 서술 많음(하드 네거티브) 오탐** | 0/10 | **0/10** |

문장 단위 기준선은 **한 자리도 바뀌지 않았다**(탐지 53.8% / 오탐 17.6% / 즉시 거절 0).

어휘를 "방향을 암시하는 말"이 아니라 **투자 판단을 명시하는 말**로 좁힌 것이 오탐 0의
이유다 — "상승 여력"·"하락 위험" 같은 서술어는 넣지 않았다(그건 시나리오지 결론이 아니다).
**양쪽 어휘가 함께 있으면 지적하지 않는다**: "차익 실현 후 재매수"는 결론이 하나인데
규칙으로는 어느 쪽이 최종인지 못 가린다 — 모르면 지적하지 않는 쪽으로 기운다.

회귀 시험은 숫자가 아니라 **모양**을 붙잡도록 바꿨다: 방향 충돌은 > 0, 크기·기간은 0,
전체는 < 0.5. 값은 코퍼스가 늘면 움직이지만 저 세 성질은 구조에서 나온다.

### I-6 — 자동 격하를 만들다 **관측이 개입에 의해 지워지는 것**을 만났다

검토가 준 완성 조건은 "오탐이 섞인 가짜 트래픽 100건을 흘려 자동 롤백이 사람 없이
격발되고, 그 지점이 수학적 기대치와 일치하는가"였다. 만들어 재니 **정확히 일치했다**:

| | 값 |
|---|---|
| 오염 시작 | 41번째 리포트부터 두 건에 한 건씩 오탐 |
| **격발** | **61번째** (창 50건 안에 정탐 39 · 오탐 11 → 순이익 −5) |
| 기대치(독립 계산) | 61번째 |
| 오탐 0건 트래픽 100건 | 격발 0회 |

그런데 만드는 도중에 **순진한 구현이 반드시 발진한다**는 것을 알았다:

```
적자 → 격하 → 학생이 소견을 안 냄 → 창에서 학생 표본이 빠짐
     → 표본 부족 → shouldRollback=false → **다시 켜짐** → 다시 오탐 → 적자 → ...
```

원인은 지표가 아니라 **개입이 관측 대상을 지운다**는 데 있다. 학생을 끄면 학생의 성적을
만들 재료가 끊기므로, 끈 상태에서 잰 값은 "좋아졌다"가 아니라 **"모른다"**이다.
그런데 `studentRollbackStatus`는 그 둘을 같은 얼굴(`shouldRollback=false`)로 돌려준다.

→ **걸쇠(latch)로 만들었다. 거는 것은 시스템, 푸는 것은 사람이다.**
`judgmentPause`가 "사람이 건 정지는 사람만 푼다"고 정한 것과 같은 계열이되 근거가 다르다:
저쪽은 *고쳐졌는지 알 방법이 없어서*이고 이쪽은 ***끈 동안에는 잴 수 없어서***다.

부수적으로 정해진 것 둘:
- **환경 변수(`STUDENT_MODE`)보다 걸쇠가 세다** — 배포 설정은 "쓰겠다는 의도"이고 걸쇠는
  "쓸 수 없다는 관측"이라, 의도가 관측을 덮으면 격하 장치가 재배포 한 번에 지워진다
- 운영 화면은 격하 상태를 **순이익 수치보다 먼저** 말한다. 격하 뒤로는 그 수치가
  갱신되지 않으므로, 말해 주지 않으면 "숫자가 안 나빠졌으니 괜찮다"로 읽힌다

### I-4 — 돌연변이 시험이 밝힌 것: **값 검사는 거의 아무것도 못 잡는다**

`training/mutation_test.py`. 파일 **이름은 model.onnx로 그대로 둔 채** 가중치의 한 비트를
뒤집고, 카나리아의 두 층을 **따로** 재봤다.

| 변이 | ⓐ 신원(sha)만 있었다면 생존 | ⓑ 값(로짓)만 있었다면 생존 | ⓐ+ⓑ 지금 구현 |
|---|---|---|---|
| 미세 (가수 끝자리) | 0/10 | **9/10** (최대 오차 0.0028) | **0/10** |
| 거친 (지수부) | 0/10 | **9/10** (최대 오차 0.216) | **0/10** |

**돌연변이 생존율 0/20 = 0.0%** — 검토가 정한 기대값이다.

값어치는 그 0%가 아니라 **ⓑ의 90%**에 있다. 로짓 대조는 가중치 훼손을 사실상 못 잡는다 —
1,400만 개 파라미터에 카나리아 입력이 3건뿐이라 대부분의 비트가 그 3건의 경로에 없다.
**ⓐ(sha)가 혼자 다 하고 있었다.** 그래도 ⓑ를 걷어내지 않는 이유는 ⓑ만 잡는 것이 따로
있어서다 — 라벨 순서·토크나이저·출력 차원. 두 층이 서로 다른 실패를 맡는다.

### I-3 — 형식 검사와 내용 평가의 경계

검토가 그은 선을 그대로 채택한다: **내부적 모순은 형식, 외부적 진실은 내용.**

- 리서처가 "오른다"고 쓴 것이 **시장에 비추어 맞는지**를 우리가 판단하면 → 내용 평가(투자자문)
- 요약에 "매수", 카드에 "하락"을 걸면 → **한 문서 안에서 두 값이 어긋난 것**. 페이로드 무결성

G-6 규칙이 하는 일은 후자뿐이다. 어휘를 "방향을 암시하는 말"이 아니라 **투자 판단을
명시하는 말**로 좁혀 둔 것이 이 경계와 정확히 같은 선이다("상승 여력"은 시나리오지 결론이
아니라 넣지 않았다). **양쪽 어휘가 함께 있으면 지적하지 않는 것**도 같은 이유다 —
어느 쪽이 최종인지 가리는 것은 내용 판단이다.

측정(구조적 보류에 대한 이의 제기율)은 **새로 만들 것이 없다.** 운영자가 보류를 승인하면
그 건은 `CARD_MISMATCH` 오탐으로 집계되고(`screeningAccuracy`), 유형별 오탐률은
`getCategoryOutcomeRates`가 이미 화면에 낸다. 출시 후 그 칸을 보면 된다.

### I-5 — NSSM이 아니라 작업 스케줄러

검토는 NSSM을 지목했고 판단(웹의 자식으로 띄우지 말 것)은 그대로 받았다. 도구만 바꿨다:
NSSM은 **내려받아야 하는 서드파티 실행 파일**인데, 윈도우에 이미 있는 작업 스케줄러가
필요한 세 가지를 그대로 준다 — 부팅 시 자동 시작 · 웹과 독립된 수명 · 실패 시 자동 재시작.
차이는 서비스 목록에 안 보인다는 것 하나이고, NSSM으로 옮기려면 `install-task.ps1`만
바꾸면 된다(`watchdog.ps1`은 그대로).

- `sidecar/watchdog.ps1` — 사이드카의 부모로 앉아 죽으면 밖으로 알리고 **종료 코드 1**로 끝난다
- `sidecar/install-task.ps1` — 부팅·로그온 트리거 + 1분 간격 재시작으로 등록 (**사람이 실행**)

### K-1 — 지표용 라벨과 억제 신호를 분리했다

10차에 찾은 결함: 승인 라벨의 기본값이 "모델이 틀렸다"인데 그 라벨이 자동 격하의
입력이 되면서, **25건 중 6건만 무심코 승인해도 학생이 영구히 꺼졌다.**

검토의 판단은 "정확도 지표용 데이터와 시스템 격하용 억제 신호는 분리되어야 한다"였다.
그대로 나눴다 — `classifyForRollback`이 **운영자가 명시적으로 오탐이라고 신고한 건만**
표본으로 센다. 무표시 승인은 오탐이 아니라 **표본이 아니다**("모델이 틀렸다"가 아니라
"운영자가 말하지 않았다"이기 때문).

| 시나리오 | 10차 | **11차** |
|---|---|---|
| 무표시 승인 25건 | 순이익 −100 → **격하** | 표본 0 → **유지** |
| 명시적 신고 6건 | 격하 | **격하** (의도된 신호는 그대로 산다) |

정확도 지표는 **바뀌지 않았다** — 거기서는 무표시 승인을 계속 오탐으로 센다
(compliance-screening §5의 근거가 그대로 유효하다). 두 숫자가 벌어질 수 있으므로,
그 간극 자체를 지표로 만들었다: `explicitFalsePositiveRate` = 명시적 신고 ÷ 승인.
0에 가까우면 자동 격하가 잠들어 있다는 뜻이고, 1에 가까우면 습관 클릭을 의심할 자리다.

운영자 콘솔은 체크박스 하나에서 **세 갈래**로 바뀌었다:
표시하지 않고 승인(기본) / 지적은 타당했다 / **오탐이었다**.

#### K-1을 고치다 만든 결함 하나 — **NULL 은 false 가 아니다**

기본값을 `false` → `null` 로 바꾼 직후, 되먹임 자료(`getCalibrationExamples`)가
**예외도 경고도 없이 0건이 됐다.** 원인은 한 줄이었다:

```ts
NOT: { aiFindingsValid: true }   // SQL 3값 논리에서 col 이 NULL 이면 참이 아니라 NULL
```

`NOT (col = true)` 는 NULL 행을 **참으로도 거짓으로도 치지 않고 통째로 버린다.**
값을 하나 더 만든 순간 그 값을 못 보는 질의가 생긴 것이고, 이 계열의 사고가 그렇듯
**아무 소리도 내지 않았다.** db 시험이 잡았다.

→ `OR: [{ aiFindingsValid: false }, { aiFindingsValid: null }]` 로 **두 값을 이름으로
적었다.** 그러면 네 번째 값이 생기는 날에도 이 줄이 눈에 띈다.

교훈: **기본값을 바꾸는 것은 값 하나를 바꾸는 일이 아니라, 그 컬럼을 읽는 모든 질의의
전제를 바꾸는 일이다.** boolean 을 tri-state 로 넓힐 때는 그 컬럼의 `where` 절을 전부
다시 읽어야 한다 (`grep aiFindingsValid`).

### K-2 — 출시 직후에도 명백한 신호는 25건을 기다리지 않는다

`순이익 < 0`은 사실 `오탐률 > 1/(1+λ)`와 **같은 부등식**이다. 그래서 잣대를 바꾸지 않고
표본 보정만 얹었다 — 윌슨 점수 구간의 하한.

| 표본 | 규칙 |
|---|---|
| 25건 이상 | 순이익 < 0 (채택선과 같은 공식, 종전 그대로) |
| 5 ~ 24건 | **오탐률의 95% 하한 > 20%** |
| 5건 미만 | 판정하지 않는다 |

실측 (`scripts/probeRollbackGates.ts`):

| 표본 5건 중 명시적 오탐 | 하한 | 판정 |
|---|---|---|
| 1건 | 3.6% | 유지 |
| 2건 | 11.8% | 유지 |
| 3건 | 23.1% | **격하** |
| 4건 | 37.6% | **격하** |

최소 표본 5를 둔 이유가 실측에 있다: 하한식만 두면 **명시적 신고 1건에도 격발한다**
(n=1, p̂=1에서 하한 20.7% > 20%). 한 건으로는 "모델이 나쁘다"와 "그 리포트가 유별났다"가
갈리지 않는다.

Wald(정규 근사)를 쓰지 않은 이유: p̂이 0이나 1에 가까울 때 구간이 무너지는데
(n=5, fp=5면 Wald 하한이 정확히 1.0), **출시 직후가 정확히 그 구간이다.**

### K-3 — 이름이 과장이었다

돌연변이 시험이 반증한 것은 카나리아의 첫 번째 주장이었다. "가중치·라벨 순서·어휘·차원
중 하나라도 어긋나면 잡는다"고 적혀 있었는데, **로짓 대조만으로는 비트 훼손의 90%가
통과했다.** 파라미터 1,400만 개에 입력이 3건뿐이라 대부분의 비트가 그 경로에 없다.

입력을 50건으로 늘려 덮게 만들 수도 있지만, 그건 **sha가 이미 100% 하고 있는 일을
기동 시간을 내고 다시 하는 것**이다. 역할을 나누고 이름을 고쳤다:

| 장치 | 맡는 것 | 실측 |
|---|---|---|
| `model_sha` | **가중치의 신원** | 돌연변이 생존 0/20 |
| 파이프라인 카나리아 | 라벨 순서 · 토크나이저 · 출력 차원 · 그래프 결합성 | 최대 오차 4.87e-07 |

`canary.json`과 `CANARY_*` 식별자는 그대로 뒀다 — 배포된 아티팩트의 이름이라 바꾸면
기존 카나리아가 통째로 무효가 되고, 이 회차가 고치려는 것은 파일 이름이 아니라
**주석이 하던 과장**이다.

### K-4 — 확인 창은 문턱이 아니다

질문에 답하는 사람과 답을 검증할 수 있는 사람이 같으면 그것은 문턱이 아니라 인사말이다.
코드가 **증거의 신선도** 하나를 본다: 커버리지 스냅숏이 지금 서빙 중인 가중치로 떠졌는가.
스냅숏은 `eval:student`가 채택선을 통과했을 때만 갱신되므로, 두 sha가 같다는 것은
**지금 이 모델이 채택 판정을 통과했다**는 뜻이다.

다만 사고 복구 중에는 운영자가 코드보다 현장을 잘 안다. 그래서 우회를 남기되
**불편한 자리에** 뒀다 — 콘솔에 "강제" 버튼을 두면 그것이 곧 일상 경로가 된다.

```bash
npx tsx scripts/unlockStudent.ts                      # 증거가 맞을 때만
npx tsx scripts/unlockStudent.ts --force --reason "…"  # 감사 로그에 남는다
```

### 스레드를 여기서 닫는다 (K-6)

검토의 판단: *"시스템 구조 검수 단계는 이미 끝났다. 지금 발생하는 문제는 모델 검수
파이프라인의 오류가 아니라 실운영 인간-시스템 상호작용(HCI) 문제다."* 동의한다 —
11차에 찾은 결함(K-1)은 모델이 아니라 **운영자의 클릭 습관**에 관한 것이었고, 그런
문제는 실제 운영자가 실제로 클릭하기 전에는 더 찾을 수 없다.

이후 발생하는 건은 **운영 모니터링·피드백 트랙**으로 넘긴다. 켠 뒤에 볼 계기판은
전부 붙어 있다:

- `/admin/compliance` — 정확도 · 순이익 · 명시적 신고 비율 · 격하 상태
- 상태 엣지 알림 (인앱 + 웹훅 + 텔레그램)
- OS 층 감시자 (사이드카 종료 → 92ms)
- 자동 격하 걸쇠 (윌슨 하한 / 순이익)

**출시 뒤 처음 할 일**: `explicitFalsePositiveRate`를 본다. 0에 가까우면 자동 격하가
잠들어 있다는 뜻이므로, 그때는 λ가 아니라 **운영 습관**을 고쳐야 한다.
