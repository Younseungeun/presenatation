## Q0. 검사기 장애 → 보류 — **서버 쪽은 구현 완료. 화면만 맡아 주세요**

지적한 구멍 그대로였고, 저희가 재구조화와 같은 파일(`complianceService.ts`)이라
서버 쪽을 함께 구현했습니다. **그쪽에서 서버 코드를 고치지 마세요** — 충돌합니다.

구현된 것:

```ts
// resolveLiveStudent — 네 가지 undefined 를 갈랐다
export interface LiveStudentResolution {
  client: StudentClient | undefined;
  outage: boolean;   // usable() 실패만 true — mode≠live / URL 없음 / 자동격하는 의도된 끔
}

// runScreening — outage 또는 호출 중 사망(studentFailed)이면:
//   규칙 BLOCK  → REJECT 그대로 (거절할 것을 보류로 낮추지 않는다)
//   그 외       → decision 'UNAVAILABLE' · action 'HOLD' · reviewer 에 '+student(장애)'
```

**Q0-a: UNAVAILABLE 재활용이 맞습니다.** 뜻이 정확히 같고("검수기 일부가 판단하지
못했다"), 정확도 집계가 이 값을 이미 표본에서 뺍니다(`classifyReview` — 판단이 없었으니
맞고 틀림의 대상이 아님). 새 값을 만들면 그 제외 로직을 한 벌 더 짜야 합니다.
**어느 검사기였는지는 `reviewer` 의 `(장애)` 조각으로 가릅니다** — 화면이 이걸로
"AI 검수 실패"와 "학생 장애"를 다르게 표기할 수 있습니다.

**Q0-b: 상한 없이 그대로 쌓는 것이 맞습니다.** 보류는 판매를 시작하지 않으니 안전측이고,
상한을 두면 넘친 건이 자동 게시(위험측)됩니다 — 벽이 뚫리는 방향으로 넘치는 상한은
상한이 아닙니다. **밸브는 사람의 결정입니다**: 장애가 오래가면 운영자가
`STUDENT_MODE=shadow` 로 내려 규칙 단독 게시를 재개합니다(환경 변수 = 배포 없는 결정,
"한도 수동 증액 모드를 만들지 않는다"와 같은 계열). 알림 문구에 이 지침을 넣어 뒀습니다.
띠지에는 **"장애 N시간째 · 보류 N건"**을 함께 띄워 주세요 — 그 두 숫자가 곧
"shadow 로 내릴 때가 됐나"의 판단 재료입니다.

알림 문구는 교체 완료(긴급 + 새 정책). 전이 1회의 한계는 그대로라 **띠지 상시 표시는
화면 몫**입니다 — 상태는 기존 `usable()` 캐시로 읽으면 됩니다.

## Q1. 승격 API — **질문 자체가 소멸했습니다**

20차 검토(X-2)가 **승격 금지**로 확정했습니다: 의미를 가진 낱말은 아무리 정확도가
높아도 코드(BLOCK)로 굳히지 않습니다. 코드 규칙은 비의미적 형태(전화번호·기호 패턴)만
BLOCK 합니다. 검증된 사전 항목의 유일한 출구는 **졸업**(학생 위임 + 항목 끔)입니다.

→ **"코드 승격 검토" 배지를 만들지 마세요.** 인계 2호 §3-①의 그 항목은 철회합니다.

## Q2. 졸업 API — 구현 완료. 배지가 아니라 **버튼 + 폼**입니다

20차 X-5: 자동 판정("학생이 이미 잡음" 배지) 기각 — 변형 자동 생성 증명은 동어반복.
졸업은 **운영자의 수동 판단**이고, 그 대가로 대비쌍을 남깁니다:

```ts
// server/phraseGraduationService.ts (신규 — 구현·시험 완료)
graduatePhrase(prisma, {
  phraseId,
  cases: { text, expectViolation, category? }[],  // 위반 ≥3 + 정상 ≥3, 위반엔 학생 라벨 필수
  operatorUserId,
})  // → 항목 비활성 + 영구 회귀 시험셋 등록 (원자적)

getRegressionCases(prisma)      // 회귀 시험셋 전체 — 재학습 채택 판단이 읽는다
reactivatePhrase(prisma, id)    // 미탐 재발 시 되살리기 — 사람이 누른다
```

화면: 항목마다 **[졸업]** 버튼 → "위반 3문장 + 정상 3문장을 직접 쓰세요" 폼 →
`graduatePhrase`. 폼 안내문에 이 문장을 넣어 주세요: *"이 문장들이 재학습 때마다
학생을 시험합니다 — 여기서 오답이 나면 그 모델은 배포되지 않습니다."*
(서버가 같은 문구로 검증 오류도 냅니다.)

## Q3. 충돌 API — **목록입니다.** 구현 완료

```ts
// createLearnedPhrase 반환에 합류 (등록은 막지 않는다):
{ ...LearnedPhrase행, collisions: PhoneticCollision[] }
// PhoneticCollision = { against: string; kind: 'term' | 'corpus' }
```

화면: 등록 직후 `collisions.length > 0` 이면 —
*"'{against}' 와 발음이 가깝습니다. 이 표현은 **정확 표기만** 감시하고, 한 글자 바꾼
변형(음성 변형 층)은 감시하지 않습니다."* — 그리고 항목 목록에서 `phoneticEligible:
false` 인 항목에 그 상태를 상시 표시해 주세요. 충돌 목록 자체는 저장하지 않습니다
(등록 순간의 사실이라 표에 쌓으면 낡습니다) — 상시 표시는 boolean 으로 충분합니다.

## Q4. `source`·`phraseId` — **살아남았습니다.** 오늘 구현의 계약입니다

사전이 규칙 엔진에 합류해도 소견은 `source: 'learned'` + `phraseId` 를 유지합니다.
1·2·3·5층 어디서 잡혀도 같습니다. 시험이 이 계약을 고정합니다
(`phraseEngine.test.ts` — "소견 계약이 유지된다"). §4 표시 규약 그대로 진행하세요.

## Q5. `layer` — **붙습니다. 의도된 것입니다**

사전 소견에 `L1_RAW` / `L2_SEPARATOR` / `L3_DEEP` / `L5_PHONETIC` 이 붙습니다.
`[규칙·사전 · 기호제거]` 같은 표기가 가능하고, **표기해 주세요** — 특히 L5(음성 변형)로
잡힌 사전 소견은 근사 매칭이라 오탐 확률이 높아, 운영자가 그 사실을 알고 봐야 합니다.

## Q6. 카나리아 — **문항 추가 완료**

`SCREENING_CANARY` 에 `사전입력` 층 문항이 늘었습니다 (총 7문항: 층 5 + 정상 2).
합성 표식(`카나리아점검용문구`)을 러너가 매번 주입하므로, 이 문항의 빨간불은
"사전 배선이 끊겼다" 하나만 뜻합니다 — 사전이 비어 있어도 초록입니다.
띠지가 문항 목록을 동적으로 그린다면 자동 반영될 것이고, 층 이름을 하드코딩했다면
`사전입력` 을 추가하세요.

## Q7. `Finding.confidence` — **추가 완료**

```ts
confidence?: number   // 학생 소견만, 0~1
```

`reason` 파싱은 하지 마세요(기존 우려 그대로). 값이 없으면(과거 기록) 표기 생략.

## Q8. 인용 없는 소견의 리서처 전달 — **(b) + (c)**

- **보류 통지 = (b) 유형 이름만**: "수익 보장으로 읽힐 수 있는 서술이 있어 검토
  중입니다" — 확신 %는 리서처에게 보내지 않습니다(숫자를 주면 문구를 조금씩 바꿔
  임계값을 이진 탐색합니다).
- **반려 = (c)**: 운영자 사유가 이미 필수(min 1)입니다. 반려 폼에 "학생 소견으로
  반려할 때는 문제 문장을 직접 인용해 주세요" 안내를 더해 주세요 — 학생은 못 짚지만
  사람은 짚을 수 있고, 그 인용이 사전 등록 기본값도 됩니다.
- (a)처럼 아예 안 보내면 리서처는 무엇이 문제인지 모른 채 재제출을 반복해
  `rejectionCount` 만 쌓입니다.

`findingMessages` 는 이미 빈 인용을 "(본문 전체 — 특정 문장을 짚지 못합니다)"로
처리합니다 — 학생 소견의 문구만 (b) 스타일로 다듬는 것은 화면 몫입니다.

## Q9. 철회 경로의 사전 등록 칸 — **네, 붙이세요**

정확한 지적입니다. 미탐(이용자가 잡은 우회)이 가장 값진 라벨이고, **빠른 길이 정확히
거기서 필요합니다** — 신고로 잡힌 표현은 지금 유행하는 우회라 몇 초 안에 막을 가치가
가장 큽니다. 신고 → 강제 철회 팝업에 판매 중 리포트 쪽과 같은 `phrase` 칸을 붙이면
서버는 이미 받습니다(`registerPhrase` 가 두 경로 공용).

## Q12. 의미 검색 — **충돌 없음. 배선 제거는 저희가 이미 했습니다**

관련 요소만 만들지 않으면 됩니다. `semanticIndexService` 는 이제 검수 경로 밖의
독립 모듈입니다.

## 덧붙임 — Q0 정책이 구현 당일에 스스로를 증명했습니다

새 정책을 넣고 전체 시험을 돌리자 **DB 시험 130건이 한꺼번에 빨개졌습니다.**
원인: 개발 .env 의 `STUDENT_SIDECAR_URL` 을 시험 프로세스가 물려받아 모드가 live 로
계산됐고, 사이드카는 안 떠 있으니 — 새 정책이 정확히 설계대로 **모든 게시를
보류**시켰습니다.

**옛 정책 아래에서는 이 상태가 몇 달을 조용히 통과했습니다** — "죽어도 그냥 게시"
덕분에 시험이 장애 구성으로 돌고 있다는 사실 자체가 안 보였습니다. 그쪽이 지적한
구멍이 시험 환경에서도 똑같이 나 있었던 셈입니다.

처방은 정책 되돌리기가 아니라 시험 환경의 정직화입니다 — 시험은 이제 명시적
`STUDENT_MODE=off`(의도된 끔)로 돕니다 (`src/__tests__/setup/studentOff.ts`).
운영 .env 는 건드리지 않았습니다.
