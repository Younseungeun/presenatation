# INTOVILL 검수 모델 3차 검토 요청 — 학생을 하네스에 물리려고 코드를 열었더니, 잣대 쪽에 구멍이 둘 있었습니다

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동 판정합니다. 적중이면 리서처에게 정산되고,
실패면 구매자에게 현금 환불됩니다. 그 사이 돈은 에스크로에 있습니다. 검수는 그 앞단에서
규제 위반 표현과 본문↔카드 모순을 찾아 거절하거나 보류시킵니다. 이 스레드는 **앱 안에서
도는 자체 검수 모델(증류)**을 만드는 스레드입니다.

2차 답변 넷 중 하나는 결론만 받고 근거를 기각했고(H-1), 하나는 제안보다 더 밀고 갔으며
(H-2 — 규율 대신 도구가 막게), 둘은 그대로 채택했습니다(H-3·H-4). 그리고 학생을 평가
하네스에 물릴 준비를 하려고 코드를 열었더니 **채택선 자체에 결함이 둘** 있었습니다 —
하나는 학생 단독 오탐률을 재는데 운영에서는 규칙과 합쳐진다는 것이고, 다른 하나는 코퍼스가
단일 라벨인데 모델은 다중 라벨이라는 것입니다.

저장소 접근 없이 읽을 수 있게 필요한 코드·수치를 인라인으로 붙였습니다. 코드를 근거로
답하실 때는 인용을 요구합니다 — 여기 없는 파일 내용은 추측하지 말고 붙여 달라고 해 주세요.

## A. H-1 (대화 라벨 혼입) — 롤백 레버는 그대로 채택, "노이즈가 증강"이라는 근거는 기각

> 제안: *"학습 데이터에서 발생하는 약간의 일관성 부족(Temperature 편차 등)은 오히려 모델의
> 일반화를 돕는 데이터 증강(Data Augmentation) 효과를 낼 수 있습니다."* +
> *"`--exclude-labeler` 등의 플래그를 추가해 롤백하면 그만입니다."*

**롤백 레버는 제안대로 구현했습니다.**

```python
# training/train.py
ap.add_argument("--exclude-labeler", action="append", default=[])
...
rows = [r for r in rows
        if not any(r.get("labeler", "").startswith(p) for p in args.exclude_labeler)]
# 접두사 일치 — 모델명이 바뀌어도 conversation: 으로 한 번에 걸린다
```

**증강 근거는 받지 않습니다.** 증강은 **입력**을 흔드는 것이고 여기서 흔들리는 것은
**라벨**입니다. 같은 문장에 다른 라벨이 붙는 것은 모델을 일반화시키는 게 아니라 결정
경계를 흐리고, 수백~수천 건 규모에서는 그 손해가 이득보다 큽니다. 섞는 진짜 근거는 그
문장이 아니라 **추적 가능성과 롤백**이며, 문서에도 그렇게 적었습니다 — 근거를 잘못 적어
두면 나중에 "노이즈는 이로우니 정제할 필요 없다"로 읽힙니다.

## B. H-2 (평가·생산 분리) — 채택하되 규율이 아니라 도구가 막게 했고, 1차 측정을 통째로 강등했습니다

> 제안: *"평가용 코퍼스 자체를 대화 교사 경로에 태우지 마십시오."* + *"손코퍼스(86건)와
> 운영자 판정만을 유일한 평가셋으로 동결하십시오."*

결론은 채택인데 **수단을 바꿨습니다.** "태우지 마라"는 규율인데, 규율은 G-α에서 이미 한 번
실패한 방어입니다(저 자신이 오염을 만들었습니다). 그래서 도구가 막게 했습니다:

```
$ npm run eval:teacher -- --from training/data/teacher.v1.jsonl
라벨 86건 · 출처 conversation:claude-opus-5

⚠⚠ 대화 교사 라벨입니다 — **이 출력은 참고용이며 채택선·천장으로 인용할 수 없습니다.**
   (2차 검토 H-2 확정) 대화 세션이 코퍼스 원본을 접했는지 검증할 수 없어, 판정이
   독립적 판단이 아니라 정답 회상일 수 있습니다. 유효한 교사 기준선은
   API 교사(npm run eval:teacher, temperature 0) 또는 운영자 판정에서만 나옵니다.
```

**두 가지를 더 밀고 갔습니다.**

1. 동결 대상은 86건이 아니라 **128건**입니다 — 문장 코퍼스 86 + 문서 코퍼스 42(채점 38 +
   관측 4). 문서 쪽이 `risk_heavy` 채택선의 근거라 여기서 빠지면 채택선이 반쪽이 됩니다.
2. **1차 측정을 전체 참고치로 강등했습니다.** 2차 요청서에서 저는 "정상 34건은 세션이
   원본을 읽기 전 구간이라 오탐률 0%는 유효"라고 주장했는데, 철회합니다 — 그 구간 구분
   자체가 **사람의 기억에 기댄 검증**이고, 그러면 이 문서가 내세운 "사람의 규율에 기대는
   방어는 방어가 아니다"와 정면으로 모순됩니다.

그래서 **지금 유효한 교사 기준선은 0건입니다.** API 키가 생기는 날 처음 나옵니다.

## C. H-3 (분포 편향) — 그림자 모드를 "비용"이 아니라 "절차"로 다시 적었습니다

> 제안: *"그림자 모드에서 무너지는 것을 확인하고 재학습 루프를 도는 것은 '사고'가 아니라
> '성공적인 검증 프로세스'입니다."*

채택했습니다. 2차 요청서에서 저는 이것을 "작업이 통째로 되돌아간다"는 **손실**로 적었는데,
그 인식이 틀렸습니다 — 에스크로 환불도 리서처 이탈도 없이 실패 데이터를 얻는 자리이고,
운영 데이터 0건인 상황에서 실제 문장 분포를 얻는 **유일한** 통로이기도 합니다.
문서에서 비용 서술을 걷어내고 정규 절차로 적었습니다.

## D. H-4 (CARD_MISMATCH 단일 출력) — 그대로 채택

> 제안: *"14M 파라미터가 [CLS] 토큰 하나로 2단 추론을 해낼 확률은 솔직히 매우 낮습니다.
> 그럼에도 단일 출력을 지지하는 이유는 채택선과 하네스가 든든하기 때문입니다."*

같은 판단입니다. 실패 가능성이 높다는 데 동의하고, 그 판정을 하네스(`risk_heavy` 오탐
이중 조건)에 위임합니다. 미달이면 NLI 교차 인코더로 분리하는 갈림길이 이미 선언돼 있어
지금 결정할 것이 없습니다. **다만 그 채택선이 아래 E-α 때문에 지금 그대로는 못 씁니다.**

## E. 이번에 새로 넘어간 주제 — 학생을 하네스에 물리기

다음 실행 단계는 ONNX 추론 어댑터를 만들어 학생을 `Detector`로 감싸고 임계값을 스윕해
채택선에 거는 것입니다. 열어 보니 전제가 하나 빠져 있고, 하나는 제가 잘못 세고 있었습니다.

### E-1'. `Detector`가 동기 함수인데 ONNX 추론은 비동기다 — 해결됨, 질문 아님

```ts
export type Detector = (input: ScreeningInput) => Finding[];   // 동기
```

선례가 이미 있습니다. 교사 성적을 재는 `evalCoherence.ts`가 같은 문제를 만나 **먼저 전부
불러 캐시에 담고 동기 함수로 되읽는** 방식으로 풀었고, 학생도 같은 방식이면 됩니다.
하네스를 비동기로 바꾸지 않는 이유는 탐지기 대다수(규칙·학습 표현)가 동기여서
비동기를 강요하면 잣대가 무거워지기 때문입니다. 답이 정해져 있어 질문으로 올리지 않습니다.

### E-2'. 임계값이 하나가 아니라 여덟이다

출력이 8차원 시그모이드라 임계값도 라벨마다 하나씩입니다. 기존 계획서에는
"임계값은 스윕해서 정한다"고만 적혀 있는데, 8차원 격자 스윕은 조합이 폭발합니다
(라벨당 10칸만 잡아도 10⁸). 스윕 도구를 만들기 전에 **무엇을 스윕할지**부터 정해야 합니다.
→ F-1.

## E-α. 별건 — 채택선이 학생 단독을 재는데, 운영에서는 규칙과 합쳐집니다

운영 파이프라인은 규칙 소견과 AI 소견을 **합집합**으로 병합합니다:

```ts
export function mergeFindings(ruleFindings: Finding[], aiFindings: Finding[]): Finding[] {
  const seen = new Set(ruleFindings.map((f) => `${f.category}:${f.severity}`));
  return [...ruleFindings, ...aiFindings.filter((f) => !seen.has(`${f.category}:${f.severity}`))];
}
```

학생은 규칙을 **대체하는 것이 아니라 얹히는** 층이므로, 리서처가 실제로 겪는 오탐률은
합집합의 오탐률입니다. 그런데 제가 확정한 채택선은 학생 단독을 잽니다:

> ① 학생의 오탐률 ≤ 교사 ② 학생의 오탐률 ≤ 규칙 기준선의 보류율(17.6%)

규칙 오탐 6건은 전부 부정문(정상 34건 중)입니다. 학생이 **다른** 6건을 잘못 잡으면 각각
17.6%로 둘 다 채택선을 통과하는데 합산은 12/34 = **35.3%**가 됩니다. 즉 지금 채택선은
"사람 손이 두 배로 드는 모델"을 합격시킬 수 있습니다. 이 스레드에서 오탐이 가장 비싼
실수라고 못 박아 놓고, 그 오탐을 재는 잣대가 실제 노출을 안 재고 있었습니다. → F-2.

## E-β. 별건 — 코퍼스는 단일 라벨인데 모델은 다중 라벨입니다

```ts
export interface CorpusItem {
  violation: RiskCategory | null;   // 하나뿐
}
```

학습셋 수출은 이것을 `labels: [violation]`으로 옮깁니다. 그런데 실제로 라벨링을 해 보니
**두 유형이 동시에 타당한 문장**이 있었습니다. 예: `"지인을 통해 들은 이야기로는 계약이
이미 확정됐다고 합니다"` — 출처가 전언이라 RUMOR이면서, 확정된 계약 정보라 PRIVATE_INFO
이기도 합니다. 코퍼스는 PRIVATE_INFO 하나만 답으로 둡니다.

**평가에서는 문제가 안 됩니다.** 하네스는 위반 항목을 `categories.has(item.violation)`로
채점해서, 맞는 유형을 포함해 여러 개를 내도 정탐입니다. **학습에서는 문제가 됩니다.**
BCE 다중 라벨은 명시되지 않은 7개 차원을 전부 **음성(0)**으로 가르치므로, 이 문장은
"RUMOR가 아니다"를 학습시킵니다 — 사실이 아닌 것을 사실로 가르치는 라벨 노이즈입니다.
→ F-3.

## E-γ. 별건 — 브라우저 온디바이스 계획이 기존 확정 사항과 충돌합니다

로드맵은 "같은 모델을 브라우저(예방)와 서버(집행) 양쪽에서 돌린다"가 확정입니다. 그런데
지금 작성 중 사전 검사는 **이미 서버에서 돌고 있고, 그 이유가 명시돼 있습니다**:

> **검사는 서버에서 돈다** — 규칙 정규식과 학습 표현 사전을 브라우저 번들에 넣으면
> **금지 목록이 그대로 공개된다.** 순수 함수라 서버 실행 비용이 사실상 0이므로 비공개를 택했다.

학생 모델을 브라우저에 실으면 **그 가중치가 곧 금지 목록**입니다 — 정규식보다 읽기 어려울
뿐, 뽑아내서 회피 문장을 자동 생성하는 데는 오히려 더 편리합니다(그래디언트로 문턱 아래
문장을 찾을 수 있습니다). 규칙을 브라우저에 안 넣기로 한 근거가 학생 모델에는 더 강하게
적용되는데, 두 결정이 서로를 모르는 채로 문서에 나란히 있었습니다. → F-4.

## F. 답을 듣고 싶은 것

### F-1. 임계값을 라벨별로 둘 것인가, 하나로 둘 것인가?

**잠정 답**: 단일 임계값부터. 채택선을 넘으면 거기서 멈추고, 미달이면 그때 라벨별로 푼다.

**자신 없는 이유**: 유형마다 **미탐의 비용이 다릅니다.** 이 코퍼스에는 위험 성격 축이
이미 있습니다 — 규제(손실보전·미공개정보·1:1 유도·풍문 — 미탐이 플랫폼 법적 노출) /
소비자(위험 투자 조장) / 무결성(검수 회피) / 품질(근거 없는 단정 — 규제 위반이 아니라
항상 WARN). 단일 임계값이면 `UNSUPPORTED_CLAIM`과 `PROFIT_GUARANTEE`가 같은 문턱을 씁니다.
반대로 라벨별로 풀면 8차원 스윕이라 **손코퍼스 128건으로는 과적합**입니다 — 라벨당 유효
표본이 4~24건뿐이라 임계값을 그 표본에 맞추는 것이 곧 노이즈에 맞추는 것입니다.
위험 성격 4단계로 묶어 4개만 두는 절충도 생각했는데, 그것도 근거가 "그럴듯하다"뿐입니다.

**틀렸을 때**: 단일로 갔다가 규제 유형에서 미탐이 나면 법적 노출이고, 라벨별로 갔다가
과적합되면 벤치마크만 좋고 실제로는 무너지는데 그 사실을 배포 전에 못 봅니다.

### F-2. 채택선을 합산으로 재면, 규칙을 줄여야 합니까?

**잠정 답**: 채택선을 **합산 기준으로 고쳐 쓴다** — "규칙+학생 합산 오탐률 ≤ 규칙 단독
기준선(17.6%)". 규칙은 그대로 두고 학생에게 "규칙이 이미 잡은 것 위에 새 오탐을 얹지
마라"를 요구하는 형태입니다.

**자신 없는 이유**: 이 기준을 그대로 적용하면 **학생의 오탐 허용치가 사실상 0**이 됩니다
(규칙이 이미 17.6%를 다 쓰고 있으므로, 학생은 규칙이 틀린 그 6건 안에서만 틀려야 합니다).
그건 어떤 모델도 통과 못 할 가능성이 큽니다. 그러면 선택지가 둘로 갈리는데 어느 쪽인지
모르겠습니다:

- **(ㄱ) 규칙을 줄인다** — 학생이 부정문을 규칙보다 잘 다루면(교사는 부정문 오탐 0%였습니다,
  강등된 수치이긴 하지만) 부정문을 잡던 규칙을 학생에게 넘기고 합산 예산을 학생에게 준다.
  위험: 규칙은 **오탐률이 검증된 유일한 층**이고 즉시 거절 권한을 가진 유일한 층입니다.
- **(ㄴ) 합산 예산 자체를 올린다** — 17.6%는 "지금 사람이 쓰는 손"일 뿐 "써도 되는 손의
  상한"이 아닙니다. 대신 탐지율이 크게 오르면 보류가 늘어도 순이익일 수 있습니다.
  위험: 예산을 올릴 근거가 "탐지가 올랐으니까"뿐이면 그 논리로 계속 올릴 수 있습니다.

**틀렸을 때**: (ㄱ)이 틀리면 검증된 층을 검증 안 된 층으로 바꾼 것이고, (ㄴ)이 틀리면
운영자 1명이 감당 못 할 큐를 만들고도 지표상으로는 합격입니다.

### F-3. 단일 라벨 코퍼스로 다중 라벨 모델을 학습시켜도 됩니까?

**잠정 답**: 코퍼스를 다중 라벨로 바꾸지 않고, **명시되지 않은 라벨을 손실에서 마스킹**한다
(그 차원을 0으로 가르치지 않고 아예 학습에서 뺀다). 코퍼스 스키마를 바꾸면 평가 하네스·
회귀 테스트·문서가 함께 움직이는데, 128건 규모에서 그 비용이 큽니다.

**자신 없는 이유**: 마스킹하면 **음성 예시가 사라집니다.** "이 문장은 RUMOR가 아니다"를
아무도 안 가르치면 모델이 모든 유형을 남발하는 쪽으로 기울 수 있고, 그건 정확히 오탐입니다.
정상 문장(labels=[])은 8차원 전부 음성이라 거기서 음성을 배우긴 하는데, 그것으로 충분한지
판단이 안 섭니다. 대안으로 "위반 항목만 마스킹하고 정상 항목은 전부 음성" 같은 절충도
생각했지만, 그러면 위반 문장에서는 유형 간 경계를 아예 안 배웁니다.

**틀렸을 때**: 라벨 노이즈를 그대로 두면 학생이 다중 라벨 문장에서 유형을 헷갈리고,
하네스는 그걸 정탐으로 세기 때문에(위 E-β) **평가에서 안 드러납니다.** 운영자가 반려
사유의 유형을 고칠 때에야 드러납니다.

### F-4. 브라우저 온디바이스를 포기하고 서버 전용으로 좁히면, 이 스레드의 절반이 사라집니다 — 좁혀야 합니까?

**잠정 답**: 좁힌다. 학생을 **서버 전용**으로 두고 브라우저에는 아무것도 싣지 않는다.

근거는 E-γ입니다. 그리고 좁히면 이 스레드에서 답 없이 남아 있던 것들이 **질문 자체로
사라집니다**:

| | 브라우저 탑재 시 | 서버 전용 시 |
|---|---|---|
| 크기 예산 (1차 F-3, 여전히 근거 없음) | 필요 — 100MB·200ms 잠정값 | **사라짐** — 서버 메모리는 100MB가 문제되지 않는다 |
| 버전 어긋남 (1차 F-4) | 필요 — 모델 식별자 실어 사전 검사 끄기 | **사라짐** — 판단 주체가 하나 |
| 가중치 재배포 라이선스 (블로커) | 필요 — 우리 도메인에서 서빙 | **사라짐** — 서버 내부 사용 |
| 첫 로드 UX | 미정 | **사라짐** |
| 금지 목록 공개 (E-γ) | 뚫림 | 막힘 |
| 사전 검사 지연 | 로컬 추론 | 서버 왕복 — **지금도 그렇게 돈다**(디바운스 600ms) |

**자신 없는 이유**: 원래 브라우저를 넣은 이유가 "작성 중 실시간 검사를 API로 돌리면
타이핑마다 호출이라 비용 구조가 다르다"였는데, **자체 모델은 자기 서버에서 도니 호출당
비용이 0에 수렴합니다.** 그러면 브라우저의 남는 이점은 지연 시간 하나뿐인데, 지금 사전
검사가 이미 서버 왕복으로 돌고 있어 그 이점도 "지금보다 나아지는 것"이지 "필요한 것"이
아닙니다. 여기까지는 명확한데, 그렇다면 **왜 처음에 브라우저를 넣었는지**를 제가 아직
설명하지 못합니다 — 놓친 이유가 있을까 봐 확정을 못 하겠습니다. (짐작 가는 것은 오프라인
동작인데, 리포트 게시 자체가 서버 없이는 불가능하므로 성립하지 않습니다.)

**틀렸을 때**: 좁혔다가 나중에 브라우저가 필요해지면 모델 후보 선정(크기 제약)부터 다시
해야 합니다. 반대로 안 좁히면 근거 없는 예산·라이선스 확인·버전 동기화 설계를 **필요하지도
않은데** 계속 끌고 갑니다.

## 검수 모델 스레드에서 이미 답이 난 것 (이번 회차에 걸리는 줄만)

| 결론 | 근거 |
|---|---|
| 오탐(정상 차단)이 미탐(위반 통과)보다 비싸다 | 미탐은 에스크로 환불로 되돌아오고, 오탐으로 떠난 리서처는 돌아오지 않는다 |
| 자동 거절 권한은 결정적 규칙에만 | 오탐률이 검증된 유일한 층이다. AI·사전·유사도·학생은 전부 보류로만 간다 |
| 즉시 거절 오탐 0건은 절대 조건 | 보류 오탐은 사람이 되살리지만 거절 오탐은 되살릴 사람이 없다 |
| 규칙은 일부러 멍청하게 둔다 | 직설·회피까지만. 나머지는 다른 층의 몫이라 비대화에 상한이 있다 |
| 검사는 서버에서 돈다 | 브라우저 번들에 넣으면 금지 목록이 공개된다 (E-γ가 이 줄과 충돌한다) |
| 모델 입력은 ScreeningInput 전체 | 카드를 뺀 모델은 본문–카드 모순을 영원히 못 배운다 |
| 채택은 val F1이 아니라 하네스로 | 그 하네스의 채택선에 결함이 있다는 것이 E-α다 |
| 평가는 동결된 Ground Truth 위에서만 | 대화 라벨은 학습 생산 전용 — 도구가 강제한다 (2차 H-2) |
| 손코퍼스는 절대 수치가 아니다 | 변경 전후 비교에만 쓴다. 운영자 판정이 쌓이면 그쪽이 진짜 검증셋 |

## 회차 기록 (검수 모델 스레드)

| 회차 | 지적 | 결과 |
|---|---|---|
| 1 | (자체) 임베딩 1단계의 우선순위 근거가 콜드스타트 계획과 충돌 | 채택 — 게이트에서 임베딩을 빼고 서버 전용 의미 인덱스로 격하 |
| 2 | 대화 라벨을 학습셋에 섞어라 + 롤백 플래그 | 부분 — 결론·플래그 채택, "노이즈가 증강"이라는 근거는 기각. 라벨 노이즈는 증강이 아니다 |
| 2 | 평가셋을 동결하고 대화 경로에 태우지 마라 | 채택 후 더 밀고 감 — 규율 대신 도구가 막게 했고, 동결 범위를 86 → 128건으로, 1차 측정은 전체 강등 |
| 2 | 그림자 모드 실패는 사고가 아니라 검증 성공이다 | 채택 — 가장 값어치 있었다. 비용 인식 하나가 바뀌자 배포 계획의 성격이 바뀌었다 |
| 2 | 단일 출력으로 먼저 밀어붙여라 | 채택 — 판단이 일치했고, 갈림길이 이미 선언돼 있어 추가 결정 비용이 없다 |

여기서 배운 것 둘.

**결론이 맞아도 근거는 따로 검증해야 한다.** 2차의 "섞어라"는 맞았지만 근거로 붙은
"노이즈가 증강"은 틀렸고, 그대로 문서에 적었다면 나중에 "정제할 필요 없다"로 읽혔을 것이다.

**규율로 막으라는 제안이 오면 도구로 막을 수 있는지부터 본다.** 2차 H-2의 제안은 옳았지만
수단이 규율이었고, 그 규율은 바로 직전 회차에 이미 한 번 실패한 것이었다.
