## B-1. 근무자 표식 → **(가) 채택 + 뿌리까지 수정했습니다** [완료]

정확한 발견입니다. reviewerId 는 설정(태그·임계값)에서 조립되므로 "무엇을 쓰겠다고
설정했나"까지만 말하고, 재학습으로 가중치만 갈리면 그대로입니다. 어제가 실증입니다 —
aeb1786b → 607ec47b → 49c4a9dd → 607ec47b(복원)로 **하루에 세 번** 바뀌는 동안
표식은 한 글자도 안 움직였습니다.

두 군데를 고쳤습니다:

1. **(가) 그대로** — `GET /api/admin/compliance/student-valve` 의 `student` 에
   `modelSha` 필드 추가 (사이드카가 실제 적재한 가중치의 지문, 없으면 null).
   표식 옆에 앞 8자를 그리시면 됩니다.
2. **뿌리** — 여러분이 지적한 위험은 화면보다 **데이터에서 더 컸습니다**: 그림자
   기록(ShadowComplianceReview.reviewer)도 같은 표식을 쓰고 있어서, 가중치가 갈린
   두 모델의 기록이 **한 판정기의 기록으로 합산**될 뻔했습니다 — "임계값이 다르면
   다른 판정기"라는 그 칼럼의 존재 이유가 무너지는 자리입니다. 이제 그림자 기록의
   reviewer 는 `student:태그@t0.7/L7#607ec47b` 처럼 **가중치 지문이 접미로 붙습니다**.
   화면에서 그림자 reviewer 를 파싱하는 곳이 있다면 `#` 뒤가 새로 생겼음을 반영하세요
   (본 기록의 reviewer 는 기존 형식 유지 — 라이브 판정의 모델은 modelSha 필드로 확인).

## B-2. 격리 승인 문구 → **격리 해제는 없습니다. 문구 한 곳만 고쳐 주세요** [확인]

문장이 섞이면 "격리가 수정의 대체재"로 읽힙니다. 권장:

> 승인하면 — 이 문항이 회귀 시험셋에서 **영구히** 빠집니다. 되돌릴 수 없습니다.

처리하는 UI 는 만들 수 없습니다.

## C-1. 사전 화면 이름·자리 [결정]

- **이름**: 화면 문구 전부 "운영자 사전"으로 교체 O. 반려 폼은 "사전에 등록" 정도로.
  **URL 파라미터(`?tab=phrases`)는 그대로** — 북마크 호환이 맞고, 코드 식별자와 화면
  문구를 분리하는 것은 이 저장소의 관례입니다(카드지갑/cart 와 같은 결정).
- **자리**: **지금 자리(도구 묶음) 유지를 권합니다.** 운영자가 사전을 만지는 주 경로는
  관리 화면이 아니라 **반려 폼**(되먹임 빠른 길)이고, 관리 화면은 점검·졸업용입니다.
  큐 옆으로 올리면 "검수 중에 사전을 직접 고치는" 동선을 유도하는데, 등록은 반려라는
  판정에 붙어서만 일어나야 합니다(근거 없는 금지어 방지 — 1호 원칙).

## C-2. 지나는 층 표기 → **(가) 자격 있는 항목에도 적습니다** [결정]

오해 여지가 실제로 있습니다 — "정확 표기만 감시"가 자격 없는 항목에만 붙으면, 자격
있는 항목은 "전부 감시"로 읽힙니다. 4층(연락처 숫자 묶음)·6층(표기 훼손 신호)은
개별 표현이 아니라 **글 전체의 성질**을 보는 층이라 사전이 관여할 자리가 원리적으로
없는데, 운영자가 그걸 알 이유가 없습니다. 권장 문구:

- 자격 있음: `감시: 원문 · 기호 제거 · 깊은 정규화 · 음성 변형`
- 자격 없음: `감시: 원문 · 기호 제거 · 깊은 정규화 (근사 표기 제외 — 등록 시 충돌)`

층 번호(L1~L6)는 화면에 쓰지 마세요 — 운영자 어휘가 아닙니다.

## C-3. 그림자 동안 졸업 → **(나) 확정** [결정]

권하신 논리 그대로입니다 — 채택 직전에 대비쌍을 미리 써 두는 것은 정상 운영이고,
서버가 막으면 그 준비를 막는 셈입니다. 관찰 창이 그림자를 읽는 것도 확인하신 대로라
"뚫리는 동안 세어진다"까지 맞습니다. 경고 문구도 제안하신 것 그대로 쓰시되 한 마디만
보태세요: "…아무도 막지 않습니다 **(규칙·코드 패턴에 걸리는 부분은 계속 막힙니다)**" —
사전 표현이 코드 패턴과 겹치는 경우가 많아, 문구가 과장이 되면 다음 경고를 안 믿습니다.

## C-4. 큐 카드의 학생 자리 → **카드에는 넣지 마세요. 목록 머리 한 줄로.** [확인]

카드마다 반복되는 상시 문구는 노이즈가 되고(같은 이유로 배경 궤적 고지도 카드마다
안 붙입니다), 학생이 라이브로 돌아오는 날 전 카드의 문구를 떼야 하는 동기화 부담이
생깁니다. 대신 **보류 큐 목록의 머리에 한 줄** — "학생 검사기: 연수 중(기록만) —
이 큐의 소견은 규칙 단독입니다" — 를 상태 카드와 같은 API(student.mode)로 그리세요.
카드 단위 표시는 학생이 라이브일 때의 `[학생·확신 N%]` 배지 하나로 충분합니다.

## 상태 공유 (여러분 화면에 곧 반영될 사실)

- 학생은 현재 **shadow** 가 맞는 상태입니다 — 어제 재학습(r3)이 회귀 게이트·DART
  실산문 오탐 축에서 기각됐고, 채택 가능한 모델이 나올 때까지 연수 중입니다.
  4라운드 자료(풍문·연락처 대비쌍)가 준비되는 대로 재학습·게이트를 다시 돕니다.
- 채택 게이트에 축이 하나 늘었습니다: **DART 실산문 오탐**(3,000문장). 화면 계약에는
  영향 없습니다.

## 추신 2 — 운영 체제 안내(Q1~Q3) 답변

### Q1. 격리의 1인 갈림길 → **구현 완료** [막힘 해소]

정확한 발견입니다 — 주석에 "1인 모드에서는 재확인이 대체한다"고 적어 놓고 갈림길을
코드에 안 넣은 저희 누락이었고, 지적하신 대로 **아무도 지나갈 수 없는 문**이었습니다.
§3 표준 모양 그대로 붙였습니다:

- `quarantineRegressionCase(prisma, { caseId, operatorUserId, reason, recheckToken? })`
- `GraduationError` 에 `code?: 'RECHECK_REQUIRED'` 추가 (payoutAccountService 와 동일 계약)
- 승인서 우선 → 없으면 1인=재확인 표 소비 / 다인=승인 요청 대신 올리고
  `"승인 요청을 올렸습니다 — 다른 운영자의 승인 후 다시 실행하세요."` 로 멈춤
- 다인 요청의 summary 는 `회귀 문항 격리 — "문항 앞 40자"` 형식으로 서버가 만듭니다
- 시험으로 고정: 1인 DB 에서 표 없이 → code=RECHECK_REQUIRED, 표 소비 → 격리 성공

http.ts 의 GraduationError 매핑과 버튼은 말씀대로 그쪽에서 진행해 주세요.
(주의: 400 본문의 code 는 RECHECK_REQUIRED 하나뿐입니다 — 다인 모드의 "요청 올림"은
code 없이 메시지로만 옵니다. 승인 대기 상태 표시가 필요하면 말씀 주세요.)

### Q2. 나머지 무관문 → **전부 의도이고, 여러분의 독해가 정확합니다** [확인]

- **졸업/재활성화/반려·승인/강제 철회**: 의도. 정리하신 비대칭 논리 그대로입니다 —
  격리는 시험을 **깎는** 방향(그래서 2인/재확인), 졸업은 방어를 더 얹는 방향(대비쌍이
  회귀셋에 들어감), 강제 철회는 돈이 구매자에게 **돌아가는** 방향입니다. 덧붙이면
  졸업·재활성화·반려는 전부 **가역**이고 기록이 남습니다.
- **밸브**: 의도이며, 여러분 의견에 동의합니다. 밸브가 필요한 순간은 장애 대응 중이라
  관문 하나가 대응을 늦추고, 오용의 대가는 "보류 큐가 길어지는 것"입니다. 관문 대신
  **시끄러움**으로 방어합니다 — 켜는 순간 운영자 전원 알림, 우회 건 전부
  `VALVE_BYPASS` 영구 꼬리표, 2시간 자동 만료, 사이드카 복구 시 자동 걷힘.
  운영자가 1~2인인 동안은 이 조합이 관문보다 정직하다고 봅니다. 다인 체제로 넘어가면
  재검토 대상입니다(그때는 "누가 내렸나"가 물음이 되므로).
