# 관리자 앱 인계 문서 3호 — 학생 검사기가 라이브로 출근했습니다 (2026-08-21 밤)

> 읽었다는 전제입니다. 어긋나면 이 문서가 이깁니다. 이번 문서의 주제는 하나 —
> **학생 검사기 운영 화면**: 오늘 학생 모델이 채택 판정을 통과해 실검수에 라이브로
> 합류했고, 운영자가 그 상태를 한눈에 봐야 합니다.

## 0. 화면 문구를 위한 비유 하나 (창업자 확정 멘탈 모델)

이 화면의 라벨·문구는 아래 비유를 따르세요 — 창업자가 시스템을 이해하는 방식이고,
운영자에게도 기술 용어보다 정확하게 전달됩니다:

```
학생 모델(가중치 파일)  = 직원 본인
사이드카(별도 프로세스) = 그 직원이 출근해 앉는 창구 (내선 8765)
검수 서버              = 본사 — 리포트가 오면 내선으로 물어본다
usable 검사            = 출근 확인 (자리에 있고 전화를 받는가)
시맨틱 핑              = 정신 확인 (쉬운 위반 문장 하나를 실제로 풀게 한다)
장애 우회 밸브          = 창구가 닫혔을 때 2시간짜리 임시 통로
작업 스케줄러 + watchdog = 자동 출근 + 당직 (OS 층 — 화면에서는 안 보인다)
```

권장 화면 제목: **"학생 검사기 출근 상태"**. "사이드카 헬스체크" 같은 말은 쓰지 마세요.

---

## 1. 데이터 원천 — API 하나로 다 옵니다

`GET /api/admin/compliance/student-valve` (운영자 인증 필요) 응답이 확장됐습니다:

```jsonc
{
  "outageSince": "2026-08-21T18:00:00Z" | null,  // null 이면 장애 아님
  "outageHolds": 3,                              // 장애로 보류된 미처리 건수
  "bypass": { "active": false, "until": null },  // 밸브 (2회차 회신 B-3 그대로)
  "student": {                                   // ★ 신규
    "mode": "live" | "shadow" | "off",
    "reviewerId": "student:koelectra-synth-v2@t0.7/L7" | null,
    "usable": true | false                       // 시맨틱 핑까지 통과했는가
  }
}
```

`reviewerId` 는 파싱하지 말고 **그대로 표기**하세요 — `모델태그@t임계값/L라벨수` 형식이라
그 자체가 "지금 어느 판정기가 근무 중인가"의 완전한 표식입니다.

## 2. 상태 카드 — 다섯 상태를 가르세요

`mode` × `usable` × `outageSince` 조합으로 상태가 정해집니다:

| 조건 | 표시 | 톤 |
|---|---|---|
| mode=live · usable=true | **근무 중** + reviewerId | 정상 (민트 아님 — 무채색. 검증 배지가 아닙니다) |
| mode=live · usable=false · outageSince≠null | **결근 — 장애 N시간째 · 보류 M건** | 경고. N = now−outageSince, M = outageHolds |
| mode=live · usable=false · bypass.active | **결근 + 우회 중 — HH:MM 뒤 자동 복귀** | 경고. until 카운트다운 |
| mode=shadow | **연수 중 (그림자)** — 판정하되 기록만 | 중립 |
| mode=off | **미출근 (꺼짐)** — 규칙 단독 검수 | 중립 |

- "결근"에는 두 얼굴이 있음을 문구로 드러내세요: 전화를 안 받는 것(연결 실패)과
  **자리에 앉아 있는데 정신이 없는 것**(시맨틱 핑 실패 — 뇌사)은 서버가 이미 갈라서
  usable=false 로 접어 줍니다. 화면은 구분할 필요 없이 "결근"으로 통일하되,
  도움말에 "출근 확인에는 실제 문제 풀이(시맨틱 핑)가 포함됩니다" 한 줄.
- 장애 표시가 하루 넘게 이어지면 안내 문구를 추가하세요: "사이드카 자동 출근(작업
  스케줄러 `intovill-student-sidecar`)이 등록·실행 중인지 확인이 필요합니다" —
  화면이 OS 작업을 직접 볼 수는 없으니 사람에게 확인 위치를 알려주는 것까지가 몫입니다.

## 3. 밸브 버튼 — 2회차 회신 B-3 그대로, 위치만 이 카드 안으로

[우회 밸브 내리기] / [미리 올리기] 버튼과 카운트다운을 이 상태 카드에 함께 두세요 —
밸브가 필요한 순간은 정확히 "결근" 상태를 보고 있는 순간입니다. POST 계약은 변경 없음.

## 4. 채택 이력 표기 — 숫자를 하드코딩하지 마세요

오늘의 채택 수치(임계값 0.7 · 새 오탐 0 · 순이익 +13 · 패러프레이즈 58.3%)를 화면에
박아 넣고 싶겠지만 **넣지 마세요** — 다음 재학습에서 낡은 숫자가 화면에 남습니다
(같은 이유로 카나리아 층 하드코딩이 2회차 A-2에서 문제였습니다). 화면이 말해도 되는
것은 `reviewerId`(항상 현재값)까지고, 채택 근거 수치는
`training/labeling/review-21.md 부록 3` 링크로 넘기세요.

## 5. 하면 안 되는 것 (기존 원칙 재확인 + 추가)

- 학생의 개별 소견·그림자 판정을 이 화면에 싣지 않는다 (X-6)
- 하드 네거티브 목록을 만들지 않는다 — 게이지 숫자까지만 (2회차 회신 B-5)
- **usable=false 라고 화면이 사이드카를 재시작하는 버튼을 만들지 않는다** —
  재기동은 OS(watchdog)의 몫이고, 화면이 프로세스를 만지기 시작하면 장애 원인이
  "누가 껐다 켰나"부터 불투명해진다. 화면의 몫은 보여주는 것과 밸브까지
- reviewerId 를 잘라서 일부만 보여주지 않는다 — L7 이 L8 로 바뀌는 날(라벨 추가)을
  운영자가 눈으로 알아채는 것이 이 표식의 존재 이유 중 하나다
