### I-6 — 격발 지점이 수학적 기대치와 일치했습니다

### I-4 — 값 검사는 거의 아무 일도 하지 않고 있었습니다

파일 **이름은 `model.onnx`로 그대로 둔 채** 가중치의 한 비트를 뒤집고, 카나리아의
두 층을 **따로** 쟀습니다.

| 변이 | ⓐ 신원(sha)만 있었다면 생존 | ⓑ 값(로짓)만 있었다면 생존 | ⓐ+ⓑ 현행 |
|---|---|---|---|
| 미세 (가수 끝자리) | 0/10 | **9/10** (최대 오차 0.0028) | 0/10 |
| 거친 (지수부) | 0/10 | **9/10** (최대 오차 0.216) | 0/10 |

**생존율 0/20 = 0.0%** — 기대값입니다. 그런데 값어치는 그 0%가 아니라 **ⓑ의 90%**에
있습니다. 파라미터 1,400만 개에 카나리아 입력이 3건뿐이라 대부분의 비트가 그 3건의
계산 경로에 없습니다. **sha가 혼자 다 하고 있었습니다.**

ⓑ를 걷어내지 않는 이유는 ⓑ만 잡는 것이 따로 있어서입니다 — 라벨 순서·토크나이저·
출력 차원. 두 층이 서로 다른 실패를 맡습니다. (J-3에서 다시 묻습니다.)

### I-1 — 알림을 조용한 채널에서 꺼냈습니다

9차에 만든 상태 엣지 알림이 `Notification` 행만 만들고 있었습니다. 그 알림이 닿는 곳이
하필 **앱 안**입니다 — 사이드카가 죽어도 앱은 멀쩡히 도니 운영자가 어드민을 열 이유가
없습니다. **조용한 실패를 잡으려고 만든 장치를 조용한 채널에 꽂아 둔 셈**이었습니다.

| 층 | 무엇을 잡나 | 채널 | 실측 |
|---|---|---|---|
| 앱 | 사이드카가 죽었는데 웹은 살아 있다 | 인앱 + 웹훅 + **텔레그램** | — |
| OS (`watchdog.ps1`) | 웹도 함께 죽었다 / 재부팅 뒤 안 떴다 | 텔레그램·웹훅 직접 | **92ms** |

되물음("감시자는 누가 감시하나")은 작업 스케줄러에서 멈춥니다.

경보는 파일 싱크로 받아 쟀습니다 — 실채널로 쏘면 종단간을 재려다 창업자 폰에 가짜
경보가 갑니다(2026-08-18에 실제로 그랬습니다).

| 유형 | 규칙 단독 | 학생 단독 | 합산 | |
|---|---|---|---|---|

| paraphrase | 0.0% | **70.8%** | 70.8% | ← 학생만 |

## C. I-6을 만들다 만난 것 — **개입이 관측을 지운다**

순진하게 만들면 **반드시 발진합니다**:

```
적자 → 격하 → 학생이 소견을 안 냄 → 창에서 학생 표본이 빠짐
     → 표본 부족 → shouldRollback=false → 다시 켜짐 → 다시 오탐 → 적자 → ...
```

원인은 지표가 아니라 **개입이 관측 대상을 지운다**는 데 있습니다. 학생을 끄면 학생의
성적을 만들 재료가 끊기므로, 끈 상태에서 잰 값은 "좋아졌다"가 아니라 **"모른다"**입니다.
그런데 `studentRollbackStatus`는 그 둘을 같은 얼굴(`shouldRollback=false`)로 돌려줍니다.

→ **걸쇠(latch)로 만들었습니다. 거는 것은 시스템, 푸는 것은 사람.**
`judgmentPause`가 "사람이 건 정지는 사람만 푼다"고 정한 것과 같은 계열이되 근거가
다릅니다. 저쪽은 *고쳐졌는지 알 방법이 없어서*이고 이쪽은 ***끈 동안에는 잴 수 없어서***.

부수적으로 정해진 것 둘:

- **환경 변수보다 걸쇠가 셉니다.** 배포 설정은 "쓰겠다는 의도"이고 걸쇠는 "쓸 수 없다는
  관측"이라, 의도가 관측을 덮으면 격하 장치가 재배포 한 번에 지워집니다
- 운영 화면은 격하 상태를 **순이익 수치보다 먼저** 말합니다. 격하 뒤로는 그 수치가
  갱신되지 않으므로, 말해 주지 않으면 "숫자가 안 나빠졌으니 괜찮다"로 읽힙니다

라이브 진입 관문도 함수로 꺼냈습니다(`resolveLiveStudent`). 걸쇠도 `usable()`도 각각
시험이 있었지만 **둘을 어떤 순서로 엮었는가**는 함수 안의 한 줄이라 아무도 붙잡고
있지 않았습니다 — 8차에 비싸게 배운 모양입니다.

## D. I-5는 판단은 받고 도구만 바꿨습니다

"웹의 자식으로 띄우지 말라"는 그대로 받았습니다. NSSM 대신 **윈도우 작업 스케줄러**를
썼습니다 — NSSM은 내려받아야 하는 서드파티 실행 파일인데, 스케줄러가 필요한 셋을
그대로 줍니다: 부팅 시 자동 기동 · 웹과 독립된 수명 · 실패 시 자동 재시작.
차이는 서비스 목록에 안 보인다는 것 하나이고, 옮기려면 `install-task.ps1`만 바꾸면
됩니다(`watchdog.ps1`은 그대로).

**이 판단이 틀렸으면 지적해 주십시오.** 제가 "내려받지 않는다"를 과하게 지킨 것일 수
있습니다.

## F. **이번에 새로 나온 결함 — 안전장치의 입력이 운영자의 클릭 습관입니다**

자동 격하는 운영자 판정으로 채점합니다. 그런데 그 라벨의 **기본값이 "모델이 틀렸다"**입니다:

```ts
// screeningAccuracy.classifyReview
if (r.verdict === 'REJECTED' || r.verdict === 'TAKEDOWN') return 'TRUE_POSITIVE';
return r.findingsValid ? 'MINOR' : 'FALSE_POSITIVE';   // ← 체크 안 하면 오탐
```

기본값을 이렇게 둔 근거는 기록돼 있고 그 자체로는 타당합니다 — *"승인의 대다수가 과잉
지적이고, 예외만 체크하게 해야 운영자 손이 덜 가면서 라벨이 비지 않는다"*(CLAUDE.md).
**정확도를 표시하는 용도로는 맞습니다.**

그런데 10차에 그 라벨이 **자동 격하의 입력**이 되면서 뜻이 달라졌습니다. λ=4가
정확히 이 방향으로 증폭합니다. 실측(`scripts/probeCarelessApproval.ts`):

```
창 50건 · 표본 하한 25건 · λ=4
  성의없는승인  정탐  순이익  격하
           5건    20       0  유지
           6건    19      -5  ✗ 꺼진다
          25건     0    -100  ✗ 꺼진다
```

**25건 중 6건을 무심코 승인하면 학생이 꺼집니다.** 그리고 걸쇠라서 스스로 안 돌아옵니다.

1인 운영이라 이건 이론이 아닙니다. 큐가 밀린 날 스무 건을 빠르게 승인하는 것이 정상
운영이고, 그날 학생 모델이 영구히 내려갑니다. **모델이 나빠서가 아니라 사람이
바빠서**입니다.

거꾸로도 위험합니다: 이 사실을 알면 운영자가 "학생을 끄고 싶지 않아서" 승인을 주저하게
되는데, 그러면 **검수 도구가 검수 판단을 왜곡**합니다.

## H. 미해결 — J-1 ~ J-6

### J-1. 승인 라벨의 기본값 (F절)

자동 격하의 입력이 운영자의 클릭 습관입니다. 25건 중 6건이면 꺼집니다. 선택지:

- ⓐ **기본값을 뒤집는다** — 승인 시 "이건 오탐이었다"를 명시적으로 체크. 운영자 손이
  늘고, 안 누르면 정확도 지표가 낙관 쪽으로 편향됩니다
- ⓑ **격하만 다른 라벨을 쓴다** — 명시적으로 오탐 체크한 건만 센다. 표본이 확 줄어
  격발이 훨씬 늦어집니다(J-2와 정면 충돌)
- ⓒ **격하에서만 λ를 낮춘다** — 9차 G-4가 금지한 것입니다(켤 때와 끌 때의 잣대가
  달라지면 두 판단이 서로를 반박한다)
- ⓓ **그대로 둔다** — 1인 운영에서 "빨리 승인했다"는 것 자체가 "지적이 성가셨다"는
  진짜 신호일 수 있습니다

어느 쪽입니까? 그리고 **무엇을 재면** 이 선택이 옳았는지 알 수 있습니까?

### J-2. 출시 직후 안전망이 구조적으로 죽어 있습니다

리포트 유입이 주당 몇 건이면 몇 주가 걸립니다 — **가장 위험한 시기에 자동 격하가

### J-3. 카나리아 입력을 늘려야 합니까

값 검사가 가중치 훼손을 90% 놓칩니다(B절). 선택지:

- ⓐ **입력을 3건 → 50건으로** — 계산 경로가 넓어져 값 검사가 실제로 가중치를 덮습니다.
  대가는 기동 시간(지금 사이드카 기동 6.5초)
- ⓑ **역할을 못 박고 그대로 둔다** — "가중치 신원은 sha, 카나리아는 라벨·토크나이저·
  차원"으로 문서화. 대가는 sha 한 층에 의존이 몰리는 것

ⓑ가 맞다고 생각하는데, 그러면 **"카나리아가 종단간을 검사한다"는 말이 과장**이 됩니다.
이름을 바꿔야 합니까?

### J-4. 해제 버튼의 문턱

지금 자동 격하 해제의 유일한 문턱은 **확인 창 하나**입니다("재학습하고 채택선을 다시

그러면 **운영자가 아는데 코드가 막는** 상황이 생깁니다(사고 복구 중에 그럴 수 있습니다).
방어를 어디까지 물리화하고 어디부터 사람을 믿습니까?

### J-5. 제가 실행할 수 없는 산출물의 검증 등급

`install-task.ps1`은 시스템 설정을 바꾸므로 제가 못 돌립니다. `design-debt.txt`의
등급 체계([Type]/[Mock]/[Live])에 **이 범주가 없습니다** — 창업자가 실행하는 것과
제가 검증하는 것은 다릅니다(실행 결과를 제가 못 봅니다).

이런 산출물의 [Live] 정의는 무엇입니까? "창업자가 돌리고 결과를 붙여넣으면 [Live]"로
충분합니까, 아니면 별도 등급이 필요합니까?

### J-6. 스레드를 언제 닫습니까

I-6은 "합성 오염으로 격발이 기대치와 일치하면 이 파이프라인의 구현은 완성"이라고
했고, **일치했습니다.** 그런데 같은 회차에 F절(승인 라벨)이 새로 나왔습니다.

이런 식이면 끝이 없습니다. **무엇을 보면 이 파이프라인을 닫고 다음으로 넘어갑니까?**
제 생각은 "출시 후 실데이터 N건"인데, 그건 출시를 막는 조건이 아니라 출시 뒤의
조건이라 지금의 종료 조건이 되지 못합니다.
