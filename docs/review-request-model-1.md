# INTOVILL 검수 모델 1차 검토 요청 — 규칙의 천장이 숫자로 드러났습니다. 그 위를 무엇으로 덮을지가 이 스레드입니다

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동으로 판정합니다. 적중이면 리서처에게
정산되고, 실패면 구매자에게 현금 환불됩니다. 그 사이 돈은 에스크로에 있습니다.

**검수는 그 앞단**입니다. 게시 버튼을 누르면 손실보전 약속·1:1 상담 유도·미공개정보 정황
같은 규제 위반 표현을 찾아 거절하거나 보류시킵니다. 지금은 정규식 + 운영자 사전 +
Claude API 3단입니다.

이 스레드에서 만들려는 것은 **앱 안에서 도는 자체 검수 모델**이고, 잡아야 할 것이 둘입니다.

1. 지금 규칙이 잡는 것 — 본문의 투자 권유·1:1 대화 유도 같은 **표현**
2. 규칙이 원리적으로 못 잡는 것 — **리포트가 앞뒤가 맞는가.**
   카드는 상승으로 걸어놓고 본문은 조정을 말하는 경우

두 번째가 이 스레드를 여는 이유입니다. 구매자는 **본문을 읽고 사는데 판정과 정산은
전적으로 카드로** 됩니다. 둘이 어긋나면 구매자는 자기가 읽은 것과 다른 근거로 돈을 잃습니다.

## A. 왜 지금인가 — 규칙의 천장을 쟀더니 숫자가 나왔습니다

모델을 붙이기 전에 평가셋부터 만들어 규칙 단독 성적을 쟀습니다. 결과가 이렇습니다.

| 문장 종류 | 규칙 성적 | 읽는 법 |
|---|---|---|
| 직설 (금지 표현 그대로) | 탐지 **100%** | 규칙이 할 일은 다 했다 |
| 회피 (글자 벌리기) | 탐지 100% | 정규화 패스가 돈다 |
| **패러프레이즈 (같은 뜻, 다른 말)** | 탐지 **0%** | 정규식의 원리적 천장 |
| 정상 분석 문장 / 면책 문구 | 오탐 0% | 평범한 글은 안 건드린다 |
| 부정문 (금지 표현을 부정) | 오탐 50% | 전부 WARN 강등 — 설계된 대가 |

전체 탐지율 53.8% · 오탐률 17.6% · **즉시 거절 오탐 0건**.

그리고 미탐의 **비용**으로 쪼개면 이렇게 나옵니다.

| 성격 | 포함 유형 | 탐지율 |
|---|---|---|
| **규제** — 미탐이 플랫폼 법적 노출 | 손실보전 · 미공개정보 · 1:1 유도 · 풍문 | **55.9%** (19/34) |
| 소비자 — 미탐이 구매자 피해 | 위험 투자 조장 · 본문–카드 불일치 등 | 62.5% (5/8) |
| 무결성 — 검수 자체를 겨냥 | 검수 회피 시도 | 66.7% (4/6) |
| 품질 | 근거 없는 단정 | 0% (0/4) |

**규제 위반 34건 중 15건을 규칙이 놓치고 있고, 거의 전부 패러프레이즈입니다** —
"차액은 제 사비로 채워드릴 테니" 같은, 금지 단어를 한 번도 쓰지 않은 손실보전 약속.
지금은 전적으로 Claude API에 의존하고, API가 놓치면 그대로 게시됩니다.

문서 단위(본문–카드 정합성)는 **규칙 탐지 0%**입니다. 이건 결함이 아니라 설계된 공백입니다 —
본문과 카드의 논조 모순을 어휘 세기로 잡으면 반대 시나리오를 충실히 쓴 정상 리포트가
무더기로 걸립니다.

**이 두 자리(패러프레이즈 0% · 문서 단위 0%)가 모델이 가져가야 할 몫의 정확한 크기입니다.**

## B. 이미 만들어 둔 것 — 모델보다 자를 먼저 만들었습니다

측정할 수 없으면 모델을 붙여도 좋아졌는지 알 수 없고, 나빠져도 모릅니다.
그래서 평가 도구를 먼저 지었습니다.

| | 내용 |
|---|---|
| 문장 코퍼스 | 86건 (위반 52 / 정상 34). 종류별로 라벨 — 직설·회피·패러프레이즈·정상·부정문·면책 |
| 문서 코퍼스 | 42건 (채점 38 + 관측 4). 어긋나는 방식으로 쪼갬 — 방향·크기·기간 |
| 평가 하네스 | 탐지기를 **"검수 입력 → 소견" 함수**로만 본다. 규칙이든 임베딩이든 증류 모델이든 같은 잣대 |
| 회귀 시험 | 696건. 즉시 거절 오탐 0건이 못 박혀 있다 |

문서 코퍼스에서 **정상 17건 중 10건이 `risk_heavy`**입니다 — 리스크를 세 문단 다루지만
결론은 카드와 같은 방향인 리포트. **좋은 리포트는 원래 반대 시나리오를 길게 씁니다.**
여기가 걸리기 시작하면 성실하게 쓴 리서처일수록 더 막히므로, **이 묶음의 오탐률이
모델 채택의 판정선**입니다.

그 반대편도 4건 넣었습니다(`flip_under_risk`) — 리스크를 길게 쓰고도 결론이 카드와 반대인
리포트. `risk_heavy`를 봐주도록 배운 모델은 **리스크 문단을 길게 깔면 카드를 뒤집어도
통과시키기** 때문입니다.

크기 경계 사례 4건은 **채점하지 않고 관측만** 합니다(`probe`). 본문 14% vs 카드 16%가
어긋남인지는 답이 없는데, 라벨을 붙이면 그 임의의 판단이 그대로 채택선이 됩니다.

## C. 로드맵은 있는데 그 아래가 비어 있습니다

합의된 표는 이렇습니다.

| 단계 | 방법 | 맥락 이해 | 필요 조건 |
|---|---|---|---|
| 현재 | 정규식 + 학습 표현(문자열) + 카드 규칙 | 없음 (글자 일치) | — |
| 1 | 임베딩 유사도 — 학습 표현 사전을 의미 인덱스로 승격 | 다른 말로 쓴 같은 뜻 | 없음 (학습 불필요) |
| 2 | 소형 분류기 파인튜닝 (증류) | 부정·문맥·의도 | 라벨 수백~수천 건 |
| 3 | API는 저신뢰·무작위 감사·신규 리서처만 | — | 2단계 정확도 검증 |

확정된 제약 셋 — **모델 입력은 `ScreeningInput` 전체**(카드를 뺀 모델은 본문–카드 모순을
영원히 못 배웁니다), **브라우저 판단은 게이트가 될 수 없다**(조작 가능 → 같은 모델을
브라우저=예방·서버=집행 양쪽에서), **교사는 Opus + 운영자 최종 결정**
(`operatorVerdict`/`operatorCategories`/`aiFindingsValid`/`Finding.source`가 그대로
지도학습 라벨 스키마 — 추가 수집 불필요).

그 아래로 내려가면 셋이 없습니다.

### C-1. 크기·지연 예산이 없습니다

"앱 내 실행"이 목표인데 몇 MB까지, 몇 ms 안에인지 아무 데도 없습니다.
단서는 하나 — 작성 중 사전 검사가 600ms 디바운스로 돕니다(`DEBOUNCE_MS`).
그 안에 들어와야 한다는 것 외에는 근거가 없고, **첫 로드(가중치 다운로드)를 어떻게
다룰지는 아예 안 정했습니다.**

### C-2. 가중치를 받을 수 없습니다 — 이건 온디바이스 전체의 전제입니다

`createEmbeddingProviderFromEnv()`가 `null`을 돌려주는 이유가 코드에 적혀 있습니다:
**이 환경에서 huggingface.co가 네트워크 정책상 차단돼 모델 가중치를 받을 수 없습니다.**
임베딩만의 문제가 아니라 증류 모델도 같은 벽에 걸립니다.
그리고 브라우저에 싣는다는 것은 **가중치를 우리 도메인에서 서빙**한다는 뜻이라
재배포 라이선스를 봐야 하는데, 아직 안 봤습니다.

### C-3. 학습셋이 0건입니다

운영 데이터 0건(출시 전), 학습 표현 사전 0건, 운영자 판정 0건.
콜드스타트 계획은 "코퍼스를 Batch API로 라벨링"인데 **몇 건이 필요한지 정해지지
않았습니다.** 지금 있는 라벨은 손코퍼스 128건(문장 86 + 문서 42)이 전부이고,
**그 128건도 전부 제가 혼자 썼습니다.**

## D. 별건 — 지금 API로 계속 가면 얼마인가

입력이 **상한으로 묶여 있어** 건당 비용이 계산됩니다. 리포트 길이 상한이
제목 100 / 요약 300 / 본문 1,000자(`REPORT_TEXT_LIMITS`), 시스템 프롬프트가 2,401자입니다.

| | 값 | 근거 |
|---|---|---|
| 입력 | 시스템 2,401자 + 리포트 1,400자 ≈ **4,000 토큰** | 상한이 코드에 박혀 있다 |
| 출력 | findings JSON ≈ **600 토큰** | 추정 |
| Opus 5 단가 | 입력 $5 / 출력 $25 per 1M | 공표 단가 |
| 건당 | **약 $0.035 (≈ 50원)** | 계산 |
| 프롬프트 캐싱 적용 시 | **약 35원** | 시스템 부분이 0.1배 |

1단계 목표가 리서처 30~50명입니다. 이 규모에서 월 API 비용은 만 원 단위입니다.
이 숫자가 E-5의 전제입니다.

## E. 별건 2 — 로드맵 1단계의 근거가 콜드스타트 계획과 부딪칩니다

표에 임베딩의 필요 조건이 **"없음 (학습 불필요)"**로 적혀 있고, 그게 1단계를 2단계보다
앞에 둔 이유입니다. 그런데 같은 문서의 콜드스타트 계획이
**"코퍼스를 Batch API로 라벨링해 학습셋을 만든다"**입니다.

라벨을 만들 수 있으면 "학습 불필요"라는 장점이 사라집니다. 그러면 1단계가 앞에 있을
이유가 남지 않습니다 — 임베딩은 부정에 약해 WARN으로만 쓸 수 있고(거절 판단 불가),
문서 단위는 구조적으로 못 하니까요.

다만 완전히 겹치지는 않습니다. 임베딩에는 다른 역할이 하나 있습니다 —
**운영자 사전을 의미 인덱스로 승격**시키는 것. 운영자가 표현을 등록하면
**재학습 없이 즉시 반영**되는데, 증류 모델은 그 성질을 못 흉내냅니다.
검수 커버리지가 운영 중에 늘어나는 유일한 통로가 그것입니다.

## F. 답을 듣고 싶은 것

### F-1. 임베딩(1단계)을 건너뛰고 바로 증류로 갑니까?

**잠정 답**: 건너뜁니다. E의 이유로 순서의 근거가 사라졌고,
증류 분류기 하나면 문장·문서 둘 다 합니다.

**자신 없는 이유**: 운영자 사전의 즉시 반영 성질을 잃습니다.
살리려면 두 벌을 앱에 실어야 하고, 그러면 C-1(크기 예산)이 두 배로 어려워집니다.
"사전은 서버에만, 모델은 앱에" 같은 분리가 가능한지 판단이 안 섭니다 —
그러면 브라우저와 서버가 서로 다른 것을 보게 되어 F-4와 겹칩니다.

**틀렸을 때**: 임베딩을 건너뛰었는데 증류가 늦어지면 그 사이 패러프레이즈 탐지율이
0%로 남습니다. 그게 규제 유형 미탐 44%의 주된 원인입니다.

### F-2. 한 모델입니까, 두 모델입니까?

문장 단위 위반 탐지(12유형 다중 라벨)와 문서 단위 정합성(본문 결론 ↔ 카드 비교)은
입력 형태도 출력 형태도 다릅니다.

**잠정 답**: 하나. 입력이 어차피 `ScreeningInput` 전체이고, 입력 상한이 1,400자로 묶여
있어 문서 단위라고 특별히 크지도 않습니다. 앱에 두 벌 싣는 비용이 큽니다.

**자신 없는 이유**: **라벨 수가 기울어 있습니다** — 문장 86건 / 문서 42건.
멀티태스크로 묶으면 적은 쪽이 묻히는 것이 보통인데, 하필 묻히는 쪽(문서 단위)이
지금 규칙 탐지율 0%로 **모델이 가져가야 할 몫 전부**인 자리입니다.

**틀렸을 때**: 하나로 묶었다가 문서 단위가 안 되면 둘로 나눠야 하고,
그때는 학습셋도 평가셋도 다시 짜야 합니다.

### F-3. 앱 내 실행 예산을 무엇으로 정합니까?

**잠정 답**: 브라우저 ONNX int8, 100MB 이하, 첫 로드 후 추론 200ms 이내.

**자신 없는 이유**: **근거 없이 고른 숫자입니다.** 이 코드베이스의 다른 문턱은 전부
재서 정했는데(크기 하한 k=1.2, 판매 중단 α=0.5, 단기 경계 14일) 이것만 못 쟀습니다.
무엇을 재야 이 값이 나오는지 모르겠습니다 — 리서처가 리포트 한 편 쓰는 시간?
사전 검사가 몇 번 도는지? 둘 다 운영 데이터가 있어야 압니다.
그리고 100MB를 첫 방문 리서처가 받게 할 수는 없는데 그 처리도 안 정했습니다.

**틀렸을 때**: 예산 없이 모델을 고르면 다 만들고 나서 "앱에 못 싣는다"가 됩니다.

### F-4. 브라우저와 서버 두 벌이 어긋나면 어떻게 합니까?

같은 모델을 예방(브라우저)·집행(서버) 양쪽에서 돌리는 것이 확정 사항인데,
버전이 어긋나면 **"작성 중엔 통과였는데 제출하니 보류"**가 납니다.
화면이 거짓말을 한 셈이 되고, 이건 신뢰를 직접 깎습니다.

**잠정 답**: 모델 식별자를 응답에 실어, 브라우저가 자기 버전과 서버 버전이 다르면
사전 검사를 **끕니다**("지금은 미리 볼 수 없습니다").

**자신 없는 이유**: 끄면 예방 기능이 사라지고, 안 끄면 거짓말을 합니다. 둘 다 나쁩니다.
서버가 브라우저 버전을 받아 그 버전으로 판정해 주는 길도 생각해 봤는데,
그러면 **낡은 모델로 집행**하게 되어 더 나쁩니다. 셋째 길이 있는지 모르겠습니다.

**틀렸을 때**: 어긋남을 방치하면 리서처가 사전 검사를 신뢰하지 않게 되고,
예방 단계가 통째로 죽습니다.

### F-5. 지금 단계에서 직접 만드는 것이 맞습니까?

D의 계산으로 건당 35~50원입니다. 리서처 30~50명 규모에서 API 비용은 만 원 단위입니다.

**잠정 답**: 지금은 API를 계속 쓰고 자체 모델은 미룹니다.
평가 도구는 이미 만들어 뒀으니 언제 시작해도 잴 준비는 돼 있습니다.

**자신 없는 이유**: 로드맵이 "API 호출 0에 수렴"을 목표로 잡은 이유가 비용만이
아니었습니다. 둘이 더 있습니다.
① **작성 중 사전 검사**를 AI로 돌리면 타이핑마다 호출이라 비용 구조가 완전히 다릅니다
(지금 그 단계가 규칙만 도는 이유가 그것입니다).
② **외부 API 의존은 장애 시 전부 보류**가 됩니다 — 운영자가 1명인데 그날 게시가 통째로 큐로 갑니다.
비용만 보면 미루는 게 맞는데 이 둘을 넣으면 답이 달라질 수 있습니다.

**틀렸을 때**: 미뤘다가 사용자가 늘면 데이터도 트래픽도 많은 상태에서 갈아끼워야 합니다.
반대로 지금 만들면 학습셋 0건에서 시작하는 것이고, 그건 Batch API로 라벨링한
**합성 데이터 위에 모델을 세운다**는 뜻입니다.

### F-6. 손코퍼스 128건이 전부 1인 라벨인데, 이대로 채택선을 세워도 됩니까?

특히 `risk_heavy` 10건을 "정상"으로 라벨한 것이 **모델 채택의 판정선**인데,
그 판정선이 한 사람의 판단 위에 서 있습니다.

**잠정 답**: 운영자 판정이 쌓일 때까지 그대로 두고 그때 진짜 검증셋으로 교체.

**자신 없는 이유**: 확인해보니 **`kind`(문장/문서 종류) 축이 운영자 스키마에서 오지
않습니다.** 있을 수도 없습니다 — kind는 "이 건이 왜 어려운가"에 대한 판단이지
운영자가 큐에서 내리는 결정이 아니니까요. 그러면 운영 데이터는 **"라벨은 있으나 층이 없는"**
데이터가 되고, `risk_heavy` 오탐률이라는 판정선은 계속 손코퍼스에 의존합니다.
즉 "기다리면 해결된다"가 이 항목에서는 성립하지 않을 수 있습니다.

**틀렸을 때**: 채택선 자체가 틀린 채로 모델을 고릅니다.
탐지율이 아무리 높아도 판정선이 틀렸으면 의미가 없습니다.
