# INTOVILL 검수 모델 4차 검토 요청 — 브라우저를 버려 블로커 절반이 사라졌는데, 그 비용이 없어진 게 아니라 서버로 옮겨왔습니다

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동 판정합니다. 적중이면 리서처에게 정산되고,
실패면 구매자에게 현금 환불되며, 그 사이 돈은 에스크로에 있습니다. 검수는 그 앞단에서
규제 위반 표현과 본문↔카드 모순을 찾아 거절하거나 보류시킵니다. 이 스레드는 **자체 검수
모델(증류)**을 만드는 스레드입니다.

3차 답변은 **두 벌**이 왔고, F-4(브라우저 폐기)는 둘 다 같은 결론이라 그대로 채택해
블로커 두 개를 지웠습니다. F-3은 **정반대**여서(마스킹 하라 / 하지 마라) 문서로 정하지
않고 스위치로 만들어 하네스에 판정을 넘겼습니다. 그리고 사용자가 "비용 최소화"를 설계
축으로 넣으라고 지시해 비용 구조를 처음으로 계산했는데, **F-4로 없앤 줄 알았던 비용이
사라진 게 아니라 형태만 바꿔 서버로 옮겨왔다는 것**을 그 과정에서 발견했습니다.

저장소 접근 없이 읽을 수 있게 필요한 수치·코드를 인라인으로 붙였습니다. 코드를 근거로
답하실 때는 인용을 요구합니다 — 여기 없는 파일 내용은 추측하지 말고 붙여 달라고 해 주세요.

> **답변 형식 요청**: 3차에 두 벌이 왔는데 두 번째가 더 유용했습니다. 이유 셋이고,
> 이번에도 같은 형식이면 좋겠습니다. ① **제가 "자신 없다"고 밝힌 지점을 직접 겨눴습니다**
> — 제가 답 못 한 "왜 처음에 브라우저를 넣었는가"에 답을 준 것이 이번 회차에서 가장
> 값어치 있었습니다. ② **미달 시 대안을 새 구조가 아니라 기존 구조 안에서** 줬습니다
> (임계값을 8차원으로 쪼개지 말고 이미 있는 위험 성격 4단계로 묶으라는 것). ③ **재지 않은
> 숫자를 주지 않았습니다** — 첫 검토는 "합산 오탐 25%"를 제시했는데, 이 저장소에는 근거
> 없는 상수를 막는 테스트가 있고 이번 회차에도 제 실수를 잡았습니다. 실측 없는 값 대신
> "무엇을 재야 하는지"를 알려 주십시오.

## A. F-4 (브라우저 온디바이스) — 폐기했습니다. 이번 회차에서 가장 큰 결정입니다

> 제안(두 번째): *"애초에 '작성 중 실시간 검사'를 고안했을 때 검사 주체는 Claude API
> (종량제 과금)였습니다. 타이핑마다 API를 태우면 파산하므로 '사용자 기기에서 공짜로
> 돌린다'는 아이디어가 나왔던 것입니다. (…) 과거 아키텍처의 잔재입니다."*

**이것이 제가 3차에서 "설명하지 못하겠다"고 적었던 바로 그 자리의 답입니다.** 전제가
소멸했는데 해법만 남아 기존 확정 사항(규칙을 브라우저에 안 넣는 이유 = 금지 목록 공개)과
충돌하고 있었습니다. 코드·문서에서 브라우저 계획을 전부 걷어냈습니다.

| 폐기로 사라진 것 | 상태 |
|---|---|
| 크기 예산 100MB·추론 200ms (1차 F-3 — 끝까지 근거가 없던 값) | **소멸** |
| 브라우저↔서버 모델 버전 동기화 (1차 F-4) | **소멸** — 판단 주체가 하나 |
| **가중치 재배포 라이선스 확인** (블로커) | **소멸** — 외부에 서빙하지 않는다 |
| 첫 로드(가중치 다운로드) UX | **소멸** |
| 가중치 역공학으로 금지 목록 유출 (3차 E-γ) | **소멸** |

남는 것은 학습용 가중치 수급 하나입니다. 계획서·`training/README.md`의 배포 절차도
"서버 전용"으로 다시 썼습니다.

## B. F-1 (임계값) — 단일로 확정, 플랜 B는 두 번째 안을 채택

**단일 임계값**으로 스윕합니다(128건에 8차원 스윕은 검증셋 과적합). 미달 시 대안은
두 번째 검토의 안을 그대로 받았습니다 — 8차원으로 쪼개지 않고 **이미 있는 위험 성격
4단계**(규제 / 소비자 / 무결성 / 품질)로 4개만 둡니다. 새 축을 만들지 않고 도메인 분류를
재사용하므로 표본이 확보되고, "규제는 보수적으로 / 품질은 엄격하게"라는 사업 논리가
그대로 붙습니다. 첫 검토의 "라벨별은 v2의 몫"보다 이쪽이 실행 가능합니다.

## C. F-2 (합산 채택선) — (ㄱ) 규칙 축소는 기각, 숫자는 박지 않았습니다

규칙은 즉시 거절 권한을 가진 **유일하게 검증된 층**이라 학생으로 교체하지 않습니다.
합산 예산은 올리되 **지금 숫자를 정하지 않았습니다** — 첫 검토가 준 "25%"는 재지 않은
값이고, 이 저장소는 근거 없는 상수를 테스트로 막습니다(이번 회차에도 제가 태그 없이 넣은
상수를 그 테스트가 잡았습니다). 개정된 채택선:

```
게이트(하네스): 학생 단독 오탐률 ≤ 교사. 그 안에서 탐지율 최대. 임계값은 단일.
함께 반드시 보고: 규칙 + 학생 합산 오탐률 (mergeFindings가 합집합이므로 실제 노출은 이쪽)
감당 한계: 고정 문턱 없음 — 그림자 모드의 실제 큐 크기를 보고 배포 직전에 확정
```

## D. F-3 (라벨 마스킹) — 두 답변이 정반대라, 판정을 하네스에 넘겼습니다

> 첫 번째: *"마스킹하지 마십시오. 라벨 노이즈를 안은 채 단일 라벨로 학습시키십시오."*
> 두 번째: *"마스킹 하십시오. `ignore_index` 처리하여 로스 계산에서 뺍니다."*

논거가 둘 다 성립해 문서로 정할 수 없었습니다. 숫자로 쓰면 이렇습니다:

| | 마스킹 OFF | 마스킹 ON |
|---|---|---|
| 양성 신호 | 73 | 73 |
| 음성 신호 | 정상 51×8 + 위반 73×7 = **919** | 정상 51×8 = **408** (위반의 511개 소멸) |
| 위험 | 겹치는 문장에 거짓 음성을 가르침 (실제 소수) | 유형 간 경계를 배울 자리가 없어 **라벨 남발 = 오탐** |

→ `train.py --mask-unlabeled` 플래그로 두고 **둘 다 돌려 오탐률이 낮은 쪽을 채택**합니다.
기본값 OFF(음성 신호가 더 귀하다는 판단). 구현 시 한 가지를 더 했습니다 — 마스킹하면
분모에서도 가린 차원을 빼야 합니다. 안 그러면 라벨이 하나뿐인 예시일수록 손실이 작아져
**적게 배웁니다**:

```python
per = (raw * m).sum(dim=1) / m.sum(dim=1).clamp(min=1.0)   # 분모도 함께 줄인다
```

## E. 이번에 새로 넘어간 주제 — 비용을 설계 축으로 넣었습니다

사용자 지시로 비용 구조를 처음 계산했습니다. 원칙은 줄이는 **순서**로 정했습니다:
① 호출을 없앤다(증류의 존재 이유) → ② 재는 것을 공짜로(대화 교사 경로) →
③ 남는 호출을 싸게(캐싱·effort) → ④ 싼 모델로 내린다(마지막, 교사는 제외).
**절대 안 하는 것**: 오탐률을 대가로 비용 줄이기.

건당 비용 (Opus 5, 입력 $5 / 출력 $25 per 1M):

| | 토큰 | 비용 | 비중 |
|---|---|---|---|
| 입력 (시스템 2,401자 + 리포트 상한 1,400자) | ≈ 4,000 | $0.020 | 57% |
| 출력 (사고 + findings JSON) | ≈ 600 | $0.015 | **43%** |

적용: 시스템 프롬프트 캐싱, 캐시 토큰 기록(사후 정산용), 비용 계산 단일화,
`effort` 상수화. **출력이 43%인데 그 크기를 정하는 `effort`가 근거 없이 `medium`으로
박혀 있었습니다** — 상수로 빼고 측정 경로를 주석에 남겼습니다(측정은 API 키 대기).

### E-1'. 캐싱은 확정이 아니라 베팅입니다

캐시 쓰기는 정가의 1.25배, 읽기는 0.1배 → **손익분기 히트율 21.7%**
(= 0.25 / (0.25 + 0.9)). TTL은 기본값(5분)을 골랐습니다 — 1시간 TTL은 쓰기가 2배라
손익분기가 52.6%로 올라가는데, 확실히 이기는 자리(평가·라벨링 연속 루프)는 5분으로도
전부 적중하므로 낮은 문턱이 맞습니다.

**운영 검수는 리서처가 게시할 때만 도는 산발적 호출이라 21.7%를 넘을지 모릅니다.**
그래서 `ScreeningUsage`에 캐시 토큰을 기록하고 평가 스크립트가 히트율·절감액을 함께
출력하게 했습니다. → G-3.

## F-α. 별건 — 서버 전용 전환이 비용을 없앤 게 아니라 형태를 바꿨습니다

F-4의 근거는 "자체 서버에서 돌리면 호출당 한계 비용이 0에 수렴한다"였습니다.
그런데 브라우저를 넣은 **원래 이유가 "타이핑마다 검사가 돈다"**였고, 그 검사는
서버로 옮겨도 사라지지 않습니다:

- 작성 중 사전 검사는 디바운스 600ms로 **타이핑하는 내내** 돕니다
- 지금은 정규식이라 서버 비용이 사실상 0이지만, 학생 모델이 들어가면
  **요청마다 신경망 추론 1회**가 됩니다
- 리서처 한 명이 리포트 한 편 쓰는 동안 몇 번 도는지 **아무도 모릅니다** (운영 데이터 0건)

즉 F-4는 "종량제 API 요금"을 "우리 서버 CPU"로 바꾼 것이지 0으로 만든 것이 아닙니다.
방향은 여전히 맞다고 보지만(자원 비용이 API 요금보다 훨씬 쌉니다), **0이라고 적으면
1차 F-3의 실수 — 근거 없는 예산 — 를 반대편에서 반복하는 것**입니다. → G-1.

## F-β. 별건 — 그림자 모드는 비용이 두 배인 기간입니다

그림자 모드는 학생을 판단만 시키고 처리 권한은 안 주는 검증 단계입니다(2차 H-3에서
"사고가 아니라 검증 성공"으로 재정의했습니다). 그런데 그 기간 동안:

- **Claude API 검수는 그대로 돕니다** (게이트가 아직 교사이므로) — 건당 $0.035 유지
- **학생 추론도 함께 돕니다** — 서버 자원 추가

즉 그림자 모드는 **비용이 가장 비싼 구간**인데, **언제 끝나는지가 정해져 있지 않습니다.**
"일치율이 쌓이면"이라고만 적혀 있고 그 문턱도, 최소 표본도, 최대 기간도 없습니다. → G-2.

## G. 답을 듣고 싶은 것

### G-1. 사전 검사의 서버 추론 부하를 무엇으로 예산화합니까?

**잠정 답**: 예산을 숫자로 정하지 않고, **부하를 만드는 구조를 먼저 바꾼다** — 사전
검사에서는 학생을 돌리지 않고 지금처럼 규칙만 돌리고, 학생은 **제출 시 집행에서만**
쓴다. 그러면 호출 수가 "타이핑 횟수"가 아니라 "게시 횟수"에 비례해 예측 가능해집니다.

**자신 없는 이유**: 그러면 **작성 중 사전 검사의 커버리지가 지금 그대로**입니다 —
패러프레이즈 탐지율 0%. 리서처는 제출하고 나서야 학생이 잡은 것을 알게 되는데,
사전 검사를 만든 이유가 정확히 그 왕복(제출→보류→수정→재제출)을 없애는 것이었습니다.
비용을 아끼려다 기능의 목적을 되돌리는 것 아닌지 판단이 안 섭니다. 절충으로 "타이핑
중에는 규칙, 저장·미리보기 같은 명시적 순간에만 학생"도 생각했는데, 그러면 사용자가
**언제 검사가 도는지 모르는 상태**가 됩니다.

**틀렸을 때**: 사전 검사에 학생을 넣었다가 부하가 감당 안 되면 리서처 수가 늘수록
작성 화면이 느려지고, 그건 공급(1단계 최우선 목표)을 직접 깎습니다. 반대로 안 넣으면
학생이 메우기로 한 몫의 절반(예방)이 배포 후에도 비어 있습니다.

### G-2. 그림자 모드의 졸업 조건을 무엇으로 정합니까?

**잠정 답**: 정하지 못했습니다. 후보는 셋인데 전부 문제가 있습니다 —
① **표본 수**(예: 판정 200건) → 숫자의 근거가 없습니다.
② **교사와의 일치율**(예: 95%) → 학생이 교사를 흉내내는 정도일 뿐이고, 교사 자체의
정확도는 별개입니다. 게다가 일치율이 높을수록 학생을 쓸 이유가 커지는 게 아니라
**교사를 계속 써도 되는 이유**로도 읽힙니다.
③ **운영자 판정과의 일치율** → 가장 옳은 잣대인데, 운영자 판정은 보류된 건에만 생겨
표본이 편향돼 있습니다(통과한 건에는 라벨이 없습니다).

**자신 없는 이유**: 이 셋이 재는 것이 서로 다른데 어느 것이 "실권을 줘도 되는가"에
답하는지 모르겠습니다. 그리고 졸업 조건이 없으면 그림자 모드가 **영구히 지속되는 것이
기본값**이 되는데, 그 상태가 비용이 가장 비싼 상태입니다.

**틀렸을 때**: 너무 일찍 졸업하면 검증 안 된 모델이 게이트에 서고(오탐 = 리서처 이탈),
너무 늦으면 API 비용과 서버 비용을 동시에 내면서 학생이 메우기로 한 이득을 하나도
못 받습니다.

### G-3. 캐싱을 측정 전까지 켜 둡니까, 꺼 둡니까?

**잠정 답**: 켜 둔다. 최악(전부 캐시 미스)이 **+6.4%**이고 최선(전부 히트)이 **−23%**라
비대칭이 유리한 쪽입니다. 계산 근거는 시스템 프롬프트가 입력 4,000토큰 중 약 1,800이고,
미스는 그 1,800에 0.25배 가산, 히트는 0.9배 감산입니다.

**자신 없는 이유**: 이 비대칭 계산은 **켜 두는 것이 이익이라는 근거가 아니라 손실이
작다는 근거**일 뿐입니다. 그리고 실제 게시 빈도를 모르는 상태에서 히트율을 추정할 수가
없습니다(1단계 목표가 리서처 30~50명인데 하루 몇 편이 올라오는지는 운영 전이라 미지).
캐시가 붙어 있으면 프롬프트를 고칠 때마다 캐시가 깨진다는 것도 운영상 성가신 지점입니다.

**틀렸을 때**: 켜 둔 채 미달이면 건당 6.4%를 낭비하는데, 이 규모(월 만 원대)에서는
금액이 무의미합니다. 오히려 진짜 위험은 **캐시 히트를 전제로 프롬프트를 길게 쓰는
습관**이 드는 것이라고 생각하는데, 이게 실제 위험인지 기우인지 모르겠습니다.

### G-4. 비용 관점에서 `effort`를 내리는 실험을 언제 합니까?

**잠정 답**: 교사 기준선을 API로 처음 잴 때 **같은 코퍼스에 effort만 바꿔 두 번** 돌린다
(medium / low). 비용 차이와 탐지율·오탐률 차이를 같은 표에 놓고 고른다.

**자신 없는 이유**: 두 번 돌리면 측정 비용이 두 배입니다(문장 86 + 문서 42 = 128건 ×
2회 ≈ $9). 금액은 작지만, **교사 기준선은 이 스레드의 모든 채택선이 걸린 값**이라
effort를 바꿔 두 벌을 재면 "어느 쪽이 그 기준선인가"가 애매해집니다. 낮은 effort로
잰 교사를 기준선으로 삼으면 학생의 천장도 함께 낮아지는데, 그게 절약인지 자해인지
구분이 안 섭니다.

**틀렸을 때**: 안 재면 비용의 43%를 정하는 값이 영원히 근거 없이 남습니다.
잘못 재면 천장을 스스로 낮춘 채 학생을 그 아래에서 평가하게 됩니다.

## 참고 — 지금 상태

시험 **1,250건 통과** · 타입체크 통과 · 규칙 기준선(탐지 53.8% / 오탐 17.6% /
즉시 거절 오탐 0건) 변화 없음. 검수 판정 로직은 이번에도 건드리지 않았습니다.

이번 회차에 바뀐 것:
- `claudeScreener.ts` — 시스템 프롬프트 캐싱(`cache_control`), `EFFORT` 상수화, 캐시 토큰 기록
- `screener.ts` — `ScreeningUsage`에 캐시 토큰 추가, `screeningCostUsd()` 단일 계산
- `evalTeacher.ts` — 비용·캐시 히트율·손익분기 판정 출력
- `train.py` — `--mask-unlabeled`(분모 보정 포함)
- `docs/model-plan.md` — 서버 전용 확정, 채택선 개정, 3차 반영 표, 비용 설계 절
- `training/README.md` — 배포 절차를 서버 전용으로 재작성

**부수 발견**: 비용 상수(`TOKEN_PRICE_USD_PER_M`)를 근거 태그 없이 넣었다가 저장소의
상수 근거 테스트에 걸렸습니다. 이 저장소에는 "근거 없는 숫자는 테스트가 막는다"는
장치가 있고, 그것이 제 손을 잡은 것이 3차의 "25%"를 받지 않은 이유와 같은 것입니다.

코드 밖 블로커:
- **`ANTHROPIC_API_KEY` 미설정** — 유효한 교사 기준선 0건. G-4가 여기 걸려 있습니다.
- **모델 가중치 수급** (개발 환경에서 huggingface.co 차단) — 학습용으로만 남았습니다.
  ~~재배포 라이선스~~는 F-4로 소멸했습니다.
- **운영 데이터 0건** — G-1(사전 검사 호출 빈도)·G-2(그림자 모드 표본)·G-3(캐시 히트율)이
  **전부 여기 걸려 있습니다.** 이번 회차 질문 넷 중 셋이 같은 블로커를 공유합니다.

## 검수 모델 스레드에서 이미 답이 난 것 (이번 회차에 걸리는 줄만)

| 결론 | 근거 |
|---|---|
| 오탐(정상 차단)이 미탐보다 비싸다 | 미탐은 에스크로 환불로 되돌아오고, 오탐으로 떠난 리서처는 돌아오지 않는다 |
| 비용을 아끼려고 오탐률을 올리지 않는다 | 오탐 1건(리서처 이탈)이 API 호출 수천 건보다 비싸다 |
| 자동 거절 권한은 결정적 규칙에만 | 오탐률이 검증된 유일한 층. 규칙을 학생으로 교체하지 않는다 (3차 F-2) |
| 검사는 서버에서 돈다 | 브라우저에 넣으면 금지 목록이 공개된다 — 가중치는 정규식보다 역공학이 쉽다 |
| 모델은 서버 전용 | 3차 F-4 확정. 크기 예산·버전 동기화·재배포 라이선스가 함께 소멸 |
| 근거 없는 숫자를 상수로 박지 않는다 | 테스트가 막는다. 못 대면 `constants-debt.txt`에 빚으로 올린다 |
| 평가는 동결된 Ground Truth 위에서만 | 대화 라벨은 학습 생산 전용 — 도구가 강제한다 (2차 H-2) |
| 채택은 val F1이 아니라 하네스로 | 학생 단독은 게이트, 규칙+학생 합산은 반드시 함께 보고 (3차 F-2) |

## 회차 기록 (검수 모델 스레드)

| 회차 | 지적 | 결과 |
|---|---|---|
| 2 | 대화 라벨을 학습셋에 섞어라 + 롤백 플래그 | 부분 — 결론·플래그 채택, "노이즈가 증강"이라는 근거는 기각 |
| 2 | 평가셋을 동결하고 대화 경로에 태우지 마라 | 채택 후 더 밀고 감 — 규율 대신 도구가 막게, 동결 86 → 128건 |
| 2 | 그림자 모드 실패는 사고가 아니라 검증 성공이다 | 채택 — 비용 인식 하나가 바뀌자 배포 계획의 성격이 바뀌었다 |
| 3 | **브라우저는 과거 아키텍처의 잔재다** | 채택 — **이 스레드 최대 수확.** 블로커 두 개와 근거 없던 예산이 함께 소멸 |
| 3 | 임계값 미달 시 위험 성격 4단계로 묶어라 | 채택 — 새 축을 만들지 않고 있는 분류를 재사용하는 안 |
| 3 | 합산 오탐률 상한을 25%로 | 기각(숫자만) — 재지 않은 값이라 상수 근거 테스트에 걸린다. 그림자 모드 실측으로 미룸 |
| 3 | 마스킹 하라 / 하지 마라 (두 답변 충돌) | 보류 — 스위치로 만들고 하네스가 판정 |

여기서 배운 것 셋.

**내가 "모르겠다"고 적은 자리가 가장 값어치 있는 답이 온 자리다.** 3차에서 유일하게
자신 없다고 밝힌 "왜 브라우저를 넣었는지 설명 못 하겠다"에 답이 왔고, 그 답 하나가
블로커 두 개를 지웠다. 모르는 것을 숨기지 않고 적는 것이 요청서의 값을 정한다.

**답이 갈리면 문서가 아니라 스위치로 만든다.** 두 검토가 정반대일 때 한쪽을 고르면
그 선택의 근거가 "누구 말이 더 그럴듯한가"가 된다. 플래그로 두면 근거가 측정이 된다.

**비용을 없앴다고 적기 전에 어디로 갔는지 본다.** 브라우저를 버려 API 요금이 사라진 게
아니라 서버 자원으로 옮겨왔다. "0에 수렴"은 1차 F-3의 근거 없는 예산과 같은 종류의 문장이다.
