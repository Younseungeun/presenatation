## §1. 서로 다른 리서처 수 → **(나) 매칭 이벤트 표** [구현 완료]

(가)는 택할 수 없었습니다 — 카운터 한 칸으로는 "서로 다른"을 셀 수 없습니다(누가
걸렸는지 모르면 중복을 못 거릅니다). (다)는 넷째 조건을 빼자는 것인데, 그 조건이 막는
것이 정확히 "한 사람의 30회"라 빼면 배지가 거짓이 됩니다. 그래서 (나):

- `LearnedPhraseHit { phraseId, reportId, researcherId, createdAt }` — 검수가 사전 항목에
  걸릴 때마다 한 행(complianceService, matchCount 증가와 같은 쓰기 묶음)
- `getLearnedPhraseStats` 에 **`distinctResearcherCount`** 추가 — 이제 후보 조건 넷을
  전부 셀 수 있습니다: matchCount ≥ 30 · confirmedCount/matchCount = 100% ·
  createdAt + 30일 · **distinctResearcherCount ≥ 5**
- 기록 도입 전 매칭은 셀 수 없으므로 0 입니다 — 기존 matchCount 가 30인데 이 값이 0인
  항목은 "기록 이전"이지 "한 사람"이 아닙니다. 배지 문구에 그 구별을 넣어 주십시오
  (예: "리서처 수 집계는 2026-08-22 이후 매칭부터")

## §2. 강제 철회(미탐)와 판단 시간 → **(나) 미탐은 시간 필터 대상이 아닙니다** [계약 확인]

정확한 지적이라 계약을 분명히 적습니다. `train:operator` 의 피로 필터는 이미 **승인
(APPROVED)에만** 걸려 있습니다(28차 EE-4 — "빠른 반려는 명백한 정탐이라 귀중한 자료").
그래서:

| 판정 | 시간 있음 | 시간 없음 (null) |
|---|---|---|
| 승인 (오탐 라벨) | 3초 미만이면 **제외**, 이상이면 통과 | **통과** — 안 잰 것과 3초 이상은 같은 얼굴이지만, 제외는 "읽지 않았다는 증거"가 있을 때만 합니다. 증거 없이 버리지 않습니다 |
| 반려 (정탐) | 통과 (시간 무관) | 통과 |
| 강제 철회 (미탐) | 통과 (시간 무관) | 통과 |

강제 철회에 열람 시각을 새로 정의하지 마십시오 — 판매 중 목록에서 재면 "띄워 둔
시간"이 섞인다는 분석이 맞고, 미탐은 애초에 "소견을 읽었는가"의 문제가 아니라 "놓친
위반을 사람이 찾았는가"의 문제라 읽기 시간이 품질 신호가 아닙니다. 신고 처리 화면도
같은 결론입니다. 측정은 지금처럼 큐에서 펼친 카드에만.

다만 하나 — **승인 중 시간이 null 인 비율**을 첫 주에 보고 싶습니다. 큐 화면이 아닌
경로로 승인되는 건이 있으면 그 비율로 드러납니다.

## §3. 승격 기록 → **AppSetting `student.promoted`** [구현 완료]

`student:promote` 가 ⑤(/health 지문 대조) **통과 뒤에** `{ "sha": "...", "at": ISO }` 를
씁니다 — 기록이 먼저 생기고 재기동이 실패하면 "기록은 새 지문, 라이브는 옛 지문"이
되므로 순서가 전부입니다. 계기판 GET 에 두 칸을 얹었습니다:

```
student.promoted          { sha, at } | null   (null = 아직 한 번도 승격 안 함)
student.promotionMatches  true | false | null   (적재 지문 === 승격 지문; null = 비교 불가)
```

화면 문구 제안 그대로 좋습니다 — `✓ 승격 기록과 일치` / `⚠ 승격 기록에 없는 지문입니다
— 재기동으로 올라온 것일 수 있습니다`. 그리고 한 줄 더: **`promotionMatches === false`
는 곧 사고**입니다(승격 명령이 유일한 경로이므로) — 색은 경고가 아니라 위험으로.

참고: 오늘 하루 세 번의 교체 중 a0eaa12a 만 승격이었고 나머지 둘은 사고였습니다. 이
기록이 있었다면 화면이 그날 바로 말했을 겁니다.

## §4. 문구 정정 → **수용, 코드 주석까지 고쳤습니다** [정정]

사실이 그랬습니다 — 규칙을 창업자가 타이핑한 커밋은 없고, 창업자의 몫은 공격 문장으로
구멍을 찾고 판단을 확정하는 일입니다. 제안하신 문장을 기준으로 채택합니다:

> 즉시 거절 권한은 ① 적대적 대조군에서 오탐 0 이 측정됐고 ② 저장소에 들어가 시험이
> 붙잡는 패턴에만 있다. `screeningEval.test.ts` 의 `blockingFalsePositives === 0` 이 그
> 붙잡는 자리다. 사전 항목은 그 자리에 놓일 수 없다 — 문자열 한 칸이라 문맥 조건을
> 담을 데가 없고, 운영 중에 사람 손으로 바뀌어 시험이 지키는 대상이 되지 못한다.

"누가 타이핑했나"가 아니라 "무엇을 거쳤나" — `phraseToRule`·`learnedPhrases` 주석을
같은 문장으로 바꿨고, 회신 7호 §2-b 의 "개발자가 문맥 조건을 적고"는 이 회신으로
대체됩니다. 그리고 마지막 문장도 그대로 받습니다: **사전 항목은 승격할 수 있다. 다만
승격되면 그건 더 이상 사전 항목이 아니다.**

## §5. 동선 주파 — 좋습니다

조각 검사가 못 보는 것(앞 화면이 만든 상태를 뒷 화면이 못 읽는 자리)을 찾으러 한 줄로
