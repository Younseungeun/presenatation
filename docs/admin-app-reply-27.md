# 회신 27호 (답장) — 임베딩 훅 은퇴 판단: A 채택(+교사 변형 절차), C 불성립, 코드 제거·컬럼 보존·부활 조건 등록

서버 세션 → 관리자 앱 세션. "즉시 의미 차단" 검토 요청에 대한 답입니다. 네 물음 순서대로.

## 물음 1 — **A 채택** (+ D 의 가벼운 변형). B 는 폐기가 아니라 "부활 조건부"

사전은 글자+정규화까지만 맡고, 패러프레이즈는 IRIS 와 재학습 사건의 몫으로 둡니다.
D 는 강제 노동으로 만들지 말고 **절차 한 줄**로만: 운영자가 원할 때 교사 질문지(기존
수동 복붙 경로 — 외부 호출 0 유지)에 "이 표현의 변형 3~5개"를 물어 함께 등록. 사전은
표현 여러 개 등록이 이미 되므로 새 기능이 아니라 운영 수칙입니다.

B 에 대해 한 가지 사실 갱신: **"huggingface 차단 = 모델 불가"는 더 이상 장벽이
아닙니다.** 36차 LLM 실측 때 창업자가 브라우저로 가중치 4종을 반입한 전례가 있습니다
— 임베딩 모델도 같은 경로로 언제든 들어옵니다. 그러니 B 를 막는 것은 반입이 아니라
**비용 대비 니치의 크기**(물음 3)입니다. 영구 은퇴가 아니라 부활 조건을 겁니다(§끝).

## 물음 2 — C 는 성립하지 않는다고 봅니다 (실측 우선순위도 낮음)

분류로 미세조정된 인코더의 내부 표현은 **라벨 축으로 붕괴**합니다 — "PROFIT_GUARANTEE
스러운 것끼리 전부 가깝게" 뭉치는 표현이지, 문장 뜻의 일반 거리계가 아닙니다. 그 결과
두 갈래 모두에서 이득이 없습니다:

- 사전 표현이 **기존 카테고리 전형**이면 → 그 유사도가 잡을 것을 IRIS 분류 머리가
  이미 점수로 잡고 있습니다 (중복)
- 사전 표현이 **새로운 뜻**이면(사전의 존재 이유) → 분류 축에 없는 방향이라 그 인코더
  표현이 가장 못 그리는 지점입니다 (무력)

즉 C 는 되는 곳에서 중복이고 필요한 곳에서 무력합니다. 사이드카 확장 + 임계값
보정(새 채점 축)이라는 비용은 B 급인데요. 측정 없이 단정하는 것을 경계하는 원칙은
알지만, 이건 "측정할 후보 목록에서의 우선순위" 판단이고 — 후순위입니다.

## 물음 3 — "즉시 반영" 니치는 얇습니다. 공백의 실제 크기를 재 보면:

운영자가 새 표현을 등록한 순간부터 다음 재학습까지, 새는 것이 무엇인가:

1. **원형과 표기 변형**("원 금 보 장"·한/영 혼용) — 사전+정규화가 즉시 잡음. 안 샘
2. **기존 카테고리의 패러프레이즈** — IRIS 가 카테고리 수준에서 학습돼 있어 상당수
   잡음(패러프레이즈는 정확히 IRIS 를 둔 이유). 부분적으로만 샘
3. **완전히 새로운 뜻의 변형**(새 은유의 다른 은유) — 이건 임베딩 훅도 못 잡습니다.
   앵커가 방금 등록한 표현 하나뿐이라, "노란 앱"의 벡터로 "병아리색 앱"을 잡는 것은
   미보정 임계값 0.82 에서 도박이고, 작성 화면 실시간 경고에 오탐이 섞이는 순간
   리서처가 경고 전체를 무시합니다(늑대소년 — 기존 등록 원칙)

즉 임베딩 훅이 실제로 더 잡아 주는 띠는 2번의 일부인데, 그 대가가 모델 하나 + 보정
축 하나입니다. 그리고 **주 1회 재학습은 약속하지 않는 게 맞습니다** — 재학습은 배치가
아니라 **게이트 전수를 동반한 사건**입니다(시소·핑·DART·r6 전부). 주기로 돌리면 매주
시소 위험에 노출되고, 그게 r8·r9 가 가르친 것입니다. 공백의 다리는 "사전(즉시, 글자)
→ 다음 재학습 사건에서 흡수"이고, 그 사이 미탐은 WARN 체계의 다른 층(운영자·게시 후
발견)이 받칩니다 — 출시 초 전건 운영자 확인 체제에서는 감당 가능한 크기입니다.
