# INTOVILL 40차 검토 요청 — 계좌 관문을 세웠습니다

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동으로 판정합니다. 적중이면 리서처에게
정산되고, 실패면 구매자에게 **현금 환불**됩니다. 그 사이 돈은 에스크로에 있습니다.

39차 답변대로 `PayoutAccount`를 세웠습니다. **결론은 전부 채택했는데, D의 근거 하나는
바로잡아야 합니다** — 그것이 "무엇을 절대 약화시키면 안 되는가"를 정하기 때문입니다.

---

## A. D 채택 — 다만 **탈취를 막는 것은 실시간 조회가 아닙니다**

지시서에 계좌를 박지 않는 결론은 전면 채택했습니다. 이유 두 가지 중 **하나는 그대로
맞습니다**: 해지하고 갈아탄 계좌로 보내면 100% 이체 실패이고 그 뒤처리가 더 복잡합니다.

**그런데 탈취 논거는 뒤집혀 있습니다.**

> 해커가 계좌를 변경했을 때 과거 지시서들이 변경된 계좌로 무비판적으로 흘러가거나
> **(스냅샷 부재)**, 혹은 정상 계좌로 돌려놓았음에도 스냅샷이 찍힌 지시서가 해커
> 계좌로 들어가는

앞 절은 **실시간 조회의 실패 모드**이고 뒷 절은 **스냅샷의 실패 모드**입니다.
즉 **둘 다 그 자체로는 탈취를 못 막습니다.** 실시간 조회를 택해도, 탈취자가 자기
계좌로 바꾸면 그 계좌로 나갈 뿐입니다.

**실제로 막는 것은 따로 있습니다** — 그리고 지금 셋 중 둘만 있습니다:

| 겹 | 무엇을 하나 | 지금 |
|---|---|---|
| ① 바꾸면 **즉시 미검증** | 미검증에는 한 푼도 안 나간다 | **있음** |
| ② **변경 쿨다운 48시간** | 그 사이 본인 알림이 가서 "내가 안 바꿨다"고 말할 창이 생긴다 | **있음** (신설) |
| ③ 예금주명 ↔ **본인 인증 실명** 대조 | 탈취자 계좌는 이름이 다르므로 영영 검증 안 된다 | **없음** |

③이 없는 이유는 E-1 순서대로 **실명을 아직 저장하지 않기** 때문입니다. 그래서
**지금 `VERIFIED`는 "계좌가 실재한다"까지만 뜻합니다.** 이 사실을 이름으로 감추지
않으려고 주석·오류 문구·시험이 그대로 말하게 했습니다 —
`'본인 실명을 모르면 대조하지 않고 통과시킨다 (실명 보유 확정 전)'`.

**이 정리가 중요한 이유**: 근거를 "실시간 조회"에 두면 ②·③을 나중에 협상 가능한
장식으로 여기게 됩니다. 실제로는 그 둘이 방어의 전부입니다.

- **A-질문.** ②의 48시간이 맞습니까? 근거를 "사람이 알림을 보고 반응하는 시간"으로
  잡아 정산 쿨다운과 같은 계산을 썼는데(알림을 못 본 하루를 흡수하고도 하루),
  **금융권 관행이 따로 있으면** 그쪽이 낫습니다. 그리고 쿨다운 동안 **리서처에게
  무엇을 보여줘야** 합니까 — "48시간 뒤 지급됩니다"인지, 아니면 변경 사실 자체를
  강조해 "본인이 바꾼 게 맞습니까"를 물어야 하는지.

## B. 만든 것

```
model PayoutAccount {
  researcherUserId  String   @unique      // 사람당 하나
  bankCode          String
  accountNumberEnc  String                // AES-256-GCM
  accountLast4      String                // 화면·감사용 — 복호화 없이 "어느 계좌인가"에 답한다
  holderName        String?               // 은행 조회 응답으로만 채운다
  status            String                // UNVERIFIED | VERIFIED | HOLDER_MISMATCH
  changedAt         DateTime              // 변경 쿨다운 기산점
}
model PayoutAccountHistory { ... }         // 덧붙이기만
```

- **관문은 한 곳**: `assertPayoutAccountReady`를 지급·보상 실행 직전에 부릅니다.
  지시서 상태는 **하나도 안 늘렸습니다**
- **암호화는 AES-256-GCM** — 해시가 아닌 이유는 **은행에 그 값을 그대로 보내야** 하기
  때문이고, GCM인 이유는 인증 태그가 조작을 탐지하기 때문입니다. CBC였다면 바꿔치기된
  암호문이 **그럴듯한 쓰레기를 내놓고 그게 은행으로 갑니다.** 지키는 범위는
  **DB·백업 유출**까지입니다 — 앱이 털리면 키도 털립니다
- **이력은 덧붙이기만**(권고 채택). 감사 로그와 따로 둔 이유: 저쪽은 **사건**의 순서,
  이쪽은 **값**의 이력입니다. 계좌번호를 감사 로그 JSON에 넣으면 검색도 안 되고
  파기 요청이 왔을 때 지울 자리가 흩어집니다

**관문을 붙이자 지급을 시험하던 파일 셋과 리허설이 한꺼번에 깨졌습니다.**
그게 관문이 빠짐없이 걸렸다는 증거라, 리허설에는 **계좌 등록 단계를 넣었습니다** —
없으면 리허설이 실제 운영과 어긋납니다.

## C. 답을 듣고 싶은 것

- **C-1. 키 관리.** `PAYOUT_ENC_KEY`를 환경 변수로 두고 운영에서 없으면 기동 실패시킵니다.
  그런데 **키 교체(rotation)** 설계가 없습니다 — 지금 키를 바꾸면 기존 암호문이 전부
  못 읽힙니다. 초기 규모에서 미리 만들 값어치가 있습니까, 아니면 **"키를 바꿔야 하는
  날 = 유출된 날"이니 그때는 계좌를 전부 재등록시키는 것**이 더 정직합니까?
  저는 후자로 기울지만, 그러면 사고 시 리서처 전원이 재인증하는 비용이 듭니다.
- **C-2. 계좌 없는 리서처의 판정.** 지금은 **판정·정산 지시서 생성까지는 그대로 되고
  실행만 막힙니다.** 그런데 계좌가 없는 사람의 카드가 계속 팔리는 것이 맞습니까?
  게시 관문에서 계좌를 요구하면 "돈 받을 준비가 된 사람만 판다"가 되지만,
  **아직 한 푼도 못 번 신규 리서처에게 계좌부터 요구하는 것**이 진입 장벽입니다.
  저는 지금처럼 **실행에서만** 막는 쪽이 맞다고 보는데, 그러면 지시서가 쌓인 채
  방치될 수 있어 **알림·큐가 필요합니다.** 어느 쪽입니까?
- **C-3. 미실행 지시서의 노화.** C-2와 이어집니다 — 계좌 미등록으로 멈춘 지시서에
  **시한이 있어야 합니까?** 구매자 환불에는 16일 절대 시한이 있는데, 리서처 지급에는
  아무 시한이 없습니다(우리가 늦추는 것이 아니라 본인이 계좌를 안 낸 것이라).
  방치하면 장부에 영원히 남고, 시한을 두면 **받을 돈을 소멸시키는 것**이라
  약관 문제가 됩니다. 관행이 어떻게 됩니까?
- **C-4. 다음은 어디입니까?** 남은 후보 셋 — ① **회계 마감**(월별 "들어온 돈 − 나간 돈
  = 남아 있어야 할 돈") ② **상수 근거 태그 래칫**(39차 B에서 합의한 것, 미착수)
  ③ **컴플라이언스 2단계**(소형 분류기 증류 — AI를 게이트에서 감사자로 강등).
  저는 ②가 가장 싸고 ①이 가장 급하다고 보는데, ①은 **실거래가 없어 지금 맞춰 볼
  장부가 없습니다.** 그러면 ②를 먼저 하고 ①은 토스 실키 이후가 맞습니까?
