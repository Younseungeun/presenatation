# INTOVILL 인증 축 검토 요청 — 생체 로그인을 붙였습니다. 그런데 **구멍을 하나 만들었습니다**

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드를 걸고 리포트를 팔면 시한에
시장 데이터가 자동 판정하고, 적중이면 리서처에게 정산되고 실패면 구매자에게 현금
환불됩니다. 그 사이 돈은 에스크로에 있습니다.

**43차로 운영 로직 검토는 닫았습니다.** 이건 그 뒤에 새로 만든 **인증 축**이라 별건으로
드립니다. 재개 조건 중 "돈이 나가는 경로를 새로 열 때"에 해당한다고 봤습니다.

---

## 0. 한 장 요약 — 도둑이 돈을 빼려면 지나야 하는 문

| | 문 | 무엇이 확인하나 | 누가 보증하나 |
|---|---|---|---|
| 1 | 계정 로그인 | 본인 인증 **또는** 생체(패스키) | 통신사 / 기기 |
| 2 | 계좌 변경 — 재인증 | 인증의 CI가 **계정 주인의 것인가** | 통신사 |
| 3 | 계좌 변경 — 이름 대조 | 통신사 이름 == **은행 예금주 이름** | 은행 |
| 4 | 48시간 쿨다운 | 그 사이 본인이 멈출 수 있다 | — |
| 5 | 정산 동결 | 본인이 건다 / **운영자만 푼다** | — |

**이름은 우리가 만들지 않습니다.** 통신사와 은행이 각각 준 이름을 맞출 뿐이고, 사용자가
입력하는 것은 은행·계좌번호뿐입니다(예금주 이름 입력란을 두지 않습니다 — 두면 양쪽을 다
본인이 적는 것이라 대조가 아니라 받아쓰기가 됩니다).

## 1. 이번에 만든 것 — 생체 로그인 (패스키 / WebAuthn)

### 왜 만들었나

지금까지 로그인은 **매번 본인 인증**이었습니다. 실공급자를 붙이는 순간 그것이 앱을 열
때마다 나가는 비용이 되고, 사용자는 매번 이름·번호를 적습니다.

그리고 방어의 축이 하나 늘어난다고 봤습니다. **본인 인증도 문자 알림도 폰 번호에 걸려
있어** 유심을 가로채이면 함께 무너지는데, 패스키는 기기 안의 열쇠라 번호와 무관합니다.

### 정한 것

```
평소 로그인       생체(패스키)           공짜·1초
계좌 등록·변경    본인 인증 + 은행 대조   여기만 무겁게
```

**패스키는 계좌 변경을 대신하지 못합니다.** "같은 기기"를 증명할 뿐 **이름을 모르고**,
은행이 돌려주는 예금주명과 맞춰볼 상대편이 없기 때문입니다.

구현 선택 몇 가지와 이유:

- `authenticatorAttachment: 'platform'` — 기기 내장만. USB 보안키까지 열면 "지문으로
  간편하게"라는 목적에서 멀어지고 분실 복구 경로가 하나 더 늘어납니다
- `userVerification: 'required'` — 지문·얼굴·기기 PIN 중 하나를 반드시 거칩니다.
  없으면 잠금 해제된 기기를 집어든 사람이 그대로 로그인합니다
- `attestationType: 'none'` — 제조사 증명을 안 받습니다. 검증 부담과 기기 식별
  개인정보만 늘고, "어느 회사 칩인지"로 우리가 결정할 일이 없습니다
- 로그인 시작에 `allowCredentials`를 **비웁니다** — 채우면 "이 사람이 가입돼 있다"가
  응답만으로 드러납니다. 실패 사유도 뭉뚱그립니다
- 챌린지는 **DB에 1회용**으로 두고 `deleteMany`의 반환 건수로 소비를 판정합니다
  (조회 후 삭제로 나누면 두 요청이 같은 챌린지를 동시에 통과합니다)
- **서명 검증은 직접 구현하지 않았습니다** — CBOR·COSE·서명 분기에서 실수하면
  틀린 서명을 통과시키면서도 테스트는 초록불입니다. `@simplewebauthn/server`를 씁니다

## 2. **제가 만든 구멍 — 설계와 구현이 어긋났습니다**

사용자와 설계를 이야기하면서 제가 이렇게 말했습니다:

> "패스키는 등록·복구 경로만큼만 강합니다. **계정을 쥔 탈취자가 자기 기기의 패스키를
> 새로 등록할 수 있으면 이 모든 게 0이 됩니다.** 그래서 패스키 등록·재등록은 본인
> 인증으로 잠가야 합니다."

**그렇게 말해 놓고 구현하지 않았습니다.** 지금 `/api/passkey/register`는 **세션만 있으면
통과합니다.**

### 다만 크기를 정확히 적습니다 — **이 구멍으로 돈은 나가지 않습니다**

처음에 이 대목을 "돈이 새는 구멍"처럼 적었다가 고쳤습니다. 사실은 이렇습니다:

```
세션을 쥔 사람이 할 수 있는 것    패스키를 하나 심는다
그래서 얻는 것                    영구적인 로그인 수단
그래도 못 하는 것                 **계좌 변경** — 본인 인증 + 은행 이름 대조가 막는다
```

계좌 등록은 **본인 인증 결과를 필수 인자로 요구**합니다(없으면 컴파일이 안 됩니다).
그래서 이 구멍의 정확한 크기는 **"임시 접근이 영구 접근으로 승격된다"**이고,
돈에는 닿지 않습니다.

### 그리고 세션을 훔치는 것 자체가 좁은 경로입니다

이 서비스는 비밀번호가 없고 로그인이 본인 인증이라, 세션이 새는 길은 이것뿐입니다:

| 경로 | 전제 |
|---|---|
| 인포스틸러 악성코드가 쿠키 파일을 빼감 | PC 감염 |
| 잠금 풀린 기기를 손에 넣음 | 물리적 접근 |
| 공용 PC에서 로그아웃 안 함 | 물리적 접근 |
| XSS | 쿠키가 `httpOnly`라 **읽지는 못함** |

즉 "통신사를 속인다"(유심 스와핑)보다 **한참 좁습니다.** 그래서 이것은 **급한 구멍이
아니라 값싸게 막을 수 있는 승격 경로**입니다 — 그 크기로 판단해 주십시오.

막을 값어치가 있다고 보는 이유는 하나입니다: 감염된 PC에서 한 번 세션이 새면,
악성코드를 지우고 나서도 **심어 둔 패스키는 남습니다.**

- **질문 A.** 제 처방은 **"최근성 요구"**입니다: 패스키 등록은 **최근 N분 이내에 본인
  인증을 통과한 세션**에서만 허용하고(세션에 인증 시각을 남깁니다), 오래됐으면 그 자리에서
  다시 인증시킵니다. N은 5~10분을 봅니다.
  이 방향이 맞습니까? 아니면 **첫 등록만 예외**로 두고(가입 직후라 방금 인증했으므로)
  두 번째 이후는 무조건 재인증이 더 단순합니까? 저는 후자가 규칙은 단순하지만
  "가입하고 한 달 뒤 처음 등록하는 사람"이 예외로 새는 것이 걸립니다.

## 3. 그리고 더 근본적인 것 하나 — **두 경로 중 약한 쪽이 강도를 정합니다**

패스키를 붙이면서 제가 "방어 축이 하나 늘었다"고 적었는데, **다시 보니 정확하지
않습니다.**

```
로그인하는 길이 둘이 됐다:
   ① 생체(패스키)   — 기기가 있어야 함
   ② 본인 인증      — 폰 번호가 있어야 함

도둑은 **둘 중 쉬운 쪽**을 고른다.
```

유심을 가로챈 공격자는 ②로 그냥 들어옵니다. 패스키가 있든 없든 상관없습니다.
**즉 패스키는 보안을 올린 것이 아니라 편의를 올린 것**이고, 계정 진입의 강도는
여전히 "본인 인증만큼"입니다.

정말 강도를 올리려면 "패스키가 등록된 계정은 본인 인증만으로 로그인 못 한다"로 가야
하는데, 그러면 **기기를 잃어버린 사람이 영영 못 들어옵니다.**

- **질문 B.** 제 처방은 **"들어오게는 하되, 돈에 닿는 것은 유예"**입니다:

  ```
  패스키가 등록된 계정에서 **본인 인증으로** 로그인하면
    → 로그인은 허용
    → 그 세션에서는 계좌 변경·패스키 등록에 쿨다운(48시간)을 건다
    → 등록된 모든 기기와 인앱에 "다른 경로로 로그인됨" 알림
  ```

  즉 **경로의 차이를 권한의 차이로 바꾸는** 것입니다. 이 설계가 타당합니까?
  아니면 과합니까 — 폰을 바꾼 정상 사용자가 48시간 동안 계좌를 못 바꾸는 것이
  실제로 큰 불편인지 판단이 안 섭니다.

## 4. 스스로 찾아 고친 것 셋 (참고)

- **운영에서 도메인 설정이 없으면 던지게 했습니다.** 조용히 localhost로 물러서면
  배포 후 **등록은 되는데 로그인이 안 되는** 상태가 되고, 증상이 "가끔 로그인이 안 돼요"로
  들어와 원인 찾는 데 가장 오래 걸립니다
- **브라우저가 보낸 챌린지를 두 번 파싱하던 것을 한 번으로.** 이 값을 신뢰하지 않는다는
  사실(DB 조회로 검증한다)을 함수 이름과 주석으로 못 박았습니다
- **기기 삭제도 알립니다.** 탈취자가 주인의 열쇠를 지우면 주인은 생체 로그인이 안 되는
  이유를 모른 채 본인 인증으로 들어옵니다 — 알림이 없으면 사고가 사고인 줄 모릅니다

## 5. 계약 전에 정해야 하는 것 — CI인가 DI인가

본인 인증 공급자는 **CI**(연계정보, 서비스 무관 고유값)와 **DI**(중복가입확인정보,
서비스별 고유값)를 줍니다. 지금 코드는 CI 해시를 저장해 1인 1계정을 강제합니다.

```
우리 목적    "우리 서비스 안에서 1인 1계정"  →  DI가 그 용도로 만들어진 값
CI를 쓰면    필요한 것보다 넓은 값을 갖게 된다 (최소수집 관점에서 불리)
DI를 쓰면    공급자를 바꾸면 값이 달라져 **재가입 세탁이 열린다**
```

- **질문 C.** 이 판단이 맞습니까? 저는 **CI 유지**로 기울어 있습니다 — 성적 세탁 차단이
  이 플랫폼의 근간이고(등급·점수가 전부 거기 얹혀 있습니다), 공급자 교체 가능성을
  포기하는 대가가 그보다 크다고 봤습니다. 다만 개인정보 최소수집 원칙과 정면으로
  부딪히는 선택이라 근거가 서면으로 필요한지 궁금합니다.

## 6. 남은 것 (질문 아님, 상태 공유)

- **문자 알림이 없습니다** — 계좌 변경·기기 등록 알림이 전부 인앱이라 탈취자가 같이
  봅니다. 지금 방어의 가장 큰 구멍이고, SMS 발송 계약으로 풀립니다
- **은행 예금주 조회 계약이 없습니다** — 문 3의 로직은 완성됐지만 물어볼 창구가 없습니다.
  계약할 때 확인할 것: **"예금주 실명을 응답으로 주는가?"** (1원 인증만으로는 이름을
  못 얻어 대조가 성립하지 않습니다)
- **본인 인증이 스텁입니다** — 지금은 이름·번호만 맞으면 통과합니다. 즉 문 1·2가
  실제로는 아직 아무것도 막지 않습니다
