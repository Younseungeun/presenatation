# INTOVILL 36차 검토 요청 — 정산 원장 (2)

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동으로 판정합니다. 적중이면 리서처에게
정산되고, 실패면 구매자에게 **현금 환불**됩니다. 그 사이 돈은 에스크로에 있습니다.

**먼저 제가 35차 프롬프트에서 사실을 틀리게 적은 것을 정정합니다.**

## 0. 정정 — 일일 한도는 이미 두 경로를 합쳐 셉니다

제가 "일일 한도는 지급 경로에만 걸려 있습니다"라고 적었는데 **틀렸습니다.**
`payoutVelocity.todayOutflowKrw`는 **지급과 환불을 합산**하고, `assertWithinDailyLimit`은
`executePayout`과 `executeRefund` **양쪽에서** 호출됩니다.

그 전제로 D-4를 답해 주셔서, 아래 D-1에 다시 여쭙니다.

## A. D-5 셋을 코드와 대조했습니다 — **둘은 이미 막혀 있었습니다**

### ① 웹훅 ↔ 재시도 이중 집행 — 이미 방어됨

- **계좌이체는 재시도 자체를 금지**합니다. 멱등키가 없으니 "다시 보낸다"가 곧 이중
  송금이라, 사람이 은행 앱에서 확인해 상태를 확정하는 경로만 있습니다
  (`resolveBankTransferAttempt`: SENT / NOT_SENT)
- **PG 취소는 같은 멱등키로** 나가 두 번 빠지지 않습니다
- **정차 스윕은 돈을 보내지 않습니다** — 알림만 내고, 이미 실행된 건의 PENDING 행은
  스스로 닫습니다

즉 제안하신 `SELECT FOR UPDATE`가 막으려는 것(이중 송금)은 **수단별 성질**로 이미
닫혀 있습니다.

### ③ PG 정산 시차 — 이미 방어됨

`PG_SETTLEMENT_LAG_DAYS = 3`이 결제 3일 이내 건의 지급을 거부하고, 운영자가 콘솔에서
입금을 확인한 경우에만(`confirmedSettled`) 넘어갑니다. 코드 주석에 **적어 주신 것과
같은 문장**이 이미 있었습니다 — "아직 받지도 않은 돈을 회사 돈으로 먼저 내주는 것이
된다. 규모가 커질수록 그대로 자본 잠식이다."

### ② 이의 경합 — **이것만 진짜였고, 고쳤습니다**

이의 검사와 실제 쓰기 사이에 **쿨다운 조회·한도 집계·PG 지연 계산**이 들어갑니다.
그 사이 이의가 접수되면 앞의 검사는 이미 지나간 뒤이고, 하필 **쿨다운 만료 직후가
구매자도 결과를 보는 시각**이라 겹치기 쉽습니다.

**다만 제안하신 방식(트랜잭션 안 재확인)은 이 코드베이스에서 거부됐습니다.**
`noIoInTransaction.test.ts`가 `src/server`의 **대화형 트랜잭션을 금지**합니다 —
안에서 `await`이 가능해지면 언젠가 외부 호출이 쓰기 락을 쥔 채 남고, SQLite에서 그
순간 결제 쓰기가 죽습니다. 근거는 실측입니다: `measureWriteContention`의 대조군
(트랜잭션 **안에서** 시간을 끄는 경우)은 p99 16초·결제 실패 2건으로 **전멸**했고,
정상군은 8벌까지 실패 0건이었습니다. **무너뜨리는 것은 엔진이 아니라 트랜잭션 길이**입니다.

그래서 재조회 대신 **조건을 쓰기에 실어 보냈습니다**:

```ts
prisma.settlement.updateMany({
  where: {
    id, payoutExecutedAt: null,
    purchase: { OR: [{ judgmentDispute: { is: null } },
                     { judgmentDispute: { status: { not: 'OPEN' } } }] },
  },
  data: { payoutExecutedAt: now, ... },
});
```

한 문장이라 검사와 쓰기 사이에 틈이 없습니다. `is: null`만 쓰면 **확정된 이의가 있는
건까지 영영 막히므로** "없거나, 있어도 확정됐거나"로 적었습니다.

## B. D-1·D-2는 채택했습니다 (구현은 다음 회차)

- **모델 분리**: 위탁 정산(에스크로)과 손실 보전(자기 자본)이 한 테이블에 섞이면
  에스크로 계좌 잔액과 원장이 어긋난다는 지적이 결정적입니다. `CompensationInstruction`
  별도 모델 + 이체 실행 인터페이스 공유로 갑니다
- **보상액 = 판매 대금 − 수수료**: "장애가 나면 정상 판정보다 더 번다"는 역유인이
  결정적입니다. 우리는 그 건의 수수료 수익을 0으로 처리합니다

스키마 마이그레이션이 필요해 이번 회차에는 넣지 않았습니다. 다음 회차 작업입니다.

## C. 답을 듣고 싶은 것

- **C-1.** 0번 정정을 반영하면 D-4의 답이 달라집니까? 지금은 **지급 + 환불(PG·계좌
  무관) 합산 1일 1천만원**입니다. 제안하신 대로 **PG 취소를 한도에서 빼야** 합니까?
  제 판단은 **빼면 안 된다**입니다 — 이 한도의 목적은 유동성 관리가 아니라
  **피해 반경 제한**이고(코드 주석: "세션이 털렸든 우리 버그든 운영자 실수든 원인과
  무관하게 같은 벽에 부딪힌다"), 탈취된 세션이 PG 취소를 대량 실행하는 것도 똑같이
  피해입니다. 다만 **유동성 통제는 따로 없는 것이 맞고**, 그건 별개 장치여야 한다고
  봅니다. 이 구분이 맞습니까?
- **C-2.** `CompensationInstruction`을 만들 때 **기존 `Settlement`의 어떤 것을 재사용하고
  어떤 것을 복제해야** 합니까? 쿨다운·일일 한도·이의 차단은 성격이 다릅니다 —
  보상금은 판정 결과와 무관하므로 이의 차단이 의미가 없고, 쿨다운(판정이 뒤집힐 수
  있으니 기다린다)도 근거가 사라집니다. 남는 것은 일일 한도뿐인데, 그러면
  "파이프라인 공유"의 실체가 거의 없어집니다.
- **C-3.** 보상 대상 판별이 **판정 시점에 확정되지 않습니다.** 상한으로 닫힌 카드의
  귀책(`DATA-A` / `DATA-B`)은 그 시점의 상태 신호로 가리는데, 신호 조회가 실패하면
  `DATA-A`(우리 책임)로 기웁니다. 그러면 **신호가 자주 실패하는 종목일수록 보상이
  자주 나갑니다.** 이걸 그대로 두는 것이 맞습니까, 아니면 보상 판별만 **나중에
  사람이** 확정하도록 큐로 보내야 합니까?
- **C-4.** 정산 영역에서 **아직 제가 못 본 것**이 있습니까? D-5에서 셋 중 둘이 이미
  막혀 있었던 것을 보면, 제가 설명한 것만으로는 실제 코드 상태를 판단하시기 어려운
  듯합니다. 필요하시면 특정 파일의 실제 내용을 붙여 드리겠습니다 — 어느 것을
  보시겠습니까?
