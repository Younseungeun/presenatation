# INTOVILL 35차 검토 요청 — **판정 코어를 동결하고 정산 원장으로 넘어갑니다**

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동으로 판정합니다. 적중이면 리서처에게
정산되고, 실패면 구매자에게 **현금 환불**됩니다. 그 사이 돈은 에스크로에 있습니다.

34차 답변대로 **E-1·E-2를 확정하고 판정 코어를 동결했습니다.** 이번 회차부터
**정산 지시서·원장**으로 검토 대상을 옮깁니다.

---

## A. 34차 마무리

### A-1. E-2 절대 시한 — **구멍이 맞았습니다. 다만 구현은 다르게 했습니다**

유예 하나하나에는 끝이 있었는데(탐침 62분, 하드락 24시간) **합에는 끝이 없었습니다.**
정지가 풀렸다 다시 걸리면 유예도 새로 시작하므로, 공급자가 30분마다 흔들리면
구매자의 환불 시각이 무한정 밀립니다.

제안하신 `maxAbsoluteDeadline` 필드를 카드에 두는 대신, **유예가 상한을 건너뛰지 않고
문턱을 올리게** 했습니다:

| 카드 상태 | 유예 없음 | 유예 중 |
|---|---|---|
| 시한 후 14~16일 | 닫는다 | **기다린다** |
| 시한 후 16일 초과 | 닫는다 | **닫는다** |

같은 보장을 얻으면서 **상태를 늘리지 않습니다** — 새 필드도, 새 종료 상태
(`TERMINATED_FAIL`)도 없습니다. 정상적인 사고 한 번은 유예를 다 쓰고도 16일 선에
안 닿고, **반복되는 사고만** 닿습니다. 원칙은 적어 주신 그대로 코드 주석에 넣었습니다:
**자동 회복의 권한보다 에스크로 정산 시한 약속이 위에 있다.**

### A-2. E-1 구매자 노출 — 전면 채택

"장애가 아니라 검증으로 프레이밍"이 맞습니다. 그리고 그게 **포장이 아니라 사실**입니다 —
한 소스가 틀렸을 가능성을 보고 멈춘 것이고, 그대로 판정하는 것보다 멈추는 편이
구매자에게 낫습니다.

```
시세 정밀 검증 중 · 에스크로 보관 중
시세 제공사의 데이터 정합성을 재검증하고 있습니다. 검증이 끝나면 판정되고,
끝나지 않으면 전액 환불됩니다 — 어느 쪽이든 검증 시한 후 최대 16일 안에 확정됩니다.
```

### A-3. E-3 낙관적 락 — 안 만듭니다

"지금 짜도 Postgres 전환 때 행 잠금으로 다시 쓰게 되어 버려지는 코드"가 맞습니다.
단일 스케줄러라 경합도 없습니다. Postgres 전환 시 테이블 승격과 함께 처리합니다.

### A-4. E-4 동결 — 받아들입니다

34회차 동안 이 영역만 팠고, 마지막 세 회차에서 나온 결함이 전부 **"둘이 동시에 걸리는
순간"**이었습니다. 그 방향으로 더 파는 것은 희귀 조합을 위한 복잡도만 늘립니다.
**판정·정지·회복은 동결하고 정산 원장으로 넘어갑니다.**

## B. 이번 회차 검토 대상 — 정산 원장의 현재 상태

**있는 것부터 정확히 적습니다** (검토가 없는 것을 있다고 가정하지 않도록).

| 구성 | 상태 |
|---|---|
| 3분기 정산 계산 (`domain/settlement.ts`) | 순수 함수. 적중/실패/판정 불가 |
| 판정→지시서 생성 (`judgmentWriter`) | 판정 트랜잭션 안에서 환불·지급 지시서를 만든다 |
| 환불 실행 (`executeRefund`) | PG 취소 / 계좌이체 2경로, 이중 실행 차단, 멱등키 |
| 지급 실행 (`executePayout`) | 쿨다운 48시간 + 일일 한도 + 이의 제기 차단 |
| 실패 재시도 (`retryRefundAttempt`, `sweepStuckRefundAttempts`) | 30분 이상 PENDING이면 회수 |
| PG 장부 대조 (`domain/reconciliation.ts`) | **순수 함수만 있고 어댑터가 없다** — 실계약 전이라 응답 모양을 본 적이 없음 |
| 플랫폼 귀책 보상 | **없음** (아래 C) |

**대조 함수가 이미 잡는 것**: `MISSING_IN_LEDGER`(차지백·콘솔 수동취소),
`MISSING_IN_PG`(팔았다고 아는데 돈이 안 들어옴), `AMOUNT_DIFFERS`(부분 취소 불일치).
**자동 보정은 하지 않습니다** — 그 파일에는 쓰기가 한 줄도 없습니다.

## C. 미착수 — 플랫폼 귀책 보상 (30차에 설계만 하고 미뤄 둔 것)

플랫폼 장애(`PAUSED` / `MANUAL_ONLY` / `ERROR`)로 카드가 판정 불가로 닫히면:
구매자는 전액 환불받고, **리서처는 대금도 점수도 못 받습니다.** 판매는 실제로
일어났고 콘텐츠는 이미 전달됐는데, 판정을 못 한 것은 우리 사정입니다.

30차에 합의한 형태: **결과를 사후에 판정하지 않고 귀책만 보고**, 팔린 카드였다면
플랫폼 예산으로 대금 상당액을 보상합니다. 그러면 운영자가 "맞았다"고 판정할 때
플랫폼 돈이 나가는 구조가 아니라 중립성이 지켜집니다.

31차에 `DATA` 귀책을 세분화했습니다: `DATA-A`(우리 피드 장애 → 보상) /
`DATA-B`(종목의 거래정지·유동성 고갈 → 제외). 상태 신호를 시세와 **다른 경로**로
이미 받고 있어(KIS `temp_stop_yn`, 나스닥 tradehalts, 업비트 `market_event`)
판별이 가능하고, **신호도 못 받으면 `DATA-A`로 기웁니다.**

## D. 답을 듣고 싶은 것

- **D-1.** 보상 지시서를 **기존 `Settlement`에 얹을지, 별도 모델로 뺄지**가 첫
  갈림길입니다. 얹으면 지급 파이프라인(쿨다운·한도·이의 차단)을 그대로 쓰지만
  "판매 대금 정산"과 "플랫폼 보상금"이 한 테이블에 섞여 **회계상 성격이 다른 돈이
  구별되지 않습니다**(전자는 위탁 정산, 후자는 손해 보전). 빼면 파이프라인을
  다시 만들어야 합니다. 어느 쪽입니까?
- **D-2.** 보상 금액을 **판매 대금 전액**으로 할지 **대금 − 수수료**로 할지입니다.
  전액이면 리서처는 적중했을 때보다 더 받습니다(수수료를 안 떼므로). 수수료를
  떼면 우리가 실패한 건에서 수수료를 챙기는 모양이 됩니다. 어느 쪽이 맞습니까?
- **D-3.** 대조(`reconcile`)에 **어댑터가 없어 한 번도 실행된 적이 없습니다.**
  토스 실계약 전에 이 함수의 정확성을 확인할 방법이 있습니까? 응답 픽스처를
  손으로 만드는 것은 **우리가 상상한 모양을 우리가 검증하는** 순환이라 값어치를
  잘 모르겠습니다.
- **D-4.** 지금 돈이 나가는 경로가 셋입니다 — 환불(PG 취소), 환불(계좌이체),
  지급(계좌이체). 여기에 보상이 넷째로 붙습니다. **"오늘 나간 돈의 총합"을 한
  자리에서 보는 장치가 없습니다**(일일 한도는 지급 경로에만 걸려 있습니다).
  전 경로 합산 한도를 둬야 합니까, 아니면 경로별 한도가 맞습니까?
- **D-5.** 정산 영역에서 **제가 못 보고 있는 구조적 위험**이 있습니까? 판정
  영역에서는 "둘이 동시에 걸리는 순간"이 반복해서 나왔는데, 정산에서 그에 해당하는
  것이 무엇일지 밖에서 짚어 주시면 좋겠습니다.
