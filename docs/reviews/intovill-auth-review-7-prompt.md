# INTOVILL 인증 축 7차 검토 — 6차를 전부 채택했고, 그 직후 **제가 만든 관문에서 구멍을 찾았습니다**

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동 판정합니다. 적중이면 리서처에게 정산되고,
실패면 구매자에게 **현금 환불**됩니다. 그 사이 돈은 에스크로에 있습니다.
운영자는 **창업자 1명**이고 당분간 바뀌지 않습니다(설계 주체 확정).

6차 답변 셋(부트스트랩 관문 · 고액 지급 재확인 · 사기 경고 배제)을 전부 채택해 구현했습니다.
그리고 **구현 직후 스스로 검토하다 생체 재확인 자체가 무력화되는 경로를 찾아 고쳤습니다** —
이번 문서의 무게중심은 그쪽입니다.

---

## 1. 6차 답변을 이렇게 옮겼습니다

### Q1 — 부트스트랩 관문 (채택, 지적이 정확했습니다)

패스키 0개인 관리자 세션은 **관리 기능이 통째로 닫힙니다.**

```
서버:  requireOperatorId가 passkey_count == 0이면 403
       → 모든 /api/admin/* 및 관리 기능 API가 닫힌다
화면:  /admin 레이아웃이 전체를 가로채 등록 관문만 띄운다
       → 개별 화면에 걸지 않은 이유: 하나라도 빠지면 그 화면이 공백기의 뒷문이 된다
```

**등록 경로 자체는 관문 밖에 둡니다** — `/api/passkey/register`는
`requireOperatorId`가 아니라 `requireUserId` + 최근성(본인 인증 직후 10분)을 씁니다.
안에 뒀다면 "패스키가 없어서 패스키를 등록할 수 없는" 교착이었습니다.

### Q2 — 고액 지급에도 생체 재확인 (채택)

"경보 피로" 논거를 받았습니다. 색 강조는 유지하고 그 위에 재확인을 얹었습니다 —
지적하신 대로 지문 1초는 **탈취 방어이자 본인의 0 하나 실수를 잡는 브레이크**입니다.

### Q3 — 재확인 창의 사기 경고 (채택, 무변경)

애초에 넣지 않았으므로 그대로 둡니다. 구매자용 계좌 유예 해제 화면의 사기 경고는
대상이 다르므로 유지합니다.

## 2. 구현 직후 스스로 찾은 결함 — 재확인이 **얹혀 갈 수 있었습니다**

6차 프롬프트를 쓰기 전에 제 코드를 다시 읽다 발견했습니다.

```
consumeOperatorRecheck(prisma, operatorUserId, now)
  → where: { id: operatorUserId, operatorRecheckAt: { gte: cutoff } }
```

**재확인 도장이 "사용자" 단위였습니다.** 그러면 이런 일이 됩니다:

```
공격자가 다른 기기에서 창업자의 세션을 쥐고 대기
  → 창업자가 자기 일(예: 동결 해제)을 하려고 지문을 댄다
  → 그 순간 도장이 찍히고, 공격자의 세션도 5분 창 안에서 통과한다
  → 1회용이라 한 번뿐이지만, **그 한 번이 동결 해제이거나 고액 지급이다**
```

이 장치가 존재하는 이유가 **"세션만 훔친 사람은 생체가 없어 못 한다"**였는데,
정확히 그 상대에게 뚫려 있었습니다. 실무적으로는 창업자가 1~2초 뒤 스스로 소비하므로
창이 좁지만, **경쟁 조건이지 방어가 아니었습니다.**

**고친 방법 — 1회용 표(token):**

```
생체 통과 → 서버가 난수 표를 만들어 그 응답으로만 돌려준다 (해시만 보관)
실행 요청 → 그 표를 함께 보내야 통과
표는 쓰면 사라지고, 5분이 지나면 죽는다
```

핵심은 **표가 생체를 통과한 화면 밖으로 나가지 않는다**는 것입니다. 세션만 가진
쪽은 그 응답을 못 받으므로 표를 손에 넣을 수 없습니다. 표와 시각을 한 조건에 걸고
건수로 판정해(승인서 소비와 같은 방식) 동시 요청이 같은 표를 두 번 쓰지 못하게 했습니다.

**"도장은 찍혀 있는데 표가 없는 요청"이 거절되는 것**을 시험으로 못 박았습니다 —
이 시험이 없으면 같은 결함이 되돌아와도 아무도 모릅니다.

## 3. 질문

### 질문 1 (최우선) — 본인 인증 공급자가 죽으면 관리자가 잠깁니다

이제 관리자 권한이 **신원(CI)** 에 걸려 있고, 부트스트랩 관문까지 붙어 사슬이 이렇습니다:

```
관리자 화면 ← 패스키 필요 ← 등록하려면 본인 인증 직후 10분 ← 본인 인증 공급자
```

즉 **본인 인증 공급자가 다운되면**: 패스키가 살아 있으면 무사하지만, 기기를 새로
바꿨거나 패스키를 모두 잃은 상태라면 **관리자가 영영 못 들어옵니다.** 그리고 공급자
장애는 대개 다른 장애와 겹쳐 오므로, **사고 대응이 가장 필요한 순간에 관리 화면이
닫히는** 최악의 상관관계를 갖습니다.

제가 검토한 선택지:

| 안 | 문제 |
|---|---|
| 비상용 환경 변수 토큰(브레이크글라스) | 그 토큰이 상시 백도어. 서버 환경 변수를 읽을 수 있는 자 = 관리자 |
| 공급자 장애 시 관문 자동 완화 | 공격자가 장애를 유발(또는 위장)해 관문을 여는 길 |
| 아무것도 안 한다 | 예비 기기(공기계 패스키)가 있으면 실제로 안 잠긴다 |

**제 판단은 세 번째 + 운영 요건화**입니다: 예비 기기의 패스키를 "있으면 좋은 것"이
아니라 **출시 요건**으로 올리고, 코드는 그대로 둡니다. 근거는 — 브레이크글라스는
막으려는 것(계정 하나 탈취)을 그대로 되살리고, 자동 완화는 공격자에게 스위치를
쥐여 줍니다. **복구 수단을 코드에 두지 않고 물리(예비 기기)에 두는 것**이 이 구조에서
유일하게 백도어를 안 만드는 길이라고 봤습니다. 동의합니까? 예비 기기마저 잃은
상태의 복구를 굳이 설계한다면, 백도어가 되지 않는 형태가 있습니까?

### 질문 2 — 재확인 표를 세션이 아니라 "화면"에 묶은 것이 맞습니까

표를 **세션 쿠키에 바인딩**하는 대안도 있었습니다(세션 지문을 함께 저장). 저는 표를
고른 이유가 셋입니다: ① 서비스 계층이 요청 컨텍스트를 몰라도 된다(순수 인자로 흐름)
② 실행 요청과 표가 **같이 이동**하므로 감사·시험이 쉽다 ③ 세션 쿠키는 XSS로 새면
표도 함께 새지만, 표는 애초에 응답 1회에만 존재해 저장되지 않는다.

다만 남는 것: **표가 XSS로 탈취될 수 있는 창**이 존재합니다(생체 통과 직후~실행까지).
그 창은 밀리초 단위지만 0은 아닙니다. 세션 바인딩을 **추가로** 얹으면(표 + 세션 지문
둘 다 맞아야 통과) 그 창까지 닫히는데, 복잡도가 늘어납니다. 지금 형태로 충분합니까?

### 질문 3 — 5분 창은 여전히 적정합니까

표를 쓰면서 창의 의미가 달라졌습니다. 전에는 "이 시간 동안 누구든 얹혀 갈 수 있는
창"이었지만, 지금은 "표를 손에 쥔 화면이 실행을 마칠 시간"입니다. 실제 흐름은
생체 통과 → 즉시 자동 재시도라 **1초 내외**입니다. 5분은 이제 지나치게 길어 보이는데,
사용자가 지문을 대고 확인 대화상자를 읽는 시간, 네트워크 지연, 화면 전환을 감안하면
**60초**가 적정선 같습니다. 줄이는 것이 맞습니까, 아니면 표가 이미 1회용이라
시간은 안전장치로만 두고 그대로 둡니까?

## 4. 상태 공유 (질문 아님)

- **고액 지급 문턱(500만원)은 사실상 발동하지 않습니다** — 정산이 구매 1건에 1행인데
  카드 가격이 5천~5만원이라, 단일 정산이 문턱을 넘으려면 카드 한 장이 625만원이어야
  합니다. 관문은 살려 두되 실제로 서는 것은 색 강조입니다.
  (관련: **카드 가격에 코드상 상한이 없습니다** — 가이드만 있고 검증은 정수 체크뿐.
  별개 항목으로 인지하고 있습니다)
- 승인 인프라(대기열·72시간 만료·48시간 재알림·건강도 지표)는 1인 모드에서 **휴면**입니다.
  코드·시험은 전부 살아 있고, 진짜 운영자가 2명이 되면 자동 복귀합니다
- **여전히 스텁**: 본인 인증(실공급자 미계약) · 은행 예금주 조회(미계약) · SMS(미계약)
