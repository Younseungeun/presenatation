# INTOVILL 인증 축 2차 검토 — 구조를 처음부터 다시 세웠습니다. 이번엔 설계자가 다릅니다

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동 판정합니다. 적중이면 리서처에게 정산되고,
실패면 구매자에게 **현금 환불**됩니다. 그 사이 돈은 에스크로에 있습니다.

1차 답변(A 최근성·B 경로별 권한·C CI 유지)을 구현한 뒤, **설계 주체(사용자)가 인증
구조 전체를 처음부터 다시 정의했습니다.** 이 문서는 그 확정 구조와 구현을 담고, 구조를
합치면서 생긴 **충돌 지점 하나**를 최우선 질문으로 올립니다.

⚠ 1차 문서에서 패스키 등록 구멍의 크기를 과장해 적었던 것을 바로잡습니다 — 이번
문서는 각 관문이 **무엇을 막고 무엇을 못 막는지**를 정확한 크기로 적습니다.

## 1. 확정된 구조 (2026-08-16, 사용자 설계)

### 로그인은 둘이다 — 이 구분이 구조의 전부입니다

| | 풀 로그인 | 간편 로그인 |
|---|---|---|
| 언제 | 가입 · 앱 재설치 · 로그아웃 후 | 설치된 앱을 다시 열 때 (**휴면 깨우기**) |
| 무엇으로 | 본인 인증 (통신사/PG — 공급자 추후 확정) | 생체(동의자, **우선**) → 간편 비밀번호(**필수**, 폴백) |
| 증명하는 것 | 이 사람이 **누구**인가 | **아까 그 기기**가 맞는가 |

- 가입(풀 로그인) 시 저장: **CI 해시**(1인 1계정 강제) + **실명(암호화)** — 실명은
  계좌 등록 때 은행 예금주명과 대조할 상대편입니다. 풀 로그인마다 갱신해 개명을 흡수합니다
- 가입 직후 **간편 비밀번호 설정을 필수로** 거치고, 그 자리에서 생체 동의를 묻습니다
- 간편 자격증명(생체·비밀번호)은 **기기에 묶입니다.** 서버가 인정하는 것은 "이 기기에서
  이 자격증명"이라, 비밀번호가 유출돼도 다른 기기에서는 못 쓰고 **새 기기는 무조건 풀
  로그인**입니다

### 계좌 등록 — 본인 인증을 여기서만 한 번 더

```
① 재인증의 CI == 계정의 CI      (지금 이걸 하는 게 계정 주인인가)
② 통신사가 준 이름 == 은행 예금주명   (그 계좌가 그 사람 것인가)
③ 둘 다 통과 → 등록. 이후 48시간 지급 유예
```

**예금주 이름 입력란은 없습니다** — 본인이 두 곳에 다 적으면 대조가 아니라 받아쓰기입니다.
재인증(①)을 두는 이유는 동명이인입니다: 이름 대조만으로는 "그 **이름의** 통장"까지만
증명되고, 같은 이름의 대포통장이 뚫습니다. CI는 이름과 달리 겹치는 사람이 없습니다.

### 사용자의 위협 분석 — 탈취자 B의 두 갈래

| B의 위치 | 결과 |
|---|---|
| **A의 기기** (비밀번호 유출) | 들어와진다. 그러나 계좌 등록에서 끝 — 재인증 CI 불일치, 설령 넘어도 예금주명 불일치 |
| **B 자기 기기** | 시작조차 못 한다 — 새 기기는 풀 로그인 = A 명의 본인 인증 필요 |

뒤를 받치는 것: 48시간 쿨다운 · 정산 동결(걸기는 본인, **풀기는 운영자만**) · 변경 알림.

## 2. 구현 상태 — 전부 코드로 옮겼고 브라우저로 확인했습니다

- **간편 비밀번호**: 6자리, 반복·연속 값 거절(111111·123456), scrypt 해시, 기기 토큰도
  해시만 저장, **연속 5회 실패 시 잠금 + 본인 알림 + 풀 로그인으로만 재설정**
- **실명 저장**: 가입 시 암호화 저장(`User.realNameEnc`), 인증 응답의 이름만 들어감
- **최근성 관문**: 자격증명(패스키·PIN) 심기는 **방금 본인 인증한 세션만.** 간편
  세션(PIN·패스키)은 `verifiedAt=0`이라 항상 재인증을 요구받음 — 열쇠로 들어와 열쇠를
  또 심는 길이 없음
- **경로 관문**(1차 B): 패스키 있는 계정에 본인 인증으로 로그인 → 48시간 기기 등록
  유예 + "다른 경로로 로그인됨" 알림
- 로그인 화면 순서: **생체 → 간편 비밀번호 → 본인 인증** (순서가 곧 우선순위 선언)

브라우저 확인: 풀 로그인 → `pinSetupRequired` → 설정 → 틀린 PIN "4회 남음" → 맞는
PIN 로그인 → **PIN 세션으로 기기 등록 시도 → `REVERIFY_REQUIRED` 거절.**

## 3. 질문

### 질문 1 (최우선) — **필수 PIN 설정과 48시간 유예가 충돌합니다**

1차에서 확정한 B(위험 경로 유예)와 사용자 구조(가입·새 기기 직후 PIN 필수)를 합치니
모순이 하나 생깁니다:

```
새 기기에서 풀 로그인
  → 구조: 그 자리에서 간편 비밀번호를 반드시 설정해야 한다
  → B 관문: 이 세션은 위험 경로일 수 있다 — 자격증명 심기를 48시간 막아야 한다
```

둘 다 지킬 수는 없습니다. 지금 구현은 이렇게 갈랐습니다:

| 자격증명 | 새 기기 풀 로그인 직후 | 근거 |
|---|---|---|
| **PIN 설정** | **즉시 허용** | PIN 기기가 주는 것은 로그인뿐 — 로그인은 이미 된 상태라 **추가 권한이 0**이다 |
| **패스키 등록** | 기존 패스키 있으면 **48시간 유예** | 생체 기기는 "평소 경로"의 지위를 얻는다 — 위험 경로가 평소 경로로 승격되는 것은 막는다 |

즉 **"권한이 늘지 않는 자격증명은 즉시, 지위가 오르는 자격증명은 유예"**입니다.
유심을 가로챈 공격자가 PIN 기기를 즉시 심어도, 그가 얻는 것은 이미 가진 로그인의
지속뿐이고 돈·열쇠에는 여전히 못 닿습니다.

이 구분이 타당합니까? 아니면 PIN 기기의 지속성 자체(유심을 돌려준 뒤에도 남는 접근)가
유예할 가치입니까 — 그 경우 필수 설정 흐름을 어떻게 살립니까?

### 질문 2 — 세션 수명 30일이 이 구조와 맞습니까

세션이 30일인 근거는 "매번 본인 인증시킬 수 없다"였습니다. **이제 그 전제가 사라졌습니다**
— 깨우는 데 지문 한 번, 비밀번호 6자리입니다. 사용자의 "휴면 깨우기" 모델대로라면
세션을 짧게(1~7일) 두고 자주 깨우는 쪽이 자연스럽고, 훔친 세션의 유효 기간도 그만큼
줄어듭니다. 줄인다면 어디까지가 적정합니까? (은행 앱들은 10~30분이지만, 우리는
조회 중심 화면이 많아 그 정도로 조이면 과하다고 봅니다)

### 질문 3 — 운영자 계정에는 아무 추가 관문이 없습니다

운영자는 **정산 동결을 푸는 유일한 사람**이고, 판정을 되돌리고, 지급을 실행합니다.
운영자 계정이 탈취되면 지금까지의 방어 대부분이 무의미해집니다. 제 처방: **운영자는
생체(패스키) 필수 + 돈이 나가는 실행(지급·동결 해제)에는 최근성 요구.** 운영자는
소수라 마찰을 감당할 수 있습니다. 과합니까, 아니면 2인 승인까지 가야 합니까?

## 4. 상태 공유 (질문 아님)

- **유심 스와핑 잔여 위험**: B가 A의 유심을 가로채면 풀 로그인도, 계좌 등록의 재인증도
  A 명의로 통과합니다. 그때 남는 방어는 **예금주 대조**(A 명의 통장이 필요 — 대포통장
  규제가 실질 장벽) · 48시간 쿨다운 · 동결입니다. 알림이 인앱뿐이라 문자(SMS)가 붙어야
  완성되는데, **문자도 유심과 같은 축**이라는 한계는 그대로 남습니다
- **기기 신뢰가 쿠키 기반**(PWA): 브라우저 데이터를 지우면 기기 신뢰가 사라지고 풀
  로그인으로 돌아갑니다 — 안전한 방향의 실패라 수용. 네이티브 앱 전환 시 키체인으로 이전
- **여전히 스텁**: 본인 인증(실공급자 미계약) · 은행 예금주 조회(미계약) · SMS(미계약).
  이 셋이 붙기 전까지 관문들은 형태만 완성입니다
