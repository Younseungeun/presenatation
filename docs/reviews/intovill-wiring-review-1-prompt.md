# INTOVILL 배선 점검 1차 — 전수 점검이 찾은 구멍 둘을 막았습니다. 코드 결정을 검증해 주세요

성과 검증형 리서치 마켓플레이스입니다(예측 카드 → 시장 데이터 자동 판정 → 적중이면
리서처 정산, 실패면 구매자 현금 환불, 그 사이 에스크로). 운영자는 **창업자 1명**입니다.

인증 축 8차 검토가 닫힌 뒤, **"설계 문서의 주장 vs 실제 코드"를 전수 대조**했습니다 —
특히 "만든 함수를 실제로 부르는 곳이 있는가"를 봤습니다. 상수·배선·스케줄러 일과는
전부 일치했고, 구멍이 둘 나왔습니다. 둘 다 막았고 이번 문서는 **그 구현의 검증 요청**입니다.

## 구멍 ① — 보상 확정·실행 함수를 아무도 부르지 않았다

플랫폼 귀책 보상(우리 사정으로 판정 못 한 카드의 리서처에게 플랫폼 자본으로 대금−수수료
보상) 제도에서:

```
지시서 생성(판정 트랜잭션)      ✓ 있었음
3일 지연 시 운영자 알림          ✓ 있었음 (매일 09:30 배치)
reviewCompensation(귀책 확정)   ❌ 호출자 0 — API도 화면도 CLI도 없음
executeCompensation(실행 기록)  ❌ 호출자 0
```

알림이 가리키는 화면(/admin/settlements)에 보상 구역이 없어, **알림은 울리는데 처리할
문이 없는** 구조였습니다. 리서처 돈이 영구히 갇힙니다.

### 구현

**API** — `/api/admin/compensations` (POST, `requireOperatorId` — 부트스트랩 관문 포함):

```ts
const bodySchema = z.discriminatedUnion('kind', [
  z.object({ kind: z.literal('REVIEW'), predictionCardId: z.string().min(1),
             decision: z.enum(['APPROVE', 'EXCLUDE']), note: z.string().max(300).optional() }),
  z.object({ kind: z.literal('EXECUTE'), compensationId: z.string().min(1),
             bankReference: z.string().min(1).max(80), recheckToken: z.string().optional() }),
]);
```

**실행 관문 순서** (`executeCompensation`):

```
상태 검사(APPROVED만) → 참조번호 필수 → 계좌 검증(assertPayoutAccountReady)
  → 일일 출금 한도 → 월 보상 예산(500만)
  → [신규] 1인 모드면 consumeOperatorRecheck(생체 재확인 1회용 표)
  → 조건부 updateMany(APPROVED & executedAt null — 건수로 판정, 동시 실행 차단)
  → 감사 로그 + 리서처 알림 (한 트랜잭션)
```

재확인을 **벽들 뒤에** 둔 것은 지급 경로와 같은 순서입니다 — 예산에 막힐 실행이
1회용 표부터 태우면 안 됩니다.

**화면** — 정산 화면에 "플랫폼 귀책 보상" 구역. **확정과 실행을 다른 문으로** 뒀습니다:
확정은 판단("우리 탓인가")이고 실행은 은행 이체 **뒤의** 기록이라, 합치면 이체도 안
했는데 실행으로 기록하는 길이 생깁니다. 확정 카드에는 그 리서처의 최근 180일 시세
미확보 판정 불가 카드 수를 띄웁니다(자동 제외 규칙은 안 만든다는 기존 결정 유지 —
판단은 사람이, 숫자는 화면이).

**오류 전달** — `CompensationError`에 `code?: 'RECHECK_REQUIRED'`를 달고 공용
`toErrorResponse`가 그대로 내려보냅니다. 화면은 그 코드를 받으면 지문 창을 띄우고
받은 표로 **한 번만** 재시도합니다(기존 지급·판정 화면과 같은 패턴).

**시험** — 표 없이 실행 → `RECHECK_REQUIRED`이고 **승인 상태는 산다**(관문에 막힌
것이지 승인이 죽은 것이 아니다) · 표와 함께 → 통과·감사·알림 확인. 개발 서버에서
확정→실행 흐름을 실제로 돌렸습니다(실행은 계좌 관문에서 정확히 멈춤 — 그 리서처가
계좌 미등록이라 맞는 동작).

### 이 구멍이 준 교훈을 코드에 남겼습니다

비상 복구 뒤 48시간 돈 정지는 `consumeOperatorRecheck` **한 점**에 걸려 있습니다.
보상 실행이 그 점 밖에 있는 동안은 **그 유예가 보상 경로를 못 덮었습니다** —
"길마다 나눠 걸면 언젠가 새 길이 생기고 그 길에는 안 걸린다"고 그 주석에 적어
뒀었는데, 정확히 그 일이 일어난 첫 사례라 주석에 기록했습니다.

## 구멍 ② — 비밀값 둘이 운영에서 조용히 개발 기본값으로 물러섰다

```
PAYOUT_ENC_KEY          운영에 없으면 던짐 ✓ (기존)
NEXT_PUBLIC_APP_ORIGIN  운영에 없으면 던짐 ✓ (기존)
AUTH_SECRET             'dev-auth-secret-change-me'로 조용히 폴백 ❌
IDENTITY_PEPPER         'dev-identity-pepper'로 조용히 폴백 ❌
```

폴백 값은 저장소에 적혀 있어 공개나 다름없습니다. 운영에서 이 값으로 세션을 서명하면
저장소를 본 누구나 **세션(관리자 포함)을 위조**할 수 있고, 아무 경고가 없어 잊은 채
배포해도 겉보기엔 멀쩡히 돕니다.

### 구현

```ts
export function authSecret(env = process.env): string {
  const v = env.AUTH_SECRET;
  if (v) return v;
  if (env.NODE_ENV === 'production') throw new Error('운영 환경에는 AUTH_SECRET이 …');
  return 'dev-auth-secret-change-me';
}
```

- **호출 시점 검사**입니다(모듈 로드 아님) — `next build`가 런타임 env 없이 돌아야 해서.
- `recoveryToken`(복구 인가 쿠키 서명)은 `sessionToken`의 `authSecret`을 **가져다 씁니다** —
  규칙이 한 곳에 살게.
- `IDENTITY_PEPPER`도 같은 형태(`identityPepper()` → `hashCi`).
- 시험: 운영 모드 + 비밀 없음 → 세션 서명·복구 인가·신원 해시 셋 다 던짐 / 개발 폴백은
  그대로.

## 질문

### 질문 1 (최우선) — 확정(REVIEW)에는 지문을 안 걸었습니다. 맞습니까?

지문 재확인은 **실행에만** 있습니다. 제 논거: 돈이 나가는 순간은 실행이고 거기가
관문이다. 확정만으로는 한 푼도 안 움직이고, 확정된 건은 "이체 대기" 목록에 떠서
실행자가 다시 봅니다.

남는 시나리오: 세션을 훔친 자가 **확정만 눌러 두고** 창업자가 나중에 무심코 실행하는
경로. 방어 근거는 ① 이 큐가 연 몇 건이라 기억에 없는 승인 건은 눈에 띈다 ② 감사
로그의 reviewedBy 시각이 남는다 — 인데, 1인 모드에서는 reviewedBy가 **어차피 창업자
계정**이라 ②가 약합니다. 확정에도 지문을 걸어야 합니까? (그러면 한 건에 지문 두 번
— 연 몇 건이라 비용은 사실상 0입니다)

### 질문 2 — 보상 실행 재확인에 금액 문턱을 안 뒀습니다. 비대칭이 맞습니까?

지급은 500만원 **이상만** 재확인입니다(하루 수십 건에 다 걸면 경보 피로로 관문이
장식이 된다). 보상은 **전액 재확인**으로 갔습니다. 제 논거: 문턱의 근거는 금액이
아니라 **빈도(습관화)**다 — 보상은 연 몇 건이라 피로해질 반복 자체가 없고, 나가는
돈이 에스크로 위탁이 아니라 플랫폼 자본이다. 같은 "실행"인데 규칙이 갈리는 것이
운영자 혼란을 만듭니까, 아니면 빈도가 다르면 문턱이 다른 것이 맞습니까?

### 질문 3 — 비밀값 강제가 "첫 호출에서 죽는" 방식입니다. 부팅에서 죽어야 합니까?

호출 시점 검사라 서버는 **일단 뜨고**, 첫 로그인/해시 시도에서 죽습니다. "전원이
안 켜진다"가 아니라 "첫 손님에서 멈춘다"입니다. 대안은 Next의 `instrumentation.ts`
(런타임 기동 시 1회 실행)에 **필수 운영 env 넷(AUTH_SECRET·IDENTITY_PEPPER·
PAYOUT_ENC_KEY·NEXT_PUBLIC_APP_ORIGIN)을 한 자리에서 검사**하는 것 — 빠뜨림 방지의
단일 지점이 생기고 부팅 순간 죽습니다. 제 기울기는 **추가하는 쪽**인데, 검사 목록이
코드 곳곳의 실제 사용처와 어긋나기 시작하면(다섯 번째 비밀이 생겼는데 목록에 안
올라가면) 거짓 안심이 됩니다. 두 겹(호출 시점 + 부팅 검사)이 맞습니까, 호출 시점
하나로 충분합니까?
