# INTOVILL 39차 검토 요청 — 이상 시세는 고쳤고, 상수 검증안은 반박합니다

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동으로 판정합니다. 적중이면 리서처에게
정산되고, 실패면 구매자에게 **현금 환불**됩니다. 그 사이 돈은 에스크로에 있습니다.

38차 답변 중 **D-α는 전면 채택해 구현했고, E는 순서를 확정했으며, D-β-2는 반박합니다.**
E-2(지급대행 vs 직접 구축)는 **결론이 아니라 전제를 다시 봐야 한다**고 봅니다.

## A. D-α 채택 — 거래량을 함께 본다 (구현 완료)

"가격 변동률이 아니라 **거래량 동반 여부**를 보라"가 정확히 맞았습니다. 자릿수 오류·통화
혼동은 **같은 체결을 잘못 적은 것**이라 가격만 튀고 거래량은 평소값인데, 진짜 사건은
거래량이 함께 터집니다. 우리는 이미 일봉에 거래량을 받고 있어 **추가 호출 0**입니다.

```ts
export const REAL_MOVE_VOLUME_MULTIPLE = 5;   // 구간 중앙값 대비
// 절대 폭을 넘어도 거래량이 중앙값의 5배 이상이면 통과
```

**대체가 아니라 완화로 넣었습니다.** 거래량이 0이거나 표본이 3일 미만이면 종전대로
막습니다 — 거래량까지 망가진 응답이나 신규 상장처럼 평소값이 없는 경우가 있습니다.
중앙값을 쓴 이유는 평균이 **그 튀는 하루에 끌려가기** 때문입니다.

**D-α-2도 채택했는데 한 걸음 더 갔습니다.** 제안하신 `OPERATOR_ANOMALY_REVIEW` 큐는
사실상 이미 있었습니다(수동 판정 큐). 없던 것은 **거기 도달하는 속도**였습니다 —
예전에는 이월 사다리를 타 백오프를 돌다 **7일에야** 올라갔습니다. 그런데
**기다림이 아무것도 바꾸지 않습니다**: 내일 같은 구간을 물으면 같은 값이 옵니다.
그래서 새 이월 사유(`IMPLAUSIBLE_QUOTE`)를 만들어 **곧장 수동 큐**로 보냅니다 —
교차 검증 불일치와 정확히 같은 성질이라 처리도 같게 했습니다.

다만 **자산군 정지는 걸지 않습니다.** 불일치는 "소스가 통째로 틀렸을 수 있다"는
신호라 그 자산군 전체를 멈출 이유가 되지만, **튀는 일봉 한 줄은 그 종목의 사고**입니다.

## B. D-β-2 반박 — 상수 일원화와 시뮬레이션 강제는 **둘 다 역효과**입니다

> 모든 도메인 임계치를 `constants.ts`에 일원화하고, 매핑된 시뮬레이션 스크립트가 없는
> 상수가 발견되면 CI가 실패하도록

### B-1. 일원화는 이 코드베이스에서 **근거를 멀어지게** 합니다

상수가 그것을 쓰는 도메인 모듈 옆에 있는 것은 의도된 배치입니다. 그리고 여기서 근거는
한 줄이 아니라 **20~40줄의 논증**입니다 — 크기 하한 옆에는 "왜 σ·√H 꼴인가"의 수학이,
쿨다운 옆에는 "왜 24가 아니라 48인가"와 기각된 대안 둘이 붙어 있습니다.

한 파일로 모으면 그 논증이 사용처에서 떨어지고, **그것이 정확히 "왜 이 값인지 모르는"
상태를 만드는 방식**입니다. 이번에 7일 문턱이 그랬던 것도 위치 때문이 아니라
**근거가 안 적혀 있어서**였습니다.

### B-2. "시뮬레이션 없으면 CI 실패"는 **가짜 시뮬레이션을 만듭니다**

근거가 시뮬레이션이 아닌 상수가 많고, 그게 나쁜 것이 아닙니다:

| 상수 | 근거의 종류 |
|---|---|
| 이상값 필터 국내 30% | **규칙** — 거래소 가격제한폭. 시뮬레이션할 것이 없다 |
| PG 입금 지연 3일 | **계약·관행** |
| 쿨다운 48시간 | **사람의 리듬** — "알림을 못 본 하루를 흡수하고도 하루" |
| 신뢰도 범위 2~10 | **상품 설계** — 참가 조건이지 최적화 대상이 아니다 |
| 규율 래더 α | **정리(Ville 부등식)** — 고르는 것이 아니라 유도된다 |

여기에 시뮬레이션을 요구하면 **통과시키기 위한 스크립트**를 쓰게 되고, 그 순간
검증 장치가 아니라 통과 의식이 됩니다.

### B-3. 대안 — **근거의 유무만 강제하고 형식은 열어 둡니다**

잡고 싶은 것은 "시뮬레이션이 없다"가 아니라 **"근거가 없다"**입니다. 그래서
상수 주석에 근거 **유형 태그**를 달게 하고:

```
@근거 시뮬 scripts/simShortHorizonCutoff.ts
@근거 규칙 거래소 가격제한폭
@근거 계약 토스 정산 주기
@근거 설계 참가 조건 — 최적화 대상 아님
@근거 미기록
```

테스트는 **`@근거 미기록`의 개수가 늘지 않는지만** 봅니다(현재 수를 못 박는 래칫).
그러면 ① 오탐이 없고 ② 근거 없는 **새 상수**는 반드시 걸리고 ③ 기존 미기록은
목록으로 남아 하나씩 줄일 수 있습니다.

- **B-질문.** 이 래칫 방식이 맞습니까? 아니면 태그 자체가 형식주의가 되어
  `@근거 설계`가 만능 도피처가 될 위험이 더 큽니까?

## C. E-2 — 결론보다 **전제**를 다시 봐야 합니다

> PG 지급대행은 결제 원장에 귀속된 판매 대금만 허용 → 보상금은 못 나감 →
> 결국 별도 이체 망이 필요하니 직접 구축이 유일하게 일관된 경로

**전제는 그럴듯한데 결론이 과합니다.** 보상금이 지급대행으로 못 나간다고 해서
"이체 망을 또 뚫어야" 하는 것은 아닙니다 — **보상은 이미 사람이 건건이 확정하는
드문 경로**이고, 지금도 운영자가 은행 앱에서 보내고 참조번호를 적습니다.
그 상태를 유지하는 것은 새 계약이 아니라 **현행 유지**입니다.

| | 건수 | 지금 방식 |
|---|---|---|
| 판매 대금 정산 | 많음·정상 운영 | 운영자 수동 이체 |
| 플랫폼 귀책 보상 | **드묾·사고 시에만** | 운영자 수동 이체 + 사람 확정 |

즉 갈림길은 "**흔한 경로를 자동화할 것인가**"이지 "보상금을 어디로 보낼 것인가"가
아닙니다. 드문 경로 하나 때문에 흔한 경로의 자동화를 포기하는 것은 순서가 뒤집힌
판단으로 보입니다.

**그리고 더 중요한 것 — 어느 쪽이든 지금 쓸 코드는 같습니다.**
`PayoutAccount` + 검증 상태 + 실행 관문은 지급대행이든 직접 이체든 **똑같이 필요**하고,
갈리는 것은 **어댑터 하나**뿐입니다(E-3에서 확인해 주신 구조가 바로 그것입니다).

- **C-질문.** 그러면 이건 **설계 결정이 아니라 계약 질문** 아닙니까? 저희가 토스에
  물어볼 것은 "자기 자본을 지급대행 망으로 내보낼 수 있는가" 하나이고, 답이 어느
  쪽이든 코드는 안 바뀝니다. 이 정리가 맞습니까? 아니면 **지금 어댑터를 고르지 않으면
  구조가 굳어 버리는 지점**이 따로 있습니까?

## D. 다음 회차 작업 — E 확정안 (구현 전 확인)

E-1·E-3·E-4를 그대로 채택해 이렇게 짜려 합니다.

```
model PayoutAccount {
  researcherUserId  String   @unique   // 사람당 하나
  bankCode          String
  accountNumberEnc  String              // 암호화 보관
  holderName        String?             // 은행 조회로 채워진다 (우리가 입력받지 않는다)
  status            String              // UNVERIFIED | VERIFIED | HOLDER_MISMATCH
  verifiedAt        DateTime?
  ...
}
```

- **관문은 실행 시점 한 곳**: `account.status === 'VERIFIED'`가 아니면 지급·보상이
  나가지 않는다. `Settlement`·`CompensationInstruction` 상태는 **하나도 늘리지 않는다**
- **계좌를 바꾸면 즉시 `UNVERIFIED`로 되돌아간다** — 검증은 계좌에 붙은 사실이지
  사람에 붙은 사실이 아니다
- **예금주명은 우리가 입력받지 않는다.** 본인이 양쪽을 다 적으면 아무것도 막지 못하므로,
  은행 조회 응답으로만 채운다(계약 전에는 그 자리가 비어 `UNVERIFIED`로 남는다)
- 실명 보유 결정(개인정보처리방침)은 **은행 조회가 붙는 시점까지 미룬다** — E-1 순서

- **D-질문.** 이 형태에서 **빠진 것**이 있습니까? 특히 "계좌를 바꾸면 미검증으로
  되돌린다"가 **정산 대기 중인 지시서를 인질로 만드는지**가 걸립니다 — 지급 직전에
  계좌를 바꾸면 그 건이 멈춥니다. 그게 맞는 동작입니까, 아니면 **지시서마다 계좌를
  박아 두어야** 합니까? (박아 두면 E-3에서 피하려던 상태 오염이 다른 모양으로 돌아옵니다.)
