# INTOVILL 배선 점검 2차 — 1차 답변을 전부 반영했고, 한 곳은 처방과 다르게 갔습니다

1차에서 물은 셋에 답을 받았습니다: Q1(확정에도 지문) 채택 권고 → **구현 완료**,
Q2(보상 전액 재확인 비대칭) 현행 확정 → 유지, Q3(부팅 검사) 두 겹 권고 → **구현
완료하되 제안하신 아키텍처(중앙 zod 스키마)와 다르게** 갔습니다. 이번 문서는 그
구현 보고와, 이탈한 지점의 논거 검증 요청입니다.

---

## Q1 반영 — 확정(REVIEW)에도 지문이 섰습니다

지적하신 잠복 승인(Sleeper Approval) 시나리오 그대로였습니다: 1인 모드에서는
확정자와 실행자가 같은 계정이라 "이체 대기 목록의 낯선 승인"이 걸러지지 않는다.

```
reviewCompensation 순서:
  사유 검사(EXCLUDE는 필수) → 대상 존재 확인(PENDING_REVIEW 있는가)
    → [신규] 1인 모드면 consumeOperatorRecheck(1회용 생체 표)
    → 조건부 updateMany → 감사 로그
```

- **대상 존재 확인을 표 소비 앞에** 뒀습니다 — 이미 처리된 카드(낡은 목록)에
  1회용 표부터 태우지 않습니다. 실행 경로가 상태 검사를 벽들 앞에 두는 것과 같은
  순서입니다.
- 부수 이득: 재확인이 `consumeOperatorRecheck` 한 점을 지나므로 **비상 복구 뒤
  48시간 돈 정지가 확정 단계까지 자동으로 덮습니다** (그 함수 안에 유예 검사가
  있습니다 — "길마다 나눠 걸지 않는다" 원칙의 배당).
- EXCLUDE(대상 제외)에도 똑같이 겁니다 — 리서처 돈을 **안 주기로 하는** 결정도
  훔친 세션이 내리면 안 되고, 연 몇 건이라 나눠서 얻을 것이 없습니다.
- 화면은 실행과 같은 패턴: `RECHECK_REQUIRED`를 받으면 지문 창 → 받은 표로 1회
  재시도.
- 시험: 표 없이 확정 → 거절 + **대기 상태는 산다** / 표와 함께 → 승인·감사 확인.

## Q3 반영 — 부팅 검사는 넣었고, 중앙 스키마는 넣지 않았습니다

### 구현한 것

`src/instrumentation.ts`(Next 규약 — 기동 1회, 요청 받기 전 완료)가
`assertProductionSecrets()`를 부릅니다:

```ts
// src/server/envBootCheck.ts — 발췌
export function assertProductionSecrets(env = process.env): void {
  const failures: string[] = [];
  const checks = [
    () => authSecret(env),                //  세션·복구 인가 서명
    () => identityPepper(env),            //  신원(CI) 해시
    () => assertPayoutEncKeyLoadable(env),//  계좌번호 암호화 키
    () => relyingParty(env),              //  패스키 origin
  ];
  // 전부 검사하고 한 번에 보고 — 첫 실패에서 멈추면 "고치고 재부팅"을 반복한다
  ...
}
```

- **실측으로 확인**: 비밀 없는 운영 기동 → 4건 전부 나열한 에러 후 프로세스 종료,
  리스너 없음(연결 거부). `next build`는 `NEXT_PHASE` 가드로 통과(빌드는 런타임
  비밀 없이 돌아야 합니다).
- **실측이 잡은 함정 하나**: register에서 던지기만 하면 Next가 에러를 삼키고
  **포트를 연 채 모든 요청에 500을 뱉으며 살아 있습니다.** 요청은 안 처리되지만
  pm2·헬스체크가 "죽었다"를 감지 못 하는 반쪽 fast-fail이라, `process.exit(1)`로
  확실히 끝냈습니다.
- 호출 시점 검사는 그대로 남습니다(두 겹) — 부팅 목록이 낡아도 마지막 방어선은
  삽니다.

### 이탈한 것 — 질문 1 (이번 라운드의 핵심)

처방은 "중앙 `env.config.ts`에서 zod 스키마로 한 번만 정의하고, `authSecret()`
등이 개별 `process.env` 대신 **검증된 스키마 객체에서 값을 꺼내게** 배선을
바꿔라"였습니다. **거기까지는 가지 않았습니다.** 부팅 검사가 스키마를 파싱하는
대신 **각 게터를 그대로 부릅니다.** 논거 셋:

1. **약속하신 보장이 실제로는 성립하지 않습니다.** "새 비밀을 스키마에 등록하지
   않으면 타입 에러"는 모든 코드가 스키마 객체를 **경유할 때만** 참인데, 새 비밀을
   만드는 사람이 `process.env.NEW_SECRET`을 직접 읽으면 타입 에러 없이 그대로
   돕니다. 즉 중앙 스키마도 **목록 누락**이라는 같은 구멍을 갖고, 강제력은 컨벤션
   준수에 달려 있습니다 — 제 방식과 같은 지점이 약합니다.
2. **내용 어긋남은 제 방식이 구조적으로 0입니다.** 부팅 검사가 실제 게터를 부르므로
   "부팅은 통과했는데 런타임 규칙은 다르다"가 있을 수 없습니다. 스키마를 따로 두면
   형식 규칙(예: PAYOUT_ENC_KEY 64자 hex)이 두 곳에 살게 되고, 지금까지 이 저장소가
   반복해서 확인한 실패 양식이 정확히 "두 곳에 사는 규칙"입니다.
3. **전환 비용이 실재합니다.** 게터들은 `env = process.env` 주입으로 시험되고
   회귀 시험이 그 형태에 걸려 있습니다. 스키마 객체가 파싱을 메모하는 순간 이
   주입이 깨지고, 메모하지 않으면 매 호출 zod 파싱이 붙습니다(세션 서명은 요청마다
   돕니다).

**반박을 요구합니다**: 남는 위험은 "새 비밀의 게터를 만들고 부팅 목록에 안 부르는
것" 하나입니다. 이 잔여 위험이 중앙 스키마 전환 비용을 정당화할 만큼 큽니까?
게터 컨벤션(운영이면 던진다 + 부팅 목록 한 줄)을 지키게 하는 더 싼 강제 장치가
있으면 제시해 주세요.

### 질문 2 — 확정·실행 지문 두 번이 한 세션에 이어질 때

한 건을 처리하는 창업자는 이제 확정에서 한 번, (은행 이체 후) 실행에서 한 번
지문을 댑니다. 두 동작 사이에 실제로는 은행 앱 전환이 끼므로 시간이 벌어져
문제없다고 판단했는데 — **표의 유효 60초가 두 동작을 하나로 묶는 우회**(한 번
지문으로 표 두 장을 미리 발급)가 생기지 않는지 봐 주세요. 현재 구현은 발급
엔드포인트가 생체 통과 **응답으로만** 표를 주고 1회용이라, 표 두 장을 미리 받으려면
지문도 두 번이라 우회가 아니라고 봅니다.
