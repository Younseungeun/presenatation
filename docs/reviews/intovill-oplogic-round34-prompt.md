# INTOVILL 운영 로직 34차 검토 요청

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동으로 판정합니다. 적중이면 리서처에게
정산되고, 실패면 구매자에게 **현금 환불**됩니다. 그 사이 돈은 에스크로에 있습니다.

33차 답변 넷 중 **셋을 구현했고, 하나(E-4 리허설)는 남겼습니다.**

---

## A. E-3 먼저 했습니다 — 흩어진 상태가 결함의 원인이었기 때문입니다

"Postgres를 기다리지 말고 지금 구조화하라"가 맞았습니다. 그리고 근거가 하나 더
있습니다: **32차에 찾은 결함이 정확히 그 파편화 때문에 생겼습니다.**

상한 유예의 기준 시각을 `AppSetting.updatedAt`으로 읽고 있었는데, 그 칸은 **행이
갱신될 때마다 미래로 밀려** 유예가 매번 새로 시작됐습니다. 값이 다섯 키에 흩어져
있으니 **"이 시각은 무엇의 시각인가"가 코드에 안 적혀 있었습니다.**

제안하신 판별 합집합을 그대로 썼습니다 (`src/server/recoveryState.ts`):

```ts
type RecoveryState =
  | { status: 'PROBING';     pausedAt; failures; nextProbeAt; targetCardIds }
  | { status: 'HARD_LOCKED'; pausedAt; lockedAt; failures; cause: 'MISMATCH' | 'PROVIDER_DOWN' };
```

이제 **하드락에는 다음 탐침 시각도 표적도 아예 없습니다** — "하드락인데 probeNextAt이
남아 있다"를 만들려면 타입을 어겨야 합니다.

**한 가지는 옮기지 않았습니다: 정지 플래그(`judgment.paused.*`).** 그 값은 배치
진입부와 운영 콘솔이 매번 읽는 **관문**이고, **사람이 거는 정지도 같은 칸**을 씁니다.
회복 상태 객체로 끌어오면 이 기계가 사람의 정지까지 표현해야 해서 상태가 오히려
늘어납니다. **관문은 플래그, 회복 절차는 상태 객체** — 역할이 다릅니다.

전용 테이블 대신 단일 JSON 키를 골랐습니다. 자산군 3개짜리 상태를 통째로 읽고 쓰는
쓰임이라 인덱스가 필요 없고, 마이그레이션 없이 지금 넣을 수 있습니다. Postgres
전환 때 테이블로 승격하면 됩니다.

## B. E-1 하드락 유예 — 채택. 다만 "무기한이 아님"을 구조로 못 박았습니다

논거가 맞습니다. 하드락은 **자동 복구가 불가능한 실제 장애**를 뜻하고, 그것은 밤에도
주말에도 납니다. 62분 뒤 곧바로 집행하면 **금요일 밤 피드 단절 때문에 실제로 적중한
카드가 전액 환불**로 끝나고, 사람이 손쓸 시간은 0입니다.

지금 유예는 **두 단계이고 둘 다 끝이 정해져 있습니다**:

| 단계 | 유예 | 근거 |
|---|---|---|
| 탐침 중 | 사고 시작 + **62분** | 자동 회복이 끝까지 갈 수 있는 시간 (백오프 합) |
| 하드락 후 | 잠금 + **24시간** | 사람이 손쓸 수 있는 최소한 |
| 사람이 건 정지 | **없음** | 끝이 정해져 있지 않으므로 |

구매자 약속은 14일 → **14일 + 25시간**입니다. 그리고 **연장되지 않습니다** — 잠금
시각 기준 한 번만 흐르고, 그 뒤에는 아무도 안 왔어도 집행됩니다. "사람이 볼 때까지"로
두면 24차에 고친 결함(사람이 건 정지 동안 카드가 환불도 못 받고 묶임)이 되살아납니다.

제안하신 구매자 UI 문구는 채택 예정인데, 지금 구매자 화면에 **"판정 지연" 상태
자체가 없습니다**(판정 전/완료 둘뿐). 상태 하나를 새로 만드는 일이라 다음 회차입니다.

## C. E-2 — 통계는 맞고, 편중이 지적보다 심했습니다

무작위 5장의 신뢰도 계산(96.9%)은 맞습니다. 그런데 **우리는 무작위로 뽑고 있지도
않았습니다** — 불일치 카드를 **나온 순서대로** 잘랐고, 배치가 시한 순으로 도니
같은 종목이 앞자리를 독차지하기 쉬운 구조였습니다. 지적하신 편중이 확률적 위험이
아니라 **기본 동작**이었습니다.

티커를 한 바퀴씩 도는 라운드로빈으로 바꿨습니다. 12건 중 10건이 A·2건이 B면
표적은 A·B·A·B·A가 됩니다.

**표적 수는 5장을 유지했습니다.** 제안하신 10장 상향은 보류합니다 — 티커 다변화가
들어간 뒤에는 5장이 이미 서로 다른 티커를 최대 5종 덮고, 표적이 늘면 정지 중
공급자 호출도 함께 늡니다(하드락까지 6회 × N장). 다변화 없이 10장이던 것과
다변화 있는 5장은 다른 물건이라, 실측 전에 수를 올리지 않는 쪽을 골랐습니다.

## D. E-4 리허설 — 시나리오 셋은 채택, 다음 회차입니다

Drill 10~12의 선정 기준("상태 × 시간 × 동시성이 교차하는 경계만")이 정확합니다.
다만 이번 회차에 상태 구조를 통째로 바꿔서, **리허설을 새 구조 위에서 짜는 편이**
낫다고 판단했습니다. 지금 짜면 곧바로 다시 씁니다.

**한 가지 미리 말씀드릴 제약**: Drill 11(탐침 비동기 구간 중 수동 개입)은 리허설
스크립트가 **단일 프로세스 순차 실행**이라 진짜 동시성을 만들 수 없습니다.
조건부 갱신 자체는 이미 단위 시험으로 고정돼 있으니(0행이면 결과 폐기),
리허설에서는 **"사람이 먼저 걸어 둔 상태에서 탐침이 성공해도 안 풀린다"**는
관측 가능한 형태로 바꿔 넣으려 합니다.

## E. 답을 듣고 싶은 것

- **E-1.** 하드락 유예 24시간 동안 **구매자에게 무엇을 보여줘야** 합니까? 지금은
  "판정 전"으로 보입니다. "시세 검증 지연 중"을 새로 만들면 정직하지만, **장애를
  구매자에게 노출**하는 것이기도 합니다. 이 시장에서 그 노출이 신뢰를 올립니까
  내립니까?
- **E-2.** 유예가 두 단계(62분 + 24시간)라 **총 25시간**인데, 이게 쌓이는 경로가
  하나 있습니다 — 정지가 풀렸다가 다시 걸리면 유예도 다시 시작합니다. 소스가
  30분마다 흔들리면 상한이 계속 밀립니다. **"한 카드가 받을 수 있는 총 유예"**에
  상한을 둬야 합니까? (예: 시한 후 16일이면 유예 무시하고 집행)
- **E-3.** 상태 객체를 단일 JSON으로 뒀는데, **동시에 두 프로세스가 쓰면 마지막
  쓰기가 이깁니다**(read-modify-write). 지금은 스케줄러가 한 벌이라 문제가 없지만,
  Postgres 전환 후 워커를 늘리면 탐침 실패 횟수가 유실될 수 있습니다. 지금
  버전 칼럼을 넣어 둘 값어치가 있습니까, 아니면 그때 테이블로 옮기며 하는 것이
  맞습니까?
- **E-4.** 33회차 동안 판정·정지·회복에 방어가 계속 쌓였는데, **이 영역에 더 쌓을
  것이 남았다고 보십니까?** 아니면 이제 다른 곳(정산 지시서·본인 인증·컴플라이언스)
  으로 옮겨야 할 때입니까? 한계효용이 꺾이는 지점을 밖에서 보시는 대로 말씀해
  주시면 좋겠습니다.
