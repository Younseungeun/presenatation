## A. 발견 두 건

### A-1. 확신 % 누수 — **(가)안으로 즉시 수정했습니다** [완료]

정확한 발견이었습니다. `studentClient.ts`의 reason이 이제 숫자 없이 나갑니다:

```
전: "수익 보장 (학생 모델, 확신 73%)"   ← 리서처에게 그대로 나가 임계값 이진 탐색 가능
후: "수익 보장 정황 (학생 모델)"        ← 숫자는 confidence 필드로만
```

권하신 대로 (가)입니다 — reason은 "리서처에게 보여줄 문장"이라는 계약을 유지하고,
숫자는 값의 자리(confidence)에만 둡니다. 관리자 화면은 `confidence`를 읽어
`[학생 · 확신 73%]`로 그리시면 됩니다. **C-2도 이걸로 저절로 닫힙니다** —
findingMessages는 손댈 필요가 없어졌습니다.

### A-2. 카나리아 층 하드코딩 — 통보 확인. 그쪽 수정이 맞습니다. 서버 조치 없음.

## B. 새 계약 — 전부 만들었습니다

### B-1. 장애 시각 → **(나)안: 전이 시각 기록** (서버가 씁니다)

(가)를 권하셨지만 (나)로 했습니다. 이유 — (가)의 "마지막 정상 시각"은 **매 성공마다
써야** 정확한데 그건 검수 경로의 상시 DB 쓰기이고, 아껴 쓰면 그 값은 "장애 시작
시각"이 아니라 "마지막 검수 시각"이 됩니다: 검수가 뜸한 밤에는 N시간째가 부풀려집니다.
전이 기록은 장애 중에만 쓰고, **키의 존재 자체가 이전 상태**라 프로세스 재시작에도
안전합니다 (카나리아 박동과 실패 모드가 다른 이유가 곧 채택 이유입니다).

```ts
// server/studentValveService.ts
getStudentOutageSince(prisma)        // Date | null — null 이면 장애 아님
getStudentOutageBoard(prisma)        // { outageSince, outageHolds, bypass } 한 벌
```

화면은 `now − outageSince`로 "N시간째"를 그립니다. 쓰는 쪽은 서버(screenAndRecord)뿐.

### B-2. 보류 건수 → **전용 칼럼 + 전용 함수 둘 다**

`ComplianceReview.studentAbsence` 칼럼이 생겼습니다 (`'OUTAGE_HOLD' | 'VALVE_BYPASS' | null`).
reviewer 문자열 LIKE는 쓰지 마세요 — 지적하신 그대로, 문구가 바뀌면 조용히 0이 됩니다.

```ts
countOutageHolds(prisma)   // OUTAGE_HOLD + 미처리(needsOperatorReview, 미검토)만 센다
```

`VALVE_BYPASS`는 아래 B-3의 밸브로 흘러간 건의 영구 꼬리표입니다. **왜 꼬리표가
필요한가**: "학생 소견 0건(정상)"과 "학생 결석(장애·우회)"은 결과값이 같아서, 이 칼럼이
없으면 훗날 미탐률을 잴 때 장애로 뚫린 건이 학생의 미탐으로 오인됩니다.

### B-3. 밸브 → **AppSetting 런타임 토글로 만들었습니다. 대칭 확인.**

지적이 맞습니다 — "재시작 없는 결정"이어야 하고, 새벽 3시의 SSH는 설계가 아닙니다.
그리고 여러분이 이걸 물은 날 외부 검토(21차)가 같은 자리에 **한 가지를 더** 요구했습니다:
**밸브는 시한폭탄이어야 한다.** 내린 채 잊히면 Q0 정책이 없던 시절과 같아지기 때문입니다.

```
POST /api/admin/compliance/student-valve  { action: 'engage' | 'release' }
GET  /api/admin/compliance/student-valve  → { outageSince, outageHolds, bypass:{active,until} }
```

- 내리면 **2시간 뒤 저절로 만료**됩니다 (연장 = 다시 내리기 — 매번 사람의 판단 기록)
- 사이드카가 복구되면 즉시 무의미해지고, 복구 시 서버가 밸브 키도 함께 걷습니다
- 내리는 순간 운영자 전원에게 알림이 나갑니다
- 우회로 흘러간 건은 전부 `studentAbsence='VALVE_BYPASS'`
- **대칭 맞습니다** — 내리는 것도 올리는 것도 운영자입니다. 화면에는 남은 시간
  카운트다운을 함께 그려 주세요 ("우회 중 · 47분 뒤 자동 복귀")

### B-4. 졸업 라벨 목록 → **STUDENT_LABELS 전부** (졸업 여부 무관)

`isStudentLabel` 검사입니다 — **학생 라벨 공간 8종 전체**를 받습니다.
회귀 문항은 미래의 모든 모델을 시험하므로 "지금 졸업한 라벨"로 좁히면 안 됩니다.

서버 오류 문구 (폼에서 미리 막을 것들, `GraduationError`):

| 조건 | 문구 |
|---|---|
| 위반<3 또는 정상<3 | `대비쌍이 부족합니다 — 위반 3문장 · 정상 3문장 이상을 직접 써 주세요. …` |
| 문장 10자 미만 | `문장이 너무 짧습니다: "…" — 실제 리포트 문장처럼 써 주세요` |
| 위반에 라벨 없음/공간 밖 | `위반 문장에는 학생 라벨 공간 안의 유형이 필요합니다: "…"` |
| **문장끼리 너무 닮음 (신설)** | `두 문장이 너무 닮았습니다 (유사도 N%) — … 상황이 다른 문장으로 다시 써 주세요.` |

마지막 것이 21차 신설입니다: 같은 편(위반끼리·정상끼리) 쌍별 자카드(글자 2-gram)
**0.4 이상이면 거절**. 실측(합성 390건)으로 자연스럽게 다르게 쓴 문장은 최대 0.323,
낱말 하나 바꾼 복붙은 최소 0.400이라 두 분포가 겹치지 않습니다. 폼에서 실시간으로
경고해 주시면 왕복이 줄어듭니다 (기준: 공백 제거 후 글자 2-gram 자카드 ≥ 0.4).

### B-5. 게이지 → **막대는 하나만 (하드 네거티브 N/50). 나머지는 참고 숫자.**

확인하신 대로입니다. "미탐 20건"은 19차까지의 근거 없는 후보였고 X-4가 죽였습니다.
정탐 앵커·정상 표본은 문턱 없는 숫자로만 두세요.

```ts
// server/retrainSignalService.ts
countHardNegatives(prisma)   // { count, threshold: 50, reached, sinceAdoptedAt }
markRetrainAdopted(prisma)   // 재학습 채택 시 리셋 기준점 — 채택 CLI가 부릅니다
```

⚠ **목록 조회 UI는 만들지 마세요** (21차 검토 지시): 카운터는 숫자 하나만 돌려주고,
엇갈린 건의 목록을 운영자가 클릭해 보는 순간 독립 라벨링이 오염됩니다. "엇갈림"은
**위반 여부만** 봅니다 — 학생이 유형을 다르게 짚은 건은 엇갈림이 아닙니다.

## D. 새로 생긴 계약 요약 (이번 회신에서 추가된 것 전부)

| 계약 | 위치 | 용도 |
|---|---|---|
| `studentAbsence` 칼럼 | ComplianceReview | 'OUTAGE_HOLD'/'VALVE_BYPASS'/null |
| `GET/POST /api/admin/compliance/student-valve` | 신규 라우트 | 장애 계기판 + 밸브 조작 |
| `getStudentOutageBoard` | studentValveService | 띠지 한 벌 (시각·건수·밸브) |
| `countHardNegatives` / `markRetrainAdopted` | retrainSignalService | §B-5 게이지 |
| `quarantineRegressionCase` | phraseGraduationService | 회귀 문항 격리 — **2인 승인 소모** (`REGRESSION_CASE_QUARANTINE`) |
| `getGraduationWatch` | phraseGraduationService | **신규 화면 필요**: 졸업 관찰 큐 (아래) |
| 사전 등록 거절 사유 추가 | learnedPhraseService | `표현이 너무 일반적입니다 — 정상 문장 표본 N건에 …` |
| 5층 강등 알림 | (자동) | 상한 초과 시 운영자 알림 — 화면 조치 불필요, 항목에 "정확 표기만 감시" 표기는 기존 계약 그대로 |

**졸업 관찰 큐 (신규 화면 하나)**: 21차 검토가 "졸업 직후 7일이 가장 위험하다 —
사전 보호는 꺼졌고 학생만 남았는데 뚫려도 모른다"를 지적해, 졸업한 표현을 7일간
규칙으로 계속 돌리되 소견 없이 기록만 하게 했습니다. `getGraduationWatch(prisma)`가
항목별 `{ hitCount, studentMissCount, lastHitAt }`을 줍니다. **studentMissCount가
쌓이면 졸업이 성급했다는 뜻** — 그 항목에 [재활성화] 버튼(기존 `reactivatePhrase`)을
붙여 주세요. 그림자 판정 자체는 실리지 않습니다 (X-6 비노출 유지 — 나가는 것은
집계 숫자뿐입니다).

또한 **회귀 문항 격리 UI**: 문항 목록(졸업 상세)에 [격리 요청] — 기존 2인 승인
흐름(`/admin/approvals`)에 `REGRESSION_CASE_QUARANTINE` 행위가 추가됐습니다.
수정 UI는 만들지 마세요 — 수정은 영구히 없습니다. 격리만 있고, 격리도 승인을 소모합니다.

## E. 덧붙임에 대해

같은 모양 일곱 번째라는 관찰이 맞고, "의도된 끔을 명시하게 만드는 자리가 다른
검사기에도 필요한가"는 좋은 질문이라 21차 검토에 그대로 실었습니다. 검토의 답:
**"아무 일도 안 일어나는 것이 정상인 정책은 자기 고장을 보고할 수 없다"** — 그래서
이번에 만든 것들이 전부 그 처방입니다 (밸브 시한폭탄·강등 실명 알림·결석 꼬리표).
studentOff.ts 같은 명시적 끔이 필요한 다음 후보는 교차검증(CROSS_CHECK_MODE)인데,
거긴 이미 off/shadow/enforce 3값 명시라 같은 구멍은 없다고 봅니다.

## 추신 (같은 날 22차 외부 검토 반영 — 계약 변경 3건)

1. **사전 등록 폼**: 등록 거절 사유가 바뀌었습니다 — §D 표의 "표현이 너무 일반적입니다"
   대신 `두 어절 이상으로 적어 주세요 (공백 포함, 예: "원금 보장") — …` 가 옵니다
   (validatePhrase — 대조군 대조 방식은 gap 17형 함정 판정으로 철거). 폼에서
   공백 없는 한 어절 입력을 미리 막아 주세요.
2. **사전 항목에 체크박스 하나 추가**: `[ ] 자동 밀어내기 면제 (영구 보존)` —
   계절성 패턴(연말정산·테마 유행) 보호용. `setPhraseCapExempt(prisma, id, exempt)`,
   20개 상한 초과 시 `면제는 20개까지입니다 — …` 오류. 면제 항목은 5층 상한이
   잘라도 살아남습니다.
3. **재학습 게이지 화면 문구**: N/50 도달이 곧 재학습이 아닙니다 — "50건 도달 ·
   창업자 진위 심사 대기"로 표기해 주세요. 심사 표본은 `sampleHardNegatives`인데
   **이 목록은 운영자 화면에 싣지 않습니다** (운영자 자신의 판정을 재심하는 재료라,
   당사자가 보면 다음 판정이 오염됩니다). 게이지는 숫자까지만.

밸브(B-3)도 강화됐습니다 — 복구 판정이 HTTP 상태가 아니라 **시맨틱 핑**(고정 위반
문장 추론)입니다. 화면 쪽 계약은 그대로입니다 (GET 응답 형태 불변).
