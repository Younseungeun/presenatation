# INTOVILL 검수 모델 5차 검토 요청 — 학생을 서버에 올리려니, 올릴 프로세스가 없습니다

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동 판정합니다. 적중이면 리서처에게 정산되고,
실패면 구매자에게 현금 환불되며, 그 사이 돈은 에스크로에 있습니다. 검수는 그 앞단에서
규제 위반 표현과 본문↔카드 모순을 찾아 거절하거나 보류시킵니다. 이 스레드는 **자체 검수
모델(증류)**을 만드는 스레드이고, 3차에서 **서버 전용**으로 확정했습니다.

4차 답변 넷은 전부 결론을 채택했고 **둘은 근거만 정정**했습니다(통과 표본이 재는 것은
오탐이 아니라 미탐 / 5분 TTL은 트래픽이 연속일 때만 수렴). 그리고 "서버 전용"이라고
적어 놓고 **정작 어느 서버 프로세스에 올릴지는 아무 데도 없다**는 것을, 올리려고 코드를
열어서야 알았습니다. 후보가 둘인데 **둘 다 이 저장소에 이미 적힌 제약과 충돌합니다.**

저장소 접근 없이 읽을 수 있게 필요한 코드·수치를 인라인으로 붙였습니다. 여기 없는 파일
내용은 추측하지 말고 붙여 달라고 해 주세요.

> **답변 형식 요청** (4차와 동일): ① 제가 "자신 없다"고 밝힌 지점을 직접 겨눠 주십시오 —
> 지난 회차 최대 수확이 거기서 나왔습니다. ② 미달 시 대안은 새 구조가 아니라 **기존 구조
> 안에서** 주십시오. ③ **재지 않은 숫자를 주지 마십시오** — 이 저장소는 근거 없는 상수를
> 테스트로 막습니다. 대신 "무엇을 재야 하는지"를 알려 주십시오.

## A. G-1 (사전 검사 부하) — 제 잠정 답을 버리고 트리거 분리를 채택했습니다

> 제안: *"1층(규칙)은 600ms 디바운스 유지, 2층(학생 모델)은 단락 이동·임시 저장·
> 유휴 시에만 백그라운드로 호출."*

제 잠정 답은 "학생을 사전 검사에서 빼고 제출 시에만"이었는데, 그러면 사전 검사를 만든
목적(제출→보류→수정→재제출 왕복 제거)이 되돌아갑니다. **빼는 대신 트리거를 나누면**
커버리지를 지키면서 호출 수를 타이핑 횟수에서 떼어냅니다. 채택했습니다.

**다만 이 답이 새 문제를 만듭니다.** 2층이 띄엄띄엄 돌면 리서처가 *"지금 보이는 소견이
방금 쓴 문단까지 본 것인가"*를 알 수 없습니다. 이 저장소는 검수 화면이 거짓말하지 않는
것을 원칙으로 못 박아 뒀으므로(`"통과 보장"이라고 말하지 않는다`), **2층이 마지막으로
돈 시점을 화면에 표시**해야 합니다 — 미해결로 기록했습니다.

## B. G-2 (그림자 졸업 조건) — 채택, 한 항목은 정정했습니다

> 제안: *"교사와 학생이 모두 통과시킨 리포트의 5~10%를 운영자가 블라인드 검수. 무작위
> 통과 표본의 **오탐**/미탐률 (…) 실측 오탐 0건."*

핵심(통과 건 무작위 감사로 라벨 편향을 깬다)이 제가 막혀 있던 지점을 정확히 뚫었습니다 —
운영자 라벨이 보류 건에만 생긴다는 문제의 답이 그것입니다. 채택했습니다.

**정정**: 통과된 건에서는 **오탐이 발생할 수 없습니다**(오탐 = 정상을 막는 것). 그 표본이
재는 것은 **미탐**이고, 오탐은 이미 라벨이 있는 보류 큐에서 잽니다. 섞으면 감사의 목적이
흐려져 갈라 적었습니다.

## C. G-3 (캐싱) — 결론 채택, 근거는 정정. 프롬프트 크기 상한을 코드로 넣었습니다

> 제안: *"운영/그림자 ON, 로컬 개발 OFF. 시스템 프롬프트 바이트 크기를 CI 테스트 항목에
> 올려 상한을 넘지 못하게 통제."*

크기 상한은 제가 G-3에서 *"프롬프트를 길게 쓰는 습관이 실제 위험인지 기우인지
모르겠다"*고 적은 자리에 대한 답이라 그대로 넣었습니다. 하한도 함께 걸었습니다 —
**1,024토큰 아래면 캐싱이 예외 없이 조용히 동작하지 않기 때문**입니다.

```
/** @근거 설계 — 현재 2,401자에서 약 25% 여유. 유형을 몇 개 더해도 들어오되, 배로 부풀면 걸린다 */
const MAX_SYSTEM_PROMPT_CHARS = 3_000;
```

**정정**: *"첫 호출 후 5분이 지나면 히트율 99%로 수렴"*은 틀렸습니다. 5분 TTL은 **마지막
사용으로부터** 5분이라, 게시가 산발적이면 매번 미스입니다. 그 주장은 트래픽이 연속일 때만
성립하고 출시 전 규모(리서처 30~50명)에서는 보장되지 않습니다. 켜 두는 근거는 여전히
비대칭(최악 +6.4% / 최선 −23%)이고, 판정은 실측입니다.

## D. G-4 (effort) — 채택하고 제약을 하나 덧붙였습니다

> 제안: *"평가 교사는 effort 절감 절대 금지. 합성 데이터 생성에만 적용."*

맞습니다. 덧붙인 제약: **집행(운영 검수)과 기준선 측정도 반드시 같은 effort**여야 합니다.
교사 기준선의 쓰임이 둘이기 때문입니다 — ① 증류의 천장 ② 지금 운영이 실제로 내는 성적.
갈라지면 그 숫자가 어느 쪽도 설명하지 못합니다.

그래서 `COMPLIANCE_EFFORT`는 **대량 라벨 생산 전용 레버**이고, 내려서 만든 라벨은
`reviewerId`에 꼬리표가 박혀 나갑니다 — 대화 라벨에 `conversation:`을 붙인 것과 같은 이유로,
싸게 만든 라벨이 섞였을 때 구분 못 하면 되돌릴 수 없습니다.

```ts
this.reviewerId = `claude:${MODEL}${effort === DEFAULT_EFFORT ? '' : `@${effort}`}`;
// → 'claude:claude-opus-5' 또는 'claude:claude-opus-5@low'   (테스트로 고정)
```

## E. 이번에 새로 넘어간 주제 — 학생을 서버에 올리기

다음 단계는 ONNX 추론 어댑터를 만들어 학생을 `Detector`로 감싸고 단일 임계값을 스윕해
채택선에 거는 것입니다. 열어 보니 전제가 **셋** 빠져 있었습니다.

### E-1'. 올릴 프로세스가 정해져 있지 않고, 후보 둘 다 기존 제약과 충돌합니다

"서버 전용"은 정했는데 **어느 서버 프로세스인지**는 어디에도 없습니다. 이 저장소에는
장기 실행 프로세스가 **스케줄러 하나뿐**이고(pm2), 웹(Next.js)은 pm2에 올라가 있지도
않습니다. 모델은 요청마다 로드할 수 없으므로(14MB + 런타임 초기화) 상주가 전제입니다.

| 후보 | 충돌하는 기존 제약 |
|---|---|
| **웹 프로세스 인메모리** | 웹 인스턴스 수가 **1로 잠겨 있습니다** — 아래 E-α의 SQLite 계측 때문. 즉 부하가 늘어도 **수평 확장이 답이 될 수 없습니다** |
| **스케줄러 프로세스** | `max_memory_restart: '500M'`. 모델+런타임 상주가 그 여유를 먹으면 재기동이 잦아지고, **재기동은 마감 판정 창구(마감+5분부터 1시간)를 갉아먹습니다** — 그 창구를 놓치면 그날 판정이 통째로 빕니다. 게다가 웹→스케줄러 호출 경로(IPC/HTTP)가 지금 없습니다 |

### E-2'. 그림자 모드의 판정을 담을 자리가 스키마에 없습니다

그림자 모드는 학생이 판단하되 처리 권한이 없는 상태입니다. 그런데 검수 기록 테이블은
**행동한 판정만** 담습니다:

```prisma
model ComplianceReview {
  decision            String   // PASS | WARN | BLOCK | UNAVAILABLE  ← 실제로 처리를 정한 값
  reviewer            String   // rule | rule+claude:모델명          ← 실제로 판단한 주체
  findingsJson        String   // 리서처에게 안내되는 소견
  operatorVerdict     String?  // 정답 라벨
  ...
}
```

학생 소견을 `findingsJson`에 넣으면 **리서처에게 그대로 안내되고**(권한 없는 판정이
사용자에게 노출), `decision`에 넣으면 처리에 영향을 줍니다. 둘 다 그림자 모드의 정의를
깹니다. 저장할 자리가 없으면 **일치율을 계산할 원본이 없어 졸업 조건(G-2) 자체가
측정 불가**입니다.

### E-3'. 토크나이저가 학습(Python)과 서빙(Node)에서 같다는 보장이 없습니다

학습은 HuggingFace `AutoTokenizer`(Python), 서빙은 Node입니다. **토크나이저가 한 글자라도
다르게 자르면 지표가 예외 없이 조용히 무너집니다** — 이 저장소가 `buildStudentText`
직렬화를 한 곳에만 두고, 임베딩 벡터에 모델 식별자를 함께 저장하는 것과 정확히 같은
종류의 사고입니다. 그리고 지금 **ONNX·토크나이저 의존성이 하나도 없습니다**(`onnxruntime`,
`transformers.js` 등 전무). 덧붙여 Node 쪽 표준 경로(transformers.js)는 기본적으로
허브에서 받아오는데, 이 환경은 **huggingface.co가 차단**돼 있습니다.

## E-α. 별건 — SQLite 쓰기 직렬화가 G-1의 답과 정면으로 만납니다

pm2 설정에 실측이 주석으로 남아 있습니다(`npm run measure:contention`):

```
결제 쓰기 p99 — 웹 프로세스 수별
    1벌 20ms · 2벌 63ms · 4벌 1,281ms · 8벌 2,137ms      (실패는 전 구간 0)

· instances: 1 → 배포 중(reload로 순간 2배) 2벌 → 안전
· instances: 2 이상, 또는 무중단 배포 도입 → Postgres 전환이 선행돼야 한다
```

즉 **웹 프로세스는 1벌로 잠겨 있고, 그 자물쇠를 여는 열쇠는 Postgres 전환입니다.**
G-1의 답(2층 학생 추론을 서버에서 돈다)은 그 1벌 안에서 CPU를 더 쓰겠다는 뜻이고,
부하가 감당 안 될 때 통상의 처방(프로세스를 늘린다)이 **이 저장소에서는 금지돼 있습니다.**
무너지는 방식도 오류가 아니라 **지연**이라 조용합니다.

두 결정이 서로를 모르는 채 각각 옳게 적혀 있었습니다. → F-3.

## F. 답을 듣고 싶은 것

### F-1. 학생을 어느 프로세스·어느 런타임에 올립니까?

**잠정 답**: 웹 프로세스 인메모리 + Node(`onnxruntime-node`). 요청 경로가 가장 짧고
새 운영 구성요소가 없습니다.

**자신 없는 이유**: 셋째 선택지가 이 문제들을 **한꺼번에 없앨 수 있는데** 그 값을
못 재겠습니다 — **Python 사이드카**(학습과 같은 런타임으로 추론 서비스를 따로 띄우고
웹이 HTTP로 부름). 그러면 E-3'(토크나이저 동일성)이 **질문 자체로 사라지고**(학습과
서빙이 같은 코드·같은 토크나이저), 웹 프로세스 메모리도 안 건드리고, 스케줄러의
`max_memory_restart`와도 무관해집니다. 대가는 **운영 구성요소가 하나 늘어나는 것**인데,
이 팀은 운영자가 1명이고 이미 pm2 프로세스 하나를 돌보고 있습니다.
"프로세스 하나 더"의 비용을 제가 과소평가하는지 과대평가하는지 모르겠습니다.

**틀렸을 때**: Node 인메모리로 갔다가 토크나이저 불일치가 나면 **지표가 조용히 틀린 채로**
채택 판정을 통과할 수 있습니다(그게 이 계열 버그의 특성입니다). 사이드카로 갔다가
운영 부담이 감당 안 되면 배포·모니터링·재기동을 전부 두 벌로 돌보게 됩니다.

### F-2. 그림자 판정을 어디에 저장합니까? 그리고 그것이 정확도 지표를 오염시키지 않게 하려면?

**잠정 답**: `ComplianceReview`에 그림자 전용 칸을 따로 만든다(`shadowFindingsJson`,
`shadowReviewer`). 새 테이블을 만들지 않는 이유는 **한 건의 검수에 대한 두 판정이라
같은 행에 있어야 대조가 조인 없이 되기 때문**입니다.

**자신 없는 이유**: 이 저장소에는 *"자동 만료는 `operatorVerdict`를 남기지 않는다 —
시간이 만든 결과를 사람의 판단으로 기록하면 정확도 지표가 오염된다"*는 불변식이 있습니다.
그림자 판정은 **기계가 만든 결과를 같은 행에 넣는 것**이라 같은 계열의 오염 위험이
있는데, 어느 쪽인지 판단이 안 섭니다 — 칸이 다르니 안전한 것인지, 아니면 집계 함수가
언젠가 그 칸을 실수로 세게 되는 구조인지. 별도 테이블은 그 실수를 **구조적으로**
불가능하게 하지만 대조가 번거로워집니다.

**틀렸을 때**: 오염되면 오탐률·미탐률이 틀린 채로 모든 채택 판단의 근거가 됩니다.
이 스레드에서 가장 비싼 종류의 실패입니다.

### F-3. 2층 부하가 감당 안 될 때, Postgres 전환을 앞당깁니까?

**잠정 답**: 아니다 — 먼저 **호출 수를 줄이는 쪽**(2층 트리거를 더 성기게, 유휴 문턱을
올림)으로 대응하고, Postgres 전환은 그것으로 안 될 때만.

**자신 없는 이유**: 두 잣대가 다른 답을 냅니다. **검수 품질**로 보면 2층이 자주 돌수록
예방이 좋아지므로 확장(Postgres)이 맞고, **위험**으로 보면 Postgres 전환은 결제·판정·
정산이 전부 걸린 저장소 교체라 검수 기능 하나를 위해 앞당길 일이 아닙니다. 그리고
**어느 쪽이 필요한지 지금 판단할 근거가 없습니다** — 2층 호출이 실제로 몇 번 도는지
(리포트 1편당 단락 이동·유휴 횟수) 운영 데이터가 0건입니다.

**틀렸을 때**: 트리거만 성기게 하다 예방 커버리지가 형해화되거나, 반대로 검수 때문에
Postgres 전환을 앞당겨 결제·정산에 새 위험을 들입니다.

### F-4. 그림자 모드 졸업이 1단계 규모에서 도달 가능합니까? (비용)

**잠정 답**: 모르겠습니다. 이것이 이번 회차에서 제가 가장 불안한 항목입니다.

G-2에서 졸업 조건을 "운영자 판정 일치율의 **신뢰구간이 수렴하는 지점**"으로 정했습니다.
잣대로는 옳은데, **1단계 목표가 리서처 30~50명**입니다. 게시가 하루 몇 편인지 모르지만
많지 않을 것이고, 그중 보류되는 건은 더 적으며, 통과 건 무작위 감사는 그 5~10%입니다.
표본이 쌓이는 속도가 느리면 **그림자 모드가 몇 달~1년 단위로 늘어납니다.**

그런데 그림자 모드는 **비용이 가장 비싼 구간**입니다 — 게이트가 아직 교사라 API 비용
(건당 $0.035)이 그대로 나가고, 학생 추론이 얹힙니다. 즉 *"졸업 조건이 엄밀할수록 그것을
기다리는 비용이 커지고, 규모가 작을수록 그 기간이 길어진다"*는 구조입니다.

**자신 없는 이유**: 표본이 안 쌓이는 것은 **운영을 잘못해서가 아니라 사업이 작아서**이고,
그러면 "더 기다린다"가 처방이 될 수 없습니다. 생각해 본 대안은 셋인데 전부 미심쩍습니다 —
① 졸업 문턱을 표본 수 대신 **손코퍼스 + 감사 표본의 혼합**으로 낮춘다(손코퍼스 의존이
되살아납니다) ② 그림자 기간에 **교사 호출을 표본화**한다(게이트를 성기게 하는 것이라
미탐이 늘어납니다) ③ **부분 졸업** — 규제 유형만 교사 유지, 나머지는 학생에게 먼저
넘긴다(유형별 신뢰를 따로 재야 하는데 표본이 더 잘게 쪼개집니다).

**틀렸을 때**: 도달 불가능한 졸업 조건을 세우면 자체 모델을 만들고도 영원히 API를
병행합니다 — 이 스레드의 목표("AI를 게이트에서 감사자로 강등")가 달성되지 않은 채
비용만 두 배인 상태가 기본값이 됩니다.

## 회차 기록 (검수 모델 스레드)

| 회차 | 지적 | 결과 |
|---|---|---|
| 2 | 대화 라벨을 학습셋에 섞어라 + 롤백 플래그 | 부분 — 결론·플래그 채택, "노이즈가 증강"은 기각 |
| 2 | 평가셋을 동결하라 | 채택 후 더 밀고 감 — 규율 대신 도구가 막게 |
| 3 | **브라우저는 과거 아키텍처의 잔재다** | 채택 — 블로커 두 개와 근거 없던 예산이 함께 소멸 |
| 3 | 합산 오탐률 상한을 25%로 | 기각(숫자만) — 재지 않은 값. 그림자 모드 실측으로 미룸 |
| 3 | 마스킹 하라 / 하지 마라 (두 답변 충돌) | 보류 — 스위치로 만들고 하네스가 판정 |
| 4 | 사전 검사를 2층 트리거로 나눠라 | 채택 — **내 잠정 답을 버렸다** |
| 4 | 통과 건 무작위 감사로 라벨 편향을 깨라 | 채택 + 정정 — 그 표본이 재는 것은 오탐이 아니라 미탐 |
| 4 | 캐싱 ON + 프롬프트 크기 CI 상한 | 채택, 근거 정정 — 5분 TTL 수렴 주장은 트래픽이 연속일 때만 성립 |
| 4 | effort는 평가 고정 / 생성만 절감 | 채택 + 제약 추가 — 집행과 기준선도 같은 effort여야 한다 |

여기서 배운 것 셋.

**근거가 틀려도 결론은 살릴 수 있다.** 4차의 두 정정은 모두 결론이 맞고 근거가 틀린
경우였다. 뭉뚱그려 기각했으면 유효한 결론까지 버렸을 것이다.

**"어디에 올릴 것인가"는 "무엇을 만들 것인가"보다 늦게 묻게 된다.** 3차에서 "서버 전용"을
확정하고 두 회차가 지나서야 올릴 프로세스가 없다는 것을 알았다. 배포 대상을 정하는 결정은
설계가 아니라 **기존 운영 제약과의 대조**로만 검증된다.

**서로를 모르는 두 결정이 각각 옳게 적혀 있을 수 있다.** SQLite 계측(웹 1벌)과 2층 트리거
(서버 추론 추가)는 각각 근거가 탄탄한데 겹쳐 놓으면 충돌한다. 문서가 길어질수록 이런
쌍이 늘고, 코드를 열어 맞대보기 전에는 드러나지 않는다.
