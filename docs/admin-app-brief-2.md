## 1. 구조 변화 — 검사기 넷이 둘로 접혔습니다

1호 기준으로 검사기가 넷이었습니다(코드 규칙 · 학습 표현 · 의미 검색 · 학생).
**질문 기준으로 둘로 접습니다:**

```
검사기 ① 결정적 규칙 엔진 — "이 글자들이 금지 목록과 맞는가"
   입력 2원천: 코드 패턴(배포로 갱신) + 운영자 사전(클릭 즉시 갱신)
   두 입력이 같은 6층 해석을 지난다 · 즉시 거절은 코드 원천만

검사기 ② 학생 모델 — "이 글의 뜻이 위반인가"
   목록 없음 · 인용 못 함 · 확률 · WARN까지
```

**의미 검색은 삭제됩니다.** 관련 화면·설정·배선을 만들지 마세요. 만들던 것이 있으면
지우세요.

**되먹임이 이 구조의 심장입니다** — 운영자 반려 하나가 두 갈래로 갈라져 두 검사기를
다 먹입니다:

```
운영자 반려
  ├─ 빠른 길: 사전 등록   →  몇 초 만에 검사기 ①에 (정확히 그 표현만)
  └─ 느린 길: 학습 라벨   →  재학습으로 검사기 ②에 (비슷한 말까지)

졸업: 학생이 그 표현을 잡게 되면 사전 항목을 끈다
```

관리자 앱의 새 숙제는 **이 두 갈래와 졸업을 화면에 드러내는 것**입니다.

### 절대 바뀌면 안 되는 것 (1호와 동일 + 추가)

- 즉시 거절(REJECT) 권한은 **코드 원천 패턴만**. 사전 항목·학생은 아무리 확신해도
  WARN까지 — **사전 항목에 심각도를 고르게 하는 UI를 만들지 마세요**
- 운영자 결정이 라벨의 유일한 원천 — 교사(대화)·학생의 답은 참고
- 외부 AI API 배선 금지

## 3. 새로 필요한 화면 셋

### ① 사전 관리 화면 개편 (`?tab=phrases` 보강)

사전이 규칙 엔진의 입력이 되면서 항목마다 **상태가 셋** 생깁니다. 목록의 각 항목에:

1. **정확도** (기존 — matchCount/confirmedCount, "재검토 권장")
2. **졸업 버튼** — 배지가 아니라 [졸업] 버튼 + 대비쌍 폼입니다 (20차 X-2가 승격을
   금지하며 경로가 졸업 하나로 단일화됨 — 상세는 admin-app-reply-1.md Q1·Q2)
3. **5층 자격 표시** — phoneticEligible=false 항목에 "정확 표기만 감시" 상시 표기
   (등록 시 충돌 검사 결과 — admin-app-reply-1.md Q3)

등록 폼에 하나 추가: **충돌 경고 자리.** 등록하려는 표현의 근사 이웃(자모 거리 1)이
종목명·금융 용어와 충돌하면 서버가 경고를 돌려줍니다(API 준비 중). 경고가 있어도
등록은 막지 않되, **음성 변형 층에서는 빠진다**는 사실을 보여주세요.

### ② 되먹임 두 갈래의 가시화 (반려 폼 보강)

지금 반려 폼은 사전 등록 한 줄(`phrase`)만 보입니다. 반려가 실제로 만드는 건 둘입니다:

```
[반려] 누르면 일어나는 일
  ✓ 사전 등록: "○○○" → 다음 리서처부터 작성 화면에서 경고     (빠른 길)
  ✓ 학습 라벨: 미탐/유형 → 다음 재학습 때 학생이 배움           (느린 길)
```

반려 확인 직전에 이 두 줄을 **일어날 일 그대로** 보여주세요. 운영자가 "내 클릭 하나가
두 검사기를 고친다"를 알아야 유형 선택·표현 등록을 건너뛰지 않습니다 —
유형을 안 고르면 느린 길이 끊기고(라벨 없는 미탐은 학습에 못 씀), 표현을 안 적으면
빠른 길이 끊깁니다.

### ③ 재학습 창구 (`/admin/training` — 1호 §5-②의 확장판)

1호의 학습 자료 큐에 **재학습 게이지**를 얹습니다:

```
쌓인 라벨               재학습 조건        ← 문턱은 20차 X-4 답 대기, 자리만
  오탐(하드 네거티브)  N건    ████░░  N/50
  미탐(운영자 지목)    N건    ██░░░░  N/20
  정탐 앵커(10% 표본)  N건
  정상 표본(10% 표본)  N건

[학습 자료 내보내기]  → npm run train:operator  (1호 §5-③ 그대로)
```

- 조건 도달 시 눈에 띄는 표시. **재학습 실행 버튼은 만들지 마세요** — 재학습·채택 판단은
  CLI(1호 §7)로 남습니다. 화면의 몫은 "때가 됐다"를 알리는 것까지
- 재학습이 돈 뒤에는 **졸업 후보 목록**이 여기 뜹니다(사전 항목 중 학생이 새로 잡게 된
  것) — ①의 졸업 배지와 같은 API를 씁니다

## 4. 소견 표시 규약 — 출처 3종을 갈라 보여주세요

소견(`Finding`)의 `source` 필드로 구분합니다. 재구조화 후에도 이 계약은 유지됩니다:

| source | 표시 | 뜻 |
|---|---|---|
| `rule` | `[규칙 · 코드]` | 배포된 패턴이 잡음. BLOCK 가능 |
| `learned` | `[규칙 · 사전]` + 등록 표현 링크 | 운영자 등록 표현이 잡음. WARN까지. `phraseId`로 사전 항목에 연결 |
| `student` | `[학생 · 확신 N%]` | 뜻으로 판단. 인용 없음 — `quote`가 빈 문자열이면 "본문 전체"로 표기 |

**왜 갈라야 하나**: 오탐일 때 고치는 곳이 다릅니다 — 코드는 개발자, 사전은 운영자가
그 자리에서 끔, 학생은 라벨을 쌓아 재학습. 운영자가 소견을 보고 **자기가 지금 고칠 수
있는 것인지**를 알아야 합니다.

## 5. 하면 안 되는 것 (추가분)

- **의미 검색** 관련 어떤 것도 만들지 않는다 (삭제 예정)
- 사전 항목에 심각도 선택 UI 금지 (항상 WARN)
- 졸업·재활성화를 자동으로 실행하지 않는다 — 표시까지만, 클릭은 운영자
- 교사 답을 운영자 결정 **전에** 보여주는 배치 금지 — `recordTeacherAnswer`가 순서를
  서버에서 막지만, 화면이 유도하면 운영자는 우회를 찾습니다 (18차 V-3)
- 학생의 그림자 판정을 보류 큐 카드에 섞어 보여주지 않는다 — 운영자 판정의 독립성이
  학생 채택 판단의 근거라, 보여주는 순간 그 지표가 자기 자신을 잽니다 (20차 X-6 논의 중)
