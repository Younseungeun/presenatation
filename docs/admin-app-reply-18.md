## ① `src/domain/screeningAccuracy.ts` — 경미를 정탐에서 떼어냈다

`BreakdownStat` · `Bucket` 에 **`minor`** 를 추가하고 루프를 가릅니다.

```ts
if (ok) {
  if (outcome === 'MINOR') b.minor += 1;
  else b.confirmed += 1;
} else b.falsePositive += 1;
```

**왜** — 지금까지 MINOR 가 `confirmed` 에 합산돼 있었습니다. 두 가지가 따라 나옵니다.

1. **처방이 갈리지 않는다.** 오탐은 규칙을 빼는 일이고 경미는 심각도를 낮추는
   일인데, 한 숫자로 뭉치면 "이 규칙을 어떻게 할 것인가"에 답할 수 없습니다.
2. **화면 숫자가 어긋났다.** 유형별 합이 건수보다 커서 `정탐 1건 (…2건)` 이
   떴습니다. 경미가 정탐 쪽에 얹혀 있었으니 당연한 결과였습니다.

**호환** — 필드 추가라 기존 읽는 쪽은 그대로 돕니다. 다만 `confirmed` 의 뜻이
좁아졌습니다(경미 제외). **정탐률 분모(`held`)는 그대로**
`TRUE_POSITIVE + MINOR + FALSE_POSITIVE` 입니다 — 셋 다 보류를 만든 건이라
분모에서 뺄 이유가 없습니다. 시험 2건을 추가했습니다.

## ② `src/infra/compliance/studentClient.ts` — 결근은 두 번 연속일 때만

**집행과 선언을 갈랐습니다.**

| | 첫 실패 | 두 번째 연속 실패 |
|---|---|---|
| `usable()` (집행) | **false** — 게시는 그대로 보류 | false |
| `attendance()` (문자·화면) | `{ok: true, pendingFailure: true}` = "확인 중" | `{ok: false}` = 결근 |
| `consumeAvailabilityChange()` | **null** — 문자 안 나감 | 전이 1회 |

새로 나간 것은 **`attendance?(): { ok, pendingFailure }`** 하나입니다(선택 항목 —
연속 실패를 세지 않는 구현에는 잰 값이 곧 상태입니다). `usable()` · `recheck()` ·
`failureReasons()` 의 뜻은 하나도 안 바뀌었습니다.

**왜** — 04:49 에 `The operation was aborted due to timeout` **한 번**으로 결근
문자가 나가고 04:54 에 복귀 문자가 또 나갔습니다. 사이드카는 멀쩡했고 원인은 그
순간 CPU 를 다 쓰던 `vitest run` 이었습니다. 그런 문자가 몇 번 반복되면 진짜
결근에도 폰을 안 봅니다.

**안전은 유예하지 않습니다** — 첫 실패에서 `usable()` 이 이미 false 라 그 사이
게시는 전부 보류로 갑니다. 미루는 것은 **알림과 표시**뿐입니다.

⚠ **`screen()` 안에서 이 값을 읽지 마십시오.** 집행 경로가 봐야 하는 것은
`usable()` 입니다 — `attendance().ok` 를 관문에 쓰면 첫 실패 5분 동안 못 미더운
모델이 소견을 내게 됩니다.

## ④ `src/server/studentAttendance.ts` — 박동을 둘로 나눴습니다

처음 이 회신을 쓸 때는 "문서만 고쳤다"고 적었는데, 그 뒤에 **로직을 바꿨습니다.**
커밋 `94dce34`.

### 무엇이 문제였나

`student.attendance.lastOk` 는 **성공했을 때만** 찍힙니다. 그래서 그 칸이 낡았을 때
원인이 둘인데 구별할 방법이 없었습니다.

| 실제 고장 | 기록에 남는 것 | 알림이 하던 말 |
|---|---|---|
| 타이머가 안 갔다 | 박동 없음 | "스케줄러를 재기동하십시오" ✅ |
| **갔는데 IRIS 가 안 나왔다** | 박동 없음 | "스케줄러를 재기동하십시오" ❌ |

두 번째 경우엔 재기동해도 안 고쳐집니다. 주석에 *"IRIS 자체의 장애는 따로 알립니다"*
라고 적혀 있었지만, 그 따로 알리는 장치(`notifyStudentAvailability`)는 **전이일 때만**
울려서 이미 죽어 있는 동안에는 조용합니다.

### 새로 나간 것

**`STUDENT_ATTENDANCE_RAN_KEY = 'student.attendance.lastRan'`** — 점검을 **시도한**
시각을 결과와 무관하게 찍습니다. 재기 **전에** 찍는 이유는 이 칸이 답하는 질문이
"성공했나"가 아니라 "타이머가 이 시각에 살아 있었나"라, 점검이 던지거나 프로세스가
그 도중에 죽어도 **여기까지 왔다는 사실**은 남아야 하기 때문입니다.

`AttendanceBeat` 에 **`lastRanAt`** 과 **`timerStale`** 이 추가됐습니다.
**`lastOkAt` · `nextAt` · `stale` 의 뜻은 하나도 안 바뀌었습니다** — 필드 추가라
기존 읽는 쪽은 그대로 돕니다.

```
timerStale && stale  →  "출근 점검이 멈췄습니다"      · 스케줄러를 재기동
!timerStale && stale →  "IRIS 가 응답하지 않습니다"   · 사이드카를 보십시오
```

dedupeKey 도 나눴습니다(`student.attendance.stale` / `.unreachable`) — 공유하면 ①이
나간 뒤 상황이 ②로 **바뀌어도** 묻혀서, 운영자가 낡은 지시만 손에 쥔 채 남습니다.

### 알아 두실 것 둘

⚠ **`stale` 만 보고 "스케줄러가 죽었다"고 판단하지 마십시오.** 그 값은 이제
"IRIS 의 답이 없다"까지만 뜻하고, 어느 쪽 고장인지는 `timerStale` 이 말합니다.
그쪽에서 `attendance.stale` 을 읽는 곳이 있으면 한 번 봐 주십시오.

⚠ **기록이 없으면 `timerStale = true`** 입니다. 이 칸은 2026-08-23에 생겨서 그 전
스케줄러의 기록에는 없습니다 — 낙관하면 진짜 정지를 놓치고, 비관해도 한 회차(5분)면
채워져 잘못된 경보가 오래 가지 않습니다. 배포 직후 5분간은 이 값이 참입니다.

## ⑤ 실화 — 왜 이걸 지금 고쳤나

2026-08-23 실제 기록입니다.

```
오후 2:59:57  IRIS 마지막 정상 응답
오후 3시 ~ 밤 9:58   문자 0통 (약 7시간)
밤 9:58      스케줄러 재기동 → 그제서야 "멈췄습니다" 문자
밤 10:02     컴퓨터 종료
밤 10:08 / 10:10   재기동 → 같은 문자 두 번
```

세 가지가 드러났습니다.

1. **스케줄러가 죽으면 문자가 못 나갑니다** — 알림을 보내는 코드(`notifyOperators`)를
   부르는 곳이 18군데인데 **전부 스케줄러 아니면 웹 서버 안**입니다. 죽은 사람이
   자기 부고를 쓸 수 없습니다. `/api/health/scheduler` 주석이 말하는 외부 업타임
   모니터가 그 구멍의 답인데, 아직 붙어 있지 않습니다(서버를 상시 호스팅으로
   옮긴 뒤에 붙이는 것이 순서입니다).
2. **10:08 과 10:10 의 중복**은 스케줄러가 두 벌 돌고 있었기 때문입니다. `npm run
   scheduler` 는 npm → tsx → node 의 3단이라 **맨 위만 죽이면 알맹이가 살아남습니다.**
   그쪽에서 스케줄러를 재기동할 때도 같은 함정이 있습니다 — 명령줄로 `scheduler` 를
   매칭해 자식까지 정리하십시오.
3. 오후 3시부터의 7시간이 위 ①이었는지 ②였는지는 **결과를 보고 사람이 추론**해야
   했습니다("그동안 문자가 한 통도 안 왔으니 타이머가 죽은 것이다"). ④가 그 추론을
   없앱니다.

## ⑥ 검수 상세 화면에 인증 관문이 없었습니다 (`dfa72cf`)

공유 파일은 아니지만 성격상 알려 드립니다. `/admin/compliance` 는 OPERATOR 가 아니면
`notFound()` 인데, **그 계기판을 펼친 화면인 `/admin/compliance/iris` 는 아무나 열 수
있었습니다.** 로그인 없이 200 이 떨어지는 것을 확인했습니다 — 모델명·적재 지문·검수
정확도·운영자 판정 건수가 그대로 보입니다.

계기판과 같은 네 줄을 그대로 넣었습니다(`403` 이 아니라 `notFound()` 인 것도 같은
이유 — `403` 은 "여기 뭔가 있다"를 알려 줍니다). 지금은 둘 다 비로그인 404 입니다.

### 왜 `admin/layout.tsx` 가 못 막았나 — 여기가 진짜 함정입니다

`admin/layout.tsx` 는 이름도 주석도 "전면 게이트"처럼 읽히지만, **인증 관문이
아닙니다.** 실제로 막는 것은 *운영자인데 패스키가 0개인 경우* 하나뿐이고,
나머지는 전부 그대로 통과시킵니다:

```tsx
if (!userId) return <>{children}</>;              // 비로그인 → 그냥 그린다
if (me?.role !== "OPERATOR") return <>{children}</>; // 일반 이용자 → 그냥 그린다
```

의도된 설계입니다(각 페이지가 자기 `notFound()` 로 닫는다는 전제). 다만 **레이아웃이
있으니 덮여 있겠지**라고 읽히기 딱 좋은 모양이라, 새 화면을 만들 때 관문을 빠뜨리면
아무 경고 없이 열린 채로 배포됩니다 — 이번이 정확히 그 경우였습니다.

### 나머지 화면은 훑어 봤습니다 — 이상 없습니다

`src/app/admin/**/page.tsx` 13개를 전부 확인했습니다. `judgments/page.tsx` 하나가
관문이 없지만 **본문 없이 `redirect()` 만 하는 껍데기**라(→ `/admin/compliance`)
새는 값이 없습니다. 나머지 12개는 전부 `getSessionUserId` + 역할 검사를 갖고 있습니다.

그쪽에서 관리자 화면을 새로 만들 때는 **레이아웃을 믿지 말고 페이지마다 네 줄을
직접 넣으십시오.**

## 확인 부탁

- ①의 `confirmed` 를 그쪽에서 읽는 곳이 있으면 뜻이 좁아진 것을 반영해 주십시오
  (학습 자료 추출 쪽에서 경미를 어떻게 다루는지 제가 모릅니다 — `train:operator`
  는 경미를 애초에 안 넣는 것으로 알고 있는데, 그렇다면 영향 없습니다).
- ②·③·④로 그쪽 시험이 깨지면 알려 주십시오. 제 쪽에서는 전부 초록입니다.
- ④의 `attendance.stale` 을 "스케줄러가 죽었다"로 읽는 곳이 있으면 `timerStale` 로
  바꿔 주십시오.
- ⑥의 레이아웃 함정 — 그쪽에서 관리자 화면을 새로 만들 계획이 있으면 미리 알아
  두시는 편이 좋습니다.
