# 자체 검수 모델 — 13차 검토 요청

**작성 2026-09-03 · 대상 `presenatation/` · 앞 회차 `docs/review-request-model-12.md` · 관련 `docs/admin-app-reply-27.md`**

이번 회차의 한 줄: **졸업 강등 "본선"을 자동 추천할 수 있는가 — ARGOS 가 의미를 수치화하니
그 수치로 묶으면 되지 않나, 라는 창업자 제안을 검토합니다.** 이건 회신 27호가 "부활 조건부"로
접은 임베딩 훅을, **실시간 게이트가 아니라 운영자용 사후 추천**이라는 새 용도로 되살릴지의
판단입니다. 답을 요청하는 것이지 판정을 요청하는 것이 아닙니다 — 아래 "바꿀 수 없는 틀"
안에서 더 나은 길이 있으면 그것을, 방향 자체가 틀렸다고 보시면 그 이유를 적어 주세요.

---

## 0. 배경 — 지금 무엇이 자동이고 무엇이 수동인가

검출 사다리의 **졸업 강등(ARGOS → 코드)** 은 두 갈래다:

| | 복귀 (지름길) | 본선 (신규 코드화) |
|---|---|---|
| 무엇 | 졸업시켰던 사전 항목을 되살림 | ARGOS 만 잡던 표현을 처음으로 코드로 내림 |
| 자동 추천 | **된다** (`UNGRADUATE`: 그림자 미탐-정탐 ≥2 · 오탐 0) | **안 된다** — 지금은 사람이 ARGOS 유형별 모음을 보고 판단 |
| 왜 | 옛 항목이 코드화돼 있어 그림자 재생으로 "잡는가"를 잰다 | 코드화가 존재하기 전이라 "잴 대상"이 없다 |

본선의 현재 흐름: ARGOS 만 잡은 확정 위반이 **유형(8개 라벨)별로 자동 집계**됨(ARGOS 유형별
문장 모음, 재료는 운영자가 짚은 근거 문장) → 사람이 유형을 골라 질문지·공식화 샌드박스로
검토 → 등록. **빠진 것은 "어느 유형·어느 하위 패턴부터 볼지"의 능동적 우선순위 신호.**

## 1. 창업자 제안

> ARGOS 의 작동 방식이 의미를 수치화해서 잡는 것인데, 비슷한 수치의 표현들을 묶어(클러스터링)
> 그룹화하면 본선 후보를 자동으로 짚어줄 수 있지 않나.

즉 카테고리(SOLICIT_CONTACT) 안을 의미 하위그룹({노란앱류}, {디엠류}, {오픈채팅류})으로
쪼개면, 각 클러스터가 하나의 "학습 표현 후보 단위"가 되고 크기·응집도가 코드화 우선순위가
된다는 것.

## 2. 우리의 1차 판단 (검토 대상 — 틀렸으면 지적해 주세요)

**(2-a) ARGOS 자체의 벡터로는 안 된다.** 회신 27호 물음 2: 분류로 미세조정된 인코더의 내부
표현은 **라벨 축으로 붕괴**한다 — "PROFIT_GUARANTEE 스러운 것끼리 전부 가깝게" 뭉치는
표현이지 문장 뜻의 일반 거리계가 아니다. 그 벡터로 클러스터링하면 **이미 나눈 카테고리를
재발견**하는 데 그친다("노란 앱"과 "디엠 주세요"가 둘 다 SOLICIT_CONTACT 축에서 가까워
안 갈린다). 창업자가 기대한 "하위 패턴 분리"가 정확히 이 인코더가 못 하는 지점이다.

**(2-b) 되는 도구는 범용 문장 임베딩이다.** 카테고리 안을 의미로 쪼개려면 라벨에 붕괴하지
않은 일반 거리계가 필요하다 — `semanticIndex`(회신 27호에서 제거 결정)가 쓰던 그것.

**(2-c) 27호가 임베딩을 접은 이유가 이 용도에는 대부분 안 걸린다.** 27호 기각은 "리서처
작성 화면 실시간 경고" 맥락이었다:

| 27호가 접은 이유 | 이 용도(운영자 사후 클러스터링)엔? |
|---|---|
| 실시간 오탐이 늑대소년을 만듦 | 안 걸림 — 운영자가 보고 판단, 리서처를 막지 않음 (게이트 아님) |
| 앵커가 등록 표현 하나뿐이라 임계값 0.82 도박 | 안 걸림 — 앵커가 아니라 문장 수십~수백 개 **집합**을 뭉침(자연 클러스터) |
| 사이드카 확장 비용 | 안 걸림 — 실시간 아닌 배치 |
| huggingface 차단 | 27호가 이미 뒤집음(창업자 브라우저 가중치 반입 전례) |

즉 임베딩을 접은 판단은 **게이트** 맥락이고, 이건 **추천** 맥락이라 반대 근거가 무력화된다.
27호가 "영구 은퇴가 아니라 부활 조건부"로 남긴 바로 그 재검토감으로 본다.

## 3. 바꿀 수 없는 틀 (이 안에서 답해 주세요)

| # | 틀 | 왜 |
|---|---|---|
| T1 | **운영 경로의 외부 AI API 호출 0회.** 임베딩 모델도 예외가 아니다 — 온디바이스(반입한 가중치)로 돌아야 하고 외부 임베딩 API 는 안 된다 | 비용·장애·법적 경계 (2026-08-24 확정) |
| T2 | **ARGOS 는 문서 전체를 판정하고 문장을 못 짚는다**(`quote:''`). 그래서 본선의 재료는 **운영자가 반려 때 짚은 근거 문장**(`operatorEvidence`)뿐이다. 클러스터링 입력도 이 문장들이다 | 모델 구조. 문장 단위 국지화는 별도 모델 |
| T3 | **재학습은 배치가 아니라 사건**이다 — 게이트 전수를 동반하고 시소 위험이 있어 주기로 못 돌린다. 임베딩 클러스터링은 재학습과 **무관**하다: 모델을 바꾸지 않고 **추천만** 낸다 | r8·r9 실측 |
| T4 | **이 도구는 게이트가 아니라 추천이다.** 클러스터가 틀려도 정상 리포트를 죽이지 않는다 — 운영자가 보고 샌드박스로 확인한 뒤 등록한다. 오탐 비용이 게이트보다 훨씬 낮다 | 본선 실행은 사람(공식화 샌드박스 통과 필수) |
| T5 | **자동 강등은 없다**(창업자 확정) — 추천은 "여기 봐라"까지고, 코드화가 되는지는 샌드박스+사람이 판별, 등록도 사람 | T10(12차) |
| T6 | **1인 운영·문턱 초안.** 수백 라벨을 전제한 설계는 못 쓴다. 클러스터 크기·응집도 문턱은 초안이고 실측 후 재보정 | 콜드스타트 |
| T7 | **`LearnedPhrase.vectorJson`·`vectorModel` 컬럼은 보존**돼 있다(20차 창업자 지시). 부활 시 스키마는 그대로 쓴다 | 회신 27호 §4 |

## 4. 설계 초안 (검토용 — 확정 아님)

**입력**: ARGOS 만 잡거나 놓친 **확정 위반**(REJECTED/TAKEDOWN/MISSED)의 운영자 근거 문장.
이미 `getArgosCategoryCounts`/`collectArgosCases` 가 유형별로 모은다 — 거기에 벡터를 붙인다.

**파이프라인**:
1. 근거 문장을 범용 임베딩 모델(반입 가중치)로 벡터화 → `operatorEvidence` 문장에 저장(온디바이스, 외부 호출 0).
2. **유형 안에서** 코사인 응집 클러스터링(카테고리를 넘나들지 않는다 — 라벨은 ARGOS 가 이미 준 유의미한 경계).
3. 각 클러스터 → {대표 문장(중심 최근접), 크기, 응집도, ARGOS 미탐 수}.
4. 추천: 크기 ≥N · 응집도 ≥τ 인 클러스터를 "코드화 검토 후보"로 ARGOS 모음에 배지. 대표 문장을 **공식화 샌드박스·등록 폼에 미리 채움**.

**산출물의 값어치**: 지금 카테고리(8개) 단위인 추천을 **의미 하위그룹 단위**로 잘게 만들고,
사람이 백지에서 표현을 짓는 대신 **뭉친 문장 집합과 대표 표현**에서 시작하게 한다.

## 5. 검토를 부탁드리는 것 (번호로 답해 주세요)

**Q1. (2-a) 판단이 맞나.** 분류 미세조정 인코더의 표현이 라벨 축으로 붕괴한다는 것 —
그래서 ARGOS 벡터 클러스터링은 카테고리 재발견에 그친다는 것. 아니면 **마지막 분류 head
직전 층**은 일반 거리계에 더 가까워 쓸 만한가? 이걸 반입 없이 실측할 방법이 있나.

**Q2. 범용 임베딩이 카테고리 안을 유의미하게 쪼개나.** "노란 앱류 vs 디엠류"가 실제로
갈리나, 아니면 그것도 노이즈(운영자 문장은 길고 문맥이 섞여 중심이 흐림)인가. 문장 전체가
아니라 **운영자가 짚은 조각**이라 짧을 텐데, 짧은 조각의 임베딩이 클러스터링에 충분한가.

**Q3. 부정 문맥.** 임베딩은 부정에 약하다("보장한다" vs "보장 못 한다" 유사도 높음).
다만 입력이 **ARGOS 가 이미 위반으로 거른 문장**이라 부정 문맥이 애초에 덜 들어온다 — 이
완화가 실질적인가, 아니면 클러스터가 여전히 긍정·부정을 섞나.

**Q4. 문턱을 뭘로.** 클러스터 크기 ≥N, 응집도 ≥τ 를 코드화 후보 신호로 쓴다면 초기값을
어떻게 두나(T6 콜드스타트 — 표본이 적다). 크기만으로 충분한가, 응집도가 꼭 필요한가.

**Q5. 비용 대비 니치.** 27호는 임베딩의 실시간 니치가 "얇다"고 봤다. **사후 클러스터링
추천**의 니치는 얼마나 두꺼운가 — 아래 (A) 만으로 충분하고 (B) 는 과잉인가?
- **(A) 임베딩 없이**: ARGOS 미탐 확정 위반 **건수**가 유형당 N건 이상이면 "검토 후보" 배지.
  값이 이미 집계돼 있어 문턱 하나. 하위 패턴 분리·대표 표현 제시는 없음.
- **(B) 임베딩 클러스터링**: 위 4절. 모델 반입 + 벡터 저장 + 클러스터링이 비용.

**Q6. 우리가 못 보는 것.** 이 방향의 함정 — 특히 클러스터를 "코드화 후보"로 제시하는 것이
운영자에게 **잘못된 확신**을 주어(뭉쳐 보이니 코드화되겠거니) 샌드박스 검증을 건너뛰게
만들 위험. 또는 라벨 붕괴 문제가 범용 임베딩에도 다른 형태로 재현될 위험.

## 6. 답 형식

Q1~Q6 마다 **결론 한 줄 → 근거 → 우리 틀(T1~T7) 안에서의 대안**. 특히 Q5 는 (A)/(B)/둘 다/
둘 다 아님 중 하나로 명확히 — 우리는 **A 를 먼저 넣고 B 는 이 회신 결과로 결정**하는 순서를
기본으로 본다. 틀을 넘는 제안은 "틀 밖"이라 표시하고, 숫자를 제안하면 그 출처(실측·경험칙·
추정)를 적어 주세요.
