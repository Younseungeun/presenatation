## B. 화면은 있지만 기능 검증용 최소 형태다 — 디자인을 입혀야 한다

각 파일 머리에 `⚠ 디자인 보류` 표시가 있다. 앱의 확정 스타일(iOS·토스풍, 화이트+민트)은
소비자 화면(홈·리더보드·리포트·MY)에만 적용됐고, 아래는 기능 확인용으로만 지었다.

### 사용자 쪽 (인증·계좌 — 2026-08-16 인증 축 작업에서 생김)
- `/login` — 생체 → 간편 비밀번호 → 본인 인증 3단 배치. **순서가 곧 우선순위 선언**이라 유지
- `/settings/pin` — 가입 직후 필수 설정 + 생체 동의. 비밀번호를 먼저 받는 순서 유지
  (생체는 안 되는 순간이 있다)
- `/settings/devices` — 생체·간편 비밀번호 **한 목록** 유지(나누면 한쪽만 지우고 안심한다),
  삭제 = 전체 로그아웃 경고 문구 유지
- `/settings/payout` — 등록·보호·동결 **한 화면** 유지(급한 사람이 헤매면 안 된다),
  동결 버튼은 숨기지 않는다, 예금주명 입력란을 만들지 않는다, 폼 위 사기 경고 유지
- `/settings/payout`의 유예 즉시 해제(`CooldownConfirm`) — **한 기기에 번호와 입력란을
  같이 보여주지 않는다 · 사기 경고 문구를 지우지 않는다** (파일 주석에 상세)
- `/recovery` 비상 복구 (2026-08-17 검토 7차 Q1) — **평생 한 번 열릴까 말까 하지만
  열리는 그날은 반드시 동작해야 하는 화면.** 두 단계(표 확인 → 지문 등록)를 한 버튼으로
  합치지 않는다(무엇이 실패했는지 구분이 안 된다), "48시간 동안 돈이 멈춘다"는 고지를
  지우지 않는다(그것이 이 경로를 안전하게 만드는 이유다), 로그인 화면에서 이 경로로 가는
  링크는 **만들지 않는다** — 필요한 사람은 절차서를 보고 오고, 링크는 피싱의 표적이 된다

### 운영자 쪽 (`/admin/*` 전부)
- `/admin` 운영 대시보드(홈) — 큐별 대기 건수 유지("사람을 기다리는 일"이 위,
  상태·설정이 아래 — 순서가 곧 우선순위), 이용자 화면으로 나가는 길 유지
- `approvals` 승인 대기열 — 요약·사유·금액·요청자를 다 보여주는 구조 유지
  ("승인" 버튼만 있는 화면은 습관을 만든다)
- `judgments` 수동 판정 큐 — 판정 입력값이 곧 원천 데이터인 자리라 입력 실수 방어가 디자인 과제
- `disputes` 판정 이의 — "우리가 쓴 값 ↔ 구매자가 본 값" 나란히 대조 구조 유지
- `settlements` 정산 지시서 — 이중 실행 차단 표시
- `compliance` 검수 큐 — 탭 분리(본문/종목/판매 중) 유지
- `abuse-reports` · `health` · `settings`
- `frozen` 정산 동결 관리 — 해제 사유 입력 필수 유지("확인한 내용"이 곧 승인자의 사유),
  본인 확인은 앱 밖 경로로 하라는 경고 유지
- 운영자 화면 전반: 지금은 데스크톱 고려 없이 모바일 폭 기준 — 운영자는 데스크톱을 쓸
  가능성이 높아 레이아웃 재검토 필요

## C. 화면을 일부러 만들지 않았다 — 만들면 안 되는 것

이유가 각 파일에 기록돼 있다. 디자인 백로그가 아니라 **하지 말 것** 목록이다.

- `npm run judgment:revert` 개별 되돌리기 — 자주 일어나면 안 되는 일에 화면을 붙이면
  화면이 먼저 낡는다. 돈이 나간 건 거부하는 안전장치는 함수 안에 있다
- `npm run judgment:bulk-revert` 등 일괄 롤백·정지 도구 — 파괴적 행위라 TOTP 없이는
  셸 접근을 요구하는 자리에 둔다 (`scripts/bulkRevertJudgments.ts` 주석)
- `npm run op:grant [--cold]` 운영자 부여·콜드 계정 — 권한 부여가 화면에 있으면
  탈취된 운영자 세션이 운영자를 만든다
- 동결 해제의 **본인용** 화면 — 걸기는 본인, 풀기는 운영자만. 비대칭이 장치의 전부다
