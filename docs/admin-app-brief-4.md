# 관리자 앱 인계 문서 4호 — 구조 확정본: 검사기는 둘이고, 사전은 검사기가 아닙니다

> 2026-08-21. 이 문서는 **오해 교정 전용**입니다. 앞선 문서들(1~3호, 회신 1~2호)과
> 어긋나는 부분이 있으면 이 문서가 이깁니다. 구조는 창업자가 확정했고 코드에 구현·시험
> 완료된 상태라, 여기 적힌 것과 다른 전제로 화면을 만들면 그 화면은 틀립니다.

## 0. 먼저, 지금 갖고 계신 오해

여러분은 지금 **코드 규칙과 사전을 동일한 지위의 검사기 둘**로 이해하고 있습니다.
아닙니다. 정확한 그림은 이렇습니다:

```
검사기 = 정확히 2대

  검사기 ①  규칙 엔진 (applyRules — 하나의 함수)
              질문: "이 글자들이 금지 목록과 맞는가"
              ┌─ 입력 1: 코드 패턴  (코드에 박힌 상수 — 배포로만 바뀜)
              └─ 입력 2: 운영자 사전 (DB의 데이터 행 — 클릭으로 바뀜)
              두 입력이 **같은 6층 해석을 지나 같은 소견 형식으로** 나온다

  검사기 ②  학생 모델 (사이드카)
              질문: "이 글의 뜻이 위반인가"
```

**사전은 세 번째 검사기가 아니라 검사기 ①의 두 번째 입력입니다.** 함수로 쓰면:

```
소견 = applyRules(글, { 코드패턴은_함수_안에, phrases: 사전행들 })
       ∪ 학생.screen(글)
```

`phrases` 는 인자입니다 — 사전 행(LearnedPhrase)은 검수 순간에 `phraseToRule()` 로
규칙 객체로 변환되어 **코드 패턴과 같은 루프**에 들어갑니다. "사전 검사"라는 별도
단계·별도 함수·별도 경로는 코드에 존재하지 않습니다 (예전에 있었는데 20차에 삭제
— `matchLearnedPhrases` 는 지워졌고, 그 삭제가 이 구조 확정의 핵심이었습니다).

비유: 금속탐지기 **한 대**에 탐지 카트리지 슬롯이 둘 있는 겁니다 — 공장 출하 때
내장된 목록(코드 패턴)과 운영자가 현장에서 끼우는 카트리지(사전). 카트리지를 꽂는다고
탐지기가 두 대가 되지 않습니다. 기계는 하나고, 통과 절차(6층)도 하나입니다.

## 1. 왜 이 구분이 화면 설계를 바꾸는가 — 지위 비교표

| | 코드 패턴 | 운영자 사전 | 학생 모델 |
|---|---|---|---|
| **정체** | 함수 안의 상수 | **DB의 데이터 행** | 모델 가중치 |
| 지위 | 검사기 ①의 입력 | 검사기 ①의 입력 | 검사기 ② 그 자체 |
| 바꾸는 법 | 개발자 배포 | 운영자 클릭 (몇 초) | 재학습 + 채택 게이트 |
| 즉시 거절(REJECT) | **가능** | 불가 (항상 WARN) | 불가 (항상 WARN) |
| 소견 source | `'rule'` | `'learned'` (+`phraseId`) | `'student'` (+`confidence`) |
| 인용문(quote) | 있음 | 있음 | **없음** (뜻 판단이라 못 짚음) |
| 통과하는 층 | 6층 전부 | 1~3층 + (자격 있으면) 5층 | 층 개념 없음 |
| 오탐 시 고치는 사람 | 개발자 | **운영자가 그 자리에서 끔** | 라벨 쌓아 재학습 |

마지막 줄이 이 구분의 존재 이유입니다 — 운영자가 소견을 보고 "내가 지금 고칠 수
있는 것인가"를 알아야 하고, 그래서 source 를 갈라 보여주는 겁니다(2호 §4). 하지만
**갈라 보여준다 ≠ 검사기가 다르다**입니다.

## 2. 화면에 이렇게 반영됩니다 (해도 되는 것 / 하면 안 되는 것)

**하면 안 되는 것:**
- "규칙 검사 결과" 패널과 "사전 검사 결과" 패널을 **따로** 만드는 것 — 검사 결과는
  검사기 ①의 소견 목록 하나이고, 항목마다 출처 배지(`[규칙·코드]`/`[규칙·사전]`)만
  다릅니다
- 사전 화면을 "규칙 설정" 화면처럼 만드는 것 — 심각도 선택, 적용 층 선택, 정규식
  입력 같은 것은 **전부 금지**입니다. 층·심각도·해석은 엔진(함수)이 정하지 운영자가
  정하지 않습니다. 사전 화면은 **표에 문자열 행을 넣고 빼는 데이터 입력 화면**입니다
- 검수 파이프라인 도식에 "1차 규칙 → 2차 사전 → 3차 학생" 같은 **3단계**를 그리는 것 —
  단계는 둘뿐이고(규칙 엔진 ∥ 학생, 병렬), 사전은 그 도식에서 1번 상자 **안으로 들어가는
  화살표**입니다

**해야 하는 것 (기존 계약 그대로):**
- 소견 출처 3종 배지: `[규칙·코드]` / `[규칙·사전]`+사전 항목 링크(phraseId) /
  `[학생·확신 N%]`(confidence 필드 — reason 파싱 금지)
- 사전 항목의 상태 표시: 정확도(matchCount/confirmedCount) · 5층 자격
  (phoneticEligible=false 면 "정확 표기만 감시") · 밀어내기 면제 체크박스(capExempt) ·
  [졸업] 버튼(대비쌍 폼)
- 되먹임 두 갈래 표시: 반려 1클릭 = 사전 등록(빠른 길, 검사기 ①에 몇 초 만에) +
  학습 라벨(느린 길, 재학습으로 검사기 ②에)

## 3. 전체 그림 확정판 (이 도식이 기준입니다)

```
                    리서처가 게시를 누름
                           │
        ┌──────────────────┴──────────────────┐
        ▼                                     ▼
  검사기 ① 규칙 엔진 (glyph)            검사기 ② 학생 모델 (meaning)
  "글자가 목록과 맞는가"                "뜻이 위반인가"
  · 입력: 코드 패턴 + 사전 행           · 확률 판단, WARN까지, 인용 없음
  · 같은 6층 해석                       · 죽으면 게시 보류 (Q0)
  · 즉시 거절은 코드 원천만             · 지금은 shadow (채택 모델 교체 중)
        └──────────────────┬──────────────────┘
                           ▼
             소견 병합 → PASS 즉시 게시 / BLOCK 거절(코드만) / 그 외 보류
                           │
                    운영자 판정 (사람)
                           │
        ┌──────────────────┴──────────────────┐
        ▼ 빠른 길                             ▼ 느린 길
   사전에 행 추가                        학습 라벨 축적
   (검사기 ①이 몇 초 만에 강해짐)        (재학습 → 게이트 통과 시 ②가 강해짐)

   졸업: 학생이 그 표현을 잡게 되면 사전 행을 끔 (+ 7일 관찰 창, 영구 회귀 문항)
```

역할 분담의 실측 근거 (2026-08-21, 창업자 공격 배터리 31건 + 채택 하네스):
글자 장난(텔le그ram·원gold 보jang·자모 분리)은 검사기 ①이 30/31 —
멀쩡한 글자로 쓴 위반("손실 나면 사재로 메워드립니다")은 검사기 ②만 잡습니다.
서로의 사각을 메우는 병렬이지, 순서를 이루는 직렬이 아닙니다.

## 4. 자주 나올 질문 선답

- **"사전 항목이 어느 층에서 걸렸는지 보여줘도 되나?"** — 됩니다. 소견의 layer 필드가
  있습니다(`L2_SEPARATOR` 등). 다만 그건 "엔진이 그렇게 해석했다"는 결과 표시지,
  운영자가 고르는 설정이 아닙니다.
- **"사전이 검사기가 아니면 왜 '학습 표현'이라 부르나?"** — 역사적 이름입니다. 뜻은
  "운영자가 등록한 패턴 입력"이고, 학습(모델 훈련)과 무관합니다. 화면 문구로는
  "운영자 사전"을 권합니다.
- **"검사기 ②가 shadow면 파이프라인 도식에서 빼야 하나?"** — 아니요. 자리 그대로 두고
  상태만 표시합니다(3호의 출근 상태 카드). shadow = 판정하되 기록만.
