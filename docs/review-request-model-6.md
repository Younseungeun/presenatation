# INTOVILL 검수 모델 6차 검토 요청 — 여섯 회차를 왔는데 추론이 한 번도 일어난 적이 없습니다

성과 검증형 리서치 마켓플레이스입니다. 리서처가 예측 카드(종목·방향·크기·시한·신뢰도)를
걸고 리포트를 팔면, 시한에 시장 데이터가 자동 판정합니다. 적중이면 리서처에게 정산되고,
실패면 구매자에게 현금 환불되며, 그 사이 돈은 에스크로에 있습니다. 검수는 그 앞단에서
규제 위반 표현과 본문↔카드 모순을 찾아 거절하거나 보류시킵니다. 이 스레드는 **자체 검수
모델(증류)**을 만드는 스레드입니다.

5차 답변 넷 중 셋을 그대로 채택했고(사이드카·별도 테이블·전환 보류), **F-4의 비용
주장 하나를 기각**했습니다 — 라벨별 졸업으로는 API 비용이 줄지 않습니다(호출 단위가
리포트이지 라벨이 아니기 때문). 그리고 그 반영을 마치고 상태를 점검하다가 **이 스레드의
진짜 문제**를 봤습니다: 여섯 회차 동안 쌓인 결정 대부분이 **한 번도 실행된 적 없는
코드 위에 서 있습니다.** 모델은 존재하지 않고, 추론은 단 한 번도 일어난 적이 없으며,
비용 최적화를 넣은 API 경로는 **0회 호출**입니다.

이번 요청의 목적은 새 기능이 아니라 **이 설계 부채를 어떤 순서로 갚을 것인가**입니다.

> **답변 형식 요청**(4차부터 동일): ① 제가 "자신 없다"고 밝힌 지점을 직접 겨눠 주십시오
> ② 대안은 기존 구조 안에서 ③ **재지 않은 숫자를 주지 마십시오** — 대신 무엇을 재야
> 하는지를 알려 주십시오.

## A. F-1 (서빙 토폴로지) — Python 사이드카 채택, 장애 처리를 보완했습니다

> 제안: *"pm2 프로세스 하나를 더 늘리는 것은 운영 부담을 거의 늘리지 않습니다.
> 이미 ecosystem.config를 쓰고 있으므로 스크립트 항목 하나 추가일 뿐입니다."*

제가 "과소평가하는지 과대평가하는지 모르겠다"고 한 자리의 답입니다 — **과대평가하고
있었습니다.** 채택했습니다. 이유가 성능이 아니라 **토크나이저 동일성**이라는 점도
그대로 받았습니다.

**보완**: 학생에게 실권을 준 뒤 사이드카가 죽으면 그 유형 판정이 `UNAVAILABLE`이 되어
**그날 게시가 통째로 보류 큐로 갑니다**(운영자 1명). 구성요소가 늘어난 만큼 확률도
늡니다. 그래서 둘을 못 박았습니다 — ① 공급자가 없으면 **완전히** 꺼진다(반쯤 켜진
상태가 가장 나쁘다, 임베딩 어댑터와 같은 패턴) ② **그림자 모드에서는 사이드카 장애가
게시를 절대 막지 않는다**(판정에 관여하지 않으므로 실패를 삼키고 기록만 비운다).

## B. F-2 (그림자 저장) — 별도 테이블로 만들었습니다

> 제안: *"같은 행에 올릴 경우, 향후 집계 SQL의 WHERE 조건 실수 하나로 그림자 소견이
> 실집행 소견에 합쳐지는 사고가 구조적으로 발생합니다."*

제가 "칸이 다르니 안전한 것인지 판단이 안 선다"고 한 자리의 답입니다. 조심으로 막을
문제가 아니라는 지적이 맞습니다. 스키마를 넣었습니다:

```prisma
model ShadowComplianceReview {
  id                 String   @id @default(cuid())
  complianceReviewId String
  /// 판정 주체 — 예: student:koelectra-v1@t0.42 (모델·임계값까지 박는다.
  /// 임계값이 다르면 다른 판정기이고, 어느 설정의 기록인지 못 가리면 비교가 무의미해진다)
  reviewer           String
  findingsJson       String   // 어떤 경로로도 리서처에게 나가지 않는다
  latencyMs          Int?     // 졸업 조건 ③(p99·이상점)의 원천
  createdAt          DateTime @default(now())
  complianceReview   ComplianceReview @relation(..., onDelete: Cascade)
}
```

`reviewer`에 **임계값까지** 박은 것은 제안에서 한 걸음 더 간 것입니다 — 임계값이 다르면
다른 판정기이므로, 스윕 중 기록이 섞이면 비교가 성립하지 않습니다.

## C. F-3 (Postgres 전환) — 걱정 자체가 해소됐습니다

> 제안: *"Python 사이드카로의 HTTP 요청은 Node.js 비동기 I/O에서 처리되므로 SQLite
> DB Lock을 전혀 발생시키지 않습니다."*

맞습니다. **F-1의 답이 F-3을 함께 풀었습니다** — 사이드카로 가면 학생 추론이 웹
프로세스에서 아예 돌지 않습니다. 전환은 앞당기지 않습니다.

## D. F-4 (졸업 조건) — 구조는 채택, **비용 주장은 기각**

> 제안: *"희귀 라벨만 Claude API 검수로 남겨두면, 게시건당 API 비용이 $0.035에서
> $0.005 이하로 급감합니다."*

**라벨별 단계적 실권 부여와 감사 배치화(`audit:batch`)는 채택합니다** — 표본 공급 속도를
인위적으로 올리는 것이 교착의 유일한 출구라는 진단이 맞습니다.

**비용 주장은 성립하지 않습니다.** 호출 단위와 라벨 단위가 다릅니다 — Claude 검수는
리포트 1건에 API 1회이고, 그 한 번의 응답이 전 유형의 소견을 함께 돌려줍니다.
**라벨 하나를 학생에게 넘겨도 그 호출은 그대로 나갑니다.** 남은 유형 중 하나라도 API가
맡고 있으면 건당 $0.035입니다.

프롬프트에서 졸업한 유형의 지침을 빼 입력을 줄이는 우회로도 닫혀 있습니다 — ① 캐시가
깨지고 ② **동결된 교사 기준선과 비교 불가능해집니다**(같은 규정문이 아니게 되므로).
기준선 재사용이 이 스레드의 뼈대라 그 대가가 절감보다 큽니다.

비용이 실제로 주는 유일한 길은 **호출 자체를 건너뛰는 것**이고, 그 설계는 이미 로드맵
3단계에 있습니다("API는 저신뢰·무작위 감사·신규 리서처만"). 라우팅은 **라벨이 아니라
건(件) 단위**로 걸어야 합니다. 두 장치를 목적별로 갈라 적었습니다:

| 장치 | 단위 | 목적 |
|---|---|---|
| 라벨별 단계적 실권 부여 | 라벨 | **안전** — 검증된 유형부터 권한을 준다 |
| 건 단위 라우팅 (로드맵 3단계) | 리포트 | **비용** — 학생이 자신 있고 위험이 낮은 건은 API를 안 부른다 |

## E. 이번에 새로 넘어간 주제 — 여섯 회차의 설계 부채를 정산합니다

사이드카 구현으로 넘어가려고 상태를 점검했더니, 넘어갈 수 있는 상태가 아니었습니다.

### E-1'. 실행 검증된 것과 문서상 합의인 것이 구분돼 있지 않습니다

여섯 회차의 결정을 실제 실행 여부로 가르면 이렇습니다.

| 실제로 실행돼 산출물이 있는 것 | 증거 |
|---|---|
| 손코퍼스 → 학습셋 수출 | `train.v1.jsonl` 46KB / 124건 |
| 대화 교사 라벨링 경로 (팩 → 답안 → 검증 → 병합) | `teacher.v1.jsonl` 86건, 검증 통과 |
| 평가 하네스 (규칙 기준선·대화 라벨 채점) | `eval:screening` 7회 대조, 전 회차 동일 |
| 회귀 시험 | 1,254건 통과 (이번 스레드 신규 4건) |

| 코드는 있으나 **한 번도 실행된 적 없는** 것 | 이유 |
|---|---|
| `training/train.py` · `export_onnx.py` | **문법 검사만 통과.** torch·onnxruntime 미설치 |
| `trainSynthesize.ts` (합성 생성·라벨링) | API 키 없음 |
| **프롬프트 캐싱 · effort · 비용 계산** | **API 경로 자체가 0회 호출** — 타입체크·단위시험은 통과하지만 실제 호출은 없었다 |
| `ShadowComplianceReview` | 마이그레이션 미적용 (아래 E-α) |

**존재하지 않는 것**: 학생 모델(가중치 0), 사이드카, 그리고 **어떤 종류의 추론도 단 한 번**.

즉 비용 최적화(4~5차)와 서빙 설계(5차)는 **한 번도 돌려보지 않은 경로 위의 합의**입니다.
결정이 틀렸다는 뜻은 아니지만, 틀렸는지 알 방법이 지금 없다는 뜻입니다. → F-2.

### E-2'. 학습 환경 자체가 없습니다

`training/*.py`는 실행 경로가 아예 열려 있지 않습니다.

```
python  → Windows 스토어 스텁 (실행 불가)
python3 → 동일
py      → Python 3.12.10  ✓ 살아 있음
pip     → PATH에 없음
torch · onnxruntime · transformers → 미설치
huggingface.co → 네트워크 정책상 차단 (가중치·토크나이저 수급 불가)
```

`training/README.md`는 `python -m venv .venv` 로 시작하는데 **그 첫 줄부터 이 기계에서
돌지 않습니다.** 6차까지 그 사실을 몰랐던 이유는 문법 검사만 하고 실행을 안 했기
때문입니다. → F-3.

## E-α. 별건 — 문서화해 둔 SQLite 제약을 제가 직접 밟았습니다

`ShadowComplianceReview` 마이그레이션이 적용되지 않았습니다:

```
$ npx prisma migrate dev --name shadow_compliance_review
Error: SQLite database error — database is locked
$ npx prisma generate
EPERM: operation not permitted, rename '...query_engine-windows.dll.node'
```

다른 개발 세션의 dev 서버가 DB와 엔진 DLL을 쥐고 있어서입니다. 마이그레이션 SQL은
정확히 생성됐고 적용만 대기 중입니다(`migrate deploy` 한 번이면 됩니다).

**주목할 점은 사고 자체가 아니라 위치입니다.** 5차에서 제가 별건으로 올린 것이 바로
"SQLite 쓰기 직렬화가 웹 인스턴스를 1벌로 잠갔다"였고, 그 계측은 `ecosystem.config.cjs`
**주석에만** 있습니다. 즉 그 제약은 **운영 설정에는 반영돼 있지만 개발 워크플로에는
반영돼 있지 않습니다** — 그래서 같은 성질의 문제를 스키마 작업에서 다시 만났습니다.

## E-β. 별건 — 비용 최적화가 전부 미검증 경로에 있습니다

4~5차에서 넣은 것들(프롬프트 캐싱, `effort` 상수화, `reviewerId` 꼬리표, 비용 계산
단일화, 캐시 히트율 정산)은 **전부 `ClaudeComplianceScreener.screen()` 안에 있고,
그 함수는 이 저장소에서 한 번도 실행된 적이 없습니다.** 단위 시험은 프롬프트 조립과
`reviewerId` 문자열까지만 검증합니다.

특히 **캐싱은 그 자체가 "손익분기 21.7%를 넘는가"라는 미검증 베팅**인데, 베팅을 건
코드 경로도 미검증입니다. 위험이 두 겹입니다. → F-4.

## F. 답을 듣고 싶은 것

### F-1. 모델이 없는 상태에서 사이드카를 먼저 만드는 것이 맞습니까?

**잠정 답**: 만든다 — 단 **스텁 모델**로. 무작위 로짓을 돌려주는 사이드카를 먼저 세우고,
웹↔사이드카 계약(요청/응답 형식, 실패 시 삼키기, 그림자 기록)과 `Detector` 어댑터,
`ShadowComplianceReview` 기록 경로를 **가중치 없이 전부 검증**한다. 진짜 모델이 오면
파일만 갈아 끼운다.

**자신 없는 이유**: 스텁으로 검증되는 것은 **배관뿐**이고, 이 스레드에서 실제로 위험한
것은 배관이 아니라 **토크나이저 동일성**입니다(그것 때문에 사이드카를 고른 것입니다).
스텁은 그 위험을 하나도 재지 못하는데, 그러면 "검증했다"는 감각만 얻고 진짜 위험은
그대로 남는 것 아닌지 모르겠습니다. 그렇다고 모델을 기다리면 F-3이 풀릴 때까지
아무것도 못 합니다.

**틀렸을 때**: 스텁으로 갔다가 진짜 모델에서 토크나이저가 어긋나면, 그때는 배관이
"이미 검증됐다"고 믿는 상태라 원인을 배관 밖에서 찾게 됩니다 — 이 계열 버그가
가장 오래 사는 조건입니다.

### F-2. 실행 검증이 0인 결정들을 어떻게 표시하고, 어떤 순서로 갚습니까?

**잠정 답**: 계획서의 결정마다 **검증 등급**을 붙인다 — `실행됨` / `시험만` /
`문서상 합의`. 그리고 등급이 낮은 것부터가 아니라 **되돌리기 비용이 큰 것부터** 갚는다.

**자신 없는 이유**: 두 잣대가 다른 순서를 냅니다. **위험**으로 보면 되돌리기 비용이 큰
것(서빙 토폴로지, 스키마)부터 검증해야 하는데, **가능성**으로 보면 지금 검증 가능한 것
(API 키만 있으면 되는 것들)부터 해야 합니다. 그리고 이 저장소에는 이미 비슷한 장치가
있습니다 — 근거 없는 상수를 `constants-debt.txt`에 빚으로 올리고 **그 파일의 줄 수가
남은 빚의 양**이 되게 한 것. 같은 방식(`design-debt.txt`)을 쓸 수 있을 것 같은데,
상수와 달리 **설계 결정은 "검증됨"의 정의가 애매합니다** — 한 번 돌아간 것과 운영에서
검증된 것이 같은 등급일 수는 없습니다.

**틀렸을 때**: 등급을 안 붙이면 7차·8차에도 같은 일이 반복되고, 어느 결정이 실측 위에
서 있는지 아무도 모르는 채 문서만 두꺼워집니다.

### F-3. 학습 환경을 어떻게 확보합니까? (비용 포함)

**잠정 답**: 로컬은 포기하고 **Google Colab 무료 티어**로 학습한다 — huggingface 접근이
열려 있고 GPU가 붙으며 비용이 0입니다. 학습은 1회성이고 모델이 14M이라 무료 티어로
충분할 것으로 봅니다. 산출물(가중치·토크나이저·ONNX)만 내려받아 저장소에 넣습니다.

**자신 없는 이유**: 세 가지가 걸립니다. ① **재현성** — Colab 노트북은 이 저장소의
`train.py`와 갈라지기 쉽고, 갈라지는 순간 "무엇으로 학습한 모델인가"를 못 답합니다
(이 스레드가 직렬화·라벨 출처를 한 곳에 묶어 온 이유와 정면으로 부딪힙니다).
② **데이터 반출** — 학습셋을 외부 노트북에 올리는 것인데, 손코퍼스는 제가 쓴 문장이라
민감하지 않지만 나중에 **운영자 판정(실제 리포트 인용문)**이 학습셋에 들어오면
같은 경로를 쓸 수 없습니다. ③ 로컬에 `py`는 있으니 CPU 학습도 가능한데(14M),
`pip` 경로와 huggingface 차단을 푸는 비용을 제가 못 재겠습니다.

**틀렸을 때**: Colab으로 갔다가 재현성이 깨지면 모델을 다시 만들 때마다 결과가 달라지고,
그러면 채택선 자체가 무의미해집니다. 로컬을 고집하다 차단이 안 풀리면 몇 회차를 더
설계만 합니다.

### F-4. API 키가 생기는 날, 무엇을 어떤 순서로 얼마까지 씁니까? (비용)

**잠정 답**: ① 교사 기준선 문장 86건 → ② 문서 42건 → ③ 캐시 히트율·비용 실측 확인
→ ④ 합성 라벨링. 총 $15 이하로 잡습니다.

**자신 없는 이유**: 순서에 **되돌릴 수 없는 지점**이 어디인지 모르겠습니다. 교사 기준선은
한 번 재면 그것이 **동결된 천장**이 되어 이후 모든 채택 판단의 기준이 됩니다. 그런데
그 첫 측정이 **캐싱이 켜진 상태**, `effort: medium`, 특정 프롬프트 버전에서 이뤄집니다 —
셋 중 하나라도 나중에 바뀌면 기준선을 다시 재야 하는지, 아니면 "그때 그 조건의 기준선"
으로 그냥 두는지 정하지 못했습니다. 다시 재면 비용이 반복되고, 안 재면 비교 대상이
낡습니다. **첫 측정 전에 프롬프트를 손볼 마지막 기회**이기도 한데, 그 판단을 지금 해야
하는지도 모르겠습니다.

**틀렸을 때**: 급히 재고 나서 조건을 바꾸면 기준선이 무효가 되고, 그것을 모르고 쓰면
학생을 잘못된 천장에 견주게 됩니다.
